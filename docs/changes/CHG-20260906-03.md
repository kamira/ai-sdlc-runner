# CHG-20260906-03 - an approval outlives the brief it was given for, and re-merges a finished run

- Project: ai-sdlc-runner
- Branch: claude/chg-20260906-03
- Date: 2026-09-06 (UTC+0)
- **Measured against `origin/main` at `714e4f8`**, pinned by sha
- Type: defect fix - behaviour, in `engine.Approval`, `Runner.approve` and the walk's config, with
  one new snapshot field and its console row
- Proposed by: **cross-review on two engines in independent sessions**, over two rounds. The first
  round found the defect; my first fix was wrong and the repository's own tests said so; the second
  round, given that evidence, moved both engines to the same answer. All of it is recorded below.
- Risk: high - this changes when a gate asks a person again. It can only ever ask more, never less,

- Autonomy: high
- Target ACC: ACC-20260906-03

## Read this first

A high-risk run, walked to the end, every gate answered by a person:

```
approved plan_confirmed  feasibility_confirmed  before_dispatch  lead_review
         qa_verify       acceptance             pr               merge
final state: finished       approvals held: 8
```

Then one file is attached:

```
state 'finished' -> 'finished'
nodes dispatched by the attach: 17
   pm_confirm  engineer_build  qa_accept  pr  merge   all re-dispatched
stopped for a person? no
reason              : "nothing further was asked for"
```

The run rebuilt, re-reviewed, re-opened the PR and **re-merged** — through `acceptance` and through
`merge`, which `policy.py` calls a one-way door — on eight answers nobody gave for the brief it was
now running. `instruct` did the same.

## The rule this repository already had, applied to models and not to people

```
engine._ask        "Reuse the answer only if the question is the same one. Anything else is
                    answering the new brief with words said about the old one."
Runner.instruct    "a changed brief changes every question, which is precisely when re-asking is
                    the correct thing to do."
engine.walk        "A confirmation is spent, not standing … because the operator confirmed *that*
                    stop having seen it."
```

A model's answer is not reused when the question changes. A person's was. `Approval`'s own docstring
says `node_id` and `run_id` are *"what make refusing a stale or misdirected answer possible"* — and
neither of them changes when the brief does, so the staleness guard could not see this.

The mechanism, in order:

```
start()      -> a new RunState; approvals reset
approve()    -> appends an Approval
instruct()   -> changes the brief; approvals retained
attach()     -> changes the brief; approvals retained
_walk_once() -> hands every retained approval to RunConfig.confirmed
walk()       -> builds a fresh spend ledger and spends them again
```

Attachments already carry the stamp this needs — `Store.add(..., instruction=len(instructions))`.
Approvals did not.

## My first fix was wrong, and the repository said so three times

I first refused `attach` and `instruct` on a run that was over. Three existing tests went red, each
naming a different reason, and each is worth recording because each is a decision the refusal would
have reverted:

1. **`test_a_finished_run_does_not_still_carry_the_failure_before_it`** — a walk that raises leaves
   the run `stopped`, and *adding to the brief is the recorded recovery path*
   (`CHG-20260903-29` / `-34`). Refusing `stopped` closes the recovery, not the hole.
2. **`test_an_action_arriving_as_the_walk_decides_to_stop_is_not_stranded`** — refusing without
   checking `_walking` strands an action that raced the walk's decision to stop, which is this
   project's own worst failure shape and the reason `_advance` coalesces rather than returning 409.
3. **`test_an_agent_that_cycles_is_stopped_by_the_step_cap`** — and this is the one that settled it.
   Its scenario, shipped in `examples/weather-spa/scenarios.py`, does this on purpose:

   ```python
   c.act("/run/instruct", {"instruction": SECOND})   # a second walk over finished work
   ```

   *A second walk over finished work* is a supported, exercised workflow. The comment is in the
   repository.

That third failure reframed the question, and both engines were asked it again with the evidence:
**is the defect the restart, or the approvals surviving the brief change?** Both answered the same
way, independently: the approvals. Neither would edit the example — `codex`: *"changing the shipped
example to accommodate the narrow refusal would hide the compatibility failure rather than fix the
approval-lifetime defect."*

## What changes

`Approval` gains a `brief` field — the third thing that makes an answer stale, next to the two its
docstring already explains. `Runner.approve` stamps it with what the operator was looking at:

```python
(len(self.state.instructions), tuple(sorted(a.id for a in self.state.attachments)))
```

The ids and not a count, because a document *replaced* is a changed brief even when the number is
the same. `_walk_once` hands the walk only the approvals whose brief matches; the rest are
**retired, not removed** — `state.approvals` is append-only and three docstrings rely on that — and
named in a new `retired_approvals` field that reaches the snapshot and the console.

`brief=None` means *any* brief, which is what `--confirm` on the command line means and what every
existing caller passes.

Nothing is refused. `attach` and `instruct` behave exactly as before on every state.

## The constraint that makes this safe rather than merely strict

A re-walk with **no** brief change must keep every approval, or every ordinary resume stops at the
gate it just cleared and no run can ever finish. Measured both ways:

```
no brief change   8 approvals, the run reaches `finished`, retired_approvals == []
brief changed     state 'finished' -> 'suspended' at plan_confirmed, 5 nodes dispatched,
                  merge / pr / qa_accept not re-dispatched
```

## `scenario_c` is unchanged, and was measured rather than assumed

Both engines walked it step by step and predicted it would still demonstrate the step cap: the
second walk cycles in the build loop and exceeds 200 steps before reaching any gate, so the retired
`merge` approval is never consulted. Measured: `tests/test_example_weather_spa.py` passes untouched.

## What both engines refused

- **Refusing `attach`/`instruct` on `finished` or `stopped`** — closes a supported workflow the
  record defends twice.
- **Clearing approvals on every `_advance`** — turns every ordinary resume back into a gate.
- **Deleting retired approvals** — the append-only property is relied on; retire by filtering what
  reaches `RunConfig.confirmed`, and say so.
- **Keying on the walk number or on `run_id`** — the first re-asks every resume; the second cannot
  work, because `run_id` is the journal path and is constant for the session.
- **Editing the shipped example to fit the fix.**
