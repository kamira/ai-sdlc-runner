## The survey

Four flags, and the question is **not** "is this relative to the shell". A CLI path *should* be —
you typed it where you were standing, and `--store-root store` meaning `./store` is correct. What
sank `agent_command` was different: it came from a **config file** and was resolved against the
shell anyway.

So the question each flag was actually asked:

> Does this path get **recorded** somewhere that outlives the shell it was typed in, and if so, is
> what got recorded still meaningful there?

Answered by running the real CLI from two shells with identical relative arguments:

| flag | recorded? | verdict |
|---|---|---|
| `--ask-journal` | yes — `str(Path(...).resolve())` | **sound**. Also its *identity* is the marker file inside the directory, so the same relative string from two shells is two directories and two runs, which is right |
| `--store-root` | no — names a directory at the moment it is used | **sound** |
| `--token-dir` | no — places `operator.token`, `attachments/`, `asks/` at use | **sound** |
| `--plan` | **yes, as typed** | **the finding** |

Two more that the ask did not name, checked because a survey that stops at the four named ones is
not a survey:

| | |
|---|---|
| `--attachments`, `--models`, `--assignment-store`, `--settings` | never recorded; used at point of use. **Sound**, with a note below |
| `server.py:521` `held["plan"]` | **not a path** — model assignments. Same word, different thing |

### The note on relative defaults

`--settings` defaults to `config/settings.json`, `--assignment-store` to `.runner/config.sqlite`,
`--token-dir` to `.runner`. All relative. So `runner settings` typed in one directory and
`runner serve` in another read different files — and what `--settings` holds is **the review seat
count and the high-risk bypass**.

That is ordinary CLI behaviour (`.git` works the same way) and it is not changed here. It is written
down because "your governance settings depend on which directory you were in" deserves to be a
sentence somebody has read, rather than something discovered.

## The finding

```python
run={"journal": str(Path(args.ask_journal).resolve()) if args.ask_journal else None,
     "plan": str(args.plan)}
```

One dict literal, two frames of reference. `journal` is resolved; `plan` — the field naming what the
run actually *did* — is whatever was typed. Reproduced:

```
shell-a recorded run = {"journal": "...\survey\shell-a\asks", "plan": "ex/plan.json"}
shell-b recorded run = {"journal": "...\survey\shell-b\asks", "plan": "ex/plan.json"}
```

Two different plan files. Identical provenance.

**Nothing reads the field back.** That is the argument *for* fixing it, not against: a field nothing
consumes is a field nobody notices is wrong, and its only reader is a person months later asking
which plan produced a conversation. To that person `"ex/plan.json"` is not an answer.

## What changed

`_where(path)` — resolve, or record nothing. Both call sites use it.

An empty value stays empty on purpose: `Path("").resolve()` is the working directory, so resolving
an absent plan would record a confident answer to a question nobody asked. That is this project's
most-repeated defect class and it is one line away here.

## My own survey script was the defect it was looking for

The first version passed `--plan` as an **absolute** path and then asserted the recorded value was
absolute. It printed `OK` next to a description saying *"stored as typed, not resolved"* — the label
was right and the check could not fail. A coarse check answering safe about the one field it existed
to examine.

Caught by reading its own output rather than by anything structural. It is the fourth instance today
of the same class, and the third of them in something I wrote to catch the class.

### Not claimed

**That the recorded plan is the plan.** It is the *path* the plan was read from, resolved. If the
file changes afterwards the record still points at it and says nothing about what it contained. A
content hash would be the honest version and is not what this does.

**That relative defaults are safe.** They are unchanged and now documented. `runner settings` from
the wrong directory still silently configures a different runner.

**That the survey covered every path in the system.** It covered every path-taking **CLI flag** and
the config keys. Paths inside a plan file's `targets`, and anything an agent is handed, were not
examined.
