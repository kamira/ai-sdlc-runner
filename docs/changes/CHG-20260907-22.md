## The finding

`tests/test_store.py`'s concurrency test failed once during CHG-20260907-20 with
`urllib.error.URLError: [WinError 10061]`. I could not explain it, filed it, and wrote in
ACC-20260907-20 that the one mechanical explanation had been **refuted**:

> the default listen backlog of 5 against 8 worker threads -- was **refuted** by measurement, 64
> concurrent connections producing zero refusals

A seat re-measured it and the refutation is wrong. My probe let the acceptor run, and **a queue
that is being drained never fills**. Against an acceptor that is not draining:

```
socketserver.TCPServer.request_queue_size            5
20 connections, acceptor not draining, size=5        5 held, 15 refused, all 10061
20 connections, acceptor not draining, size=128     20 held,  0 refused
```

`10061` is *connection refused* - the same error a client gets from a port with nothing on it at
all. So the server answers a caller past the backlog by saying it does not exist.

## What is measured, and what is not

- **Measured**: a full backlog refuses, deterministically, with the same error as the sighting -
  and the trigger reproduces too. With `serve_forever` running and eight spinner threads beside
  it, bursts of twenty draw **51 refusals in 200 connects at 5, and none at 128**.
- **Recorded earlier**: the same failure under concurrent pytest processes, across six rounds,
  by two seats.
- **Not established**: that this is what happened on the one run in CHG-20260907-20. Nobody
  instrumented that process. The hypothesis was **not refuted** and is well supported; it is not
  proven for that instance.

An earlier draft of this record called the starved acceptor *"the sighting's condition"* and said
*"the explanation was correct"*. A seat would not let either stand, and then a second measurement
showed the opposite error as well: calling the trigger pure inference undersold a week of it.

## Why the depth matters in production, not only under test

The acceptor is one Python thread. It does not have to be absent to be starved: it competes for
the GIL with every handler thread it has already spawned, and `_OneRunner` is a
`ThreadingHTTPServer`, so a burst of requests creates its own competition. A browser opens six
connections to one host as a matter of course, and the console is a browser page that holds an
SSE stream open while issuing ordinary requests beside it.

## What ships

```python
request_queue_size = 128
```

on `_OneRunner`, beside `allow_reuse_address = False`, with the measurement written at the code:

```
listen(5)                  5 held    the 6th refused after 2.03s
listen(128)              128 held    the 129th, 2.03s
listen(200)              200 held
listen(201)              200 held    <- Windows clamps here
listen(socket.SOMAXCONN) 200 held    the constant is 2147483647 and is truncated
```

**The number needed an argument for its size and the first draft gave it a false one:** *"128 is
what `http.server`'s own `HTTPServer` subclass has used since it was written."* A seat checked
what I had not. It does not - neither `HTTPServer` nor `ThreadingHTTPServer` overrides
`request_queue_size` on any supported version, and both inherit `socketserver`'s 5. **The
citation was invented**, in the record meant to remove exactly that shape.

The argument it needed is two bounds, and the table above has both: **above** the largest burst
anything here makes (eight pool workers, twenty in the test that pins this), and **below** the
200 the platform silently truncates to. The other seat proposed `socket.SOMAXCONN` on the grounds
that a constant states the policy where a number states nothing - a fair objection to the draft,
and the clamp answers it: `SOMAXCONN` is 2147483647 here and `listen()` quietly rewrites it to
200, so it would be a value the platform ignores. On Linux the cap is `net.core.somaxconn`, read
and not measured.

## The sentence in the merged record

ACC-20260907-20's paragraph is replaced rather than deleted. It said a hypothesis had been
refuted; the hypothesis was right and the measurement was of the wrong setup. Leaving the claim
standing would leave a reader believing an explanation had been ruled out when it had been
confirmed one probe later, and this repository has spent the week removing exactly that shape.

## Tests

`test_a_burst_of_connections_is_queued_rather_than_refused` - twenty connections against a real
`serve()` whose acceptor was never started, asserting none is refused. The acceptor is deliberately
absent rather than loaded, because load is what made the original sighting rare and the starvation
is what made it happen.

Two mutations in `backlog`: the value back to 5, and the attribute deleted so the default is
inherited by accident again. Both name the test rather than the file - a bare `LOOPBACK` edit
would trip several other tests first and report `CAUGHT` for something else.

## What this does not do

It does not establish that the backlog caused the one run in CHG-20260907-20; nobody
instrumented that process. It does not touch `tests/test_store.py` - nothing measured says that
test is wrong. And **it does not make a loaded server fast**: at 128 under the same starvation
every connect succeeded, and 49 of 80 responses still took over four seconds. What it removes is
a false error, not a stall.

Its sibling in the same phase is CHG-20260907-23, the fixed `%TEMP%\aslr_deep` path in
`tests/test_attachments.py`. Different file, different fix, separate records - but the same
trigger, concurrent pytest processes, which is what ACC-20260831-03 recorded and what the queue
this record opens is about to create more of.
