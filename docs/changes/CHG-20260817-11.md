## Motivation

`src/ai_sdlc_runner/executors.py:87-88` is the launch-failure path:

```python
except (OSError, subprocess.SubprocessError) as exc:
    raise ExecutorError(f"command backend failed to launch {cmd!r}: {exc}") from exc
```

It is currently **untested**. This is a gap CHG-20260817-09 created, and the way it was created is
the interesting part.

Before that CHG, five tests wrote a `#!/bin/sh` stub and handed it to `CommandExecutor`. On Windows
those never got past `subprocess.run` — they landed in exactly this `except` clause. So the branch
was covered, continuously, **by five tests that were failing**. Fixing them to launch successfully
moved all five onto the success path and left the failure path bare. Line coverage for the module
went 86% → 85% across a change that unambiguously improved it.

The only other test that reaches `ExecutorError` is `test_command_executor_empty_argv_errors`, which
raises at the empty-`argv` guard on line 74 — before `subprocess.run` is ever called. It does not
exercise this clause.

Why it is worth a test rather than a shrug: this clause is the runner's contract that a
**mis-configured agent command fails loudly and legibly**. `config/runner.yaml` lets a user point
`argv` at any local CLI; the overwhelmingly common misconfiguration is a binary that is not
installed or not on `PATH`. Without this clause a raw `FileNotFoundError` would escape the executor
abstraction; with it, the caller gets an `ExecutorError` naming the command it tried. That behaviour
is currently held up by nothing but the source reading correctly.

## Decisions & trade-offs

| Decision | Options | Assumptions | Why this choice |
|----------|---------|-------------|-----------------|
| How to provoke a launch failure | non-existent path vs a non-executable file vs mocking `subprocess.run` | a path that does not exist fails identically on every platform (`FileNotFoundError`, a subclass of `OSError`) | **Non-existent path.** Portable by construction — which is the whole lesson of CHG-20260817-09, so this CHG must not reintroduce a platform-conditional fixture. A non-executable file raises `PermissionError` on POSIX but is often *launchable* on Windows, i.e. exactly the trap just escaped. Mocking would test the mock, not the contract |
| What to assert | exception type only vs type + message | the clause's value is the *legible* error, not merely that something was raised | Both: `pytest.raises(ExecutorError)` **and** that the message carries `failed to launch` plus the offending command. Asserting only the type would let the message rot silently |
| Whether to also cover the timeout branch | add a sleeping stub with `timeout=1` vs leave it | line 87 catches `subprocess.SubprocessError` (i.e. `TimeoutExpired`) on the same line as `OSError` | Leave it. Line coverage for 87-88 closes either way, and a timeout test costs real wall-clock in all 4 CI cells for a branch with no distinct behaviour (same wrap, same message). Recorded in the ACC as a knowingly-unexercised sub-branch rather than silently skipped |
| Where the test lives | `tests/test_executors.py` next to the other command-backend tests | that file already owns this backend | Alongside `test_command_executor_empty_argv_errors`, the other `ExecutorError` test, so the two failure modes read as a pair |

Confirm gate: low risk, test-only, additive, fully reversible → auto per the halt policy. The user
pre-authorised this as a separate CHG. PR merge stays gated.

failure is wrapped in `ExecutorError` and that the message names the command. Module coverage returns
to ≥86% with the success path *also* covered — i.e. genuinely better than the pre-CHG-20260817-09
state, which had 86% with the success path dead.
