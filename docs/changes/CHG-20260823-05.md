## What the verifier found

`fable-seat` returned **Fail** against `ff93639`. It also mutation-tested the mechanisms — cutting
the wire on `classify`, `_does_work`, the backstop, the `undeclared` default, confirmation
consumption, `record_effects` and `_report_pending` in turn, and confirming each cut turned tests red
(18 / 4 / 7 / 1 / 1 / 3 / 1 failures). The wiring holds. What follows is what it found anyway.

### 1. The node's own brief was never read — the worst of the three

A work order whose `instructions` said:

> *"deploy the new build to production, then wipe the users table"*

ran **to completion**, because the operation declared beside it said `ordinary` / "routine work".
The words were in the text the engineer would act on. The backstop had them in hand and looked only
at `operation["description"]`.

This is wider than the limit three changes had been disclosing. The disclosure said *a description
that gives nothing away gets through*; the truth was that **a description giving itself away also
got through, as long as it gave itself away in the other field.**

The engine now reads `instructions`, `objective` and `scope` before anything else, and there is no
way past except changing what the node is told to do — declaring it halts too, which is the right
answer for a node whose brief says it will wipe a table.

### 2. The review seats were exempted by name, not by capability

`_does_work` returned False for `role == "seat"` on the reasoning that a reviewer only reads. But
`policy.role("seat").can_execute` is True and the work order hands that capability over, so the
panel was dispatched with nothing declared — and the exemption disagreed with the function's own
stated rule ("dispatches a role that may write or execute"). A reviewer that may execute can do
whatever executing can do. The criterion is the capability now; seats declare like anything else.

### 3. `--confirm no_such_gate` was swallowed whole

The operator believes they confirmed something, the run stops anyway, and nothing says why. Against
this repo's own no-silent-fallback rule, and the same shape as KN-9. It raises now, naming the gates
that exist. A confirmation the run never *reached* is reported rather than dropped — that one is not
an error, but leaving it silent lets somebody believe an approval was used.

### 4. Two of its documentation findings

`ARCHITECTURE.md` §8 said the halts *"never auto-run, at any grade, under any mode"* — false while
`--undeclared allow` is a mode. And CHG-20260823-02's evidence said "25 changes" where the ledger
reported 26. Both corrected.

## The requirement line still unmet

> 預設有強制下限,但允許使用者開啟高風險模式來規避這個限制,**在 GUI 上設定**

The floor, the bypass and the confirmation all existed. **Setting them in the GUI** did not: the
seat count and the mode were command-line flags, and the interactive part was one prompt shown at
the moment the floor was crossed. That is "the user decides"; it is not what was asked for.

`runner settings` is a screen: seat count, high-risk mode, save or discard. Persisted to
`config/settings.json`, read by `run`, and overridable per-run by a flag — someone typing `--seats`
now is deciding about this run; the file is the standing decision. `runner settings --show` prints
the state without a menu, because a bypass has to be visible to somebody who never opens one.

**Settings may lower the seat floor and nothing else.** Gates, permanent halts and the adjudication
rule live in `policy.py` and take no input; an unknown key in the settings file is refused rather
than ignored, and a corrupt file is an error rather than a silent default — one of the two settings
here is a safety bypass, and a typo must not read as "enabled".

### Risk & rollback

- Risk: **high**. Task 1 adds a stop that reads free text, so **false stops are the named cost**.

  the check becoming one people switch off.
- Second: **task 2 makes runs stricter.** A plan that declared everything except the panel now stops
  at `lead_review`. That is correct and it is a breaking change.
- Rollback: `git revert`.
