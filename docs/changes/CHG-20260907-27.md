## What CHG-20260907-04 saw, and what was under it

`CHG-20260907-04` named this *"`(asked twice)` while the tally says 1"* and left it as a display
split. It is not one. Reproduced here on `3a8caf2`, through the real `Runner`, driving the console's
own two fields and building the row `console/index.html` builds from them:

```
walk       the <p> counts   options?   tally after   the row under the aspect
start      asked once       no         1             not stated
instruct   asked twice      no         2             not stated
instruct   asked 3 times    YES        3             asked 3 times. Options ...

start      asked once       no         1             not stated
instruct   asked twice      no         2             not stated
attach     asked 3 times    YES        2             asked twice. Options ...
```

Row six is the finding. **Options are on the table on the attach lap** — the run has left the
ask-again path for somebody who was asked twice and answered by nobody, because they attached an
unrelated file. That the two numbers in the box disagree is the symptom that makes it visible; the
escalation is the defect.

It is `CHG-20260904-05`'s own headline, one lap over. That record measured that exactly three
methods walk from an incomplete stop and that `attach` is the one where nobody was asked, and
repaired the **tally**: `server._walk_once` stops appending. It left the arithmetic alone —

```python
def asks_including_this_one(history, aspect):
    return times_asked(history, aspect) + 1        # unconditionally
```

— so the walk that is not counted still counts *itself*, and `2 + 1` is `intake.ASK_LIMIT`.

## The repair is an input

`asks_including_this_one(history, aspect, in_flight=True)`, and `+ (1 if in_flight else 0)`.

**A parameter and not an inference.** `intake.py` is handed a history of stops and an aspect. An
attachment leaves no trace in either, nor in `cfg.instructions` (unchanged by `attach`) nor in the
artifacts (which change on an `instruct` that also attaches nothing new only by not changing). The
engine cannot tell an `attach` walk from an `instruct` walk from anything it is given; only the
caller that performed the walk knows why it walked. A synthetic history entry would corrupt the
thing the tally is, and a `walk()` keyword is the same new input carried further from the config the
engine takes its whole world through.

So: **`RunConfig.intake_ask_in_flight: bool = True`**. It is not the whole input — see *Two
inputs* below, which is what a review seat's blocking finding added — but it is the half nothing
else can supply.

### And to `stop_reason`, which is not a widening

`stop_reason` and `needs_options` answer the same question at the same moment. CHG-20260903-42
exists because they read it differently — *"(asked 3 times)"* over a decision that had counted two —
and its repair was one name both of them call. Handing this record's keyword to one and not the
other is that defect back in a new spelling, and it is also what leaves row six's second half true.
One input, two readers:

```python

stop_reason(survey, cfg.intake_history, in_flight)
```

Measured after, on the same two sequences:

```
walk       the <p> counts   options?   tally after   the row under the aspect
instruct   asked 3 times    YES        3             asked 3 times. Options ...   <- unchanged
attach     asked twice      no         2             not stated                   <- the fix
```

The instruct path is byte-identical to what shipped. On the attach path the run stays suspended and
asking, and the sentence and the counter are one number again.

## Two inputs, because neither caller can answer for the other

This is the half the first build got wrong, and a review seat blocked it.

**The caller's declaration** — `RunConfig.intake_ask_in_flight` — is the only thing that can tell an
`attach` walk from an `instruct` walk. Both dispatch the same asks; the difference is entirely in
why the walk happened, and only the caller knows that.

**Whether a session was opened at all** is the fact the caller cannot know in time. On a resumed
walk every seat's answer can come back out of the journal without a session being opened, and a walk
that opened no session asked nobody. `engine.walk` measures it where it is knowable — over the
survey node's own asks, after the seats and before the escalation:

```python
asks_before, resumed_before = len(report.asks), len(report.resumed)
...
asked_somebody = (len(report.asks) - asks_before) > (len(report.resumed) - resumed_before)
in_flight = cfg.intake_ask_in_flight and asked_somebody
```

**This is not a unification of the server's rule and the command line's.** Those two ask *"did the
requirement grow?"* — a fact about the brief, at two moments, in two callers, and they stay where
they are. This asks *"did this node open a session?"*, and it is strictly weaker: it can take an ask
away and never add one. It cannot see an attachment; the declaration cannot see a journal hit. Both
have to be true, which is why they are two inputs and not one function.

## Who fills the field: the server does, the command line cannot

**Server.** `_walk_once` already decides *"did the requirement grow?"* to know whether to record the
stop — `server.py:926` on `3a8caf2`, not `788`, which is a paragraph of `_advance`'s docstring; the
three line numbers in the brief were checked and two had drifted. The same expression, read once
before the walk:

```python
cfg = dataclasses.replace(
    cfg, intake_ask_in_flight=(len(self.state.instructions)
                               > self.state.instructions_when_last_asked))
```

Deliberately the same expression rather than a shared helper. The two live at two moments, and
`cmd_run` decides the same thing a third way, from the report; what has to hold is that the
**server's** two answers agree, and `test_the_walk_is_told_whether_it_is_an_ask` asserts it walk by
walk — reading the config the runner actually handed each walk, rather than reading the source.

Set on the config rather than through `_make_config`, for the reason already written six lines
above it: twenty callers build that one and several are `lambda *a, **k:`, which would accept a
seventh argument and drop it.

**Command line: left at the default, and covered by the engine instead.** `cmd_run` builds its
config before the walk, and its rule — *"at least one intake ask was dispatched this lap"* — is a
fact about a report that does not exist yet. Measured on a journal driven the way `cmd_run` drives
one, before and after:

```

1  fresh                             0     3  no                  1
2  fresh, one more instruction       0     3  no                  2
3  --resume, same brief              3     4  YES                 3      <- the first build
3  --resume, same brief              3     3  no                  2      <- now
```

Run 3 asked nobody — its three intake asks all came back from the journal, no session opened — and
escalated anyway. The fourth ask counted in row three is the **option ask the escalation itself
dispatched**, so `cmd_run`'s own guard read *"somebody was asked"* because the runner had given up.

**The first build shipped this as a known residue and a review seat refused it**, correctly: *"the
claim that the fact is knowable only after `walk()` is too strong — by the time the engine evaluates
`needs_options` it has already performed the intake survey asks and populated `report.resumed`."*
That is right, and it is what the section above now does. The rejected alternative stands rejected:
`not cfg.resume` is right for run 3 and wrong for `--resume` with a **new** instruction, where every
ask is re-dispatched because the order changed (CHG-20260901-14) — the normal way to answer an
intake stop here, which would have started needing four asks instead of three. What was wrong was
concluding from one bad alternative that there was none.

The server is **not** unaffected by the conjunct, and the first build said it was. That claim, and
what it cost, is the next section; the sentence it stood on was *"start, instruct and attach each
change instructions or artifacts, so the order and the journal differ and every seat asks again"*,
and it is false for `start`. `Runner.start` builds a fresh `RunState`; `cmd_serve`'s journal
(`cli.py:1571-1572` on `3a8caf2`; every other line number in this record is against that sha and
this one silently was not — a second seat caught it pointing at an uncommitted file) lives at
`token_dir/asks`, persists across processes, has no run id, and nothing clears it. The same brief
started again replays every seat — **when the journal's last intake walk was on exactly that
brief**, which the third round adds because the sentence without the clause claims more than the
journal does. The journal keeps one order per ask id and the last walk overwrote it, so
`start a, instruct b, restart, start a` finds an order for `a + b` against a brief of `a`, and
re-asks. Measured through the real `Runner`:

```

start a                             0     3      1      1  asked once
restart, start a                    3     3      0      0  not asked yet   <- replayed
start a, instruct b, restart, start a
```

Worth stating plainly, because it is what an operator meets: a restarted server needs **one extra

What is true of the other two laps, and is all that was ever measured: `instruct` and `attach` each

### Two repairs, both measured

**Chosen — the guard takes both halves, the same two numbers the engine takes.**

```python
if (stop.get("incomplete") and told > self.state.instructions_when_last_asked
        and len(report.resumed) < len(report.asks)):
```

The second conjunct is the rule `cli.cmd_run` already uses at its own `record_intake_stop`. The
engine measures its own node's asks (`asks_before` / `resumed_before`), and at an incomplete intake
stop those start at zero — `intake_review` is the first asking node and nothing routes a rejection
back to it, which is the sentence `cmd_run`'s own comment already carries — so the deltas are the
absolute counts and the two readers are reading one pair of integers.

**What that costs, corrected in the third round — this record overstated it.** The two red lines

that stood here called them *"written up as something a client reads"*. Measured:
`RunReport.as_dict()` is called by **nothing in `src/`** — `cli.py`'s own comment at the

Two lines in an inventory is not a wider change than the defect.

The honest reason to reject it is the one this record made only in passing: **a field whose only
reader is two lines downstream is a worse shape than a conjunct.** It would put a handoff between
two objects inside one process onto the report's documented shape and leave it there for every
later reader to account for. The choice stands — the seat that raised this agrees with it — but the
argument for it was inflated, and an inflated cost is the same defect class as an inflated
guarantee.

The escalation's own option ask cannot make the chosen guard read true where it was false — but
**not for the reason this record gave**, which was *"an option ask is dispatched only for an aspect
where `in_flight` already held"*. That sentence is false, and `intake.needs_options` is where it
fails:

```
needs_options = times_asked + (1 if in_flight else 0) >= ASK_LIMIT

recorded=3  in_flight=False  ->  3 >= 3  ->  True
```

Swept over every sequence of `instruct` / `attach` / same-brief restart up to five operations —
2004 walks through the real `Runner`, 194 of them dispatching an option ask:

```
where the option ask fired    the engine's in_flight    the guard's `told > mark`
instruct, 151 walks           True                      True
attach,    43 walks           False                     False
```

So it **is** dispatched with `in_flight` false, 43 times, and the guard is still right. `in_flight`
is a conjunction, so a false one is false in one of two ways, and each is closed on its own:

- the **caller's** half is false — the requirement did not grow. Then `told > mark` is that same
  falsehood and the first conjunct has already refused the append, whatever the third says. This is
  the `attach` column.
- the **node's** half is false — the survey came back entirely out of the journal. Then the
  requirement cannot have grown: a grown brief changes every work order, the journal keeps one
  order per ask id, so the orders mismatch and every seat is re-asked. The one walk that survives
  with `told > mark` is a replayed `start`, where the mark is `-1` on a fresh `RunState` — and a
  fresh `RunState` has an empty `intake_history`, so `times_asked` is 0 and no option ask can fire
  there at all. Measured: all 363 swept walks with `told > mark` and a fully resumed survey are
  restarts, every one with an empty history and no option ask.

Measured as well as argued: across those 2004 walks the escalation's own option ask changed the
guard's answer **zero** times. The conclusion was right and the reason was not, which is this
record's own subject — a reachability claim the code does not support. ACC finding 5 blocked the
same class here already, in the mirror direction: there a comment described a race the state machine
forbids, reachable in the prose and unreachable in the code. This direction is the more dangerous
one, because the conclusion drawn from it is right and only the reason is rotten.

That is the difference between this guard and `cmd_run`'s, which is still stated over a report that
includes the escalation's ask — see *What this does not do*, where the third round also corrects
what this record claimed about **that**.

### Zero turned out reachable, so zero has a spelling

Measured after the guard repair, not reasoned about: the second `start` renders

```
The requirement does not say: the architecture … (asked 0 times).
```

because `intake_history` is empty on a fresh `RunState` and `in_flight` is false, so
`asks_including_this_one` returns `0` and `intake.py`'s table began at `1`. `{0: "not asked yet"}`
is added. It is per-aspect, so it is also the right word for an aspect nothing has ever been asked
about while other aspects have.

**A test was already asserting the ugly string.**
`test_the_sentence_and_the_decision_agree_on_the_same_run[False]` sweeps `recorded` from zero, so
its first lap has always read *"asked 0 times"* — the mirror in the test stopped at one exactly
where the table did, which pinned the string instead of noticing it. Both say *"not asked yet"* now.
A mirror inherits the original's blind spot, which is the second time in this record that a guard
turned out to be shaped like the thing it was guarding.

**The console is deliberately not given the same word.** `console/index.html` renders its count
only where options are on the table, and options need `ASK_LIMIT` asks — so nothing a browser can
draw counts zero. Prose nothing can produce is what this record has already had to withdraw a
registry entry for.

### The test

`test_the_same_brief_started_twice_says_one_number` starts the same brief twice on one journal,
with a floor per lap: the first must have resumed nothing, the second must have resumed **every**
ask, or the test is measuring an ordinary run. It then asserts the sentence and the counter are one
number, and asserts the agreement off the `in_flight` the engine actually used — the stop recorded
has to be the walk the engine called an ask, walk by walk — rather than off either of the two
expressions that produce it. Reverted both ways, it goes red on the claim: with the guard's second
conjunct removed, *"the counter says 1 ('asked once') and the sentence reads … (not asked yet)"*;
with the zero spelling removed, *"asked 0 times"*.

## What the tests could not see, and what they see now

Three of these were named by the seats before the build; the last two are the review's.

**`test_the_runner_does_not_give_up_on_somebody_it_never_asked_again`** started from **one**
recorded ask and attached four files, so the tally never came within one of `ASK_LIMIT` and no walk
could have escalated whatever the engine decided. Then it asked `needs_options` about the history
**after** the walk — re-deriving from a fixture a decision the runner had already made, with an

of the limit, walks an `attach`, and looks at what the run put in front of the operator; and then
takes the real third ask, so this is not "the escalation stopped working" wearing the name of a fix.

**`test_the_console_shows_one_answer_to_how_many_times_it_has_been_asked`** compared two snapshot
fields and walked `start` and `instruct` only. On those laps the stop is always appended, so the two
columns can differ only by *which* stops were counted — which is CHG-20260904-03's defect, and was
fixed. The lap where they differ by the ask in flight is `attach`, and it is in the sequence now.
It also builds the row `console/index.html` builds, because the claim is about two numbers in one
rendered box and a test comparing snapshot keys never enters the box.
`test_the_row_this_file_renders_is_the_row_the_page_renders` is the floor under that mirror: a
mirror nobody checks is a second implementation.

**The row assertion was an `or`, and on the attach lap the `or` was satisfied by the left side**
— `_console_gap_row` returns `"not stated"` whenever there are no options, so the assertion said
nothing on the one lap the test had just been extended to reach. A review seat found it. It is
split by lap now: an `attach` lap must render `not stated`, which under the defect reads
*"asked twice. Options, ..."* and fails.

**`test_a_resumed_walk_that_opened_no_session_asked_nobody` is new**, and is the blocking finding's
own test: a journal driven the way `cmd_run` drives one, two recorded stops, then a fully resumed
walk. It asserts the absence of options **before** its own floor, because under the defect the extra
ask the floor counts is the option ask the escalation dispatched — the floor would have fired first
and named the symptom instead of the finding.

**`test_a_journalled_console_run_still_reaches_the_escalation` is new for the opposite reason.** The
conjunct is inert on `serve`'s `instruct` and `attach` laps only because both change something every

of `_order_for`, not of this change. (It is **not** inert on `start`; that lap is the second round's
subject below, and has its own test.) Every other server test builds a config with **no journal**,
which makes `resumed` structurally `0` and the conjunct structurally true, so nothing measured the
inertness this change now depends on: if artifacts or instructions ever stopped reaching every work
order, `serve` would quietly stop escalating and no test would go red. Named by the second seat,
which measured the inertness by hand and said so. Its floor captures the config the runner hands the
walk — `resume=True`, this journal — and asserts the journal actually holds answers, because
without both the conjunct is trivially true and the test would pass over its own subject.

**`server.py`'s comment table** (at `intake_asks_by_aspect`, `server.py:369-372` on `3a8caf2` — the
brief cited `285-299`, which is `_adjudication_for` and the head of `RunState`; there is exactly one

## A comment that described a race the state machine forbids

The first build's comment beside the new assignment said an `instruct` arriving mid-walk could make
the two reads differ, and called that the harmless direction. A seat measured that **the divergence
is not reachable at all**, which is worse than harmless in a comment: a reader could take it as
licence for a divergence that really would be.

`start`, `instruct` and `attach` each set `state = "running"` under the lock before calling
`_advance`, and `instruct` refuses anything but `suspended`, `idle`, `finished` or `stopped` — so no
instruction can be added while a walk is in flight. `attach` is the one method that can arrive
mid-walk and it does not touch `instructions`. `instructions_when_last_asked` is written in
`_walk_once` and nowhere else, one walk at a time. Both operands are fixed for the whole walk, and
the comment now says so. The agreement is the state machine's, not luck.

## The fourth round: a regression the third round's own sweep hid

A seat had cleared this build's behaviour and refused only its text. Asked to read the corrected

The third round counted walks that *dispatched an option ask*. The defect lives in the walks that

```
op         declared  recorded  walks    before      after
start      True      True        363    correct     unchanged
instruct   True      True        547    correct     unchanged
restart    True      False       363    correct     unchanged, mark now moves
restart    True      True        184    correct     unchanged
attach     False     False       447    correct     unchanged
attach     True      True        100    **wrong**   declared False, no append
```

`instructions_when_last_asked = told` and the append shared one `if`. The second round added
`resumed < asks` to that `if`, so a replayed `start` correctly recorded nothing — **and stopped
moving the mark**. `Runner.start` builds a fresh `RunState`, so the mark restarts at `-1`; the
next `attach` read `1 > -1`, was declared an ask by the same expression, and appended. The
console said *"asked once"* after `POST /attachments`.

`docs/API.md` carries a **written contract** that this never happens. It is `CHG-20260904-05`'s
defect — the tally moving on an attachment — on the path this record itself opened, and at
`3a8caf2` and `28afbc2` the replayed start still set the mark, so it is a regression this record
introduced rather than one it inherited.

### What ships

```python
if incomplete and told > mark:
    mark = told
    if resumed < asks:
        history.append(...)
```

The mark moves on its own condition; only the append takes the third conjunct. And the field is
renamed **`instructions_when_last_read`**, because that is what it records: a replayed walk asks
nobody and still leaves every seat's answer standing against that brief, so the requirement has
not grown since. `told > mark` is *"did the requirement grow since the answers in hand were
given?"* — a question unchanged by whether a session was opened.

The pin's target set widens to `{"intake", "intake_review"}`: it looked for edges into
`intake_review` only, so an edge into `intake` would have revisited it with other nodes' asks in
the report and stayed green. True before, pinned now.
