## 1. The empty answer was a permanent latch — the worst of it

CHG-50 taught `_frontier` that `{"module": ""}` means *nothing left to build*. It kept that answer
for the rest of the walk. `next_module` is the **only** ordinary route into `engineer_build` —
`engineer_selfverify.rejects_to` needs the builder to have just run — so once the engineer had said
it, the engineer could never be asked again.

A seat drove the real CLI through a second instruction:

```
003-pm_plan          modules: ["alpha"]
007-engineer_build   {"module": "", "note": "every module already matches the brief"}
...merge...
017-pm_plan          modules: ["alpha", "beta"]      <- the new instruction
021-lead_review      <- next_module said "none"; engineer_build NEVER re-asked
state: finished
```

`engineer_build` appears once in 28 asks. `lead_review → pass` printed twice. **Nothing on disk.** A
governance runner whose current plan named two modules merged and closed having attempted neither,
and no line of output said so.

A new `pm_plan` now retires the engineer's previous last word. "Nothing left" is about the plan that
was current when it was said.

### And the test written for that exact claim could not have caught it

CHG-50's task table read *"'Nothing left' is not a latch — [x]"*. Its test:

```python
assert _frontier_over([
    ("pm_plan",        {"modules": ["markup"]}),
    ("engineer_build", {"module": "markup"}),
    ("engineer_build", {"module": ""}),
    ("pm_plan",        {"modules": ["markup", "charts"]}),
    ("engineer_build", {"module": "charts"}),      # <- appended by hand
]) == "none"
```

The last ask is one **the shipped graph cannot produce**: reaching `engineer_build` requires
`next_module` to answer `"module"`, which is the thing under test. The assertion never examined the
reopening moment. It is retired to a named marker; the claim is now pinned by a test that drives the
real CLI through a real re-plan.

## 2. Failure evidence was read as completion

The other seat drove `{"module": "", "error": "compiler failed"}`:

```
engineer_build → engineer_selfverify → lead_task_review → record_module
→ next_module → lead_review ×3 → qa_verify → qa_accept → pr → merge → done
STATE finished
```

`missing.py` never built. Note `record_module` runs **before** `_frontier` reads the empty answer.

"There is nothing left to build" and "I could not build it" are two different claims. An answer
making both is refused by name now, the same way the importer refuses two conversations claiming one
id.

## 3. Nothing downstream checks any of it

CHG-50 said *"Review is the thing that catches that"* and ACC-50 said `lead_review` and `qa_verify`
*"stand between a silently empty build and a merge"*. **I wrote both without checking.** Both seats
checked:

- `lead_review` adjudicates whatever verdict strings the seats return
- `qa_verify` is a **branchless step**; one seat passed it with `{"summary": "verification complete"}`
- `qa_accept` accepts `{"verdict": "pass"}` unconnected to any probe or artefact
- **no node compares `pm_plan.modules`, `expected_outputs`, or the filesystem**

This runner does not inspect work products, so it cannot decide whether "nothing left" is true — the
artefacts may genuinely predate the run, which is the case CHG-50 existed for. What it can do is
refuse to be silent: ending the loop with planned modules unrecorded now writes a line into the run
report naming them and saying no node after this one checks it.

## 4. `agent_cwd` silently substituted a review seat

CHG-48 applied it to **every** spawned command. `--seat-model` argv is typed in the operator's
shell — CHG-49's own doctrine says a CLI path belongs to the shell you typed it in — and was being
relocated into the config's directory. A seat put a same-named file beside the config answering
`pass` while the operator's own script answered `fail` on everything:

```
panel: lead_review → pass (conformance=pass, ...)
state: finished
```

**The operator's veto seat was replaced by a file in someone else's directory and nothing said so.**
Every shipped example keeps an `agent.py` beside its `runner.yaml`, so `--seat-model
risk="python3 agent.py"` hits it immediately.

`agent_cwd` now applies only to the command `runner.yaml` itself named. Seat commands and
registry-sourced commands keep the shell's directory, which is what they meant before CHG-48.

## 5. An explicit relative `agent_cwd` was resolved against the shell

`load_config` only `setdefault`-ed, so `agent_cwd: sub` survived as the bare string `"sub"` and
`subprocess.run` resolved it against the operator's shell — the config-sourced-path-resolved-against-
the-shell defect, **inside the key introduced to remove it**. README asserted both "can be set
explicitly" and "means one thing no matter where you are standing"; both could not hold. Relative
values are anchored to the config file now; absolute values are left alone.

## 6. One unreadable conversation in the target aborted the whole import

`in_target` was a dict comprehension over `into.conversations()`, so a single target conversation
whose header lacked `project` raised `KeyError` out of the whole expression, was caught as
*"(the target) could not be listed"*, and returned **zero imported** with the offending conversation
unnamed. That is CHG-47's own defect 4 mirrored onto the target side, inside the change whose Risk
section said "a stray file no longer aborts the store".

One seat called it a defect; the other saw the same mechanism and judged it consistent with the
backend contract. **The record was wrong either way**, so both the behaviour and the sentence are
fixed. Rows are read one at a time now, and a row this runner cannot compare against is named while
everything else imports.

## 7. `mutation_check.py` believed any red

`caught = returncode != 0` could not tell *"the pinning test failed for the pinned reason"* from a
collection error, an import failure, or a pre-existing red. Both seats named it independently. Each
test file is now run **unmutated** first, and a mutation whose file is not already green reports
`NO BASELINE` rather than caught.

The deeper limitation is now written into the module docstring, in a seat's words: it answers *"can
the tests I wrote fail?"*, never *"did I write the test for the case that matters?"* CHG-50's
`frontier` group was 2/2 caught, its table read clean, and the latch shipped anyway — because no
mutation of the *code* can expose a test whose *scenario* is unreachable.

## What went wrong while fixing it

Three more, all mine, all caught by running rather than by reading:

**My headline test passed against the defective code.** The first draft of the latch test did not
pre-seed, so round one built `alpha` by the ordinary route, `remaining` emptied, the engineer was
never asked twice, and no empty answer was ever produced. A test for a latch that never reached the
latch — the same mistake one layer up from the one it replaced. Found by running it against
`origin/main` and seeing it pass.

**A patch script truncated `tools/mutation_check.py` to zero bytes.** `io.open(path, "w")` truncates
before it validates its arguments, and the `newline` argument was wrong. Restored from git. The
lesson is not the typo: I overwrote a file without looking at it first.

**A stale mutation anchor.** Renaming `cwd` to `config_cwd` rotted one of the twelve existing
mutations. The tool reported `ANCHOR GONE` and failed the run rather than counting it as caught —
which is the one part of this that worked as designed.
