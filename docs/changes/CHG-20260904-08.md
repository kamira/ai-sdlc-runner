## Read this first

`tools/ledger_check.py` has four supersession checks. The first three all begin at `_supersedes`,
which the file's own comment says out loud: *"they all start at a `Supersedes:`"*. The fourth was
added by `CHG-20260903-30` for the case they miss, and it asks one question - whether the record a
`Superseded by:` names **exists**.

So a record can drop its `Supersedes:` line and every check is skipped, while the record it used to
claim goes on pointing forward at it. Measured on the withdrawal branch:

```
                                 _supersedes(-24)        _superseded_by(-15)
origin/main                      ['CHG-20260901-15']     ['CHG-20260903-24', 'CHG-20260903-25']
origin/claude/chg-24-withdrawn   []                      ['CHG-20260903-24', 'CHG-20260903-25']

python tools/ledger_check.py <the branch>   ->   ledger check passed (186 changes)
```

`CHG-20260901-15` records that `-24` replaced it. `-24` denies it. The lint is green, because the
only check that starts at the back-pointer stops at *does the file exist*.

This is the same asymmetry `CHG-20260828-02` found between ACC and CHG, that `CHG-20260903-26` found
one field later, and that `CHG-20260903-30` found one direction later. **One direction further in,
and it is live** - and the record that found it is the one that created it.

## What check 4 does not have

`grep -rn "leads nowhere" tests/` returns nothing. The check `CHG-20260903-30` shipped has **no
test**. It is fixed here because a check nothing mutates is a check nobody knows still works.

## What is deliberately not changed

`_supersedes` reads **one line**, and both `-24` and `-25` wrap the field:

```
  Supersedes: the second half of CHG-20260901-15, which is withdrawn and re-issued as this
  record and [CHG-20260903-24](CHG-20260903-24.md)
```

The leading `-` is stripped from that quotation deliberately, and finding out why is the sixth
defect of this family. Quoted verbatim, the lint read **the example as this record's own field**
and reported `CHG-20260904-08: says it supersedes CHG-20260901-15`. `_supersedes` matches
`^[-*]\s*…` under `re.M` with no idea that it is inside a fence, so any record that quotes a field
acquires it. That is one more reader that cannot tell a declaration from a quotation of one, and it
is filed separately rather than widened into here — the fix touches `_status_line`, `_target_chg`
and both supersession readers, and this record's subject is the edge, not the parser.

The conformance seat reported the one-line read as luck rather than design. Re-measured, **widening
it is the wrong fix**: the continuation line names the *sibling* record, not a superseded one, so a
multi-line read would invent the edges `-25 -> -24` and `-24 -> -25` and then demand each say the
other back. The one-line read is what keeps those two out. A test pins that, so the next reader who
sees the narrowness does not widen it.

## Task 5, and why the gate is on the other id

Checks 1-3 skip a record older than `SUPERSESSION_REQUIRED_FROM`, because the field did not exist
before it. This check reads the **old** record's back-pointer and asks the **new** one to answer, so
the gate belongs on the record being asked. `CHG-20260901-15` is older than the threshold and its
two claimed successors are not: gating on the claimant would silence exactly the case that found
this.

## Risk & rollback

  on `main` does; the withdrawal branch does, which is the point.
- Rollback: revert. The half-trail becomes invisible again.
