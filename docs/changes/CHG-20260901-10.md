## The gap, measured

`Survey.complete` is one line:

```python
@property
def complete(self) -> bool:
    return not self.missing
```

`Survey` has **three** fields. `missing` stops a run. `problems` and `safety` do not:

```
missing: [] | problems: {'defect': ['the auth path is unspecified']} | safety: ['deletes user data']
complete -> True   <- the run proceeds, nobody confirms any of it
```

So the seats read the requirement, find that a function is unspecified and that the change deletes
user data, and the run walks straight on to `pm_plan`. Nothing stops. Nothing is shown — the
console's whole findings panel is behind `if (s.incomplete)`, so on a `complete` survey it renders
nothing at all.

That is 「功能性哪裡有缺」 with no effect whatsoever, and it is the whole of this change.

## What the first draft got wrong

The first draft proposed a new node `intake_confirm` and a new gate `findings_confirmed`. Four
seats took it apart, and two findings killed it outright:

1. **The node could never see the list.** `engine` returns SUSPENDED whenever `not survey.complete`,
   so a walk reaches anything after `intake_review` **only** when `missing` is empty. The proposed
   list's "what is missing" column would have been empty by construction at every visit, and a
   person would have been halted in front of an empty table — verbatim what `intake_review`'s own
   note refuses: *"a gate that fires on a complete requirement would be asking a person to approve
   the absence of a problem."*
2. **The list already exists.** `engine` already puts `missing`, `problems` (per seat, via
   `all_problems()`), `safety` and `options` into `report.suspended`, and the console already
   renders them as rows with the ask count and the raising seat. What is absent is not the list.

Two more that would have bitten later: the `no` branch routing to `intake_review` could not
converge (fixed generally in CHG-20260901-12, but `intake_review` is a `SURVEY` and no node's
`rejects_to`, so it is still not reached); and with `gate_when="after"` the person's **yes** was
not expressible at all — the panel's outcome routes, so approving the gate said nothing.

## The design

**No new node. No new gate.** The survey already stops the run; it stops for one of its three
fields and should stop for all three.

1. `Survey` gains `acknowledged: bool` — has a person seen these findings and said "yes, that is
   the list"?
2. `complete` keeps its meaning (`not missing`) and a second predicate joins it. `intake_review`
   suspends when the requirement is **incomplete** *or* when there are findings nobody has
   acknowledged.
3. The suspension says which it is. `incomplete` is "supply what is missing"; the new one is
   "confirm this list, or add to it". They want different things from a person and the existing
   record already draws that line for `safety` — *"'this is dangerous' and 'this is underspecified'
   want different responses from a person."*
4. Acknowledging is an **answer**, not an approval: it can carry additions. A person who reads the
   list and says "you have also missed the migration path" is giving the run something no seat
   produced, and today there is nowhere for that to land.

### Why this is not the gate the first draft proposed

A gate fires on `policy.verdict(gate, risk)` — the grade, and nothing else. That is what made the
first draft decoration: it would have halted on a clean survey at `high` and passed a filthy one at
`low`.

This fires on **content**: findings exist and nobody has acknowledged them. A clean survey does not
stop. That is the same shape as the `incomplete` suspension beside it, which is why it needs no new
vocabulary — and it is the distinction `intake_review`'s NO GATE note was drawing, kept rather than
argued past.

## Open questions for the panel

1. **Where does the acknowledgement live?** `RunConfig.intake_history` is the precedent for
   per-aspect state carried across walks. Acknowledgement is per-**survey**, and a survey is not
   currently identified by anything.
2. **Does a re-survey invalidate it?** If the person adds an item and the seats are asked again,
   the new survey has findings nobody has acknowledged — correct, and also a loop. It converges
   only if the seats see the addition, and `intake_review` is a `SURVEY`, which CHG-20260901-12
   deliberately does not reach.
3. **Does `safety` deserve a stronger answer than `problems`?** Today they are separate fields for
   exactly that reason and this change treats them alike. A safety finding that a person waves
   through is a different act from acknowledging an underspecified function.
4. **Should an acknowledged finding still be visible later?** It is the closest thing this flow
   would have to "known and accepted", and nothing downstream reads it.

## Risk & rollback

- **Runs that proceeded now stop.** Any requirement the seats had findings on — which is most of
  them — now waits for a person. That is the point of ⑤ and it is the largest behaviour change here.
- **No plan migration.** Nothing is added to the graph, so no `node_specs` and no `operations` entry
  is needed and no existing plan breaks. The first draft's three new asking nodes killed every
  shipped plan at the third node; this touches none of them.
- **The console must be changed too**, or the operator is stopped and shown nothing.
- Rollback: revert. Findings go back to being collected, rendered only when something else stopped
  the run, and never confirmed.
