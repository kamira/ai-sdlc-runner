## The gap

The point of writing *"pinned by `test_one_node_one_kind_of_work`"* in an acceptance is that a later
reader can go and look. When that test has been renamed or deleted, the sentence still **reads** like
evidence and is not — and nothing in this repository noticed, because nothing looked.

Ninety-seven such references have accumulated across 223 records:

| the record's month | dangling references |
|---|---|
| 2026-06 | 41 |
| 2026-07 | 12 |
| 2026-08 (to the 27th) | 44 |
| **2026-08-28 onward** | **0** |

Most name an architecture that no longer exists — `executors.py`, `dashboard.py`, `workspace.py`,
`orchestrator.py` and the tests that went with them. `ACC-20260617-03` alone points at five panel
tests, none of which survive.

## The check

A record may not name a test that does not exist. A name counts as existing if it is a **test
function** or a **test module** — both spellings are in use and both are useful, `test_flow` naming
a file and `test_one_node_one_kind_of_work` naming one case in it. A rule that knew only functions would
report every file reference as a ghost, which is how a lint teaches people to stop reading it.

Only **backticked** names are pointers. These records discuss tests constantly in prose, and a
sentence saying *"we considered writing test_a_ghost and decided against it"* is not a claim about
evidence.

## Prospective, and that is the argument not the convenience

`TESTS_MUST_EXIST_FROM = "20260828"`. The ninety-seven are **history**: those changes were real, the
tests existed, and rewriting the records to name today's tests would be inventing a past rather than
fixing one. `BRANCH_REQUIRED_FROM` makes the same case in the same file —

> a lint that fails on history it cannot change teaches people to ignore the lint

Zero records from the cutoff onward break the rule, so it ships green and catches the *next* typo
rather than the last ninety-seven. Today's records were written by an agent citing test names from
memory all session; that a mistyped one would have gone unnoticed is the live risk, not the 2026-06
ones.

## What is not done

**The ninety-seven are not fixed, and this change does not pretend otherwise.** Auditing them means
deciding, for each, whether the named test was renamed (fix the name) or deleted with its subsystem
(say so in the record). That is a judgement per record, ~97 of them, and it is exactly the work
`ACC-20260828-08` reserved. This makes the pile stop growing; it does not shrink it.

## Risk & rollback

- The check can only add problems. A ledger with no dangling recent reference still passes.
- A false positive is possible in one direction: a record naming a test that is about to be added in
  the same commit will fail until the test lands. That is the intended order.
- Rollback: delete `check_named_tests_exist` and its call. Records go back to citing whatever they
  like.

### Not claimed

**That a test which exists says what the record claims it says.** This checks the pointer resolves,
not that the target supports the sentence. A record citing a real test for a guarantee that test
does not make would pass — and that is the defect class `tools/mutation_check.py` exists for, from
the other direction.

**That other kinds of reference are checked.** The survey also found 23 dangling `src/…py` paths.
They are not checked, because a record naming a module that has since been deleted is far more often
legitimate history than a broken pointer, and a rule that could not tell them apart would be noise.
