## The finding

`plan.check` validates the **shape** of every `decisions` value — a string, or a list of strings —
and never asks whether the names mean anything:

```
plan.check({"decisions": {"nonesuch": "x"}})           ACCEPTED   no such node
plan.check({"decisions": {"feedback": "elsewhere"}})   ACCEPTED   offers ['done', 'more']
plan.check({"decisions": {"module_built": "yes"}})     ACCEPTED   read, never supplied
plan.check({"decisions": {"next_module": "sideways"}}) ACCEPTED
```

`plan.py`'s own top-level rule refuses an unknown **key** with *"Ignoring them would let a setting
look configured and do nothing"*. **The doctrine stopped at this mapping's contents.**

`feedback` sits **after `merge`**. So a one-word typo was discovered past the one-way door, having
dispatched every ask, as an exception out of the walk rather than a refusal about a plan.
CHG-20260907-15 gave that run a closed record; this refuses the plan that produces it. Neither
fixes the other: an unknown *node* name ran to `finished` with a clean close and nothing said
anywhere.

## What ships

**One validator, `engine.check_decisions`**, so there is one spelling of the rule:

- a node this flow does not have — refused, and pointed at `graph.NODES`
- a branch the node does not offer — refused, and the message lists what it does offer
- one of the four nodes `_choose` answers before it reads `decisions` — `plan_scope`,
  `reconcile`, `module_built`, `change_retry` — refused, because supplying one is not overridden,
  it is **ignored**
- `"frontier"`, a branch name, or a list of them — accepted, and **every member** of a list is
  checked rather than the first

**Two call sites.** `RunConfig.__post_init__`, because a config built directly bypasses the plan —
two tests do it and so does `dataclasses.replace` in `server._walk_once`; and `plan.check`, which
catches the `EngineError` and re-raises it as `PlanError`, so a plan is refused in a plan's
vocabulary and a run in the engine's.

## A cost neither reviewer measured, and what it settles

Both reviewers chose `RunConfig` as the choke point. Neither measured what that does to
`_choose`'s four guards: a config carrying a derived-node decision can no longer be **built**, so
the guards become unreachable through the public API — and a guard nothing can reach is
CHG-20260907-09's subject.

Measured: they stay reachable by setting the attribute after construction, and `_choose` still
returns the derived answer. So the two tests keep their property and gain the new one, and say in
their own comments that going round the front door is what they are doing:

```
the front door         RunConfig(..., decisions={"module_built": "yes"})   refused
around it              object.__setattr__(cfg, "decisions", …)             _choose still says "no"
```

A test that has to go round the front door is being honest about what it proves: defence in depth
against a state the public API does not admit.

## The blast radius, measured twice because the first measurement was of the wrong population

A sweep over every dict literal keyed by node ids reported **26** offending sites. All but two were
CHG-20260907-11's gate-phase pin (`{n.id: n.gate_when …}`) and a change-class map — dicts that are
not decisions at all. Scoped to `decisions=` arguments and `*DECISIONS*` bindings:

```
a decision for a derived node      2    test_module_built.py, test_sub_planning.py
a node that does not exist         0
a branch the node does not offer   0
```

The full suite agreed: **exactly those two tests** failed. Sizing the repair from the first
population would have been worse than not sizing it.
