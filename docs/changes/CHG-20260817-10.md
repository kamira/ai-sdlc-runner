## Motivation

PR #5 was to be merged "if CI passes". Probing found there is **nothing to pass**:

| Probe | Result |
|-------|--------|
| `gh pr checks 5` | `no checks reported` |
| PR `statusCheckRollup` | `[]` |
| `gh api …/actions/workflows` → `total_count` | **0** |
| `gh api …/actions/runs` → `total_count` | **0** |
| `gh api …/branches/main/protection` | `404 Branch not protected` |
| CI config tracked in the repo | none — no `.github/`, `.gitlab-ci`, `tox.ini`, `noxfile`, `Makefile`, `.pre-commit-config` |

So every change in this repo's history has merged on locally-run, self-reported evidence. CHG-20260817-09 is the direct cost of that: five tests were red on Windows across at least four prior CHGs (they were introduced by CHG-20260617-06 / CHG-20260703-02 / CHG-20260617-08) and nothing mechanical ever said so. A Linux-only maintainer would never have seen them; a Windows-only maintainer would have seen nothing else.

**The lesson is specifically about the matrix, not about "having CI".** The defect was platform-conditional. A single-OS pipeline would have been green throughout and would have caught nothing.

There is a second, sharper reason recorded here because it constrains what this CI may promise. Measuring coverage during the CHG-20260817-09 close-out showed `executors.py` at **86% before** the fix and **85% after** — coverage went *down* while five broken tests became five working ones. The pre-fix tests executed the whole body of `CommandExecutor.run` and died inside it at `subprocess.run`, landing in the `except OSError` branch; coverage counted those lines as executed while **not one assertion in those tests ever ran**. A coverage threshold would have reported that module as well-tested for the entire period it was completely broken on Windows. This CI therefore gates on **tests passing**, and deliberately does **not** gate on a coverage percentage.

## Decisions & trade-offs

| Decision | Options | Assumptions | Why this choice |
|----------|---------|-------------|-----------------|
| Whether to have CI at all | keep self-reported local evidence vs add a pipeline | the repo is dogfooding ai-sdlc, whose whole premise is mechanical rather than promised verification | Add it. CHG-20260817-09 is a worked example of the failure mode: governance docs asserted green, the machine never checked |
| Platform matrix | Linux only vs Windows only vs both | the motivating defect was platform-conditional and invisible on one of them | **Both** — `ubuntu-latest` + `windows-latest`. This is the single decision that gives the CI its value; a one-OS pipeline would have stayed green through all five failures |
| Python matrix | pinned single version vs floor + current | `pyproject.toml` declares `requires-python = ">=3.9"`; an untested floor is an unbacked claim | `3.9` (the declared floor) and `3.13` (current). 4 cells with `fail-fast: false` so one red cell never masks the others. If 3.9 turns out red, that is a real pre-existing finding, not a reason to quietly narrow the matrix |
| Gate on coverage % | add a threshold vs tests-only | the 86%→85% result above | **Tests-only.** Coverage is measurable on demand but is demonstrably blind to this repo's actual failure mode; a threshold would have manufactured false confidence and, applied naively, would have *blocked* CHG-20260817-09 for lowering the number while fixing the bug |
| Governance gate in CI | local-only vs a CI job | `doc_integrity_check.py` is stdlib-only and the skill is vendored in-repo | Add a `doc-integrity` job. The CHG↔ACC pairing is a rule of this repo; letting the machine enforce it costs one short job |
| Submodule handling | `submodules: recursive` vs default checkout | `ai-skills/` is an **optional** fallback (CHG-20260617-05) and is not present in the working tree at all | Default checkout, **no** submodule fetch. Fetching it would make CI depend on a repo the runner is designed never to need, and would fail today since the submodule was never wired up |
| `AI_SDLC_SKILL_PATH` in CI | leave unset (7 tests skip) vs point at the vendored store | `skills/v1.16.0` is tracked in-repo (154 files) and the 7 tests pass against it locally | Set it to `skills/v1.16.0`. Verified locally: skips drop 9 → 2 and the suite goes 149 → **156 passed**. Leaving it unset would ship a CI that silently skips the skill-cache tests |
| Trigger events | every branch push vs PR + main | avoid two identical runs per PR push | `pull_request` (any base) + `push` on `main`. One run per PR update, one per merge |
| Where the workflow lives | `.github/workflows/ci.yml` vs several files | one pipeline, two job kinds | Single `ci.yml` with a `test` matrix job and a `doc-integrity` job |

Confirm gate: the user explicitly chose "Add CI first, then merge" when presented the no-CI finding. Low risk, additive, fully reversible → auto per the halt policy. The PR merge itself remains gated.

## Modification Guide

### Goal

Every push to `main` and every pull request mechanically runs the full pytest suite on Linux **and**
Windows, on Python 3.9 **and** 3.13, plus the `doc_integrity_check.py` governance gate — so the class
of defect fixed in CHG-20260817-09 can never again survive unnoticed. Local gates stay green and
unchanged.

### Global constraints (all tasks)

- **Do not touch `src/`, `tests/`, `config/`, or `skills/`.** This CHG adds a detector; it does not
  change what is detected. The suite must pass in CI byte-identically to how it passes locally.
- No submodule fetch — `ai-skills/` is an optional fallback and is absent from the tree.
- No coverage threshold, no lint gate, no auto-merge, no auto-format, no write permission: the
  workflow declares `permissions: contents: read` and only reads + runs.
- `fail-fast: false` on the matrix — a red cell must never hide the state of the other three.
- `PYTHONUTF8=1` / `PYTHONIOENCODING=utf-8` set for every job: the skill's scripts emit UTF-8 and
  raise a false-positive encoding error on Windows without them.
- New file ⇒ `docs/structure/directory.md` must be updated in the same round (structure-sync lint).
- Verification bar: `doc_integrity_check.py --repo .` exit 0 locally, **and** all 5 CI jobs green on
  PR #5 — the first real evidence this repo has ever had.

### Tasks

TDD note: the workflow *is* the test harness, so "green" is its own observed run on PR #5, not a
unit test. The pre-state is unambiguous and recorded above (0 workflows, 0 runs).

### Risk & rollback

- Risk: low. The workflow has read-only permissions, runs no deployment, publishes no artifact, and
  cannot modify the repo. Worst case it reports red on something pre-existing — which is information,
  not damage.
- The one real exposure: **the matrix may surface pre-existing failures** (most plausibly Python 3.9,
  never before exercised, and the 2 `curses` tests which have never run anywhere because the
  maintainer's platform lacks `_curses`). Per the Global constraints these are to be **reported as
  findings, not silenced by narrowing the matrix**.
- Rollback: delete `.github/workflows/ci.yml` and revert the two doc edits. Nothing else is affected;
  the repo returns to local-evidence-only.
