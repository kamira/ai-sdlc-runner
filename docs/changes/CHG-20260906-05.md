## Read this first

`docs/API.md` documents `POST /attachments`: its request body, its row shape, and three refusals.

```
grep -rln '"/attachments"' tests    ->    (empty)
```

Every other POST route in the page has a test that goes through HTTP. This one had none, so its
documented body, its documented row and all three documented refusals were pinned by nothing
executable. The upload path was exercised only by calling `Runner.attach` directly, which skips
base64, the body reader and the route.

## Why nobody had written it, which is not what was reported

The finding arrived as *"no test posts to `/attachments` over HTTP"*, which reads as an oversight.
Writing the test found the actual reason:

```
POST /attachments  ->  409 {"error": "this runner has no attachment store"}
```

The `live` fixture — the only one that speaks HTTP — builds its `Runner` through `_runner()`, which
never passed a `store`. So a test written at that layer could not have reached the route at all; it
would have hit that refusal and stopped. **The gap was not that nobody wrote the test. It was that
the fixture could not hold one.**

That is worth the distinction: an oversight is fixed by remembering, and this needed the fixture
changed.

## What changes

- `tests/test_server.py::_runner` takes `store=None`. Every existing caller gets exactly what it got
  before.
- The `live` fixture passes a real `attachments.Store` under its own `tmp_path`.
- Three tests go through HTTP: a successful upload whose row carries the five documented fields and
  no others, a body that is not base64, and a type the store will not hold.

## Tests

- `test_an_attachment_posted_over_http_comes_back_in_the_snapshot`
- `test_the_route_refuses_a_body_that_is_not_base64`
- `test_the_route_refuses_a_type_the_store_will_not_hold`

Three mutations pin the **route** rather than the store, since the store already has its own group:
the base64 refusal, the field name the page actually sends, and the filename surviving the trip.
