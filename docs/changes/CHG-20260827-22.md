# CHG-20260827-22 — one planning tier cannot plan a programme, and nothing reviewed two plans against each other

- Project: ai-sdlc-runner
- Branch: claude/chg-20260827-22-sub-planning
- Date: 2026-08-28 (UTC+0)
- Type: a second planning tier, and the node that reconciles it
- Proposed by: the same decision behind CHG-20260827-18 — a mid-to-large organisation shape, where
  one instruction becomes several workstreams
- Risk: **high** — it widens the dispatch tree and adds a node that can stop a run
- Autonomy: high
- Related: CHG-20260827-18 (a workstream has its own grade — this is where a workstream comes from),
  CHG-20260827-17 (the grade is adjudicated), CHG-20260827-23 (`can_write` reaches the factory;
  the new `planner` role relies on that wiring)

## The gap

`pm_plan` produced one list of modules at one scope, and `pm_plan.next` was `pm_confirm`. For a
programme that is really several workstreams that is the wrong shape twice over:

1. **One level of detail for parts that do not share one.** A schema change and a copy tweak get
   planned at the same granularity because there is only one planning node.

2. **Nothing reviews the plans against each other.** `lead_review` reviews the **change**. Two
   workstreams could pick incompatible interfaces and the first thing to notice would be a failing
   build several nodes later — or nothing, and the inconsistency ships. There was no node whose job
   was to compare two plans, and no equivalent of one anywhere in the flow.

## What it adds

Three nodes, plus one the build turned out to need:

| node | kind | who | why |
|---|---|---|---|
| `plan_scope` | loop | **nobody** (runner) | one workstream or several, read from the plan's own `workstreams` |
| `sub_plan` | step | `planner` (pool, `main="pm"`) | each workstream planned at its own scope |
| `reconcile` | decision | **nobody** (runner) | the declared interfaces are compared |
| `halt_unreconciled` | terminal | — | the same conflict twice is not something re-planning fixes |

`pm_plan.next` becomes `plan_scope`. A plan with one workstream or none takes `single` straight to
`pm_confirm` — which is every plan written before this change, and why the shipped example is
untouched.

**Scope is read, never answered.** There is no decision key for `plan_scope`. A run that could
answer it could declare itself simple and skip the reconciliation that exists to catch it, and
`visited` would show a clean single-workstream run.

**Reconciliation is not a vote.** Two declarations naming one interface differently is a fact about
the plans, and a fact is not improved by voting on it. `reconcile` has no role, no panel and no
gate. It compares strings and reports the disagreement by name — an operator sent back to `pm_plan`
by a boolean would be guessing at which interface.

## Where this departs from the proposal

The proposal's task 2 read **"Depth is bounded at three, and asserted"**. Three is wrong, and the
first defect below is how that was found. The bound is **two**, it is derived from the graph rather
than asserted as a number, and `check_dispatch_depth` refuses anything deeper on every run. Task 1
in the table above is that task, restated to what turned out to be true.

Every other task in the proposal is delivered as written.

## Four defects this change found in itself

**`MAX_DISPATCH_DEPTH = 3` was wrong, and the sentence I wrote is what misled me.** The record said
*"`pm` → `planner` → `lead` → `engineer` is three dispatches"*. The planner does not dispatch the
lead; `reconcile` returns to the runner's main line. The chains are `pm → planner` and
`lead → engineer` — siblings, not nested — so the tree is **still two deep**.

Which means `engineer`'s old note, *"cannot dispatch further, so the tree stays two deep"*, was
**still true**. It had merely stopped being true *for the reason it gave*. That is this
repository's own dominant defect class, reproduced while writing the change that removes it.
`test_nothing_is_unwired` is what caught it: `MAX_DISPATCH_DEPTH` was defined and nothing computed
it. A bound nothing computes is the same defect one release later.

**`conflict → pm_plan` cycled.** `pm_plan`'s answer cannot change `cfg.interfaces` — they are read
from the plan file — so a conflict routed back is unchanged by definition and the flow spins until
`max_steps`, where the operator is told only that something looped. Bounded to **one revision
pass**, which is the bound `re_review` already puts on a fix.

**`interfaces` was never wired to the run.** `plan.load` parsed it, `RunConfig` had the field,
`conflicts()` was correct, and every unit test passed. The end-to-end case through the real CLI is
what found that `cli.py` never passed `plan.get("interfaces")` into `RunConfig`.

**The depth bound was not enforced where this record claimed** — found by a mutation, during
acceptance, *after* the first defect above was supposedly fixed. Deleting
`policy.check_dispatch_depth(...)` from `engine.walk` left the whole suite green, because the test
called the function directly and nothing drove it through a run. That is the **same defect as the
first one, in the same change**: a guarantee stated in one place and checked in another that never
meets it. `test_the_bound_is_enforced_on_a_run_not_only_available_as_a_function` closes it.

## A halt was reporting success, and that is fixed here rather than separately

Every `TERMINAL` node set `state = FINISHED`, whose own docstring reads *"the flow ended where it
was designed to"*. `STOPPED` is documented as *"a permanent halt"*. So `halt_second_fail` — a run
that gave up — reported the same state as `done`, which is exactly the distinction the
`FINISHED`/`SUSPENDED`/`STOPPED` vocabulary was introduced to draw.

Found because `halt_unreconciled` halted correctly, named the interface, and said `state: finished`.

`Node.permanent` is **declared**, not matched on a `halt_` id prefix: a convention is not a
constraint, and a terminal added tomorrow and called `abandoned` would report success with nothing
to say so. `graph.validate` refuses `permanent` on a non-terminal node.

**This changes what `halt_second_fail` reports.** That is outside this change's stated scope, and it
is stated here rather than slipped in. Fixing it only for the new node would leave two halts
disagreeing about what a halt is, which is worse than either answer alone.

## A test that read source text instead of behaviour

`test_finished_and_suspended_are_not_the_same_shape` asserted
`"report.state = FINISHED" in inspect.getsource(engine.walk)`. This change rewrote that line to
`STOPPED if node.permanent else FINISHED` — the behaviour it cares about is intact, `done` still
reports `FINISHED`, and the assertion failed anyway. It was matching **vocabulary** for a claim
about **behaviour**. Replaced with a run that reaches `done` and checks the state it reports.

## Risk & rollback

The compatibility path is a **branch**, not a special case inside the new nodes, so "did this run go
the old way" is answerable from `visited` rather than by reading code. Reverting is deleting four
nodes and restoring `pm_plan.next`; nothing outside the planning prefix changed except the halt
state, which reverts with `Node.permanent`.

The `permanent` change is the part with reach beyond this feature: any caller reading `state` to
mean "did it end" now sees `stopped` where it saw `finished` for a second module failure. That is
the correct answer to the question they were asking, and it is the reason this is graded high.
