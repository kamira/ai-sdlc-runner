## Read this first

`settings.py` is the answer to the operator's 「在 GUI 上設定」. Measured, the GUI reaches **two of
its three fields**, and the edit that would fix that silently inverts save and discard.

### The screen is the only place in the runner that keys by position

`tui.select` returns a bare index. Everywhere else this repository maps a name to an effect by
name - `policy.GATES`, `policy.BY_SEAT`, `policy.BY_ROLE`, `graph.BY_ID`, `settings.FIELDS`.
`edit()` compares that index to the literals `2` and `3` while the labels live in a list literal,
and `_edit_seats` builds `options` and `values` as two parallel lists with `extra <= len(SEATS)`
written twice.

So the natural next edit - adding the missing `ordinary_commands` row in the obvious place -
produces this, with the suite green:

```
operator types 3  ->  "3. Vouched commands - none"        edit() SAVES and closes
operator types 4  ->  "4. Save and close - write the ..." edit() DISCARDS
```

**Nothing in the repository asserts what label sits at any index.** Swapping the `Save and close`
and `Discard` rows leaves 2145 passing. So does making every below-floor option silently yield the
floor. The screen's eight tests drive the numbered fallback with strings and assert on the returned
`Settings`; they pin index to effect and never label to effect.

That is why this record fixes the keying **before** it adds the row.

### And the file may hold values the screen cannot open on

```
{"review_seats": 5}   load()                  accepted   - the bound is `>= 1`, with no ceiling
                      seats()                 PolicyError: 5 seats requested but this runner defines 4
                      runner settings --show  uncaught traceback, exit 1
                      runner settings         crashes in describe() before the menu renders
```

`cmd_settings` catches `SettingsError` only. The command whose stated purpose is that a bypass is
visible *"whether or not anybody is there to look at a prompt"* is the one that tracebacks, and the
screen that would repair the file will not open on it.

`save()` has no validation at all - every check in the module is on the read side - so the GUI can
write three shapes `load` then refuses: `review_seats=0`, a multi-word vouch, and a vouch on the
executor list. Recovery is hand-editing JSON.

And a vouch is stored unstripped while it is validated stripped: `{"ordinary_commands": ["  npm  "]}`
loads, `describe()` lists it, and `recognise("npm ci", ("  npm  ",))` is `unrecognised`. It fails
closed, and it is exactly what `FIELDS`' own comment warns of - *"a setting nobody reads looks
identical to a setting that works"*, produced by the module's own validator.

## The four properties this record adds, none of them about text

The idiom seat named the shape three withdrawn records failed to have. Each of these is derived
from `FIELDS` or `policy.SEATS`, and each is **red at this sha**:

```
every name in settings.FIELDS is reachable from edit()
    reachable ['high_risk_mode', 'review_seats']    unreachable ['ordinary_commands']
every value load() accepts, describe() can render
    review_seats 5, 6, 7, 8 -> PolicyError escapes cmd_settings
every option tui.select renders, the value it yields matches its own label
    nothing in the repository asserts this
every shape save() writes, load() accepts
    three counterexamples, all reachable from the screen
```

A rewrite cannot satisfy any of them by rewording.

## Risk & rollback

- `edit()`'s return contract is unchanged; what changes is how a choice is resolved to an effect.
- `load` refusing `review_seats > len(SEATS)` turns a display-time crash into a load-time refusal.
  A file that was accepted and then crashed is now refused with a sentence.
- `save` validating means a caller that built an invalid `Settings` fails at the write rather than
  at the next read. Nothing in the runner does that today.
- Rollback: revert. The screen goes back to two of three fields and to keying by position.
