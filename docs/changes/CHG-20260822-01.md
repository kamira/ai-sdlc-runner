## Motivation

The ai-sdlc entry handshake's step 0 is `toolchain_probe.sh`. It is three-state and **default-deny**:
`PASS`(0) / `BLOCKED`(3) / `NOT_RUN`(4). On this repo it returns **`NOT_RUN`(4)**, every session:

```
直譯器:python3 (3.11.9)
  - requirements-dev.txt 不存在——判不出該裝什麼。這不是「沒有相依」,是沒有查成
TOOLCHAIN: NOT_RUN
```

The environment is in fact fine — python 3.11.9, pytest 9.1.1, PyYAML 6.0.3 all present and
verified by hand. The probe simply cannot see them: it reads dev dependencies from
`requirements-dev.txt` and nothing else, while this repo declares them in `pyproject.toml`'s
`[project.optional-dependencies]` (`yaml = ["PyYAML>=6.0"]`, `test = ["pytest>=7.0"]`) because the
runner is deliberately zero-runtime-dependency.

The cost is not cosmetic. `NOT_RUN` means *the check did not run* — the handshake protocol says stop
and provision. So every session either halts on a false negative or is waved through by hand, and
waving it through by hand is exactly the KN-005 pattern (rules maintained by human memory get
repeatedly violated) that the probe was built to eliminate. A gate that must be manually overridden
every single time is a gate that will eventually be overridden on the one occasion it was right.

**Why the fix cannot be probe-side.** The correct long-term fix is for the probe to read
`[project.optional-dependencies]`. That fix belongs to the `ai-skills` repo, which is not reachable
from here: the `ai-skills/` submodule was never wired and the directory is absent, and the vendored
offline store tops out at `skills/v1.16.0`, which **predates the probe entirely** (no
`toolchain_probe.sh` is vendored anywhere in this tree). KN-1 forbids editing the vendored store in
any case — it is a verbatim `git archive`. So the only surface this repo controls is its own root.

## Empirical finding that drives the file's content

The probe's parser was tested directly against four candidate files before choosing one. This
matters because the obvious content — copy the pyproject extras verbatim — **does not work**:

| `requirements-dev.txt` content | Probe result | Why |
|---|---|---|
| `-e .[yaml,test]` | `NOT_RUN` (4) | matches the `-*` (and `*\[*`) unparsable pattern |
| `PyYAML>=6.0` / `pytest>=7.0` | `NOT_RUN` (4) | range specifiers fall to the `*)` branch — "existence verified only, range not compared" — and any unparsed line forces `NOT_RUN` |
| `pytest==7.0.0` (env has 9.1.1) | `BLOCKED` (3) | exact pin, mismatch correctly detected |
| `PyYAML` / `pytest` | **`PASS` (0)** | bare distribution names are the only fully-parsable form |

So the only two forms that can reach `PASS` are bare names and exactly-matching `==` pins. `==` pins
are rejected: this is a machine whose image is rebuilt every session and a CI matrix spanning
py3.9/3.13, so a pin would flip to `BLOCKED` on the next routine version bump — a false negative
replacing a false negative.

## Decisions & trade-offs

| Decision | Options | Assumptions | Why this choice |
|----------|---------|-------------|-----------------|
| Where to fix | probe-side (read pyproject) vs repo-side (`requirements-dev.txt`) vs do nothing + manual override each session | the skill repo is unreachable from here (submodule absent, vendored store predates the probe, KN-1 forbids editing it) | **Repo-side.** The probe-side fix is the better fix and cannot land on any known timeline from this tree; "do nothing" institutionalises a manual override per session, which is the failure mode the probe exists to prevent. Reporting the probe gap upstream stays worth doing and is independent of this change |
| File content | copy pyproject extras verbatim (`PyYAML>=6.0`) vs `-e .[yaml,test]` vs bare names vs `==` pins | measured, not assumed — see the table above | **Bare names.** The first two measurably return `NOT_RUN`, i.e. they would leave the gate exactly as broken while *looking* fixed. `==` pins would false-`BLOCK` on every environment upgrade |
| Drift control | hand-maintained second list vs generated + verified by test | this repo's knowledge base repeatedly flags hand-copied duplicates as a defect family | **Test-verified derivation.** Two files now state the dev dependencies; the test makes disagreement a CI failure rather than a silent divergence. `pyproject.toml` stays the single authority for *versions* |
| Parser for the test | `tomllib` vs regex/string scan | CI's floor cell is py3.9; `tomllib` arrived in 3.11 | **String scan of the `[project.optional-dependencies]` block.** A `tomllib` import would make the test silently skip or error on the 3.9 cells — half the matrix |
| Honesty about what is lost | claim the probe now validates versions vs state plainly that it validates presence only | bare names carry no floor | **State it plainly**, in the file header and in the ACC. The probe now answers "are the dev dependencies installed"; `>=6.0`/`>=7.0` remain enforced by pip at install time, not by the probe |

Confirm gate: low risk, additive, no `src/`, fully reversible → auto per the halt policy. PR merge

## Modification Guide

### Goal

`bash <skill>/scripts/toolchain_probe.sh` run against this repo's root returns **`PASS` (exit 0)**,
and a test fails if `requirements-dev.txt` ever stops matching the distribution names declared in
`pyproject.toml`'s `yaml` + `test` extras.

### Global constraints (all tasks)

- **Do not touch `src/`.** No runner behaviour changes.
- **Do not touch `skills/`.** The vendored store is a verbatim archive (KN-1).
- Do not alter `pyproject.toml`'s dependency declarations — it remains the version authority. (Its
  content may be *read* by the new test; it is not edited.)
- The new test must be **stdlib-only and run on py3.9** — no `tomllib`, no new dependency. A test
  that skips on half the CI matrix is not a drift guard.
- Do not weaken or alter any existing test.
- Verification bar: probe returns `PASS`/exit 0; whole suite green locally **and** all 5 CI jobs
  green; `doc_integrity_check.py --repo .` exit 0.

### Tasks

TDD note: the red state is demonstrable before any file is written — the probe returns exit 4 today,
and the sync test fails with `requirements-dev.txt` absent. Green is exit 0 plus the test passing;
red returns if either file's dependency names are edited without the other.

| # | Task | Interface / output | Done-when |
|---|------|--------------------|-----------|
| 1 | Add `requirements-dev.txt` at repo root | bare distribution names `PyYAML`, `pytest`, with a header comment stating it is derived, why names carry no version ranges, and which test guards it | file exists; probe returns `TOOLCHAIN: PASS`, exit 0 |
| 2 | Add the drift guard | `tests/test_requirements_dev_sync.py` — extracts distribution names from `[project.optional-dependencies]` (`yaml`, `test`) by string scan, asserts set-equality with the non-comment lines of `requirements-dev.txt` | test passes; mutating either file's names makes it fail |

### Risk & rollback

- Risk: low. No runner code path changes; the added file is metadata read only by the probe and the
  new test. The named failure mode is the two dependency lists drifting apart — which is precisely

- Rollback: `git revert` the commit. The probe returns to `NOT_RUN`; nothing else affected.
