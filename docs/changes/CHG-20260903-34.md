## L-47 — the rung guard tested which ledger the answer arrived in, not what it names

CHG-20260903-27's ruling was right: *a blanket `--confirm` cannot open `halt_independent`; a person
answering the stop they were shown can.* It was implemented on the **counter** path only, reasoning
that an `Approval` object **is** the person-at-the-stop path.

It is not. `node_id` is optional, `server.approve` passes whatever the client sent, and
`Approval(gate="acceptance")` naming no node is exactly what -27's own text calls blanket —
*"naming no node, for a stop nobody has seen yet."* Measured:

```
                               halted_at    rung opened
nothing extra                  qa_accept    no      <- correct
targeted, names the node       done         yes     <- intended
BLANKET, names no node         done         YES     <- defeats the guard
```

And the report then contradicted itself two adjacent lines apart, **with the reassuring line being
the false one**:

```
acceptance = halt_independent at risk high at qa_accept, decided by the operator (acceptance)
acceptance was confirmed 1 time(s) and none was spent: the run stopped there and a
  confirmation does not open that rung
```

**Reachable through the shipped HTTP surface.** `_require_suspension` checks *that* the run is
waiting, never *which* gate it waits at, and `state.approvals` is append-only with no removal route.
So a client can `POST /run/gate {"gate": "acceptance"}` while the run is suspended at
`plan_confirmed`; the operator then answers only the seven stops the console shows them; and the
pre-authorisation opens `halt_independent` at `qa_accept`, a stop they are never shown.

This falsifies `README.md`'s Known gaps verbatim — *"`halt_independent` does not check independence
… **but it always stops for a person**"* — and it is the half of that sentence that made the gap
survivable.

**Two fixes, one on each side of the door:**

- `_gate` tests what the answer **names**, not which ledger holds it: `if independent and
  approval.node_id is None: continue`.
- `server.approve` refuses a gate or node that is not the one being waited at, and stamps
  `node_id` and `run_id` from the suspension — which is what `Approval`'s own docstring says those
  fields are for: *"what make refusing a stale or misdirected answer possible"*, and `None` is
  *"the wrong one for an answer typed into a console after a stop."*

## L-48 / L-54 — I reported this as not reproducing, from two of six paths

`CHG-20260903-29` and `ACC-20260903-29` both say the stale-error defect *"does not reproduce"* and
*"no fix is shipped for it."* The measurement behind that tested `start()` (rebuilds the state) and
`approve()` (guards on `_require_suspension`). `_advance()` has **six** call sites; **`instruct` and
`attach` guard on neither**, and `instruct` explicitly lists `STOPPED` as an acceptable state.

```
1 the walk failed          state=stopped    error='RuntimeError: the disk went away'
2 operator adds to brief   state=finished   error='RuntimeError: the disk went away'
```

A person whose run failed adds a line to the brief; the walk succeeds; the console shows the old
error box on a finished run — **and it shows it because CHG-20260903-29, the same record that
reported the defect as absent, is what made the field reach the page.**

**The method lesson, which is the part worth keeping: a negative finding needs a stronger
measurement than a positive one.** A positive finding is proved by one reproduction. A negative one
is only ever as good as the paths enumerated, and I enumerated a third of them.

This also discharges `ACC-20260903-23`'s reservation, which deferred **both** halves of L-27 to a
task in a record that was later withdrawn. The conformance seat raised the orphan in two consecutive
rounds. First half: CHG-20260903-29. Second half: here.

## Risk & rollback

- **Task 4 is a tightening on a live HTTP route.** A client that today approves a gate the run is not
  waiting at gets a `409` instead of a queued approval. Any console doing that was relying on the
  defect — but it is a behaviour change on a shipped surface and belongs first.
- **Task 6 clears a field an operator might want kept.** A run that failed, was re-driven and
  finished has *had* a failure. The answer taken is that `state` already carries that, and a field
  documented as *"the run failed"* must not be true of a run that did not. An audit trail of past
  failures is a different field and this record does not add one.
- **Task 8's rule is still a two-phrase list**, now correctly scoped. A third wording of the same
  claim still slips past it, and the record says so rather than calling it a rule that cannot be
  evaded.
- **Task 10 strikes a tick in a merged record rather than re-opening the change.** The work is real
  and unbuilt; naming it here is the smaller lie than leaving the tick. A later record should carry
  it properly.
- Rollback: revert. The rung opens to a blanket approval again, a finished run flies the previous
  failure's banner again, and the independence rule is switched off again in nine files.
