## Two tables

```sql
CREATE TABLE node_assignments (
  node_id  TEXT NOT NULL,
  ordinal  INTEGER NOT NULL,
  model_id TEXT NOT NULL REFERENCES models(id),
  PRIMARY KEY (node_id, ordinal));

CREATE TABLE seat_assignments (
  seat     TEXT PRIMARY KEY,
  model_id TEXT NOT NULL REFERENCES models(id));
```

**`ordinal`, not a set.** The order of a node's list is load-bearing: a pool's seeded choice and a
model panel's ask ids both read it positionally, so a set would lose something real.

**One model per seat.** A seat is one voice; a list would be a panel inside a panel.

## Two routes

`POST /config/nodes` and `POST /config/seats`. Both take the run `version` like every other POST,
both return the **resolved** assignment with a `source` map. An empty `models` list clears a node —
this API has no `DELETE`, and adding one for a single case would be a second way to say a thing that
already has one.

### Four refusals, each verified by driving the real server

| Refused | Because |
|---|---|
| a node the flow does not have | — |
| a node whose **mode ignores a model list** — `runner`, `follows`, `seat_panel`, `survey` | *a setting that looks configured and does nothing is worse than one that was rejected* |
| a model the registry does not have | a foreign key, refused **by name**: "assigned a model the project does not have" must not read like "assigned nothing" |
| a seat this runner does not define | checked against **every** seat, not only the ones today's floor opens — a standing assignment must survive a run that opens more |

## Precedence: the plan wins, and it is never silent

The plan file is this change's declaration; the store is the project's standing assignment. **The
plan wins where it says something; the store fills where the plan is silent** — `settings.py`'s rule
one layer out, for the same reason: a per-change declaration must not be silently overridden by
something configured weeks ago.

`resolve()` returns a **`source`** map beside the merged result. A merged dict alone cannot say which
of the two put an assignment there, and an override nobody can see is worse than no override.

Clearing a node the plan speaks for therefore changes nothing visible: the store row goes, the plan's
assignment stands, and `source` still says `"plan"`. Tested, because that is surprising unless shown.

## What driving it found that no unit test did

**`ThreadingHTTPServer` handles every request in its own thread, and a SQLite connection cannot cross
threads.**

```
unknown node  -> 409 no node 'nope' in this flow
mode ignores  -> 409 node 'record_module' is mode 'runner', ...
unknown model -> 500 ProgrammingError: SQLite objects created in a thread can onl...
```

Every refusal that fires **before** touching the database returned `409` correctly. Everything that
reached SQLite returned `500`. A test exercising the store directly passes on both.

Fixed with `check_same_thread=False` and a lock **on a `Connection` subclass** — the C type takes no
arbitrary attributes, which the first attempt found by raising `AttributeError`. A lock rather than a
connection per thread, because the design already declares **one writer**: serialising is the honest
implementation of a rule that is already stated, where a pool would quietly permit what the design
says is unsupported.

### And a second one, from the same drive

After a restart the assignment persisted and the model list came back **`[]`**. `make_handler` never
read the registry back out of the store — so the console showed no models while the assignments
referenced them by id. That is precisely the "assignable and invisible" split this module's own
comment on `POST /models` warns about, arriving from the other direction.

### And my own test script was lying to me

It printed `"added"` regardless of the status code, so the first failing run reported a success. A
check that does not look at what it is checking is the defect this whole repository is about, and it
was in the script I was using to find defects.

## The pinning tests did their job

Three failed the moment the API changed, and all three were right to:

- `test_every_route_the_server_answers_is_on_the_page` — `/config/seats` was not documented
- `test_the_route_count_the_page_states_is_the_real_one` — fifteen routes became seventeen
- `test_the_registry_persists_and_the_assignment_does_not` — **written to say a writer appearing
  would fail it and one of the three must change.** A writer appeared. It is now inverted.

One test was **too weak** and passed on a false page: it asserted `DATABASE.md` said *"proposed, not
built"* and that no file in `src/` had `sqlite` in its **name**. `store.py` does not, so it passed
while the page claimed nothing was built and three tables were. It now compares the page against the
tables the code actually creates.

## Risk & rollback

- The store is created on `serve`; a run that never edits an assignment behaves as before.
- An existing `models.json` is **imported once and left on disk**. Nothing is deleted.
- Rollback: revert. The store file can be deleted; the plan file still carries whatever it carried.

## Status

**Under review.** Nobody independent has read this, and it is the first change in this sequence with

### Not claimed

**That two runners on one store are safe.** The lock serialises threads in one process;
`busy_timeout` is what stands between two processes, and no two-process test exists.
`docs/DATABASE.md` has said one writer since it was written.

**That an `api` model can be assigned usefully.** It can be assigned, and dispatching to one still
raises — see `MODELS.md`. Assigning one now fails later rather than never.

**That the conversation tables work.** They are still created by no code.
