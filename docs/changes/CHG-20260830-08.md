## The one that matters: I turned a loud failure into a silent one

CHG-20260830-07 fixed a real defect — the in-flight guard was blinding the mutation harness — by
excusing the guard when the record's owner was still **alive**. That coupled the guard to `_alive`,
and it was wrong in both directions:

```
a genuinely stranded tree: src/ file mutated, record owner = pid 4 (alive, not openable)
  before this change:  18 passed, 1 skipped   rc=0     <- green over a mutated tree
  git status        :  nothing (the record is gitignored)
  --recover         :  REFUSING …             rc=1
```

That is the *quiet* failure `mutation_recovery.py`'s own docstring exists to describe, with the
detector switched off — and CHG-20260830-07 widened it, because making a denied `OpenProcess` read
as alive is what makes `_alive(4)` true. Its Risk section said *"A record whose owner is gone still
fails it, which is the incident it was built for."* Measured: it did not.

The other direction, from the defect seat: two of the eleven `stranded` mutations break `_alive`, so
the owner read dead, so the guard **failed** rather than skipping — and `_pytest` runs with `-x`, so
the run stopped there and the tests written for `_alive` never executed. `--only stranded 11/11, all
CAUGHT for the right test` was true of 9 of 11.

### Announcing beats inferring

`mutation_check._pytest` now sets `MUTATION_RUN` in the child's environment, and nothing else sets
it. A run in progress says so; everything else is a leftover and fails. There is no inference left
to get wrong, and no coupling to `_alive` at all.

```
a genuinely stranded tree, same fixture:   1 failed, rc=1   test_this_repository_has_no_mutation_in_flight
_alive broken, harness running:            1 failed         test_a_live_process_reads_as_alive_and_a_dead_one_as_dead
no SYNCHRONIZE, harness running:           1 failed         test_a_live_process_reads_as_alive_and_a_dead_one_as_dead
```

And the branch has a test now. Nothing drove it before: CHG-20260830-07 changed the condition that
decides whether this repository's stranded-tree detector is armed, and recorded the change as
verified, with no test on the branch either way.

## `_alive` is two functions

`except PermissionError: return True` — the POSIX half of the denied-is-alive rule, cited twice as
the already-correct precedent the Windows half should have followed — was **executed by no test on
any platform**. Reaching it meant standing in for `os.name`, and `mutation_recovery.os` *is* the
`os` module, so that patches it for the whole process: measured, `pathlib` then raises
`NotImplementedError: cannot instantiate 'PosixPath' on your system` from a test about something
else entirely.

So the branches are `_alive_posix` and `_alive_nt`, each callable and each with a registry entry.
The Windows one also moves to `ctypes.WinDLL(use_last_error=True)` + `ctypes.get_last_error()`:
`kernel32.GetLastError()` is a second foreign call, and any ctypes work between the two — including
resolving `GetLastError` itself the first time through — can overwrite the code before it is read.
Reading it wrong reads a denied live process as dead, silently.

## The advice in a refusal was unsafe

The live-owner refusal offered `git checkout -- <path>` as a way back. It restores from the
**index**, so a mutation that had been staged — and the CHG-20260828-18 incident is literally *"the
next commit would have shipped it"* — gets written back, after which the message told the operator
to delete the record that proves it. The refusal now names the record as the only copy and says
explicitly not to use `git checkout --`.

`--recover` was also unreachable: `main()` raised `SystemExit(1)` on a REFUSING string *before* it
reached `if args.recover`, so the documented way out could not be taken. Ordered correctly now.

## The line endings, at the third time of asking

`write()` forced `newline="\n"`, so on a `core.autocrlf=true` checkout every file the harness
touched came back LF and `git status` reported it modified with an empty `git diff`. Content was
never at risk. What was at risk is that `git status` is what four separate refusals in this module
tell an operator to read.

It now preserves the newline the file already has. Measured: `git status` is completely clean after
a full `--only stranded` run, which it has not been for three rounds.

## A verdict the model cannot express

`policy.SEATS` gives conformance `veto=True`, and `adjudicate` computes
`[s for s, v in verdicts.items() if BY_SEAT[s].veto and v != "pass"]` — so **any** non-pass from that
seat is a veto. The round-4 seat returned `fail` and wrote *"No veto"*, with a reason: the three
prior vetoes were about permanent records losing what happened, and this change restores the deleted
section verbatim and marks its corrections, so *"nothing here is unrecoverable by a reader"*.

The outcome is `fail` either way. What is wrong is the **reason** recorded: it says veto where the
seat said not-a-veto, which is a record stating something untrue — this repository's recurring
defect class, in the governance code. Not changed here: what "veto" means is a design decision about
the tool, not a correction, and it goes to the seats.

## Risk & rollback

- No `src/` change. `tools/mutation_recovery.py`, `tools/mutation_check.py`,
  `tools/ledger_check.py`, two test files, `.gitignore`, `README.md`, and six records.
- The guard is **stricter** than before: any record present without `MUTATION_RUN` fails the suite.
  That is the point, and it is the state a killed run leaves.
- `_alive` is split. Both halves keep their answers; the registry has an entry per half.
- Rollback: revert. The detector goes quiet again on a reused pid, and `--recover` becomes
  unreachable from the refusal that names it.
