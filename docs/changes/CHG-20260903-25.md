## Read this first: the marginal reach is zero cells

```
cells a project may pre-authorise standingly : 1     plan_confirmed @ medium
cells already reachable on `main` by a class : 5     including that one
marginal reach over `main`                   : 0
```

Every `confirm` cell is already lowerable today by a `standard` or `emergency` class. So the whole
delta is **who** may pre-authorise and **for how long** — a project setting rather than a signed,
dated, self-expiring declaration. That is the thing to accept or refuse.

**The strongest sentence available for this design, which draft five did not make:** the mechanism
is not merely equivalent to the class route — it is **strictly narrower**. A project-level default
change class, the obvious cheaper alternative, would lower all five `confirm` cells including
`merge@low` and `pr@high`. The derived predicate lowers one. The contribution is not new reach; it
is *a narrower pre-authorisation than the one already shipped*.

**And 「merge 永遠留一個人」 is already false on `main`.** Measured: `risk: low` plus a signed
`standard` class makes `merge` `auto`, and `_permanent_halt` passes because the shipped example plans
declare merge `{"kind": "ordinary"}`. This design cannot reach `merge`, which is not the same as
securing it. **That requirement needs its own change**, and it is not this one.

## The exemptions are derived. There are none to list.

```
confirm ∧ ¬grades_risk ∧ ¬settles_risk ∧ rejects_to is not None
```

| cell | excluded by |
|---|---|
| `feasibility_confirmed` @ medium | `grades_risk` |
| `before_dispatch` @ medium | `settles_risk` |
| `pr` @ high · `merge` @ low | `rejects_to is None` |
| **`plan_confirmed` @ medium** | **nothing — this is the one cell** |

`rejects_to is None` selects exactly `{pr, merge}` among the ten gated nodes.

**And the idiom seat, who proposed that predicate, has since retracted it.** Its retraction is on
the record and this design has to answer it:

> Three different node properties select `{pr, merge}` — `rejects_to is None`, `gate_when ==
> "before"`, and `mode == "single"`. A predicate with two rivals that agree on every cell is not
> derivation; it is a list of two written in a different font. And the entailment does not hold: the
> outcome a person keeps at those gates is **withholding**, which is available at *every* gate.

The seat's counter-proposal is `gate_when == "before"`, on the ground that *a gate consulted before
its own step guards an act that has not happened, and there is nothing yet to have an opinion
about* — which also derives [CHG-20260903-24](CHG-20260903-24.md)'s task 10 for free, so the
exemption and the pre-answer's scope stop being two arguments.

**This record does not choose.** It states both and hands the seats a decision, because the
difference is invisible today and load-bearing tomorrow: whoever adds a `merge_declined` node — a
strictly *pro*-operator edit, giving refusals somewhere to go — silently makes `merge@low`
pre-authorisable under one reading and not the other.

## The reach is pinned, because a predicate's reach is not structural

The predicate is structural; **the set it selects is a property of `GATES` and `graph.NODES`, which
are data.** And it fails in the direction nobody watches. Measured:

```
auto -> confirm  (a TIGHTENING)  silently adds a lowerable cell at  13 cells
halt -> confirm  (a LOOSENING)   at                                  4 cells
```

Draft five said *"editing a cell from `halt` to `confirm` — a **tightening**"*. That is backwards
against `policy.verdict`'s own rank order — `auto < confirm < {halt, halt_independent}` — which this
session shipped in CHG-20260902-19. The hazard is real and **three times larger** than stated, and it
is the smaller, mislabelled class that got named.

So the **derived set** is pinned by value — not `GATES` alone, because the predicate reads node
attributes too, and a graph edit widens it identically.

## Where it lives, and the ruling that is against it

Draft five moved the mechanism from `policy.verdict` into `engine._gate`, as a standing confirmation
in `--confirm`'s vocabulary. The reasoning was right about `verdict`: a lowering there returns `auto`,
so `_gate` exits at its first line and writes **no** `report.confirmations`, **no**
`conversation.decision` — erasing the record its own measurement task depends on.

**But three seats then found the `_gate` placement is also wrong, and each found a different reason:**

1. **`Approval`'s docstring rules against it**, thirty lines above the ledger `_gate` reads: *"**This
   is the same ledger as `confirmed`, not a second one beside it.** … two overlapping approval
   ledgers with slightly different audit semantics is the one failure here that would be
   **silent**."*
2. **`_gate`'s own invariant is that a confirmation is not standing**, and it was written about this
   exact cell: *"A confirmation is **spent, not standing** … an independent verifier found that one
   `--confirm plan_confirmed`, given to unlock a revision loop, also waved through the final approval
   on the way out."* Pinned by two tests that drive `plan_confirmed` through the `pm_confirm` →
   `pm_plan` → `pm_confirm` loop — the one loop this cell actually has.
3. **The recording path would forge a person.** `_gate` writes *"confirmed by the operator"* and
   `conversation.decision(..., who="operator")`. A project-configured, someone-else-signed standing
   clearance filed as an operator act is what `test_a_declared_class_is_exported_as_the_operators_act`
   exists to catch. *"A recorded pre-authorisation is materially safer than an unrecorded one only
   if the record is not a forgery."*

The idiom seat's own counter to its own proposal: **materialise the configuration at the door into
`cfg.confirmed` as `Approval` entries**, so `_gate` gains no branch at all, `Approval` gains
`authorised_by` and `review_by`, and there is one ledger rather than two.

## The rung was copied; the contract it belongs to was not

`relax`'s bound is one half of a pair. The other half is `policy.class_in_force`, which refuses a
class with no `authorised_by` — *"A pre-authorisation nobody signed is a relaxation on nobody's
authority"* — and no `review_by`, and expires it back to `normal` past that date.

Measured: the class route to `plan_confirmed@medium` is signed, dated and self-expiring; a project
table would be anonymous and permanent unless both are required. **That is the entire marginal risk
of this design.**

And the two must be handled differently, which no earlier draft said: **an expired row degrades to
"the gate stops"; only a malformed one refuses.** A per-change class is typed this run, so refusal is
right. A project table is ambient and long-lived — raising on the review date would brick every run
in the project, including runs by people who cannot edit the table.

Related and inherited: `conversations.emergency_runs()` derives a review queue from the `CLOSED`
turn's `change_class`. A standing pre-authorisation produces no class, so it reaches no queue. The
class it duplicates is **`standard`**, not `emergency` — `standard` is in no queue either and none is
owed; its obligation is signature and expiry. What *is* owed is the durable surface: `standard`
reaches `conversation.relaxation(..., by=class_authorised_by)`, and this must too.

## Risk & rollback

- **The marginal reach is zero cells**, and the design's contribution is that it is *narrower* than
  the mechanism already shipped. If that is not worth eleven text rewrites, thirteen tasks and two
  annotated acceptance records, **this record should be refused** — and one seat says plainly that
  it would refuse it. The number is in the first section so that decision can be made there.
- **The reachable sequence nobody has written down:** `pm_confirm.rejects_to = "pm_plan"`, so the one
  cell is re-enterable. A person rejects the plan → the model revises it → the standing
  pre-authorisation passes the revision with no person. The class route has the same shape, so this
  adds no reach — but it is the worst-reading sentence about this design and it belongs here.
- **`_permanent_halt` is unchanged and is not a defence this design provides.** It checks
  declarations, not actions.
- **`--confirm` already opens a `halt`, including the one `halt_independent` cell.** Measured: `_gate`
  has no rung check, so `relax`'s and `verdict`'s shared premise — *"`confirm` can be pre-authorised
  with `--confirm` and a halt cannot"* — is false on `main` today. **That is a defect and it is not
  this design's**; it is carried out separately, and the rank order this session shipped in
  CHG-20260902-19 rests on it.
- Rollback: revert. Every gate answers cold and the eleven texts are true again.
