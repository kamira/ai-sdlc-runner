## Read this first: the marginal reach is zero cells

```
cells a project may pre-authorise standingly : 1     plan_confirmed @ medium
cells already reachable on `main` by a class : 5     including that one
marginal reach over `main`                   : 0
```

Every `confirm` cell is already lowerable today by a `standard` or `emergency` class. The whole
delta is **who** may pre-authorise and **for how long** — a project setting rather than a signed,
dated, self-expiring declaration. That is the thing to accept or refuse.

The mechanism is not merely equivalent to the class route; it is **strictly narrower**. A
project-level default change class — the obvious cheaper alternative — lowers all five `confirm`
cells including `merge@low` and `pr@high`. The derived predicate lowers one.

**And 「merge 永遠留一個人」 is still false on `main`.** `risk: low` plus a signed `standard` class
makes `merge` `auto`, and `_permanent_halt` passes because the shipped example plans declare merge
`{"kind": "ordinary"}`. This design cannot reach `merge`, which is not the same as securing it. That
requirement needs its own change and it is not this one.

## Task 3 is decided: `gate_when == "after"`

The first draft stated both candidates and handed the decision to the seats. **Three seats reached
`gate_when` independently** — the conformance seat decided it with five pieces of evidence, the
idiom seat chose it *and retracted its own rival proposal*, and the risk seat measured the same
numbers. The exemption predicate is:

```
confirm ∧ ¬grades_risk ∧ ¬settles_risk ∧ gate_when == "after"
```

**Identical today**, so the choice is free:

```
rejects_to is not None  ->  plan_confirmed@medium
gate_when == "after"    ->  plan_confirmed@medium
```

**Strictly narrower under a `GATES` edit**, which is the design's own stated contribution:

```
cells a tightening would silently add to the pre-authorisable set
  rejects_to is not None   auto->confirm  [=============] 13
  gate_when == "after"     auto->confirm  [==========]    10
  both                     halt->confirm  [====]           4
```

The first draft pinned **13** as *the* hazard, in a section printed after it refused to choose. 13 is
the *other* predicate's number. The three-cell difference is `self_verify`'s row, which `gate_when`
excludes structurally.

**And it fails open in the safe direction, which is what decides it.** The load-bearing edit is a
*pro-operator* one — adding a `merge_declined` node so refusals have somewhere to go:

```
                          before                          after that edit
rejects_to is not None    {plan_confirmed@medium}   ->    {merge@low, plan_confirmed@medium}  WIDENS
gate_when == "after"      {plan_confirmed@medium}   ->    {plan_confirmed@medium}             HOLDS

what watches the attribute
  merge.rejects_to is None   NOTHING — no test in tests/ asserts it
  gate_when == "before"      test_a_one_way_door_is_gated_before_it_swings, by name,
                             plus FR-4 (P0, docs/ai-guideline.md)
```

`rejects_to` fails open on a **good** edit with **nothing** watching. `gate_when` fails open only on
an edit that is independently a P0 violation and turns a named test red the moment it lands.

### The retraction this record quoted was itself wrong, and the correction is on the record

The first draft quoted its proposer: *"Three different node properties select `{pr, merge}` —
`rejects_to is None`, `gate_when == "before"`, and `mode == "single"`."* Measured over the ten gated
nodes:

```
rejects_to is None     ->  {merge, pr}                        2   <- the only one that matches
gate_when == "before"  ->  {engineer_selfverify, merge, pr}   3
mode == "single"       ->  {qa_verify, merge, pr}             3
```

They agree at the **cell** level only because `engineer_selfverify` and `qa_verify` have no `confirm`
cell at any grade — a coincidence of `GATES`, not a property of the predicates. *"A list of two
written in a different font"* was itself a list of two written by only one of the three.

### The entailment into CHG-20260903-24 does not hold, and is withdrawn

The first draft said `gate_when` *"also derives CHG-20260903-24's task 10 for free, so the exemption
and the pre-answer's scope stop being two arguments."* Task 10 is about `{pr, merge}`;
`gate_when == "before"` derives **three** nodes. What makes task 10 true is that `self_verify` is
`auto` at every grade — a fact about `GATES`, nothing to do with phase. **The one sentence that
reached across the split was the wrong one**, and it claimed the two halves shared an argument.

### The entailment that does hold, and its condition

At an `after` gate the run has produced and recorded a judgement of its own before the door opens; at
a `before` gate nothing has looked but the clearance itself. A standing pre-authorisation is
defensible only where something other than the pre-authorisation looked.

**And that is conditional, which the first draft could not see because the measurement lives in
-24.** On a default install (`node_models = {}`) `pm_confirm` takes the single-ask path and produces
**no adjudication** — so at the one cell this design pre-authorises, nothing looked either. That is a
finding against this record and it belongs here, beside the zero.

## Where it lives: `policy.verdict`, and the reason it was abandoned is false

The first draft moved the mechanism from `policy.verdict` into `engine._gate`, reasoning that a
lowering in `verdict` returns `auto`, so `_gate` exits at its first line and writes **no**
`report.confirmations` and **no** `conversation.decision` — erasing the record its own measurement
task depends on.

**It erases nothing.** Measured: whenever a class changes a gated verdict, `walk` appends to
`report.relaxations_by_class`, named not counted — *"merge: merge at risk low would have been
'confirm' and passed on the 'standard' class"* — and `_finish` exports every one through
`conversation.relaxation(relaxed, by=report.class_authorised_by or None)`, whose `by=` exists
because *"an export that files a person's pre-authorisation under `runner` misattributes it in the
one dimension the document exists to record."* That path shipped four days ago as CHG-20260902-21
L-22, and it is **exactly what this record's task 9 asks for**.

And the `_gate` placement is refused by three seats for three different reasons:

1. **`Approval`'s docstring rules against it** — *"This is the same ledger as `confirmed`, not a
   second one beside it … two overlapping approval ledgers with slightly different audit semantics
   is the one failure here that would be **silent**."*
2. **`_gate`'s invariant is that a confirmation is not standing**, written about this exact cell:
   *"A confirmation is spent, not standing … one `--confirm plan_confirmed`, given to unlock a
   revision loop, also waved through the final approval on the way out."*
3. **The recording path would forge a person.** `_gate` writes *"confirmed by the operator"* and
   `conversation.decision(..., who="operator")`.

**The idiom seat's counter-proposal — materialise into `cfg.confirmed` as `Approval` entries — is
retracted by its own author, and the prototype says why.** Driven through the `pm_confirm → pm_plan
→ pm_confirm` loop the one cell actually has:

| materialised | result |
|---|---|
| **one** `Approval` | **spent on the first visit; the run suspends at the second.** The standing pre-authorisation does not stand. |
| **two** | passes — and `report.confirmations` carries the same operator approval line twice, for a person who pressed nothing, once |
| **five** | the ledger shows two; the count in the store and the count in the record differ silently |

It solves task 5 and fails task 6 outright: the `targeted` branch writes *"decided by the operator"*
and calls `conversation.decision` at its `"operator"` default. And the number of entries is
unknowable at the door, because the cell is re-enterable an unbounded number of times.

**So: `policy.verdict`'s neighbourhood**, as a **narrowing of the class route** resolved where
`_class_in_force(cfg, node, today)` already resolves per node — not a fourth mechanism beside it.
Under that placement task 5 is satisfied *vacuously* (there is no second ledger because there is no
ledger), task 6 by construction, and task 9 by code that already exists.

## The rung was copied; the contract it belongs to was not

`relax`'s bound is one half of a pair. The other half is `policy.class_in_force`, which refuses a
class with no `authorised_by` — *"A pre-authorisation nobody signed is a relaxation on nobody's
authority"* — and no `review_by`, and expires it back to `normal` past that date.

The class route to `plan_confirmed@medium` is signed, dated and self-expiring; a project table would
be anonymous and permanent unless both are required. **That is the entire marginal risk of this
design.**

And the two are handled differently: **an expired row degrades to "the gate stops"; only a malformed
one refuses.** A per-change class is typed this run, so refusal is right. A project table is ambient
and long-lived — raising on the review date would brick every run in the project. `class_in_force`
already has exactly this asymmetry; the honest sentence is *copy the contract, including the
asymmetry it already has*, not that no earlier draft said it.

## Risk & rollback

- **The marginal reach is zero cells**, and the contribution is that it is *narrower* than what
  already ships. If that is not worth ten text rewrites, sixteen tasks and two annotated acceptance
  records, **this record should be refused** — and one seat says plainly that it would refuse it.
  The number is in the first section so that decision can be made there.
- **The strongest argument against it, which its refuser makes:** *narrower than what already ships*
  argues for **replacing** the class route at this cell, not adding a second mechanism beside it.
  The one edit that changes that answer is binding `relax` by the same predicate, which would take
  the marginal reach from zero to **negative two** and make 「merge 永遠留一個人」 true on `main` for
  the first time. **That is a different record and this one does not build it.**
- **The reachable sequence nobody wrote down:** `pm_confirm.rejects_to = "pm_plan"`, so the one cell
  is re-enterable. A person rejects the plan → the model revises it → the standing pre-authorisation
  passes the revision with no person. The class route has the same shape, so this adds no reach —
  but it is the worst-reading sentence about this design and it belongs here.
- **`_permanent_halt` is unchanged and is not a defence this design provides.** It checks
  declarations, not actions.
- **The `--confirm`-opens-a-`halt` defect is now carried.** The first draft named it, scoped it out
  and said it was *"carried out separately"* — and nothing carried it for a day. It is
  **CHG-20260903-27**, shipped, along with the ruling that a blanket `--confirm` cannot open
  `halt_independent` while a person answering the stop can.
- Rollback: revert. Every gate answers cold and the ten texts are true again.
