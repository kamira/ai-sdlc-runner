## Why

CHG-20260827-21's Task 6 measured `examples/weather-spa`, four modules, with a scripted agent. It
recommended against building concurrency and named what would change that answer:

> A measurement of a **real** backend on a programme of ten or more modules.

Asked how to proceed with step two, the user chose to measure first and decide afterwards.

## What changes

1. **A new example, `examples/weather-live`, shows real data in ten modules** (the user,
   2026-10-19: 「weather spa 需要對外請求真實數據」, then 「可改寫或者成立新專案」; Open-Meteo chosen
   as the source). It covers the same content as `weather-spa`.
   - **The runner builds it; no example agent does** (the user, 2026-10-19: 「sample 是要基於runner
     去執行 不是使用該agent」). The example holds only what a person gives the runner: the brief,
     the plan, `runner.yaml` pointing at the real backend, and a README. There is no `agent.py`
     and no page code written in advance. The page is whatever the runner's real run builds.
   - **The data source is Open-Meteo** (`api.open-meteo.com`). It needs no API key, so no
     credential is stored, sent or captured. The page asks it for Taipei's current temperature and
     humidity and seven days of high, low and rain chance, the same content the page shows today.
   - **The Central Weather Administration (CWA, formerly CWB) is a second source, through its
     API only** (the user, 2026-10-19: 「CWB 如果可以只使用API 的話可以納入」).
     - It is reached only through the open-data REST API (`opendata.cwa.gov.tw/api/...`). No
       page is scraped and no file is downloaded by hand.
     - It needs an authorisation key. The key is **never committed**. The person running the page
       types it in at run time, and the page keeps it only in that browser. For the measured run
       it is held as an environment secret.
     - Without a key, the page uses Open-Meteo. With one, it uses the CWA and says which source
       the numbers came from.
     - The dataset ids for Taipei's current observation and seven-day forecast, and whether the
       API answers a browser's cross-origin request, are checked against the API's own
       documentation and a live call once the host is reachable (task 1a). If the API cannot be
       called from the page, the record says so and the CWA is left out, rather than adding a
       proxy that would hold the key.
     - The key never appears in a capture: the field is masked, URLs carrying it are not shown,
       and each capture is checked for it before commit.
   - **Where the request happens:** in the built page, in the browser, at run time. The runner and
     its agent make no request to Open-Meteo; building the page is still a local job.
   - **Ten modules**, each its own file, small enough to build one by one, so the loop really runs
     ten times. The brief names them: the page shell, styles, the source settings, the Open-Meteo
     client, the CWA client, normalising and formatting, the current conditions panel, the
     seven-day list, today's curve, and the app entry with its loading and error states. `pm_plan`
     answers with the real list, and the report records the count the run actually built, even if
     it is not ten.
   - **What a failed request shows:** a visible error state, never made-up numbers. The page shows
     no fallback data.
   - **The brief** asks for real data from Open-Meteo, or from the CWA when a key is given, where
     `weather-spa`'s says 「不要連外網」.
   - **What the built page is checked against:** after the run, the built page is loaded in
     Chromium twice: once against the real Open-Meteo, and once with its requests answered from a
     recorded Open-Meteo response (labelled as a recording, with its date) and with a failing
     response, to see the numbers match the recording and the error state show. Those checks are
     steps of the report, not CI tests, because the page is the run's output, not repository
     code. The built page is kept with the report.
   - **Network access for the run:** this session's network policy refuses `api.open-meteo.com`
     and `opendata.cwa.gov.tw` today. The user adds both under the environment's allowed domains
     before step 2, and sets `CWA_API_KEY` as an environment variable (done 2026-10-19; a new session picks it up). Until then
     every part that does not need it goes ahead, and nothing stands in for the real response.
2. **One measured run with a real backend.**
   - The backend is `claude-sonnet-5-5` at effort `medium`, the coding default (DIR-3).
   - Every node gets the same backend, so ask cost is comparable.
   - After the run, the built page is opened in Chromium against the real Open-Meteo, and the
     screenshot shows the live data with the time it was fetched.
   - The run is measured the way Task 6 was, from the conversation record's timestamped `ASK` and
     `ANSWER` turns: total wall-clock, the time inside asks, the module loop's share, and the time

3. **The result is written into CHG-20260827-21's Task 6** as an "after" section beside the existing

   the measured share), and what the measured rate limits allowed. A recommendation follows,
   **for the user to decide on**. This change does not decide step two.
4. **Tests on what the repository holds:** the example's plan and `runner.yaml` load in the runner
   and name `claude-sonnet-5-5` at `medium`; the brief names the ten modules, both sources and the
   error state; no file in the example or the report holds a key; every image the report links
   exists. CI does not run the real backend.
5. **Every command and setting is screenshotted and written into a measurement report (the user,
   2026-10-19: 「實測時 每筆指令 設定都要截圖記錄 並寫入實測報告操作流程」).**
   - **Commands.** Every command run for the measurement is captured with its output: setup,
     `runner` invocations, the backend probe, the run itself and the measurement script. Each is
     rendered as an image of the terminal (the command line, its full output and a UTC timestamp)
     and also kept as plain text, so the image can be checked against the text.
   - **Settings.** Every setting the run depends on is captured before the run starts:
     - `runner.yaml`, the plan and the settings file;
     - the model registry and its effort;
     - the console's node and seat panels.
     The files are captured as rendered images plus their text, and the console with the
     pre-installed Chromium.
   - **The runner's screen is shown while it runs** (the user, 2026-10-19: 「執行時展現畫面」,
     「使用runner執行時展示runner畫面」).
     - The measured run is driven through `runner serve` and its operator console, the way
       `weather-spa` drives it, not through a bare `runner run`. The console is what a person
       watches, so it is what is captured.
     - While the run walks, Chromium captures the console at every node change, and at least once
       a minute during a long ask. Each capture names the node on screen and its UTC time.
     - Captures are sent to the user as they are taken, so the run can be watched while it happens,
       not only read afterwards. The same images go into the report's procedure.
     - Driving the console adds the console's own requests to the run. They are not asks, and the

     - what was done and why;
     - the exact command or file;
     - its screenshot (embedded);
     - what the output showed.
     Someone else can repeat the run from the report alone. The report ends with the measured
     numbers and how each was computed from the conversation record.
   - **What is kept out.** Images and text are stored next to the report. No credential, token
     or API key appears in a capture: environment values are not printed, and each capture is
     checked for secrets before it is committed. If a capture would show one, it is redacted and
     the report says so.

## Interpreted, and what it was chosen over

- **"實測" means one real run at the size the record named (ten modules), not a benchmark suite.**
  One run gives the loop's share of wall-clock, which is what the Amdahl ceiling needs. Repeating it
  would tighten the number but multiply the cost. It is chosen over three runs, and if the result
  lands near the decision line the record will say so and offer more runs.
- **Sequential, as the runner is today.** The question is what concurrency *could* buy, so the
  sequential share is the input. Building a concurrent prototype to measure would be building step
  two.
- **One backend for every node.** Mixing models would make the per-node times incomparable.
- **A new example rather than rewriting `weather-spa`** (the user left either open). `weather-spa`
  is offline on purpose: its brief says so, its five console scenarios, the demo page, the
  documented numbers and comments in `src/` all rest on it. A new example measures the same thing
  and changes none of that. The cost is two weather examples, and the README says how they differ.
- **Open-Meteo by default, the CWA when a key is given.** Open-Meteo needs no key, so the example
  and its tests work for anyone. The CWA is official Taiwanese data but needs a key, so it is the
  optional source: kept out of the repository, typed in at run time, masked in every capture.
  It is chosen over a small server that holds the key, which would add a component the example
  does not otherwise need.

## Cost, stated before anything runs

- Each ask is one `claude -p` session. Task 6's table puts a ten-module run at about 44 asks.
- From this session's runs, a `claude-sonnet-5-5` session at effort medium on a small repository is
  roughly $0.10–$0.40 at API-equivalent prices.
- **So the run is estimated at $5–$20, and well under an hour.** On a subscription it draws on the
  same account quota the review panels use.
