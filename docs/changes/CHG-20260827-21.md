## Two steps, and the first is worth having alone

**Step one: a worktree per module.** Isolation without concurrency. Modules still build one at a
time, but each builds in its own tree, so a module cannot see or disturb another's half-finished
state. This is worth shipping by itself and it changes no ordering.

**Step two: concurrency.** Only after step one, and only if measured to be worth it.

The frontier is the hard part. Today "already recorded" means "not the frontier", which is a
sequential reading. With several modules in flight the frontier is a set, and resume has to
reconstruct which members were in flight versus done — from postconditions, per `probes.py`, never
from a receipt.

**`_frontier` now carries a second piece of state, and it is also sequential.** CHG-20260823-51 gave
it `last_word` — the engineer's most recent answer *since the current plan* — so that an engineer
saying `{"module": ""}` ends the loop without latching it shut for every later plan. With one module
in flight "the engineer's last word" is well defined. With several it is not: two builders finishing
in either order give two different last words, and one of them says there is nothing left while the
other names a module. A parallel frontier has to decide what "nothing left" means when only one of
several builders said it, and that question does not exist in the sequential reading this record was
written against.

`_frontier` also **refuses** an answer that reports no module alongside a failure. That refusal is
per-answer and survives parallelism unchanged; it is the `last_word` reduction that does not.

## Step one was not additive, and both reasons were reproduced

> Added 2026-08-28, after building it. Spike:
> `claude/chg-20260827-21-worktree-parallel-impl` (`df8dde7`), deliberately unmerged.

The claim above — *"This is worth shipping by itself and it changes no ordering"* — does not hold.
It is true that ordering does not change. What changes is **where the work ends up**, which matters
more, and neither of these was reasoned:

**1. The work is deleted, and the run reports success.** `examples/minimal`, built with a tree per
cycle, prints `worktree: 3 module ask(s) isolated`, then `state: finished`, and leaves no
`examples/minimal/greet.py`. The engineer wrote it inside the tree and the tree was removed with the
work still in it. A run that discards its own output while reporting success is worse than no
isolation at all — the failure this repository keeps naming, a green result standing in for a claim
nobody checked.

**2. Module N+1 cannot see module N.** `git worktree add HEAD` is a clean checkout of the commit,
so a second module's tree does not contain the first module's finished work. Sequential modules that
build on one another — which is the normal case, and what the module loop is for — cannot.

These are the same problem from two sides: **step one has no answer for how work leaves a tree.**
The only answer that fixes both is committing each module's work in its own tree and cutting the
next tree from that commit — which makes every module a commit. That is a substantially larger
change than this record proposes, it touches `ship.py` and what `record_module` means, and it is not
one to invent underneath a record that did not consider it.

**Step one was therefore blocked, not deferred**, and the block was a design question for a
person: *is a module a commit?* Task 1 could not be marked done by any amount of care in the code.

## The operator answered: **a module is a commit**

> 2026-08-28. That answer is the whole design, and it resolves both reproductions at once.

* a tree is cut from `Trees.tip`, which starts at `HEAD`;
* when the loop moves on, the finished module is **committed** and the tip advances;
* the next tree is cut from that commit — so module N+1 sees module N, which was the second
  failure;
* the commits are landed at the end, so the work is not deleted, which was the first.

### Source becomes commits; artifacts become files

`.gitignore` is the project saying which files are **not** repository content, and a runner that
force-added them would be overriding that on the project's behalf. So a module commits tracked
content only, and files it created that git is told to ignore are copied into the working tree —
where a build normally leaves them. `examples/minimal/greet.py` is exactly that case: in this
repository it is ignored and lands as an artifact; in a repository that tracks it, the same build
lands it as a commit. Both are tested.

### Landing: fast-forward if it is one, a branch if it is not

The operator's branch is theirs. It moves only when moving it discards nothing, and `--ff-only` is
what makes that a question git answers rather than one this code guesses at. Anything else leaves
the commits on `ai-sdlc/<plan>` and says why.

### Which modules are committed

Every module but the last is committed when the next asks for a tree — by then the loop is past
`record_module`, so it is finished by construction. The last is committed only if
`report.visited` counts a `record_module` for it. A build that halted at `halt_second_fail` must not
enter history as though it had passed, and *"the walk ended"* is a different question from *"this
module finished"*.

## Two things building it turned up

**A build cannot see uncommitted work.** A tree is cut from a commit, so an edit sitting in the
operator's working tree is invisible to it. Inherent to isolation rather than a defect — and a
surprise, so the run now says so before it starts. Found the hard way: a test edited the agent,
left it uncommitted, and the build ran the *previous* agent for thirty-nine cycles before the step
guard stopped it.

**A cycling run made thirty-nine worktrees and printed thirty-nine paths**, burying the halt message
that explained why they existed. Summarised past five now.

### What the spike established that survives the block

* **The isolation unit is the build cycle, not the module name.** The proposal assumed a name.
  `engine._frontier` says otherwise in as many words — *"the work order does not name a module, so
  the runner never tells it which one to build"* — the engineer reports the name in its **answer**,
  and a directory has to exist before the session opens. So no name exists at the moment one is
  needed, and keying on the cycle number is not a workaround but the only available identifier.
* **Cycle membership must be derived.** `graph.module_cycle()` walks from `engineer_build` to
  `record_module`; a hand-written list of five node ids would leave a node added to the loop later
  quietly outside the isolation.
* **`agent_cwd`'s offset has to be carried into the tree.** A worktree is a checkout of the
  repository *top*, and `agent_cwd` is usually deeper. Handing a command the tree's root makes the
  isolation look real and resolve nothing.

## Task 5a — what `last_word` means with several builders in flight

> Answered 2026-08-28, **before any code**, which is what this task asks for. Nothing in `src/`
> changes with this section; it is the rule step two has to implement.

### What it means today, exactly

`_frontier` computes three things from the run's record: `planned` (the latest `pm_plan` answer),
`built` (every module name an engineer has reported), and `last_word` — the engineer's most recent
`module` value **since the current plan**. It has three states: `None` (not asked under this plan,
or answered without a `module` key), `""` (nothing left to build), and a name.

`last_word` decides exactly one thing, at `engine.py:1031`:

```python
if remaining and last_word == "":
```

The loop ends **despite the plan still naming unbuilt modules**, because the engineer is the only
party who knows what is left — the work order never names a module. It is a terminator, and the
whole reason it exists is that nothing downstream verifies it: `lead_review` adjudicates verdicts,
`qa_verify` accepts any object, and no node compares the plan against the filesystem.

### Why the sequential reading does not survive, and it is not about ordering

The record already says two builders finishing in either order give two different last words. That
is true and it is the smaller half. The larger half is that **the answer means something different
when there is more than one builder**.

With one builder, that builder was asked about the whole frontier, so `""` is a statement about the
whole frontier: *there is nothing left*. With several, each was asked while others were mid-flight
and holding work it cannot see. `""` from one of them can only mean *nothing left **for me***,
which is a weaker claim and not the one the terminator is reading.

So the question is not "which builder's word wins". No builder is in a position to say the thing
`last_word` is used to conclude.

### The rule

**`last_word` stops being one value and becomes one value per builder, and the terminator becomes a
conjunction over all of them:**

> The module loop ends on the builders' word only when **every builder dispatched under the current
> plan has answered, and every one of those answers was `""`**.

Three consequences, each of which is the rule doing work:

1. **A builder still in flight blocks termination.** You cannot conclude there is nothing left while
   somebody is still building. An unanswered dispatch is not a quiet `""`; it is not an answer.
2. **One `""` among several does not end the loop, and does not latch.** A builder that says
   "nothing for me" while another is building `beta` is re-asked next round. This is the same
   property CHG-20260823-50 established for the single-builder case, and the reason `last_word` is
   reset by a new plan rather than remembered.
3. **The recorded note names which builders said it.** Today it says "the engineer reported nothing
   left". With several it must say which, or an operator reading a run that ended early cannot tell
   whether one builder was confused or all of them agreed.

### Why not the two alternatives

**Not "the most recent answer wins."** That is `last_word` read literally, and it makes the loop's
end a **race**: the same two answers arriving in a different order end the run differently. A
governance decision that depends on scheduling is one nobody can reproduce, and this runner's whole
argument is that its decisions are re-derivable from the record.

**Not "any `""` ends it."** That is the sequential rule generalised without noticing the meaning
changed. Builder A says "nothing for me", builder B is halfway through `beta`, the loop ends, and
`beta` is never recorded — the run reports success with planned work missing. It is the exact defect
CHG-20260823-50 fixed, reintroduced by concurrency.

### What survives parallelism unchanged, and why

Worth stating so step two does not re-litigate it:

* **`built` is a set union**, so it is order-independent already. Two builders reporting `alpha` and
  `beta` in either order give the same set.
* **`planned` is not concurrent.** `pm_plan` runs before the split; the latest plan still wins.
* **The `_went_wrong` refusal is per-answer.** *"No module, and also a failure"* is two claims in
  one answer, and that is a property of the answer rather than of how many are in flight.

### What this rule requires that does not exist yet

Stated here because the rule is not implementable without it:

**The record cannot tell two concurrent builds apart.** `engine.Ask` carries `node_id`, `role`,
`seat`, `result` and `model` — and nothing identifying *which* dispatch it was. Two concurrent
`engineer_build` asks are indistinguishable in `report.asks`, so "every builder has answered" is not
computable from the record as it stands. Step two must give a dispatch an identity that survives
into the record, and the cycle key from step one (`worktree.key_for`) is the obvious candidate
because it already exists and already means "one module's work".

Until that identity exists, this rule cannot be implemented and no amount of care in `_frontier`
substitutes for it.

### Not claimed

**That concurrency is worth it.** Task 6 is there because it might not be. Most of this runner's
wall-clock is one backend thinking, and running four of those at once is only a win if the machine
and the rate limits allow four.

**That worktrees isolate everything.** They isolate the tree. Two modules writing the same database,
port or cache still collide.
