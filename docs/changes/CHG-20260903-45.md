## Read this first

`class_in_force` compares `review_by < today` as text, and its own docstring calls that *"compared
as ISO strings, which sorts correctly"* — a precondition nothing enforced. Measured at
`today = 2026-09-03`, `merge@low` being `confirm`:

```
review_by                                  class in force   merge@low
  2026-12-31   a real future date            standard         auto
  2026-01-05   a real PAST date, padded      normal           confirm     <- correct
  2026-1-5     the SAME past date, unpadded  standard         auto        <- the door opens
  26-12-31     two-digit year                standard         auto
  31/12/2026   an ordinary human date        standard         auto
  whenever / asap / 2026-13-45               standard         auto
```

**The same day, written the way a person ordinarily writes it, takes the one-way door from *a
person is asked* to *it happens*** — for a review that fell due eight months ago.

## The file already refuses this harm, in the branch above

```python
if not review_by:
    raise PolicyError(
        "a change class must carry a review date. Without one it never expires, and a class "
        "that never expires outlives the assessment it was granted for.")
```

A date nobody can parse never expires either. The reason for refusing a missing date **is** the
reason for refusing an unparseable one, and the code refused one and admitted the other.

**Refused, not degraded.** Degrading a malformed date to `normal` is the quieter choice and the
wrong one: it turns a typo into a silently weaker run rather than a stopped one, and the person who
typed it never learns. Refusal matches the branch this sits under.

## One function, two readers

`check_review_date` is called where the value is **compared** (`policy.class_in_force`) and where a
person **types** it (`cli._change_class`). The CLI's own docstring already says *"a mistyped class
relaxes a gate for a whole run"* — a mistyped date did exactly that, unguarded.

Two readers rather than one because a project table would reach `class_in_force` without passing the
CLI at all — which is precisely what CHG-20260903-25 task 12 proposes, and its task 8 says the
expiry contract can be discharged by copying `class_in_force`'s asymmetry. Measured, that asymmetry
had no malformed branch to copy.

Same move as `models.COMPUTED` (-39), `_declare_classes` (-41), `asks_including_this_one` (-42) and
`_answering` (-44).

Reverting the CLI's call left every other guard green, because `policy` still refuses — the run

applying it here found the gap while the change was still open.

## Risk & rollback

- **A run that worked yesterday can now be refused at startup.** Anyone whose `--change-class`
  carried `2026-1-5` was running with a class that should have expired; they will be told, and the
  run will stop rather than proceed on it. That is the point, and it is a behaviour change at the
  command line.
- **`emergency` is affected identically.** A class typed in a hurry is the most likely to carry a
  hurried date, and the one whose relaxation is widest.
- **Nothing about expiry itself changes.** A real past date degrades exactly as before.
- Rollback: revert. `2026-1-5` opens the one-way door at low risk without asking, on an authority
  that lapsed in January.
