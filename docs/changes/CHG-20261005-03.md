# CHG-20261005-03 — the console draws the flow; clicking a node sets its models and seats

- Project: ai-sdlc-runner
- Branch: local/chg4-console (built in parallel on top of CHG-20261005-02; lands on the session
  branch after CHG-20260929-01, -20261005-01 and -02 are accepted)
- Date: 2026-10-05 (UTC+0)
- Measured against `local/chg3-seats` at `51de9b6` (CHG-20261005-02 accepted, ACC-20261005-02), after that change was accepted and this stack was rebased onto it.
- Type: feature (runner console): `console/index.html`, and server routes only if one is missing
- Proposed by: the user, 2026-09-29 (CHG 4 of the six-change plan)
- Risk: **medium**. The console is the operator's control surface, and an assignment made there
  changes which model answers a node. It is reversible: assignments are the ones `POST /config/nodes`
  and `/config/seats` already take, with the same validation.
- Autonomy: high
- Related: CHG-20261005-01 (tier, effort), CHG-20261005-02 (seats × models)

## Why

The user, verbatim:

> UI設計上可以採取流程圖，使用者點選節點後能設定審查的席位模型與可扮演角色

## What changes

1. **The flow is drawn as a chart.**
   - The `#flow` aside becomes an inline SVG flowchart, laid out in the browser from `GET /flow`.
     There are no external libraries: the console is local-only and must work offline.
   - Shapes follow the graph's kinds: step, decision, loop and terminal. Gated nodes and halts are
     marked, and edges carry their branch names.
   - It is keyboard-navigable and readable without colour.
2. **Clicking a node opens its settings.**
   - Its role, mode, gate and the role's capabilities are shown read-only.
   - For nodes whose mode can carry models (SINGLE, MODEL_PANEL, POOL), the models assigned to the
     node can be chosen from the registry, each with its tier, effort template and reach shown.
   - For the seat-panel node (`lead_review`) and the survey (`intake_review`), the user can choose
     which review dimensions open and which models sit on each seat.
   - Saving goes through the existing `POST /config/nodes`, `POST /config/seats` and settings paths.
     Every refusal the server returns is shown on screen, not swallowed.
3. **Each model shows the roles it plays.** In the `#models` list, each model shows the nodes and
   seats it answers — the roles it plays.

## Interpreted, and what it was chosen over

- **「可扮演角色」 is shown, not edited.** A node's role and that role's capabilities are governance
  (`policy.py`), and the console must not rewrite governance. So clicking a node shows its role.
  Choosing which models answer it is what decides which role each model plays, and the model list
  shows that back. Chosen over making roles editable in the UI, which would let a click change what
  a node is allowed to do.
- **No new layout engine is shipped.** A small layered layout in the page is enough for a graph of
  this size. Chosen over vendoring a graph library: the console is offline, and a vendored library
  is a supply-chain dimension finding waiting to happen.

- **One version, so a panel left open during a run is refused.** The server has a single
  `version`, advanced by every run step and every configuration edit; it has no counter of
  configuration changes alone, and adding one would change what `POST /run/*` and the stream mean.
  Round 1's behaviour is therefore kept: an editor opened at version N is refused once the version
  has moved, including by plain run progress, and the operator closes and reopens the panel.
  (Round 2 considered a configuration-only version and did not build it.)

## Rebased onto the accepted CHG-20261005-02

This change was built against CHG 3 before its three review rounds. After CHG-20261005-02 was
accepted (`51de9b6`) the branch was rebased onto it, and seven tests in `tests/test_console_flow.py`
failed. Cause: `GET /config/seats` read `Seat.enabled_by_default`, which CHG 3 round 1 renamed
`Seat.opt_in` (inverted), so the route answered 500 and every test that reads it failed. What
changed here, and why:

- `server.py` (`_seat_choices`): each seat is sent with `opt_in` instead of `enabled_by_default`,
  and the answer adds `max_seat_count` (`policy.MAX_SEAT_COUNT`, 12). `docs/API.md` says the same.
- `console/index.html`: the dimension chooser reads `opt_in`; it marks `conformance` as "veto seat,
  required unless high-risk mode is on" and an opt-in seat as "opt-in, open only when ticked"; it
  shows each seat's question as text, not only as a tooltip; and the unchosen default it offers is
  the first `floor` (or `review_seats`) seats that are not opt-in, as a count opens them. The page
  does not check the veto rule, duplicates or unknown ids itself: it shows the server's refusal.
- `POST /config/dimensions` and `/config/seats` needed no change. They already save through
  `settings.save` and `store.set_seat_model`, which now refuse a list without `conformance` outside
  high-risk mode, a model listed twice, and an unknown model id.
- No existing test expected the old contract; the seven failed only on the 500. Their expectations
  were kept. `test_the_seats_route_lists_every_seat_and_what_is_chosen` now also asserts `opt_in`,
  the single veto seat, the questions and `max_seat_count`. Eight tests were added: the veto seat
  refused without high-risk mode and allowed with it (route, plus one case in the refusals table),
  opt-in seats saved when named, duplicate and unknown seat models refused by the route, and four
  through the page: the chooser's veto and opt-in marks and questions, an untouched chooser opening
  no opt-in seat, a dropped `conformance` showing the server's words with nothing written, and a
  duplicate or unknown seat model showing the server's words. They were not cut by hand.
