## Read this first: the detector written for L-34 is wrong in both directions

`LongPathsEnabled = 0` on this machine, which is the Windows default. Reproduced, twice, at two
directory lengths:

```
store dir 252 chars                        store dir 235 chars
  add("spec.md")   -> no exception           all()          -> ['plan.md', 'spec.md']
  all()            -> []                     missing()      -> BOTH reported missing
  add("plan.md")   -> no exception           real listing   -> both present on disk
  all()            -> []
  order_paths()    -> 0
  missing()        -> []                     <- the declared detector, saying nothing is wrong
  real listing     -> both blobs + manifest.json
```

**`missing()` exists to detect exactly this**, and it is wrong at 252 (says nothing is missing while
nothing is readable) and wrong at 235 (says everything is missing while everything is there). It
iterates `all()`, so it inherits whichever lie `all()` is telling.

## The asymmetry is mechanical, and `paths.py` already has both halves

Every **write** in `attachments.py` goes through the long-path layer; every **read** is a bare
`pathlib` call, which past `MAX_PATH` reports absent rather than raising:

```
writes   paths.makedirs (116, 137) · paths.write_bytes (141) · paths.write_text (205)
reads    Path.exists()   139 · 161 · 181 · 200        <- bare
         Path.read_text() 164                          <- bare
paths.py already exports  exists()  and  read_text()   <- the functions those five want
```

Five call sites. The blast radius is not local: `server.py::Runner._walk_once` feeds `order_paths()` into
`_make_config`'s artifacts for **every** walk, so on a deep checkout every work order is briefed
with no attachments and nothing says so. And `add()` reports success while `all()` reads `[]`, so
the manifest is rebuilt from an empty list and the previous entry is destroyed.

`tests/test_attachments.py` has 39 uses of `tmp_path` (~60 chars) and **zero** long-path cases.

## L-42 — the settings file guards a field it denies exists

```
settings.FIELDS                    ('review_seats', 'high_risk_mode', 'ordinary_commands')  -> 3
settings.py:24    "Settings can lower the seat floor and can do nothing else."
settings.py:31    "one of the two settings here is a safety bypass"
settings.py:131   the same sentence again
settings.py:150   the SettingsError an operator reads on a typo: "Settings may lower the seat
                  floor and nothing else"
```

The third field is not decorative. Measured:

```
policy.unverified({kind: ordinary, targets: ['npm ci']}, ordinary_commands=())        -> ('npm ci',)  on_trust=True
policy.unverified({kind: ordinary, targets: ['npm ci']}, ordinary_commands=('npm',))  -> ()           on_trust=False
```

`engine.py:1557` refuses on that tuple, and `engine.py:1563` tells the operator to declare the
command in `ordinary_commands` to get past. So the third setting **standingly clears a refusal and
flips `on_trust`** — the opposite of "can do nothing else".

And the file knows: `policy.py:641` records that **`settings.load` refuses to accept certain
commands in `ordinary_commands`** so the operator finds out while configuring. **A guard exists for
the field whose existence the same module denies**, and the denial is the sentence printed to the
operator. `tests/test_settings.py:347` pins `FIELDS` to all three and its own docstring names the
third; nothing compares the tuple to the prose.

## L-46 — one subcommand drops a global flag, and the comment explains why

Measured through the real parser:

```
runner --settings /tmp/CUSTOM.json settings   ->  /tmp/CUSTOM.json
runner --settings /tmp/CUSTOM.json run        ->  /tmp/CUSTOM.json
runner --settings /tmp/CUSTOM.json serve      ->  config/settings.json     <- silently dropped
```

`cli.py:1588` re-declares `--settings` on the `serve` subparser with `default=settings_mod.
DEFAULT_PATH`, applied after the global. The comment above it says why the shadow exists:

> *"Not `default=None`: this flag shadows the global `--settings`, whose default exists precisely so
> nobody has to pass it. With None it reached `Path(None)` and `runner serve` — the dashboard, in
> its plainest form — died with a raw TypeError."*

**The comment is right about the problem and the fix is wrong.** `default=None` breaking `serve` is
a reason to fall back to *the global's value*, not to `DEFAULT_PATH` — falling back to the constant
is what discards what the operator typed. One defect's fix made this one.

## Risk & rollback

- **Task 1 changes behaviour on deep checkouts only.** Shallow ones read identically. What changes is
  that a store that was silently empty becomes readable — so a run that had been briefed with no
  attachments starts receiving them, which is the intent and is still a live change.
- **Task 2 may turn a green `missing()` red on an existing deep store** whose manifest was already
  destroyed by task 3's defect. That is the honest report of a loss that already happened; it is not
  caused here.
- **Task 5 rewrites sentences rather than code**, except the operator-facing `SettingsError`, which
  is a string a test may match on.
- **Task 8 is a behaviour change for `serve`.** An operator passing `--settings` to `serve` today is
  silently ignored; afterwards they are obeyed. Anyone who had been relying on the flag being
  ignored was relying on a defect.
- Rollback: revert. Attachments vanish again, the settings file miscounts itself again, and `serve`
  drops the flag again.
