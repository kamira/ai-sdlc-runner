## Motivation

The offline store topped out at `skills/v1.16.0` while the published skill is at **v1.64.0** — 48
minor versions of drift, flagged as an open item in this session's entry handshake and again in
ACC-20260822-02 Reservation #4.

It stopped being cosmetic the moment the runner was asked to become **node-driven**: driving the
skill's flow requires reading the skill's machine-readable policy, and v1.16.0 barely has any.

| | v1.16.0 | v1.64.0 |
|---|---|---|
| `assets/` | **3** (`halt_policy`, `knowledge_entry.schema`, `role_refs`) | **26** — adds `autopilot_policy.json`, `review_seats.json`, `sentinel_policy.json`, `interaction_kinds.json`, `quality_checks.json`, … |
| `references/` | 32 | 46 |
| `scripts/` | 7 | 51 |

`autopilot_policy.json` is the decisive one: it carries the six per-risk decision points
(`confirm_gate` / `task_review` / `operational_verify` / `acceptance` / `pr` / `merge`) plus
`permanent_halts`. Without it the runner has only `halt_policy.json`'s five gates to drive from.

Worth stating because it is easy to miss: **this checkout includes the probe fix landed hours earlier

pyproject-reading `toolchain_probe.sh` into this repo's store — the upstream fix that
ACC-20260822-01 listed as outstanding is now, transitively, here.

## Decisions & trade-offs

| Decision | Options | Assumptions | Why this choice |
|----------|---------|-------------|-----------------|
| Bump the store, or read the skill from elsewhere | vendor v1.64.0 / point at the sibling clone / leave at v1.16.0 | the runner is offline-first and the store is PRIMARY (KN-1) | **Vendor.** A sibling checkout is non-portable — the same objection that eliminated it as a fallback target in CHG-20260822-02. Leaving it at v1.16.0 blocks the node work |
| Keep or replace v1.16.0 | keep all versions / prune old ones | per-project locks resolve against their own version (KN-2) | **Keep.** Pruning would break every project locked at 1.0 / 1.1 / 1.12 / 1.16. Verified: all four still resolve to their own store dir after this change |
| `contract_version` default | bump to 1.64.0 / leave at 1.16.0 | it is the **first-run default only** (KN-2) | **Bump.** New projects should lock at the current published skill; existing locks are untouched by construction, and that was tested rather than assumed |
| The vestigial `skill_path` fallback | leave at `./skills/v1.16.0` / co-bump | CHG-20260822-02 predicted it "co-bumps with `contract_version` under the same CHG discipline" | **Co-bump**, in both `runner.yaml` and `cli.py`. This is the first time that prediction was put to the test; it held, and the two files stayed in lockstep |

Confirm gate: low risk, additive, no runner logic → auto per the halt policy.

## Modification Guide

### Goal

`skills/v1.64.0/` exists as a verbatim archive; `runner check` and the store resolver select it for
new projects; **every existing per-project lock resolves exactly as before**; the suite is green
against the new version.

### Global constraints (all tasks)

- **Verbatim archive only.** No edit to anything under `skills/v1.64.0/` — KN-1 makes the store a
  faithful snapshot, not a fork.
- **Do not remove or alter any existing store version.**
- No runner logic change. The only `src/` edit permitted is the vestigial fallback's version string,
  which must stay identical to `runner.yaml`'s.
- Verification bar: suite green with `AI_SDLC_SKILL_PATH=skills/v1.64.0`; all four legacy locks
  demonstrated to resolve unchanged; `doc_integrity_check.py` exit 0; probe still `PASS`.

### Risk & rollback

- Risk: low. Additive; the only behavioural surface is which version a **new** project locks at.
  The named failure mode — silently re-pointing existing projects — is exactly what task 4 tests.
- Second-order: the store grows (51 scripts vs 7). That is the price of the skill having grown;
  the alternative is not having the policy files the node work needs.
- Rollback: `git revert`. New projects lock at 1.16.0 again; existing locks were never touched.
