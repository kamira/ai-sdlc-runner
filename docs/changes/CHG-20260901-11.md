# CHG-20260901-11 — two of the flow's five panel decisions had no route at all

- Project: ai-sdlc-runner
- Branch: claude/chg-20260901-11-panel-branch-unroutable
- Date: 2026-09-01 (UTC+0)
- Type: a live defect on `main`, found while a panel prototyped a design
- Proposed by: the operator — 「先修那個缺陷 再重寫四份設計」
- Risk: **medium** — how every panel-routed decision node picks its branch
- Autonomy: high
- Related: CHG-20260901-07..10 (the designs whose review found this; none of them shipped)

## What happened

The four front-phase designs went to a four-seat panel. The defect seat built a prototype of the
proposed nodes, and the prototype died — not on the new nodes, on the **shipped** ones.

A `MODEL_PANEL` node is routed by `policy.adjudicate`, whose vocabulary is `pass` / `fail` /
`undecided`. The engine took that outcome **as the branch name**. Three of the five panel-routed
decision nodes happen to name their branches `pass` and `fail`, so they worked. Two do not:

```
pm_confirm         offers ['no', 'yes']    reachable by a panel: nothing      UNROUTABLE
pm_signoff         offers ['no', 'yes']    reachable by a panel: nothing      UNROUTABLE
lead_task_review   offers ['fail', 'pass'] reachable by a panel: pass, fail   ROUTABLE
re_review          offers ['fail', 'pass'] reachable by a panel: pass, fail   ROUTABLE
qa_accept          offers ['fail', 'pass'] reachable by a panel: pass, fail   ROUTABLE
```

Configure more than one model on `pm_confirm` or `pm_signoff` — the only configuration
`MODEL_PANEL` exists for — and the run dies at that node with `has no branch 'pass'`. `pm_confirm`
is the fifth node of every run.

Nothing said so. `graph.validate()` never compared a node's branches against what could route them,
and `tests/test_panel_and_pool.py` configured several models only on `lead_task_review`,
`engineer_build` and `qa_verify` — every one of them a `pass`/`fail` node. The two `yes`/`no` nodes
appear in that file only in a single-model answer map.

## Why the engine was right and the graph was silent

The engine's rule is correct and is kept: *"The panel's outcome is what routes. `answer_decides`
reads ONE answer, and reading one of several voices would silently make a panel into whichever model
happened to be asked first — a vote held and then ignored."*

What was missing is the translation. A panel answers in the panel's words; a node answers in its
own. `pm_confirm` asks a person-shaped question and offers `yes` and `no`, and nothing said which of
those a `pass` means.

**Declared, never inferred.** Reading `yes` as the affirmative *because the string says yes* is a
name standing in for a constraint, which is the defect `graph.py` is written against — and a node
offering `approve`/`reject` tomorrow would silently have no route again.

## The fix

1. `graph.Node` gains `panel_branches: Dict[str, str]` — which branch each panel outcome names.
2. `pm_confirm` and `pm_signoff` declare `{"pass": "yes", "fail": "no"}`. The three `pass`/`fail`
   nodes declare nothing and are unaffected.
3. `engine` routes through it: `node.panel_branches.get(panel_outcome, panel_outcome)`.
4. **`graph.validate()` refuses a `MODEL_PANEL` node whose branches `pass` and `fail` cannot
   reach**, and refuses a mapping that names a branch the node does not have.
5. `undecided` is refused in the mapping. It is not a branch, it is the absence of one, and it
   already has somewhere to go — the ruling path, where a person decides and it is recorded as
   theirs. Mapping it would let a split panel look like a decision it never reached.
6. A parametrised test configures a panel on **every** `MODEL_PANEL` node with branches, driven off
   `graph.NODES` so a node added tomorrow is covered without anybody remembering.

## What this does not do

`graph.validate()` is called by `cli.cmd_flow` and by the tests — **not by `run`**. So a graph
edited to be unroutable is caught by `runner flow` and by the suite, and a `run` still finds out at
the node. Making `run` validate is a behaviour change to every run's startup; it belongs in its own
change and is reservation 3.

The first version of the source comment here claimed validate was "a startup error". It is not, and
the claim was corrected before this shipped.

## Risk & rollback

- **`pm_confirm` and `pm_signoff` behave identically on a single-model run.** `MODEL_PANEL` with one
  model is adjudicated trivially to `pass`, which now maps to `yes` — the branch a single answer of
  `"yes"` already took. No shipped plan or example changes behaviour.
- **A cross-model run on either node now works**, where it previously ended the run. That is the fix.
- **`validate()` is stricter.** A graph edited to add a decision node routed by a panel must now say
  how the panel's words reach its branches, or name its branches in the panel's words.
- Rollback: revert. Both nodes become unroutable again and nothing reports it.
