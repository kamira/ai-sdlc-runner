## The promise that is not kept

`policy.py:87` — `Role("qa", can_write=False, note="deliberately cannot write, so it cannot fix
while verifying")`.

That note states a real safety property: the one verifying must not be able to quietly repair. But
`capabilities` goes into the work order (`workorder.py:197`) and **nothing enforces it**. The only
other readers are `cli.py:351`, which prints them as `swx` flags, and `engine.py:924` —
`return bool(role.can_write or role.can_execute)` — which classifies nodes.

The dispatched process runs in `agent_cwd` with the operator's full rights. A QA node that writes is
not stopped, and nothing notices. The same holds for `can_spawn=False` on engineers.

`grep -riE "sandbox|bwrap|seatbelt|landlock" src/` returns nothing.

> Line numbers checked against `origin/main` at `7e9c276`. CHG-20260823-51 moved them after this record was written; each is quoted by its own text as well as its line, so the next shift is visible instead of silently pointing somewhere plausible.

## Why the enforcement has to be at the OS

A harness enforces a capability by withholding a tool. This runner cannot: the work order carries no
tool names by design, and depends on no harness. That portability is what makes the flags advisory —
it is the cost of the invariant, not a bug in it.

The only enforcement that is portable, that needs no cooperation from the backend, and that does not
put a harness-specific field in the order, is the operating system. Which is what Codex already
demonstrates on four platforms.

## The grade decides the policy

Codex's sandbox policy is configured once per session by whoever starts it. This runner computes a
risk grade per change already, so the policy can be **derived**:

| risk | writable | network |
|---|---|---|
| low | workspace | yes |
| medium | workspace | no |
| high | nothing | no |

Capabilities narrow it further: a role with `can_write=False` gets no write, whatever the grade
allows.

That table is a claim and the part of this change most likely to be wrong. It is written here so a
seat can argue with the table rather than the code.

## No silent fallback

No mechanism available — Windows, or `bwrap` missing — and the run **refuses to dispatch**, naming
the platform and the flag that would override it. An operator who wants an unsandboxed run says so,
and it is recorded as an operator turn.

## Task 6's rule did not survive the platform, and the operator chose the replacement

*No mechanism ⇒ refuse to dispatch* refuses **every** dispatch on Windows, where `available()` is
always `None` — fourteen test files and the runner itself, on the platform this is developed on.
That is this repository's own named failure about the red lines: *a check that gets switched off.*

Put to the operator rather than decided here. Chosen: **enforce where the machine can, record where
it cannot, refuse only when `--sandbox` was passed and cannot be honoured.** Nothing is silent
either way; what changed is which case stops a run.

## Three tasks are built and unexercised, and the record says which

Tasks 3, 5 and 8 need a machine with `bwrap`. This one has none, so what is verified is the argv and
what is not is the denial. `test_a_denied_write_actually_fails` **skips**, naming what it did not
check, and `ACC-20260827-23` carries a table of verified-versus-not rather than a count that reads
as coverage.

### Not claimed

**That the grade→policy table is right.** It is one reading of "expensive to undo" applied to a
second axis. The first axis took several rounds to grade well.

**That a sandbox makes the work correct.** It bounds a blast radius. It says nothing about whether
the module is right, and nothing about what the process does inside the workspace — which contains
this repository, `docs/changes/` and the conversation store.

**That `can_spawn` is enforced by this.** Writes and network are. Stopping a process from starting
another process is a further restriction and is not in this change.
