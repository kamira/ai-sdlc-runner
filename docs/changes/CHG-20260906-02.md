# CHG-20260906-02 - the request body is read before anything decides whether it should be

- Project: ai-sdlc-runner
- Branch: claude/chg-20260906-02
- Date: 2026-09-06 (UTC+0)
- **Measured against `origin/main` at `caafa29`**, pinned by sha
- Type: defect fix - behaviour, in `server.py`'s request layer; one new status code in
  `docs/API.md`; a raw-socket test fixture the suite did not have
- Proposed by: **cross-review on two engines in independent sessions** - `fable` and `codex`, each
  given the measurement and not the conclusion. They agreed that all three measured behaviours are
  defects and differed on one status code and on B's root cause; both differences are recorded and
  both were settled by measurement.
- Risk: medium - every POST route goes through this code before route dispatch, and the change adds
  a deadline to every connection. The deadline is the part that could break something, and what it
  could break is the event stream.
- Autonomy: high
- Target ACC: ACC-20260906-02

## Read this first

`_body` ran before route dispatch, for every POST:

```python
length = int(self.headers.get("Content-Length") or 0)
if not length:
    return {}
try:
    return json.loads(self.rfile.read(length).decode("utf-8"))
except ValueError as exc:
    raise ServerError(f"the request body is not JSON: {exc}")
```

Three things measured against a real server on a real loopback socket, with requests hand-written so
`Content-Length` can disagree with the bytes:

```
A. an honest, very large Content-Length
   38.1 MB on the wire (attachments.MAX_BYTES is 25.0 MB)  ->  409 after 0.1s
B. a Content-Length that lies: 200 MB promised, nothing sent
   no reply within 6s; the handler thread is blocked in rfile.read
C. a Content-Length that is not a number
   500 Internal Server Error

the server itself survives:  GET /flow -> 200
```

`attachments.py` says *"A limit nobody can state is a limit nobody enforces."* The limit it states is
enforced in `Store.add`, after the whole body has been read, decoded and parsed - and only
`/attachments` has one underneath it at all. A 500 MB body aimed at `/run/instruct` was read in full.

## B's root cause is not in `_body`, and only one seat said so

The obvious reading is "bound the read". Measured, that fixes nothing about B:

```
20 bare connections that send nothing at all   ->  threads +20
after the client closes them                   ->  threads +0
a request already refused with 401, socket open->  threads +1
```

A connection that says nothing never reaches `_body`. The thread is held by the handler waiting for
a request line, and `_guard` runs and returns without releasing it. So the property is the
**connection's deadline**, not the body's bound - and closing the client socket released every one
of them, so what this bounds is *one thread per open connection*, not a leak. That downgrades the
severity the twelfth round recorded ("cumulative thread exhaustion") and it changes the fix.

## Two cases neither the original finding nor I had measured

- **`Content-Length: -1`** parses, `not -1` is False, and `rfile.read(-1)` reads to EOF - so a
  negative length was case B wearing a different hat.
- **A JSON array body** parses here and fails on the next line at `body.get(...)`, which is a 500
  for something the server understood perfectly well.

## The trap in bounding this at all

base64 is 4 bytes out for every 3 in. An attachment of exactly `attachments.MAX_BYTES` arrives as
**34,952,586 bytes** - 33.33 MB - measured, not computed from the constant:

```
MAX_BYTES         26214400   25.00 MiB
base64 of that    34952536   33.33 MiB
the JSON envelope 34952615   33.33 MiB
a wire cap set to MAX_BYTES would reject a legal maximum attachment by 8.33 MiB
```

So the wire limit is **derived** from `MAX_BYTES` rather than written down beside it. Raising one
without the other would reintroduce exactly the refusal the limit exists to prevent.

## What changes

| where | change |
|---|---|
| `server.MAX_BODY_BYTES` | `attach_mod.MAX_BYTES * 4 // 3 + 1 MiB` = 36,001,109 |
| `server.BodyTooLarge` | its own class, because it is the one refusal here that is not a 409 |
| `_body` | length validated **before** the read: not a number or negative -> 409; over the limit -> 413 with the connection closed and nothing drained; a body that arrives short -> 409; a body that is not an object -> 409 |
| `Handler.timeout` | 30 seconds, so a connection cannot hold a thread indefinitely |
| `docs/API.md` | a `413` row, and what the body limit is derived from |

## Which status code, and why the two engines disagreed

`codex` said `400` for malformed framing: `API.md`'s table calls `409` *"the request was understood
and refused"*, and a `Content-Length` of `abc` was not understood. `fable` said `409`.

Settled on evidence neither seat cited: **this server already answers 409 for a body that is not
JSON** (`test_a_body_that_is_not_json_is_refused_in_words`), which is the same class of malformed
input. It has no `400` anywhere. Splitting one existing category across two codes to gain a
distinction the page does not draw would make the page less true, not more. `413` is genuinely new
and gets a documented row.

## The new behaviour, stated

- An honest client sending a body over the limit now gets **413 with both numbers**, at once,
  instead of a 409 after the whole thing was read.
- A connection may hold a thread for **30 seconds** without saying anything. 30 because a legal
  at-limit upload was measured at 0.37s.
- Neither number is a flag. The sentence that keeps the bind address off the command line applies:
  a timeout somebody can lower is one that gets lowered until a slow disk fails a legal upload.

## What the deadline could break, and does not

`_stream` blocks on its queue, not on the socket. Measured: a stream idle for longer than the
deadline still delivers the next event. Without that check the fix would trade a parked thread for a
console that goes quiet.
