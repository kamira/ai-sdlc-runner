## 1 · The migration silently truncated, permanently

The worst finding, reached by both seats and reproduced here before anything was changed:

```
legacy conversation: 7 turns, duplicate_seqs=[2]
import RAISED: refused: turn 2 already exists…
turns imported: 3 of 7        HALF-POPULATED
second import: skipped        -> permanent
```

A legacy conversation carrying a duplicate `seq` — a state the file backend **permits and reports**
— imported partially, crashed, aborted every conversation after it, and on retry reported the stump
as *"skipped, already here"*. Silent, permanent loss of an operator's history, by the migration
whose only job is to preserve it.

`docs/DATABASE.md` §6 had required the opposite in bold, four sections above the section
CHG-41 quotes as implementing "exactly as designed":

> a conversation carrying duplicate `seq` values is **refused whole, named, and left on disk**
> be **atomic per conversation** — a failure leaves no half-populated conversation

### What it does now

1. **Reads first, decides, then writes.** `_assemble` already computed `duplicate_seqs` and
   `incomplete_lines`; both were ignored. A conversation carrying either is refused **by name**.
2. **One transaction per conversation** — a new `Backend.import_conversation`. `FileBackend`
   implements it by writing beside the target and `os.replace`-ing it into place; `SqliteBackend`
   by one transaction. A failure writes nothing.
3. **A short copy is not "already here".** Skipping is by id **and turn count**; a target holding
   fewer turns than the source is reported as an unfinished import, not passed over. That is what
   made the truncation permanent.
4. **One bad conversation no longer stops the others**, and a file with no readable header is
   reported by name rather than silently absent.
5. **Computed keys never become stored facts.** The header carried `duplicate_seqs` and
   `incomplete_lines` into the target — dropped by SQLite, and written into a *file* target as a
   permanent fake fact that `_assemble` would re-emit for ever.

`--import-from` now exits **2** when anything was refused.

## 2 · The lock that sat unused on the object it protects

`store.Connection` carries `runner_lock`, and `_locked`'s docstring says *"Every entry point takes
it"*. Every entry point in `store.py` did. **`SqliteBackend` took it nowhere.**

fable-seat ran two writers against one shared connection: **seq 150 and 333 vanished with no
`write_errors` entry at all** — an append that returned success was rolled back by the other
thread's transaction exit, breaking `_guarded`'s promise that a failed write is never silent.

The concurrency is reachable: `server._advance()` runs the walk **outside** `self._lock`, and
`attach()` gates only on version, so an attachment posted mid-walk starts a second walk over the
same `Conversation`.

Every entry point takes the lock now, and `Conversation.turn` allocates `seq` and writes it under
one lock — outside it, the number was read, incremented and used in three separate steps. A test
runs four threads and asserts contiguous, unique `seq` with no `write_errors`.

`SQLITE_BUSY` is also named now instead of escaping as a raw `OperationalError` past `_guarded`.

## 3 · The test that guarded the audit guarded nothing

CHG-40 claimed:

> the audit is run against a module that definitely bypasses (the test file itself) and asserted to
> notice — otherwise deleting a call shape from its list would retire the check while leaving it
> green.

**False.** It re-scanned the test file against its *own hardcoded tuple* and never invoked the
audit. fable-seat gutted the audit's shape list to `("write_text",)` and both tests passed. I
repeated it: same result.

Now there is **one scanner**, used by the audit and by twelve parametrised cases that feed it a
module containing one write each. Repeating the sabotage fails seven cases by name.

The shape list was also short — it missed the **builtin `open`**, the most ordinary way to write a
file in Python. Widening it first went too far the other way and matched `str.replace`,
`dataclasses.replace` and `Conversation.open`: 30 false positives, the same over-broad rule arriving
from the other side. It is now precise about what it can identify, and **says what it cannot**: a
write through a pre-bound handle, or reached dynamically, is not caught, and no test claims it is.

## 4 · A constant standing in for a queried constraint

`NAME_MAX = 255` and `measure()`'s `os.name` test conflate the OS with the **filesystem**. A macOS
machine can mount APFS, HFS+, SMB and FAT at once.

- POSIX can be asked: `name_max()` uses `pathconf(dir, "PC_NAME_MAX")` on the nearest existing
  ancestor. Windows has no `pathconf`, so 255 stands there with that scope stated.
- macOS **normalises to NFD before storing**, so a composed name measured as typed can pass and
  still be refused with `ENAMETOOLONG` — the very failure this module exists to pre-empt. Darwin now
  counts NFD bytes.
- The docstring listed **HFS+** at 255 beside ext4 as though the unit were shared. HFS+ counts
  UTF-16 units. That claim is gone, and the remaining gap — an HFS+ volume measured in NFD bytes
  over-refuses — is stated rather than hidden.

## Risk & rollback

- **The importer now refuses what it used to half-import.** An operator with a damaged store gets a
  refusal naming the conversation instead of a partial copy. That is the change.
- Every SQLite call serialises on one lock. One writer per conversation is still the design; this
  makes the second writer visible rather than destructive.
- `name_max()` calls `pathconf` on POSIX. On a filesystem reporting something other than 255 the
  limit now follows it.
- Rollback: revert. Nothing in the stored schema changes.
- 1264 collected; 1261 passed, 3 skipped.

### Not claimed

**That the server's double-walk is fixed.** It is not. `_advance()` still runs outside `_lock` and
`attach()` still gates only on version. What changed is that the resulting contention is now
serialised and visible instead of silently destructive. The gate belongs in `server.py` and is not
in this change.

**That the write audit is complete.** It catches the shapes named in `WRITE_CALLS`,
`WRITE_METHODS`, `shutil.*`, the builtin `open` and `Path(...).open`. A write through a pre-bound
handle or a dynamic name walks past it, and that is written next to the list.

**That `measure()` is right on every filesystem.** An HFS+ volume on macOS counts UTF-16 units and
is measured here in NFD bytes, which over-refuses. Closing that needs the filesystem type, which
nothing here has.
