## The one that mattered: a shipped fix that did not work

CHG-20260828-24's title was *"two messages promised to strip a path prefix and neither did"*. After
it, **they still did not.**

`str(OSError)` is `f"[Errno 2] ...: {filename!r}"` — **`repr`**, which doubles every backslash. So a
real error carries `'\\\\?\\C:\\…'`, and the four-character prefix `plain_in` looked for matches
starting at the *third* backslash. Removing it left `'\\\C:\\…'`: three backslashes and a drive
letter. Still not a path anybody can type, which is the entire failure the function exists to
remove.

Measured, not argued:

```
raw : [Errno 2] No such file or directory: '\\\\?\\C:\Users\…\x.json'
out : [Errno 2] No such file or directory: '\\\C:\Users\…\x.json'
```

`plain_in` now handles both spellings, longest first in each. And there was a **third** site with
the same defect — `conversations.py:971`, ~~three lines above~~ **139 lines above** one of the two
the change did fix. ~~The count is no longer made by hand:
test_every_recorded_os_error_goes_through_plain_in (since renamed, so not a live pointer) walks the AST for anything appended to an
operator-facing error list that interpolates an exception.~~

**WRONG on both counts, and corrected in CHG-20260830-06.** The distance is 139 lines, not three.
And the walk reached one of the three live sites: its filter was the substring `exc` in the
append's argument, so any message built into a variable first was invisible to it — including
`conversations.py:1113`, one of the two sites this change's predecessor fixed. A rule keyed on a
name, replacing a hand count, in the change about rules keyed on names.

## The panel found a concurrency failure I caused while convening it

Four agents in one worktree, one of them running `mutation_check`, which rewrites source in place.
Two seats read a half-mutated tree; one took a false positive from it and recovered by reading
committed blobs instead. Nothing was lost because the runs did not collide on one file.

~~The sentinel is now created exclusively, so it is the lock as well as the record: a second run is
refused rather than overwriting the first one's way back.~~

**WRONG — this is the round-2 veto.** Exclusive creation was necessary and not sufficient: `main()`
calls `recover()` before its first `apply()`, so the second run deleted the first one's record on
the way in and then created its own uncontended. The failure this section describes was therefore
still live after the change that claimed to close it. The record now carries the owning pid and
recovery refuses while that process is alive (CHG-20260830-06).

### Not claimed

**That the panel found everything.** It read six changes. The eight before them in this session were
not reviewed, and neither was anything older.

**That `plain_in` is the right shape.** It is a string substitution over driver text. Building the
message from `exc.filename` through `plain` would be exact rather than approximate, and would need
every call site to have the filename to hand. That was not attempted here.

**That the risk seat's other findings are closed.** It passed, and disclosed five things this change
does not touch: `reach_of` grading every single-label host `internal`, the secret scan reading only
the query string, two markdown formats now pinned by test, and the constant-time test foreclosing a
move to hashed tokens. Each is a judgement about the code as it stands, not a defect in this change.
