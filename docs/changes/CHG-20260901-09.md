## The gap, in three greps

The grade exists and is graded onto the right gate:

    "acceptance": {"low": AUTO, "medium": AUTO, "high": HALT_INDEPENDENT}

And it is consumed **nowhere**:

    $ grep -rn "HALT_INDEPENDENT" src/ai_sdlc_runner/*.py
    policy.py:50   HALT_INDEPENDENT = "halt_independent"
    policy.py:53   STOPPING = (CONFIRM, HALT, HALT_INDEPENDENT)
    policy.py:184  "acceptance": {..., "high": HALT_INDEPENDENT}

Three lines: the definition, membership of `STOPPING`, and the table entry. Nothing distinguishes it
from `HALT` at any point in the walk. The README says so plainly and has since it was written —
*"it does not currently enforce that the person differs from the builder"* ([README.md:141](../../README.md)).

So ④ is **two claims**, and only one holds. *High risk stops for a person* is true — eight gates
halt. *The person is independent* is a word in a constant name.

## Why this is not a small fix

An approval carries no identity.

```python
@dataclass
class Approval:
    gate: str
    node_id: Optional[str] = None
    run_id: Optional[str] = None
```

There is no `by`. Nothing anywhere records **who** approved a gate, so "not the same person" has
nothing to compare. `server.py` has a single operator identity, which means today there is exactly
one person and independence is not merely unenforced — it is unachievable.

That is the whole shape of this change: **identity first, then the rule**. Adding a comparison
before there is anything to compare would be a check that always passes, which is this repository's
most-repeated defect and the reason CHG-20260901-06 deleted a whole feature.

## The design, in the order it has to happen

### 1. An approval says who gave it

`Approval` gains `by: Optional[str]`. `None` keeps exactly today's meaning — an untargeted approval
from the command line — and is what every existing caller passes, the same compatibility argument
the `node_id` and `run_id` fields already make in that docstring.

### 2. The run records it

`RunReport.confirmed` is described as *"gates the operator had already confirmed, recorded so an
approval leaves a trace"*. The trace gains the identity. A resumed run must not lose it, or
independence is enforceable only within one process.

### 3. `HALT_INDEPENDENT` refuses an approval from the wrong hands

At an `acceptance` stop graded `halt_independent`, an approval whose `by` matches the `by` recorded
at `before_dispatch` is **refused, not spent** — the run stays stopped and says why.

### 4. And it refuses an *anonymous* approval

This is the half that decides whether the change is real. If `by=None` opens the gate, then every
existing caller opens it and the rule is decoration. So under `halt_independent` specifically, an
approval without an identity does not open the gate.

That is a breaking change for anyone using `--confirm acceptance` on a high-risk run, and it is the
correct breakage: that flag is exactly the thing the grade exists to prevent.

## What "the builder" means here, and why the README's phrasing needs deciding

The README says *"the person differs from the builder"*. But the builder is a **model** —
`engineer_build` is a `POOL` of models. A person and a model always differ, so read literally the
rule is trivially satisfied and the constant means nothing.

The reading that has teeth is about the **operator**: the person who approved the change on its way
in must not be the person who accepts it on its way out. `before_dispatch` is the gate where a
person authorised the work; `acceptance` is where a person signs it off. Those two should be
different people on a high-risk change.

**This is a design question for the operator, not for me to settle**, and it is the first open
question below.

## Open questions for the panel

1. **Which two acts must be independent?** `before_dispatch` vs `acceptance` is the proposal.
   Alternatives: every stopping gate on the run vs `acceptance`; or `qa_verify` vs `acceptance`,
   since QA running it and QA accepting it are the two closest together.
2. **What is an identity here?** A string an operator passes is an identity the same operator can
   type twice. Anything stronger needs authentication, which this runner does not have and should
   probably not grow. A string that is merely *recorded* is honest; a string that *enforces* is a
   check somebody can walk around, and saying which one this is matters more than which one it is.
3. **Single-operator runs.** Most runs have one person. Under this rule a high-risk change cannot be
   accepted at all by a lone operator — which may be exactly right (that is what independent
   acceptance means) or may make the grade unusable and get it downgraded in practice, which is
   worse than not having it.
4. **Does the refusal have a bypass?** Every other stop here has a way through. This one, by design,
   does not — for the person who already approved. If it needs one, the bypass is the rule.
5. **Should `halt_independent` be a grade at all, or a property of a gate?** It is graded onto one
   gate today. If independence is about *who answers*, it may belong beside `RECIPIENTS` — routing —
   rather than in the risk table.

## Risk & rollback

- **`--confirm acceptance` stops working on a high-risk run.** Deliberate: it is the mechanism the
  grade exists to prevent. It is also the loudest breakage in this change and the one most likely to
  be worked around rather than complied with.
- **A lone operator cannot accept a high-risk change.** See open question 3. This may be the feature.
- **An identity nothing authenticates is a name, not a proof.** Whatever ships must say which of the
  two it is, in the source, where the person reading the refusal will look.
- Rollback: revert. `halt_independent` goes back to being a synonym for `halt`, and the README's
  sentence goes back to being true.
