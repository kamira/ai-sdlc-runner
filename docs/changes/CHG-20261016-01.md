## What changes

1. **A seat spec.** Each seat may carry two optional texts:
   - **`role`**: the point of view to review from. For example, on `security`: "a payments-industry
     security auditor"; on `ux`: "a blind user who works only with a screen reader".
   - **`spec`**: the conditions to judge against. Inline text, or a path to a text file in the
     repository. For example, on `portability`: "target: Raspberry Pi 4, ARM64, 2 GB RAM,
     Python 3.9"; on `performance`: "at most $1 of API spend per run".
2. **Where it applies, most specific first:**
   - one model on one seat;
   - the whole seat;
   - every open seat (a shared context, such as the product's target devices).

   The more specific text replaces the less specific one; they are not merged.
3. **What the seat is asked.** The seat's question is unchanged. Below it come the role ("Review as:
   …") and the spec ("Judge against this spec: …"), clearly delimited and labelled as the user's.
   The model's instructions are not changed otherwise. The veto, the conjunction inside a seat and
   adjudication are untouched.
4. **Where it is set.**
   - Settings (`seat_specs`): written in the settings file.
   - Store: saved alongside `seat_models` (a schema bump, keyed by seat and optionally model).
   - The console's seat editor (CHG-20261005-03).
5. **Every review brief is recorded (the user, 2026-10-16: 「審查書也要進行記錄，並且要記錄spec資訊與角色」).**
   - For each (seat, model) session, the run keeps **the exact brief that was sent**: the seat's
     question plus the role and spec, byte for byte. It is written in the run's directory next to
     the journal, one file per session, with its sha256 in the journal entry.
   - The journal entry for that session also records, as fields:
     - the role text;
     - the spec's `kind`, its source (inline, or the file path inside the repository), a copy of
       its text as sent, and its sha256;
     - the level it came from (model, seat or shared).
   - The copy is taken at the moment of asking. A spec file edited later does not change what the
     record says was sent.
   - The run report lists the same per (seat, model) and links the stored brief. A seat with no
     role and no spec is listed as "no role, no spec", so an empty one is visible, not missing.
   - Resume (CHG-20261005-02's identity check) also compares the brief's sha256. A changed role or
     spec re-asks that session instead of reusing an answer given to different instructions.
   - A spec file is part of what is sent to that seat's model, so the existing `reach` disclosure
     covers it, and the report names the file.
   - Stored briefs follow the run directory's existing retention and cleanup. They hold nothing
     the seat's model was not already sent.
6. **Limits.**
   - Each text has a size cap, and a spec file must sit inside the repository.
   - A file that cannot be read stops the run before any seat is asked. It is not silently
     dropped.

## Interpreted, and what it was chosen over

- **"設備 spec" is text the reviewer judges against, not an environment the change is run in.** The
  user chose text first. A seat reads the spec and reasons about the change under it; nothing runs
  on, or emulates, that device.
- **Room left to extend, recorded here as the user asked.** The spec has a `kind` field, and only
  `text` exists now. Later kinds could hand the seat evidence from a real or emulated run instead of
  only words:
  - a CI matrix entry;
  - an emulator or container profile;
  - a remote device;
  - a measured benchmark.

  Those later kinds would attach that evidence (logs, measurements) to the seat's brief. Any of
  them is its own CHG. Each would need to say what runs, where, and what leaves the machine.
- **Replace, don't merge, across levels.** A merged role ("auditor" + "blind user") reads as
  nonsense. Replacing is predictable, and the report shows which level applied.
- **Runner only.** `tools/panel.py`'s dimensions keep their fixed questions, as the user chose.
- **No effect on verdicts.** A role or spec changes what a seat considers, never how its answer is
  counted. Chosen over letting a spec mark a seat as a veto. Vetoes stay a separate, explicit policy
  decision (CHG-20261005-02).

## Trade-offs, as agreed with the user (2026-10-16)

**Conclusion.** Build it, and recording each brief is part of the mechanism, not an option. A role
or a spec changes how a seat judges, so a verdict without the brief that produced it cannot be
explained afterwards.

**For:**
- **Reviews fit the real use.** A `security` seat as a payments auditor and as a general developer
  catch different things. A product with a known audience or setting gets reviewed in that setting.
- **Written conditions.** A spec is the same text every round, and the record says which one was
  used.
- **Several models on a seat become several viewpoints.** For example, one model reviews for
  accessibility and another for performance.
- **Nothing changes unless set.** Unset is today's question, byte for byte.
- **Room to grow.** `kind` leaves a place for real or emulated runs later, with no change of shape.
- **The record.**
  - Every verdict traces to the role, the spec and the exact brief.
  - A spec file edited later, or one carrying planted instructions, is visible by its hash.
  - A changed brief re-asks instead of reusing an old answer.
  - A stored brief can be re-sent to another model to compare.

**Against, and what this change does about each:**
- **A role can narrow a review.** A `ux` seat as a screen-reader user may stop looking at other UX.
  The role is added below the seat's question and never replaces it. The docs say a role shifts
  the seat's focus.
- **Text is reasoned about, not measured.** A model reading "2 GB RAM" can misjudge memory use. The
  report and docs say the verdict was reasoned from the spec's text, not measured on that device.
  Measuring is what a later `kind` is for.
- **A wrong or loose spec misleads with confidence.** The runner checks size and location, not
  content. The spec's correctness is the user's.
- **Prompt injection through a spec file in the repository.** The spec is labelled as the user's
  and kept apart from the seat's instructions. The record carries its hash, and a spec cannot change
  votes, vetoes or adjudication. This lowers the risk; it does not remove it.
- **Cost and egress.** A spec file is sent to the seat's model, under the existing `reach`
  disclosure, and adds to every round's cost. Each text has a size cap.
- **More to configure.** Three levels with replace-not-merge can hide which one applied. The report
  and the console show the level used per (seat, model).
- **Another schema bump.** It is forward-only; back the store up before upgrading.
- **The record's own costs.**
  - One stored brief per session grows the run directory. The size caps and the existing cleanup
    bound it.
  - The record holds a local copy of what the model was sent. If a spec is sensitive, the run
    directory needs the same care.
  - The journal, the report and resume are more to build and test.
