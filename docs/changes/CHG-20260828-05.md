# CHG-20260828-05 — Windows has no enforcement path, and that is a gap in the table rather than a fact about Windows

- Project: ai-sdlc-runner
- Branch: claude/chg-20260828-04-05-mechanism-conformance
- Date: 2026-08-28 (UTC+0)
- Type: a third entry in `MECHANISMS`, and the rule it makes affordable again
- Proposed by: a code-level comparison against microsoft/autogen, whose
  `DockerCommandLineCodeExecutor` bounds executed code through the Docker SDK — a mechanism that
  runs on the platform this runner is developed on
- Risk: **high** — it decides what a dispatched process may touch, and it reopens a rule this
  repository deliberately weakened. Both halves can be got wrong.
- Autonomy: high
- Related: CHG-20260827-23 (the refusal it weakened), CHG-20260828-04 (the suite this must pass)

## What the code says today

```
MECHANISMS = (
    ("bwrap",    "linux",  "bwrap"),
    ("seatbelt", "darwin", "sandbox-exec"),
)
```

Two entries, two platforms. `sandbox.py` then reasons from that table to a design decision:

> **Refusing whenever no mechanism exists was the proposal, and it does not survive contact with
> Windows** — `available()` is `None` there for every run, so every dispatch would raise: fourteen
> test files and the runner itself, on the platform it is developed on.

That reasoning is correct **given the table**. It is the table that is incomplete. Docker runs on
Windows, macOS and Linux, and AutoGen has been bounding executed code through it for years.

So the sentence to correct is not the refusal rule. It is the premise underneath it: *Windows has no
mechanism* is a statement about `MECHANISMS`, not about Windows.

## What this changes, and what it makes affordable

A third builder beside `_bwrap` and `_seatbelt`. The policy maps cleanly, which is why this is an
entry rather than a redesign:

| `sandbox_for` says | docker |
|---|---|
| `write: workspace` | the workspace mounted `rw`, everything else absent |
| `write: none` | mounted `ro` |
| `network: False` | `--network none` |

And then the consequence worth having: with a mechanism on every platform, **`--sandbox` can stop
being the narrow flag and become the default**, because "nothing on this machine can enforce it" is
no longer the ordinary case. That is the property CHG-20260827-23 wanted and gave up. This record
does not make that switch — it removes the reason it could not be made, and says so.

## What is worse about docker, stated rather than discovered later

* **Coarser.** A container is not seatbelt: the bound is the container, not a per-role file scope
  inside it. `can_write=False` becomes a read-only mount, which is the right shape but a blunter
  instrument.
* **A daemon.** `available()` must not report docker on a machine where the daemon is not running —
  which is the same defect this repository already carries once, `shutil.which` answering for a
  capability it has not tested. Task 3 fixes it here for all three mechanisms rather than adding a
  third instance of it.
* **Slower.** Container start is not free, and every ask pays it.

## Risk & rollback

- Task 3 changes behaviour for the two existing mechanisms as well: a machine with `bwrap` installed
  but unprivileged user namespaces disabled currently reports `enforced: True` and will stop doing
  so. That is a correction, and it will look like a regression to anyone reading only the field.
- Rollback: revert. Removing the entry returns `available()` to two mechanisms.

**Proposed.** Reads after CHG-20260828-04, whose suite task 2 depends on.

### Not claimed

**That docker is a good sandbox.** It is a bound, on a platform that currently has none. Container
escapes exist, and a mounted workspace is still a workspace.

**That the default can flip.** This removes the stated obstacle. Whether `--sandbox` becomes the
default is a decision for a person, on evidence this change does not yet have.

**That every environment has docker.** A CI runner or a locked-down laptop may have none of the
three, and the `enforced: False` path stays exactly as CHG-20260827-23 built it.
