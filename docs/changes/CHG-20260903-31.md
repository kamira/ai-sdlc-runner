## Read this first

All three are the same shape from the operator's side: **a thing the runner tells you, that is not
so.** None of them stops a run. Each of them makes a person act on something that is not true.

```
L-37   `uncommitted()` reports a filename that exists nowhere
L-43   `runner flow` prints 25 of the graph's 40 edges, and three nodes read backwards
L-32   the README reads a step count as a node count, and its guard asserts a literal
```

## L-37 — one slice, two opposite errors

`git status --porcelain -z` emits one NUL-terminated field per entry — **except** a rename or a
copy, which emits **two**: the new path with its `XY ` prefix, then the old path with **no prefix at
all**. The parser sliced `[3:]` off every field:

```
git emits (fields)   ['R  DOCS.md', 'README.md', ' M agent.py', 'R  x.md', 'a.c']
uncommitted()        ['DME.md', 'DOCS.md', 'agent.py', 'x.md']
                       ^^^^^^ invented — 'README.md'[3:]
                     and 'a.c', an old path of three characters, silently dropped by
                     the `len(entry) > 3` guard beside it
```

**One direction invents a name and the other loses one, from the same line.** And the operator reads
it as *"uncommitted: DME.md, DOCS.md, agent.py — a module builds from the last commit…"*

`uncommitted`'s docstring says what it is for: *"this repository's rule is that a surprise gets said
out loud rather than discovered"*, and it exists because a test left an edit uncommitted and the
build ran the previous agent for **thirty-nine cycles**. A filename that exists nowhere is a
different surprise.

## L-43 — the fastest way to see what it will actually do, showing 25 of 40 edges

```
edges reachable via node.branches   25   <- what `cmd_flow` printed
edges only in node.next             15   <- what it did not
total                               40
```

A node with no branches printed a line with **no successor at all**, so the reader could only infer
one from the **listing order** — which disagrees with the graph at three nodes:

```
node             printed position implies      actually goes to
pm_plan          pm_confirm                    plan_scope
record_module    fix_pass                      next_module
review_failed    qa_verify                     change_retry
```

`test_flow_prints_every_node_and_agrees_with_the_graph` asserts node ids and three counts. Despite
its name it makes **no edge assertion**, which is why fifteen missing edges were invisible to it.

## L-32 — the check written against a false referent, being one

`README.md`: *"That **visits 22 of the 31 nodes** — five are failure paths a green run never takes,
and two (`sub_plan`, `reconcile`)…"*

```
len(report.visited)      22   <- STEPS. `next_module` is entered twice; the CLI prints this
                               as `visited:`
distinct nodes visited   21
never visited            10   = 8 failure paths + sub_plan + reconcile
README accounting        22 + 5 + 2 = 29, of 31   <- two nodes unaccounted for
```

The sentence reads a step count as a node count **and** its own arithmetic is two short.

**And the guard is the defect it was written to close.** `test_the_readme_says_how_many_nodes_a_run_actually_visits`
opens with:

> *"The README said the example drives all 24 nodes. A run visits 20 … and the check passed it
> anyway, because its regex matched 24 and compared it to `len(graph.NODES)`. The figure was right
> about the graph and the sentence was wrong about the run: **a check on the right number against
> the wrong referent.**"*

and then asserts `visited == 22` — **a literal typed into the test.** It runs no walk. Its failure
message tells the reader to *"read the `visited:` line"*, which prints the step count. The right
number, against the wrong referent, one layer out.

It now runs the example walk, compares against `len(set(report.visited))`, and **checks the
sentence's accounting as well**: what a green run never reaches must be exactly what the sentence
says it skips, and the three numbers must sum to the graph.

## Risk & rollback

- **Task 1 changes what an operator is shown on a rename**: two paths now instead of one wrong one.
  Both halves of a rename are reported because a build cut from a commit sees neither the old path
  (gone from the working tree) nor the new one (not in the commit), which is the thing being
  reported.
- **Task 4 makes `runner flow` longer** by fifteen lines. That is the whole point, and it is the
  only cost.
- **Task 8's test now runs a walk**, so it is slower than a regex and it can fail for a reason that
  is not the README's — a genuine change to the flow moves the number, and the sentence must move
  with it. That is intended: the sentence is *about* the run.
- **The failure message no longer points at the `visited:` line**, because that line prints steps.
  Anyone who learned to check it that way will need the new sentence, which says both numbers.
- Rollback: revert. A rename invents a filename again, fifteen edges vanish again, and the README
  counts steps as nodes again.
