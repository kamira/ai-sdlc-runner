## What was missing, and why it was easy to miss

The `Model` **shape** was already in three documents: the registry file in `SCHEMAS.md` entry 10, the
`models` table in `DATABASE.md`, and `GET`/`POST /models` in `API.md`.

**The rules that govern it were in none of them.** Three documents showing eight fields, and nothing
saying what a model must have, what it may not have, how `reach` is decided, or how a model gets from
the registry to an actual ask. A shape written down three times still leaves a reader unable to
answer *"will this entry be accepted, and what will it do?"*

## [`docs/MODELS.md`](../MODELS.md)

### The two halves are separate on purpose

`Registry`'s own docstring draws the line: *"the models this project may use, and nothing about which
node uses which."* The registry is **what exists**; the assignment is **what this change does**. One
is closed, the other is not.

### Every refusal, in the order `validate` makes them

Fourteen, each with the reason from the code. The two worth naming here:

- **A `cli` model carrying an `endpoint` or `key_env` is refused** — *"a field nothing reads is one
  somebody will later assume was honoured."*
- **A secret in a query string is refused**, matched on the **key** rather than the shape: *"shapes
  differ per vendor and change without notice, while somebody writing `?api_key=` has told you what
  it is."* And `_SECRET_KEYS` is **not exhaustive**, by its own comment — a check that refuses what
  it recognises without claiming to recognise everything, which is the opposite of the coarse check
  this project keeps finding.

### `reach` — the classification table, written down for the first time

Two decisions worth reading twice, both now on the page:

- **A single-label name is `internal`.** `gpu-box` is a network name; `api.example.com` is not.
- **Unresolvable is `external`** — *"guessing the generous answer about where data goes is the wrong
  way to be wrong."*

### Assignment: the same list means different things at different nodes

`node_models: {"lead_review": ["opus", "gpt", "gemini"]}` is three adjudicated voices on a
`model_panel`, a pool of three on a `pool`, and ignored entirely on a `follows` or a `seat_panel` —
and the difference is the node's **declared** `mode`, never its name.

A pool's choice is random **and** reproducible, seeded by `dispatch_seed`, the node id and the ask
ordinal. Not a contradiction: *"the choice is arbitrary with respect to the work, not with respect to
the record."*

## The thing I found while writing it

**An `api` model validates, appears in the console with its `reach`, and cannot be dispatched to.**

```
model 'gpt' is 'api', and this runner dispatches by running a command. An api model needs a
backend that speaks to it — there is none yet, and pretending otherwise would send the work to
the default and report it as 'gpt'.
```

Nothing about registering one goes wrong. The first ask routed to it raises.

**The refusal is right** — the alternative its own message names is sending the work to the default
and reporting it as `gpt`, which is a lie in the dispatch record. But it means `transport: "api"` is
a declaration this runner cannot yet honour, and that was written down nowhere.

It was found by a test failing: my first version of
`test_the_page_states_the_resolution_order_the_factory_uses` asserted against the line that
*assigns* `default` rather than the branch that *uses* it, and reading the factory properly to fix it
is what surfaced the refusal.

## The tests

52, and every refusal is **driven** rather than read out of the source — a refusal that stops firing
fails here rather than quietly widening what the registry accepts.

| Pinned | How |

### Not claimed

**That `_SECRET_KEYS` catches every secret in a URL.** It does not, by design, and both the code and
the page say so. `?auth=` gets through.

**That an `api` model works.** It registers and it cannot be dispatched to. That is now written down
rather than discovered at the first ask.

**That the assignment side is closed.** It comes from the plan file, which ignores unknown keys — a
misspelt `node_models` silently assigns nothing and every node falls back to one backend. Recorded in
CHG-20260823-21 and still open.
