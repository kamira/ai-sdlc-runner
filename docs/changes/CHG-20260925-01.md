# CHG-20260925-01 — every order says how to answer it, and a backend gets an hour

- Project: ai-sdlc-runner
- Branch: claude/ai-sdlc-runner-skill-tuning-91tsiv
- Date: 2026-09-25 (UTC+0)
- **Measured against `origin/main` at `5216941`**, the tree this branch is cut from. Every claim
  below was taken by reading or running the code, and each says how.
- Type: one field added to the closed work order, one resume rule for journals written before it,
  and one dispatch default.
- Risk: **medium** — every order every backend receives changes shape, and so does the rule that
  decides whether a resumed run reuses an answer. Nothing is loosened: no gate, halt, verdict
  reader or red-line scan changes.
- Autonomy: high
- Related: CHG-20260823-01 (the closed order this extends); CHG-20260901-14 (the resume rule this
  narrows); CHG-20260823-11 (retries, and the timeout they wrap)
- Status: see `## Status`

## Why

A backend here is a model run once per ask with no person attached: the order goes in on stdin, one
JSON object comes back on stdout, and the process ends. Current models follow what an order says
literally and run long agentic turns. Three things the runner does not tell them, or does not allow
for, now cost runs.

**1. No order says what shape its answer must take.** The readers are exact, and which reader
applies depends on how the ask was dispatched, not only on the node. Measured with `engine.walk`
and stub sessions:

| the ask | what the run reads | what the docs say |
|---|---|---|
| `pm_confirm` / `pm_signoff`, one model | `verdict` ∈ `yes`/`no`; `pass` raises `EngineError` | `{"verdict": "<branch>"}` |
| the same nodes, two or more models | `verdict` ∈ `pass`/`fail`/`undecided`; `yes` raises `PolicyError` | `{"verdict": "<branch>"}` — wrong |
| `lead_assess`, two or more models | `risk` ∈ `low`/`medium`/`high` | not listed |
| `lead_assess`, one model | nothing | not listed |
| the intake option ask | `options`, ≥ 3 distinct strings | not listed |
| `engineer_build` | `module`; an empty one with `error` stops the run | `error` not listed |

The only statement of the contract is prose outside the order — README's table, which calls
`examples/minimal/agent.py` *"the only place the answer contract is written down"*, and SCHEMAS §6.
A backend receives neither. A model that answers a panel ask the way the README says (`yes`) stops
the run with `PolicyError`; one that answers in prose is read as having said nothing.

**2. No order says nobody is there.** A model that ends its turn with a question, or with *"shall
I proceed?"*, prints prose. Prose is not one JSON object, so the answer reads as silent: a decision
node raises *"named no branch"*, a seat raises, `engineer_build` loops to the step guard (200 steps,
measured). The question itself is lost — no reader looks at `stdout` as text.

**3. The default timeout kills builds.** `cli.session_factory` reads `agent_timeout` with a bare
default of `600` seconds, and `config/runner.yaml` ships `600`. `engineer_build` asks for a whole
module in a worktree; a current agentic model spends longer than ten minutes on that as a matter of
course. What the kill does, measured (`agent_timeout: 1`, an agent sleeping 5 s): the direct child is
killed, a grandchild it started kept running and wrote its file 3 s later, the files written so far
stay in the kept worktree, a configured retry starts on top of them, and without one the run stops
with exit 10 and the question pending. A resumed run re-asks it from scratch.

## What ships

### 1. `reply` — the eighteenth field of the work order

`workorder.WORK_ORDER_FIELDS` gains `reply`. Its value is closed, like `policy_verdict`:

```json
"reply": {
  "format": "One JSON object on standard output, and nothing else there. ...",
  "keys": { "verdict": { "one_of": ["no", "yes"] } },
  "unattended": "No person watches this ask while it runs ..."
}
```

- `format` and `unattended` are fixed sentences, the same on every order (text in
  `workorder.py`).
- `keys` names each key the run acts on in **this** answer and what it accepts. A descriptor is
  exactly one of `{"one_of": [...]}`, `{"list_of": [...]}`, `{"list_of": "text"}`,
  `{"text": "<what it says>"}`, plus an optional `at_least` (with `list_of`) and an optional
  `means`. `{}` says the run acts on nothing in this answer. `render` refuses any other descriptor
  shape, so the vocabulary the order speaks is closed the way the answer vocabularies are.

**Computed where the dispatch is decided, from the readers' own constants.** Each ask site in
`engine.walk` passes which path it is on — one voice, a model panel, a seat panel, an intake survey
seat, the option ask — and `engine._reads(node, cfg, voices)` returns `keys` from the same
constants the readers use (`policy.VERDICTS`, `policy.RISKS`, `node.branches`,
`intake.ASPECT_IDS`, `intake.MIN_OPTIONS`) and the same condition `_frontier` runs under (a
`"frontier"` decision):

| the ask | `keys` |
|---|---|
| a node that decides on its answer, one voice | `verdict`: one of the node's branches |
| the same node, a panel of two or more models | `verdict`: one of `pass`, `fail`, `undecided` |
| a `grades_risk` node, a panel of two or more models | `risk`: one of `low`, `medium`, `high` |
| a seat on the review panel | `verdict`: one of `pass`, `fail`, `undecided` |
| a seat at intake | `missing` (list of the aspect ids), `problems`, `unsafe` (lists of text) |
| the intake option ask | `options`: list of text, at least 3 |
| `engineer_build` | `module` (text); `error` (text) too when a decision is `"frontier"` |
| `pm_plan`, when a decision is `"frontier"` | `modules`: list of text |
| every other ask | `{}` |

`render(node, node_spec, verdict, seat=None, *, reads)` takes `keys` as a **required** keyword: a
call site that forgets it is a `TypeError`, not an order that silently says "nothing is read".

**Why a field, and not a paragraph in `instructions`** (chosen over appending to `instructions`,
where the seat line and the send-back reason already go):

- the contract is a fact the runner computes, and a fact belongs in a field a program can read —
  KN-9's rule for answers, applied to the question;
- `instructions` is the plan's text, checked blank-or-not and read against the red lines; runner
  text mixed into it would ride through the one check and be invisible to the other;
- seat orders stay identical apart from `seat` and `instructions`, and `weather-spa`'s agent, which
  quotes `len(instructions)`, answers exactly as before.

**KN-5, interpreted.** KN-5 keeps model and dispatch settings out of the order. `reply` names no
model, no seat routing, no tool and no deadline. It does carry one consequence of dispatch — a
panel reads `pass`/`fail`/`undecided` where one voice reads the node's branch names — because that
is what the answer must say, and an order that hides it is the defect above. Chosen over unifying
the two vocabularies in the readers, which would change what every existing backend must answer.

### 2. `unattended` — the fixed sentence

> No person watches this ask while it runs, and nobody can answer a question asked in it: do not
> stop to ask, or to wait for approval. Do the work this order describes, then answer. Where it
> cannot be done, say so in the terms `keys` gives you. Put what you assumed, and anything a person
> should read, in `why`: it is kept with the run's record and decides nothing.

Every claim in it is true of every ask: a `_Process` has no channel to a person, `why` is recorded
in the conversation (`conversations._summary` and every export) and read by no router.

### 3. A journal written before this change still resumes

Adding a field to every order makes every answered journal entry differ from the order the walk now
renders, and `_ask` reuses an answer only when the two are equal. Measured by patching one sentence
into `render`: a resume went from 17 answers reused to 0 reused and 17 dispatched. Under `serve`,
which always resumes against its journal, the first walk after an upgrade would re-ask every node —
`engineer_build` included, in the worktree it already wrote.

So `_ask` compares a stored order that has **no** `reply` with the new order **without** `reply`.
Such an answer was accepted by the walk that recorded it; reusing it is what this runner did the day
before. A stored order that has a `reply` is compared whole, as now. Chosen over documenting a
one-time re-dispatch (what earlier field changes accepted), because this change touches every order
rather than one node's.

### 4. `agent_timeout` defaults to 3600 seconds

`cli.DEFAULT_AGENT_TIMEOUT = 3600`, read by `session_factory`; `config/runner.yaml` and README's
example say `3600`, with what the number is: seconds, per attempt, a ceiling for a backend that has
hung — not an estimate of how long an ask takes. The comment says what expiry does (the measured
list above). Worst case per ask stays `timeout × (agent_retries + 1)`. The three examples keep `60`:
their agents are scripts that answer at once.

## Tests, and the wire each one cuts

- **An agent that reads only `reply` finishes the flow** — on the default configuration, and with
  every model-panel node given two models. The agent builds each answer from `order["reply"]["keys"]`
  alone. Any ask site that passes the wrong path, or a `_reads` row that names the wrong vocabulary,
  stops the walk.
- **The option ask's `reply` gets an answer accepted** — the escalation path is not on a green walk,
  so it is driven on its own.
- **Descriptors are closed** — an unknown descriptor key is refused by `render`.
- **A journal from before this change resumes without re-asking**, and a changed brief under the
  new format still re-asks.
- **The default timeout reaches `subprocess.run`**, and **README and `config/runner.yaml` state the
  number the code uses**.
- Mutations registered for each, group `reply-contract`.

## What this does not do

- **Does not give every node a way to say "I cannot".** The answers of `engineer_selfverify`,
  `fix_pass`, `qa_verify`, `pr`, `merge` and `sub_plan` are read by nothing, and so is
  `lead_assess`'s with one model: `{"verdict": "fail"}` at `qa_verify` walks on to `qa_accept`
  (measured). Their `reply` says `{}` truthfully; routing a refusal from them is a flow change, not
  an order change.
- **Does not tell a backend its deadline.** A timeout is a dispatch setting (KN-5).
- **Does not kill a timed-out backend's children.** `subprocess.run` kills the direct child only;
  measured above, recorded here, not fixed.
- **Does not fix** the rejection-reason red-line gap found while mapping this change: a person's
  rejection reason reaches the next order's `instructions` (`engine.py` `_order_for` via
  `sent_back`) without the red-line scan that `--instruction` text gets since CHG-20260903-23.
  Measured: *"drop table users from the production database"* reached `pm_plan`'s second order and
  the run carried on. Reported to the user as its own change.
- **Does not change** `branch` beating `verdict` in `_answered_branch`, the dead `decisions` entries
  for asked nodes, or the unread fields of `intake.option_request`.

## Review

(DIR-1). Implementation: the same four-seat composition on the pinned tree.
