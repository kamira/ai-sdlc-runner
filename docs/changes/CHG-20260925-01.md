## Why

A backend here is a process run once per ask: the order goes in, one JSON object comes back, and
nothing else passes between them. The user reports that current models follow what an order says
literally and run long agentic turns — a report, not a measurement here. Three things the runner
did not tell them, or did not allow for, cost runs.

**1. No order said what shape its answer must take.** The readers are exact, and which reader
applies depends on how the ask was dispatched, not only on the node. Measured with `engine.walk`
and stub sessions:

| the ask | what the run reads | what the docs said |
|---|---|---|
| `pm_confirm` / `pm_signoff`, one model | `verdict` ∈ `yes`/`no`; `pass` raises `EngineError` | `{"verdict": "<branch>"}` |
| the same nodes, two or more models | `verdict` ∈ `pass`/`fail`/`undecided`; `yes` raises `PolicyError` | `{"verdict": "<branch>"}` — wrong |
| `lead_assess`, two or more models | `risk` ∈ `low`/`medium`/`high` | not listed |
| `lead_assess`, one model | nothing | not listed |
| the intake option ask | `options`, at least 3 distinct strings | not listed |
| `engineer_build` | `module`; under a `"frontier"` decision an empty one with `error` stops the run | `error` not listed |

The only statement of the contract was prose outside the order — README's table, which called
`examples/minimal/agent.py` *"the only place the answer contract is written down"*, and SCHEMAS §6.
A backend received neither. A model answering a panel ask the way the README said (`yes`) stopped
the run with `PolicyError`; one answering in prose was read as having said nothing.

**2. No order said nobody can reply.** A model that ends with a question, or *"shall I proceed?"*,
prints prose. Prose is not one JSON object, so the answer is recorded and read by no router: a
decision node raises *"named no branch"*, a seat raises, `engineer_build` loops to the step guard
(200 steps, measured).

**3. The default timeout kills builds.** `cli.session_factory` read `agent_timeout` with a bare
default of `600` seconds, and `config/runner.yaml` shipped `600`. `engineer_build` asks for a whole
module in a worktree; that a current agentic model spends longer than ten minutes on it is the
user's report, not a measurement here. What the kill does, measured unsandboxed (`agent_timeout: 1`,
an agent sleeping 5 s): the direct child is killed, a grandchild it started kept running and wrote
its file 3 s later, the files written so far stay in the kept worktree, a configured retry starts on
top of them, and without one the run stops with exit 10 and the question pending.

## What ships

### 1. `reply` — the eighteenth field of the work order

`workorder.WORK_ORDER_FIELDS` gains `reply`, closed like `policy_verdict`:
`{"format": <sentence>, "schema": <JSON Schema of the answer>, "unattended": <sentence>}`.

**`schema` is a closed subset of JSON Schema**: an object with exactly `type: "object"`,
`properties`, `required` and `additionalProperties: false`; each property `type: "string"` (with an
optional `enum`) or `type: "array"` of strings (with optional `enum` items, `minItems`,
`uniqueItems: true`), and a `description` always. `workorder.reply` refuses anything else. JSON
Schema was chosen over the draft's own descriptor vocabulary (`one_of`/`list_of`/`text`/`means`),
which the design panel measured could not say "leave this out" or "an empty list means none": a
model already reads JSON Schema for structured answers, and `required` and
`additionalProperties: false` say both of those things in words it knows. Every answer may carry
`why` (text), which no router reads.

**The field is named `reply`, not `answer`**, because a journal entry already holds the answer —
under `result` — beside the order, and `order.answer` would read as that.

**Computed where the dispatch is decided, from the readers' own constants.** Each of the six ask
sites passes which path it is on — `ONE`, `MODELS` (the first round and the reruns), `SEATS`,
`SURVEY`, `OPTIONS` (the option ask, the one site that calls `render` directly) — and
`engine._answer_schema(node, cfg, voices)` builds the schema from `policy.VERDICTS`,
`policy.RISKS`, the veto seat in `policy.SEATS`, the node's `branches` (sorted), `intake.ASPECTS`,
`intake.MIN_OPTIONS`, and the frontier predicate: **any decision's value is `"frontier"`**, because
`check_decisions` lets any node carry it. `voices` is closed (KN-9): an unknown path raises rather
than falling through to the one-voice schema. A grading panel is checked before a verdict panel.
`render(node, node_spec, verdict, seat=None, *, answer_schema)` takes it as a **required** keyword,
so a call site that forgets it is a `TypeError`, not an order that silently says nothing is read.

What each ask is told (`required` in bold; every schema also offers `why`; descriptions as shipped
at this change):

| the ask | `properties` |
|---|---|
| a node that decides on its answer, one voice | **`verdict`** ∈ the node's branches, sorted — *"the branch you choose"* |
| the same node, a panel of models | **`verdict`** ∈ `pass`/`fail`/`undecided` — *"`pass` or `fail` on what this order asks; `undecided` counts as not passing"* |
| `lead_assess`, a panel of models | **`risk`** ∈ `low`/`medium`/`high` — *"your grade of this change's risk; when unsure between two, the higher"* |
| a seat on the review panel | **`verdict`** ∈ `pass`/`fail`/`undecided` — as a panel voice, plus *"and from the `conformance` seat, which holds a veto, it is a veto"* |
| a seat at intake | **`missing`** (unique ids from `ASPECT_IDS`, each described; *"only aspects this change needs … Each id stops the run to ask a person before anything is planned"*), **`problems`**, **`unsafe`** (text lists; *"[] when …"*; *"Each entry stops the run for a person"* on `unsafe`) |
| the intake option ask | **`options`**: at least 3, unique — *"each option one string saying what it is and what it costs; at least 3 different ones; do not pick one"* |
| `engineer_build` | **`module`** — *"the id of the planned module this order built, exactly as the plan names it; "" only when nothing is left to build. If you could not build it, answer "" and set `error`"*; `error` — *"only when you could not build: why. The run stops at this order for a person. Leave it out otherwise"* |
| `pm_plan`, under a frontier decision | **`modules`** — *"every module the plan now has, as short ids, one string each; [] if you could not plan — the run then stops for a person"* |
| every other ask | nothing required |

**Why a field, and not a paragraph in `instructions`**: the contract is a fact the runner computes
and a program can check (KN-9's rule for answers, applied to the question); `instructions` is the
plan's text, checked blank-or-not and read against the red lines, and runner text mixed into it
would ride through one check and be invisible to the other; and seat orders stay identical apart
from `seat` and `instructions`, so `weather-spa`'s agent, which quotes `len(instructions)`, answers
as before.

**KN-5, interpreted** (recorded in KN-5 itself, so a later strict reading does not remove it).
`reply` names no model, no route, no tool and no deadline, and is built from runner constants and
the graph only — pinned by a sentinel test. It does carry one consequence of dispatch — which words
the answer's reader accepts — because the answer must use them. Chosen over unifying the readers'
vocabularies, which would change what every existing backend must answer.

### 2. The two fixed sentences

As shipped at this change — the code is the authority, and `_comparable` keeps later rewording
from re-asking anything. `workorder.REPLY_FORMAT`, worded without the transport, which is the
dispatcher's business (KN-5):

> Your answer is one JSON object that `schema` describes, and nothing else: no code fence, no text
> before or after it, not a list. Write it as your own final message — not printed by a tool and not
> written to a file. Spell every word an `enum` lists exactly as listed, in the same case. Include
> every `required` key, and no key `schema` does not name. When `required` is empty, the run acts on
> nothing in your answer.

`workorder.REPLY_UNATTENDED`:

> Nobody can reply to you while this order runs: do not stop to ask a question or to wait for
> approval, because no reply will come. Do the work this order describes, then answer. Nothing in
> this order permits performing any of `permanent_halts` against a real system — writing ordinary
> code about such things is not performing them. If the work would need one, leave that part undone
> and say so. Where the work cannot be done, say so with what `schema` offers for that (`error`,
> where it offers one); where it offers nothing, say so in `why`, and never claim the work was done.
> The approvals `policy_verdict` names are the runner's to take, before or after this order: that
> the order reached you means its work may go ahead, so do not seek an approval yourself.

The `permanent_halts` clause is there because the sentence removes a stop: a cautious model that
used to end with *"shall I drop the table?"* stopped the run; told not to ask, it must be told what
it still may not do. It is scoped to *performing* one against a real system, because the halts are
short phrases ("any hard delete", "changing … permissions") and an engineer asked for a delete
endpoint or a migration file must not read writing that code as crossing one (KN-13).

### 3. An engineer that reports a failure stops the run at that ask

`reply` offers `error` for a failed build, so the run must act on it. Before this change, with the
decisions a list, `_module_built` read `{"module": "", "error": …}` as "no" and the run walked to
`finished` — measured, 17 asks, nothing said — and a *named* module with a failure was counted as
built on both paths, so `record_module` ticked, committed and wrote the worklog for it.

`engineer_build` now carries an `accept` (`_stop_on_failed_build`): a reported failure raises at
the ask itself, so nothing after it is asked and the answer is journaled `refused` — a resumed run
asks the engineer again. The implementation panel measured why it has to be there and not only at
`module_built`: the run went on asking `engineer_selfverify` and `lead_task_review` first; a fix pass
that repaired the build and passed review still stopped on the stale `error`; and the `answered`
entry replayed the stop on every resume with nothing asked (4 of 4). `_module_built` and `_frontier`
keep the same check as backstops, pinned by calling them directly.

What counts as a failure (`_build_failure`): with `module` empty, any of `FAILURE_KEYS`, the rule
that predates this change; with a module *named*, only `error`, the key the order offers — a backend
that never read `reply` and reports `"errors": ["lint warning"]` beside a module it built is still
recorded as built. The shared message no longer tells the operator to *"fix the backend"* for giving
the answer the order asked for, and says a resumed run asks again.

### 4. Resume across the change

`_ask` reuses a journaled answer only when the stored order asks what the new one asks
(`_same_question`) **and** the ask's own reader would accept the answer (`_heard`):

- **An entry written before `reply` existed** is compared with the new order minus its `reply`.
  Without that, the first resume after an upgrade re-asked every node — measured by patching one
  sentence into `render`: 17 reused before, 0 reused and 17 re-asked after; under `serve`, which
  always resumes, that is every `engineer_build` again, in the worktree it already wrote.
- **Any other entry** is compared whole, except the runner's own wording: `reply` is reduced to its
  schema's structure — no fixed sentence, no property `description`. Tuning that wording must not
  re-ask every journaled node; a changed key, word or requirement does.
- **`_heard`, for every entry.** A journal records `answered` before any reader runs, so an answer
  the walk refused — prose at a decision node, a seat's `PASS` — was replayed on every resume and
  refused again, with nothing dispatched, until somebody deleted the file. This predates `reply`;
  the draft's claim that journaled answers "were accepted by the walk" was false. `_heard` consults
  the readers themselves (`_answered_branch`, `_spoken`, `intake.collect`; a failed build is
  `engineer_build`'s own `accept`, which reuse already checks), so it is exactly as strict as the
  walk: an old journal in the shapes the readers accept — `branch` for
  `verdict`, a survey naming one key of three, an engineer's prose — is reused in full. The first
  implementation used a schema check (`_conforms`) instead, and the implementation panel measured it
  stricter than the readers: it re-asked old `engineer_build` answers, the cost this rule exists to
  avoid.

Permanent by design: a reused entry is never rewritten, so a `serve` journal on an unchanged brief
keeps its reply-less entries indefinitely. **Rolling back** to a runner without `reply` re-asks
every node once (measured by the design panel's risk seat: 0 of 17 reused). **New re-ask
triggers**: changing a decision to or from `"frontier"` changes what `pm_plan` is asked; and a
journaled rework order after a refusal with no reason carries the reworded send-back line (§5) in
its `instructions`, which is compared whole — re-asked once after the upgrade.

### 5. Smaller alignments

- `conversations._summary` puts `why` after everything the run acts on, and now shows `error`
  first (the key that stops a build — "module: m1" on the ask that stopped the run read as a
  success), `risk` and `options`: every order invites `why`, and reading it first hid each intake
  finding behind a seat's aside.
- `examples/minimal/agent.py` answers only the keys its orders name, moving its extra text to
  `why` (the orders say `additionalProperties: false`).
- The send-back line for a refusal with no reason said *"say what you would need"*, which invites a
  question; it now says *"say in `why` what you would need"*.

### 6. `agent_timeout` defaults to 3600 seconds

`cli.DEFAULT_AGENT_TIMEOUT = 3600`, read by `session_factory`; `config/runner.yaml` and README's
example say `3600`, with what it is: seconds, per attempt, a ceiling for a backend that has hung —
not an estimate. The comment says what expiry does (the measured list above). Worst case per ask
stays `timeout × (agent_retries + 1)` on Linux and macOS; on Windows, CPython's `subprocess.run`
waits after the kill until every process holding the child's output has exited (read in CPython's
source, not run here), so a grandchild can hold the runner past the timeout. **Under `serve`**, which runs the walk inside the request and
has no route to cancel it, a hung backend now holds the console up to an hour per attempt instead
of ten minutes. Chosen over a per-role timeout (3600 for roles that write, 600 for the rest): a
reviewer reading a whole branch runs long too, and one number is the one an operator can reason
about. A `runner.yaml` that says `600` keeps 600 — README now says so. The examples keep `60`; their
agents answer at once.

## Tests, and the wire each one cuts

`tests/test_reply.py` — `ReplyAgent` answers every order from `reply.schema` alone, plus a fixed
preference among offered words (`pass`, `yes`, `low`) and the module ids it made up at `pm_plan`
(an order never names one):

- the default flow, a `"frontier"` decision (the walk that reads `module` and `modules`), and every
  model-panel node on two models all **finish**; the option ask's answer is **accepted**;
- a failed build **stops** the run, under a list decision and under `"frontier"`, with `module`
  empty and with a module named; it stops **at its own ask**, journaled `refused`; a resume **asks
  the engineer again**; a failure an older runner journaled `answered` is asked again too; a named
  module beside an old failure key other than `error` is still a build; the `_module_built`
  backstop stops when called directly (`_frontier`'s is pinned in `test_frontier_latch`);
- a sentinel model name, instruction and attachment never reach `reply`, and the brief's sentinels
  do reach every order; the seats of one node share their `reply`; an unknown dispatch path is
  refused;
- a schema outside the subset is refused, eight ways;
- a reply-less journal resumes with nothing re-asked; an old journal **in the shapes older backends
  used** (`branch`, `outcome`, a one-key survey, prose at `engineer_build`) resumes in full; an
  answer the walk refused is asked again, with or without `reply`; a changed schema with an
  unchanged brief is asked again; reworded fixed text is not;
- the conversation's log line leads with `error`, `risk`, a finding or options, and `why` last;
- no current document names the rejected draft (`reply.keys`, `engine._reads`, descriptors).

`tests/test_agent_timeout.py` — the default reaches `subprocess.run` (captured, not waited on); a
configured value wins; README and `config/runner.yaml` state the number the code uses.

Existing tests that changed: 30 direct `render` calls pass `answer_schema=NOTHING_READ`
(`test_workorder` 18, `test_flow` 8, `test_cli` 2, `test_plan` 1, `test_schemas` 1); the closed-count
test in `test_schemas` now expects `WorkOrderError` "outside the contract" — `pytest.raises(Exception)`
was satisfied by the missing keyword's `TypeError` with the closed check disabled; `test_frontier_latch`
checks the new stop message and pins `_frontier`'s backstop directly.

Mutations: group `reply-contract`, one per wire above; `frontier` and `modules` re-anchored. No
`after` is the length of its `before`, and no two mutations in a row on one file change its size by
the same amount: two same-size rewrites inside one second let pytest import the previous mutation's
`.pyc`, and the first draft's two `enum` swaps did exactly that on alternate runs. The
claim-referent anchor on the field count moves from "Seventeen" to "Eighteen".

## What this does not do

- **Does not give every node a way to say "I cannot".** The answers of `engineer_selfverify`,
  `fix_pass`, `qa_verify`, `pr`, `merge` and `sub_plan` are read by nothing, and so is
  `lead_assess`'s with one model: `{"verdict": "fail"}` at `qa_verify` walks on to `qa_accept`
  (measured). Their schema requires nothing and says so; routing a refusal from them is a flow
  change.
- **Does not carry a voice's `why` into the rework it causes.** `_send_back` and the panel rerun
  carry verdict words only; the design panel found the rework brief's "address what X raised" can
  therefore never quote it.
- **Does not scan the send-back reason for red lines.** A person's rejection reason reaches the next
  order's `instructions` without the scan `--instruction` text gets since CHG-20260903-23;
  measured, *"drop table users from the production database"* reached `pm_plan`'s second order and
  the run carried on. The `permanent_halts` clause above tells the model not to act on such a line;
  the scan itself is its own change, reported to the user.
- **Does not tell a backend its deadline** (KN-5), **and does not kill a timed-out backend's
  children**: measured unsandboxed; under `bwrap` the process `subprocess.run` kills is the wrapper
  (`_bwrap` passes no `--die-with-parent`), so the backend itself would outlive it — reasoned, not
  probed, since no `bwrap` was available.
- **Does not name the modules in `engineer_build`'s order** (no prior answer, FR-8); a module id
  spelled differently from the plan's still never shrinks the frontier.
- **Does not change** `branch` beating `verdict` in `_answered_branch`, the dead `decisions` entries
  for asked nodes, the unread fields of `intake.option_request`, or the conformance seat's question
  at intake.

## Review

Design: two `fable` seats and two `opus` seats, each in its own session, independent and then
cross-read, before the build (DIR-1: `codex` could not be reached — no binary, no credentials, the
API host unreachable). Both `opus` seats failed the draft, and the `defect` seat after cross-reading:
the model-facing text was not written out, the draft's vocabulary could not say "leave this out",
its `unattended` clause steered a failing engineer into "nothing left to build", and its resume rule
rested on a false claim. The amendments above answer each.

Implementation, on `0b8119a`: the same four seats, independent and then cross-read. All four failed
it, on two findings every seat held: README, SCHEMAS and `design.md` still published the rejected
draft (`reply.keys`, `engine._reads`, the unconditional resume rule); and a failed build replayed its
stop on every resume, stopped only after two more asks, and survived a fix pass that repaired it.
Both are answered above (§3, §4, Docs), with the should-fix findings — the schema check stricter than
the readers, `voices` open, the log line hiding `error` and `risk`, the model-facing wording, the
example agent's extra keys. The verdicts and the disposition of every finding are in
ACC-20260925-01, together with the verification of these fixes.
