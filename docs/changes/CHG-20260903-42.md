## Read this first

Two readers of one history, in one module, twelve lines apart:

```
intake.py:216  stop_reason      times_asked(history, aspect) + 1     counts the ask being made now
intake.py:174  needs_options    times_asked(history, aspect)         does not
```

Measured, run by run, on the aspect `architecture`:

```
run 1   the person is told "(asked once)"      the decision beside it: asks again
run 2   the person is told "(asked twice)"     the decision beside it: asks again
run 3   the person is told "(asked 3 times)"   the decision beside it: asks again      <-
run 4   the person is told "(asked 4 times)"   the decision beside it: OFFERS OPTIONS
```

**On run 3 the operator reads the exact number three declarations say triggers options, and the
runner asks again.**

## Where the lap is lost, and where it is not

Not in the comparison. `needs_options` uses `>=` and its docstring is right about why:
*"the third unanswered ask is the one that has failed, not the fourth."*

It is in what the history holds at the moment of the check. `server.py:530` walks with
`tuple(self.state.intake_history)` and appends **this** run's stop at `server.py:554`, after the
walk returns — so the run currently failing on the aspect is not in its own history. `stop_reason`
knows this and adds the one; `needs_options` does not.

Three declarations say three:

```
intake.py:30   "After the third time a given aspect has been asked for and not supplied, the
                runner stops asking and proposes at least three options"
intake.py:57   "How many times one aspect may be asked for before the runner stops asking"
intake.py:172  "the third unanswered ask is the one that has failed, not the fourth"
```

## The fix is a name, not a `+ 1`

Adding `+ 1` at the second site closes today's gap and leaves the next reader to rediscover the
same thing. `asks_including_this_one(history, aspect)` is the count both questions are actually
about — *how many times has this been asked, counting now* — and `times_asked` stays as the raw
tally over recorded stops, which is what a caller reading history alone still wants.

Same move as CHG-20260903-39's `models.COMPUTED` and CHG-20260903-41's `_declare_classes`: when two
readers of one fact disagree, the fix is one name they both read, not a correction applied to the
one that was wrong today.

## Two tests were named for the third ask and asserted the fourth

This is why nothing caught it. Both guards agreed with the defect, in the **same confusion between
"stops recorded" and "times asked"** that caused it.

```
test_options_are_offered_only_after_the_third_time
    docstring   "the third unanswered ask is the one that has failed, not the fourth"
    body        two recorded stops -> asserts the runner must NOT offer options
                (two recorded stops means the ask in flight IS the third)

test_the_command_line_can_reach_the_escalation_it_documents
    message     "the escalation fires on the ASK_LIMIT-th unanswered ask and not before"
    assertion   reached == [False] * ASK_LIMIT + [True]        <- fires on the FOURTH
```

The second one's assertion contradicts its own failure message, in the same statement. Its docstring
is about a **previous** defect in this exact area — CHG-20260901-17, an escalation that could never
fire from the command line at all — so this ground has been walked twice and the vocabulary was
never fixed.

**Both were rewritten, and that needs saying plainly**: changing a test so a change passes is
otherwise the move that most deserves suspicion. They are rewritten because they measured a
different quantity than their own names and messages claim, and the fix here is to make the module
speak in one of them. Each now counts **asks**, and the second's assertion now matches the sentence
it prints on failure.

## Task 6 — the mutations, on the changed lines

Mutating **the line the change edited**, not the helper it introduced — two changes ago that
distinction was the difference between a guarded fix and an unguarded one shipping green.

```
needs_options reads the raw tally again        ██████████  4 red
stop_reason re-derives its own + 1             ██████████  1 red — the rule, and only the rule
the one name stops counting the ask in flight  ██████████  5 red
```

The middle one is the interesting result: re-deriving `+ 1` inside `stop_reason` is **behaviourally
identical today**, so no behavioural test can see it. Only the rule does — which is what a rule is
for: it refuses the arrangement that let the two readers drift, not the symptom they drifted into.
