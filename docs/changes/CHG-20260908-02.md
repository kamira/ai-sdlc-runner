## The four, and what re-measuring did to two of them

The queue handed these over as items 4, 5, 6 and 7 of eleven. Two are wider than they were written,
which is why they were re-measured before anything was opened.

### 1. The page says every POST but one returns the run snapshot. Three do not.

`docs/API.md` states it as a blanket rule above the route table:

> **Every POST except `/models` returns the run snapshot** ([§3](#3--the-run-snapshot)) with `200`.

`POST /config/nodes`, `POST /config/seats` and `POST /config/halts` all go through `_config_edit`
(`server.py:1236`), which ends:

```python
out = runner.edit(body.get("version"), under_lock)
return {**out, "version": runner.state.version}
```

`under_lock` returns `_reassign()` (`server.py:1219`), which returns `{**merged, "source": source}`,
and `store.resolve` (`store.py:520`) builds `merged` with exactly `node_models` and `seat_models`.
So those three routes answer four keys — `node_models`, `seat_models`, `source`, `version` — and
none of them is a run snapshot.

**The item said the drift was three documented keys against four answered.** It is not a key count:
the page names a different object entirely, for three of the eleven POST routes it governs.

### 2. `known` is documented, built, and read by nothing

`docs/API.md`'s `GET /config/nodes` block documents `by_model.<id>.known`. Every mention of it in
`server.py` — lines 1483, 1489, 1494, 1498, 1502, 1503 — is inside the branch that *builds* the
answer. The console reads it nowhere.

It is **nested**, inside `by_model`, which is why no guard sees it: the rule that catches an
unrendered key iterates `RunState.snapshot()`, and this is not on the snapshot at all.

### 3. A comment counts the snapshot's keys, and the count was wrong

`tests/test_server.py:2377`:

> `test_every_key_the_server_sends_reaches_the_console` (CHG-20260903-29) watches the 19 keys
> `RunState.snapshot()` builds.

Measured on `b6f942f`, by running it:

```
snapshot keys        said 19    measured 21
as_dict fields       said 30    measured 30
NOT_ON_THE_CONSOLE   said 15    measured 15
```

Two of the three counts in that paragraph are right, which is the reason to fix the third by
**deriving** it rather than retyping it: a typed count is right until the next key, and this
paragraph has already proved it can carry both.

### 4. A guard's message says the console renders; the guard checks that a token appears

`tests/test_server.py:1360-1366`:

```python
page = _console_code()
unreached = [key for key in snapshot
             if not re.search(r"\b%s\b" % re.escape(key), page)]
assert unreached == [], f"the server sends these and the console renders nothing for them: {unreached}"
```

The check is that the key's token occurs somewhere in the console's code. The message says the
console **renders** nothing for them. A key named in a `const` and never drawn passes this guard
and is described by its failure message as impossible.

This is the shape CHG-20260907-28 corrected in its own guards, and the comment three lines above
this assertion already records a version of it: a key named only in a comment once reached no front
end and this passed.

## What ships

- `docs/API.md`: the blanket sentence names its exception. The three `/config/*` POSTs are
  documented with the four keys they answer.
- `docs/API.md`: `known` is marked as built and read by nothing, the way this page already marks
  `assignable` and per-assignment provenance, so the inventory of what ships unread stays in one
  place.
- `tests/test_server.py`: the snapshot-key count in the `NOT_ON_THE_CONSOLE` preamble is derived
  from `RunState().snapshot()` instead of typed.
- `tests/test_server.py`: the assertion message says what the assertion checks — that the token
  never appears in the console's code — and the guard's docstring says what it therefore cannot
  catch.

## What this does not do

- No route changes what it answers, and no console changes what it draws.
- It does not make `known` read, or delete it. Whether an unread key should ship is the question
  CHG-20260907-28 left open for `assignable`, and answering it for one nested key alone would
  decide it for the other by accident.
- It does not strengthen the guard from *appears* to *renders*. That needs a renderer to ask, which
  is the view CHG-20260907-28 names and no record has built.
