## The finding

`server.py` spells the loopback boundary twice, four lines apart:

```
LOOPBACK       = ("127.0.0.1", "::1", "localhost")           what serve may bind
LOOPBACK_HOSTS = frozenset({"127.0.0.1", "localhost", "[::1]", "::1"})   what a header may say
```

Read by different code for different questions:

```
serve              if host not in LOOPBACK              the bind address
_loopback_host     host.lower() in LOOPBACK_HOSTS       the Host header, brackets KEPT
_loopback_origin   host in {h.strip("[]") for h in ...} the Origin header, brackets STRIPPED
```

Two names is the right shape - a bracketed `[::1]` only means anything in a header. But where
they overlap they must agree, and **nothing required it**. No test named either constant;
every mention outside `server.py` is a historical record.

## What nothing caught

Removing one member of `LOOPBACK_HOSTS` at a time, and asking what says so:

```
removed      who objects
127.0.0.1    test_a_cross_origin_request_is_refused
localhost    test_our_own_origins_are_still_accepted[http://localhost:8765]
[::1]        nothing at all -- the file's 127 tests all passed
::1          nothing at all
```

`"[::1]"` is the member `_loopback_host` looks up for a server bound to `::1`, because it keeps
the brackets. Nothing required it to be there. And in the other direction:

```
LOOPBACK = ("127.0.0.1", "127.0.0.2", "::1", "localhost")
     tests/test_server.py:   127 passed
```

`127.0.0.2` is loopback on Linux and on Windows, the two this repo's CI runs. The server binds
it, the browser sends `Host: 127.0.0.2:8765`, and the request is refused as foreign - a server
that will not answer at the address it is listening on, blaming the request.

## The first draft was refuted, by both seats independently

The test shipped for review compared the two constants as **sets**:

```python
bare = {host.strip("[]") for host in server.LOOPBACK_HOSTS}
addr.lower() in server.LOOPBACK_HOSTS and addr in bare
```

Both seats read `_loopback_host` and said the same thing: it keeps the brackets, so the string
it looks up for a bound `::1` is `"[::1]"`, while `_loopback_origin` gets `"::1"` out of
`urlsplit`. **One bound address is two different lookups**, and no membership test over one
normalisation models both. Measured: with `"[::1]"` deleted, the set version passed and so did
the whole file - the exact hole the test was written to close.

The tests now call the two functions with the authority a client would send. That costs
nothing and models nothing.

## The reverse direction, which the first draft declined for a bad reason

The first record said the reverse must not be asserted because `[::1]` is header-only. Both
seats pointed out that this refutes only the **literal** reverse. Normalised, the two sets are
equal today:

```
{h.strip("[]").lower() for h in LOOPBACK_HOSTS} == {a.lower() for a in LOOPBACK}   True
LOOPBACK_HOSTS with "runner.local" added:   tests/test_server.py 128 passed
```

That direction is not about reachability, it is the rebinding surface: a name this server
accepts for a socket it will never listen on. `LOOPBACK_HOSTS`' own comment calls anything
else *"a rebinding attempt or a proxy"*. It is asserted now, with a message saying what to do
if a header-only alias is ever deliberate.

## Measured and filed, not fixed here: `::1` cannot be bound at all

Raised by the seat that could run things. `ThreadingHTTPServer.address_family` is `AF_INET`
and `serve` does not change it:

```
AF_INET bind    127.0.0.1         ok
                localhost         ok  (resolves to 127.0.0.1)
                127.0.0.2         ok
                ::1               gaierror [Errno 11001] getaddrinfo failed
                ::ffff:127.0.0.1  gaierror
```

So `LOOPBACK` names an address `serve` cannot listen on, and the `OSError` branch reports it
as *"Something is already there"* - a resolution failure told as a port conflict. `cli.py`
never passes `host`, so production binds `127.0.0.1` and this is latent. It is a production
defect in a different constant's direction and gets its own record; this one does not touch
`src/`. The claim in this record's first draft that `::ffff:127.0.0.1` is *"the same story"*
as `127.0.0.2` was wrong for the same reason - it never reaches the header check.

## What ships

Two tests in `tests/test_server.py`:

- `test_every_address_the_server_binds_is_accepted_as_a_host` - for each address in `LOOPBACK`,
  the authority a client would send (`[addr]` for an IPv6 literal), through `_loopback_host`
  with and without a port and through `_loopback_origin` on both schemes
- `test_no_host_is_accepted_that_the_server_would_not_bind` - normalised reverse containment

## Follow-ups this names rather than answers

- `LOOPBACK_HOSTS` is mechanically derivable, and the derivation is measurably equal today:
  `frozenset(LOOPBACK) | {f"[{a}]" for a in LOOPBACK if ":" in a} == LOOPBACK_HOSTS` is `True`.
  Deriving it would make both rules here unfalsifiable rather than checked, which is the better
  end state; it changes production code, so it is a separate record and not this one.
- `::1` in `LOOPBACK` against an `AF_INET` server, above.
