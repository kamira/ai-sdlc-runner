## The finding

`server.py` spells the loopback boundary twice, four lines apart:

```
LOOPBACK       = ("127.0.0.1", "::1", "localhost")     what serve PERMITS as a bind argument
LOOPBACK_HOSTS = frozenset({"127.0.0.1", "localhost", "[::1]", "::1"})  what a header may say
```

Read by different code for different questions:

```
serve              if host not in LOOPBACK              the bind argument
_loopback_host     host.lower() in LOOPBACK_HOSTS       the Host header, brackets KEPT
_loopback_origin   host in {h.strip("[]") for h in ...} the Origin header, brackets STRIPPED
```

*Permits*, not *binds*: see the filed defect below - one member cannot be bound at all. Two
names is the right shape, since a bracketed `[::1]` only means anything in a header. But where
they overlap they must agree, and **nothing required it**. No test named either constant; every
mention outside `server.py` is a historical record.

## What nothing caught

Removing one member of `LOOPBACK_HOSTS` at a time, and asking what says so:

```
removed      who objects
127.0.0.1    test_a_cross_origin_request_is_refused
localhost    test_our_own_origins_are_still_accepted[http://localhost:8765]
[::1]        nothing at all -- the file's 127 tests all passed
::1          nothing at all
```

The last two rows are not the same row. `"[::1]"` is what `_loopback_host` looks up for a
server on `::1`, because it keeps the brackets, and nothing required it to be there - that is
the hole. The bare `"::1"` is **unreachable by any compliant request**, and is meant to have no
guard:

```
Host: [::1]        looks up '[::1]'     accepted
Host: [::1]:8765   looks up '[::1]'     accepted
Host: ::1          looks up ':'         refused
Host: ::1:8765     looks up '::1'       accepted   <- an unbracketed IPv6 authority, which
                                                      RFC 7230 5.4 does not permit and no
                                                      client sends
```

and on the other side, `_loopback_origin` looks up `{127.0.0.1, localhost, ::1}` - the
bracketed member already strips to the bare form, so the bare member adds nothing there.
Removing it leaves the file green after this change too (129 passed), and that is correct.

In the other direction:

```
LOOPBACK = ("127.0.0.1", "127.0.0.2", "::1", "localhost")
     tests/test_server.py:   127 passed
```

`127.0.0.2` binds on Windows, measured here; on Linux it is loopback because `lo` carries the
whole of 127.0.0.0/8, which is read and not measured. Those are the two platforms CI runs. The
server binds it, the browser sends `Host: 127.0.0.2:8765`, and the request is refused as
foreign - a server that will not answer at the address it is listening on, blaming the request.

## The first draft was refuted, by both seats independently

The test shipped for review compared the two constants as **sets**:

```python
bare = {host.strip("[]") for host in server.LOOPBACK_HOSTS}
addr.lower() in server.LOOPBACK_HOSTS and addr in bare
```

Both seats read `_loopback_host` and said the same thing: it keeps the brackets, so the string
it looks up for a permitted `::1` is `"[::1]"`, while `_loopback_origin` gets `"::1"` out of
`urlsplit`. **One address is two different lookups**, and no membership test over one
normalisation models both. Measured: with `"[::1]"` deleted, the set version passed and so did
the whole file - the exact hole the test was written to close.

The tests now call the two functions with the authority a client would send. That costs nothing
and models nothing.

## The reverse direction, which the first draft declined for a bad reason

The first record said the reverse must not be asserted because `[::1]` is header-only. Both
seats pointed out that this refutes only the **literal** reverse. Normalised, the two sets are
equal today:

```
{h.strip("[]").lower() for h in LOOPBACK_HOSTS} == {a.lower() for a in LOOPBACK}   True
LOOPBACK_HOSTS with "runner.local" added:   tests/test_server.py 128 passed
```

That direction is not about reachability, it is the rebinding surface: a name this server
accepts for a socket it will never be asked to open. `LOOPBACK_HOSTS`' own comment calls
anything else *"a rebinding attempt or a proxy"*.

Asserting **equality** was one seat's proposal, and it withdrew it on measuring: normalised
equality still holds with `"[::1]"` deleted, so it is blind to the bracket split this change
exists to hold. Behaviour forwards plus containment backwards is strictly stronger.

## Measured and filed, not fixed here: `::1` cannot be bound at all

Raised by the seat that could run things. `ThreadingHTTPServer.address_family` is `AF_INET` and
`serve` does not change it. Measured on Windows:

```
AF_INET bind    127.0.0.1         ok
                localhost         ok  (resolves to 127.0.0.1)
                127.0.0.2         ok
                ::1               gaierror [Errno 11001] getaddrinfo failed
                ::ffff:127.0.0.1  gaierror
AF_INET6 bind   ::1               ok
```

So `LOOPBACK` names an address `serve` cannot listen on, and the `OSError` branch reports it as
*"Something is already there"* - a resolution failure told as a port conflict. `cli.py` never
passes `host`, so production binds `127.0.0.1` and this is latent. It is a production defect and
gets its own record; this one does not touch `src/`.

Two consequences for the words used here, both caught by the seats after the first rewrite:
`LOOPBACK` is a **permit list**, not a list of addresses this server binds, and the draft's
claim that `::ffff:127.0.0.1` was *"the same story"* as `127.0.0.2` was wrong - it never reaches
the header check, because it never binds.

## What ships

Two tests in `tests/test_server.py`:

- `test_every_address_the_bind_list_permits_is_accepted_as_a_host`, a name removed in
  CHG-20260907-24 and replaced by
  `test_the_derived_table_answers_both_lookups_for_any_address_it_is_given` - for each address in
  `LOOPBACK`, the authority a client would send (`[addr]` for an IPv6 literal), through
  `_loopback_host` with and without a port and through `_loopback_origin` on both schemes. The
  follow-up named below derives `LOOPBACK_HOSTS` from `LOOPBACK`, which turns that check into a
  tautology over the constant, so the replacement asks the same two functions about a bind list
  the constant does not have
- `test_no_host_is_accepted_that_the_bind_list_does_not_permit` - normalised reverse containment,
  a name removed in CHG-20260907-21 and replaced by
  `test_the_header_set_is_the_bind_list_plus_the_one_name_a_standard_fixes`, itself removed in
  CHG-20260907-24 because deriving the header set turned that equality into a tautology, the
  containment having been named for the wrong reason in the first place.

## Tests

Five mutations in `loopback`: an alias added to the bind list, the bracketed IPv6 form dropped,
the header set tightened, the bind list shortened, and a non-permitted name accepted. The second
was **NOT CAUGHT** by the first draft of the test, which is why it is registered.

A sixth was proposed and **refused on measurement**: removing the bare `"::1"` is caught by
nothing, and should be, for the reason set out above. A mutation nothing can catch is not
coverage to add - it is a claim that a dead member is load-bearing.

## Follow-ups this names rather than answers

- `LOOPBACK_HOSTS` is mechanically derivable, and the derivation is measurably equal today:
  `frozenset(LOOPBACK) | {f"[{a}]" for a in LOOPBACK if ":" in a} == LOOPBACK_HOSTS` is `True`.
  Deriving it would make both rules here unfalsifiable rather than checked, which is the better
  end state; it changes production code, so it is a separate record. That record should know
  that the two functions' bracket handling is *already* unfalsifiable while both forms sit in
  the table: swapping either function's normalisation for the other's changes no test.
- `::1` in `LOOPBACK` against an `AF_INET` server, above.
