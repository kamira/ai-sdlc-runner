## The veto: exclusive creation was not the lock

`begin()` creates its record with `"x"`, and CHG-20260830-05 recorded that as *"a second run is
refused rather than overwriting the first one's way back"*. It was not.

`mutation_check.main()` calls `recover()` **before** its first `apply()`. So a second run deleted the
first one's record on the way in, and then created its own uncontended. Measured, with a real second
process:

```
A holds lock; file is 'MUTATED\n'
B recover() said: restored victim.py, which a killed run left mutated
file is now      : 'ORIGINAL\n'   <- A is still running
A sentinel exists: False
```

Two wrong results, both concrete. A's tests then measure **unmutated** source, so A reports
`NOT CAUGHT` for a mutation its tests do catch — the same false reading that started this whole
sequence. And A's `finally: restore()` calls `end()`, which unlinks **B's** record, so a kill of B
afterwards strands B's file with nothing saying how to put it back.

The test carrying the claim called `begin()` twice in one process: the path no real second run takes.

### What the record needed, and did not have

An owner. *"A killed run left this file mutated"* and *"another run is mutating this file right
now"* are identical on disk, and the recovery that is right for the first is a corruption of the
second. So `begin` records `os.getpid()`, and `recover` refuses while that pid is alive.

Recovery is **not** moved behind a flag, which was the other way to close this. Recovery at startup
is the guarantee on Windows, where a kill becomes `TerminateProcess` and no handler fires; putting
it behind `--recover` would have closed this hole by giving that up. A dead owner still recovers
automatically, exactly as before. `--recover` exists as well, for the refusal cases.

`_alive` does not use `os.kill(pid, 0)`. On Windows `os.kill` calls `TerminateProcess` for every
signal but the two console events, so the liveness probe would kill the run it is asking about.

## The rule that was a keyword match

The survey that replaced the hand count — test_every_recorded_os_error_goes_through_plain_in,
named in plain text because this change renames it — got the number wrong the same way. Its
filter was `"exc" in ast.unparse(argument)` — a name standing in for a constraint, in the change
about names standing in for constraints. Measured over `src/`, three appends fell inside the rule's
own stated scope and it examined **one**:

```
conversations.py:975   append(f'...{paths.plain_in(str(exc))}') -> examined
conversations.py:1114  self.write_errors.append(note)           -> skipped
engine.py:1549         report.store_errors.append(note)         -> skipped
```

Both skips are the same cause: the argument is a variable, so the substring `exc` is not in it. The
first of them is one of the two sites CHG-20260828-24 fixed — the rule did not police the sites it
was written for. Renaming `exc` to `err` would have defeated it as well.

It now compares against the name the **handler bound** — `except OSError as err` makes the rule look
for `err` — rather than against the literal `exc`. That is still a name; the difference is that it is
the name the code under test chose, so no rename can slip past it. And it has a
floor: `test_the_rule_finds_the_violations_it_claims_to_find` holds it against fixtures that break
the rule in each shape, and against the corrected forms it must not flag. Without that floor a
survey passes by examining nothing — which is what the first one did.

  have is a **refusal** to recover after a pid has been reused, which leaves the tree wrong and says
  so loudly. The failure it removes was silent.
