## Read this first

`effects.py`'s module docstring states the rule this repository's crash-safety rests on:

> **a probe must describe the postcondition, not the action.** "did we run push?" is a receipt
> question and cannot survive a crash; "does the remote have this branch?" is a postcondition and
> can.

`branch_on_remote` is the push probe, and its docstring quotes that second phrase as its own
description. The trouble is that *"does the remote have this branch?"* is not the push's
postcondition either. The postcondition is that the remote has **what was committed**.

```python
proc = _run(["git", "ls-remote", "--heads", remote, branch], cwd=repo)
...
return bool(proc.stdout.strip())
```

`ls-remote` returns the SHA. The probe throws it away:

```
raw: 'a996199f3970f01fb2e02d0ad3c8fae6c38b7434\trefs/heads/main'
the probe keeps: bool(...) -> True
the SHA it discards: a996199f3970
```

## The second probe, found while re-measuring the first

`commit_exists_for` decides whether a change has been committed:

```python
argv = ["git", "log", "--fixed-strings", f"--grep={needle}", "--format=%H"]
...
return bool(proc.stdout.strip())
```

`git log --grep` searches the **whole message**, body included. Citing another change in a commit
body is this repository's normal way of explaining a reversal or a supersession. Measured on
`origin/main`:

```
total commits                                          378
commits whose body cites an id not in their own subject 232
distinct ids cited in some body but never in any subject 63

   ACC-20260617-01   subject hits 0   commit_exists_for -> True
   ACC-20260617-02   subject hits 0   commit_exists_for -> True
   ACC-20260617-03   subject hits 0   commit_exists_for -> True
```

So 63 ids read as already committed on this repository today. And the window is not historical -
measured live, in this session's own work:

```
a46de7b   09-05 17:36   CHG-20260905-03 …   its body cites CHG-20260905-05
a996199   09-06 02:32   CHG-20260905-05 itself lands
```

For those nine hours `commit_exists_for(repo, "CHG-20260905-05")` answered `True` for a change with
no commit at all.

**What that costs is the module's own justification.** `probes.py` says the id is *"what makes a
commit findable by intent rather than by hash"*. A citation is not the cited change's commit. Worse,
the engine's post-apply re-probe is the only thing enforcing "every commit carries its id" - and a
body citation anywhere in history turns that refusal into a pass, so a commit carrying **no** id can
land and then be pushed. The `fable` seat drove that: a plan message without the id, an older body
citing it, and the run finishes with a commit nobody can find by intent; the control, an id nothing
cites, halts with `EffectError` as it should.

The fix reads the **subject**. `--grep --fixed-strings` stays as git's prefilter — it cannot admit
anything the subject check then rejects, and dropping it would read the whole log into Python on
every resume. `%s` is git's folded first paragraph, so an id wrapped onto the subject's second line
is still found.

## What changes

`branch_on_remote` becomes an exact tip comparison:

1. resolve the local branch with `git rev-parse --verify refs/heads/<branch>`;
2. query the live remote with `git ls-remote --heads <remote> refs/heads/<branch>` - the full ref,
   so a branch whose short name is ambiguous cannot answer for another;
3. return `False` when the remote ref is absent;
4. return `True` only when the remote SHA equals the local SHA;
5. raise `ProbeError` for an unreachable remote, an unresolvable local branch, or output that does
   not parse as one `<sha>\t<ref>` record.

`ship.py`'s `push` postcondition string changes from `"{remote} has {branch}"` to name the tip.

## The new behaviour, stated because it is new

**A remote that is ahead of, behind, or divergent from local reads `False`.** The ordinary
non-force push is then attempted: a remote that is merely behind fast-forwards, and a remote that is
ahead or divergent rejects the push, `_git` raises `ShipError`, and the run halts.

That is the correct outcome and it is written down here rather than discovered: a remote someone
else has moved is evidence that needs reconciling, not permission to overwrite. The probe must not
treat ancestry as equality — `ls-remote` gives a SHA and nothing else, so guessing whether the
remote's tip contains ours would be a second false green.

## Checked against everything that pins this probe

| pinned case | before | after |
|---|---|---|
| absent, then pushed | False, then True | unchanged |
| deleted upstream while the tracking ref is stale | False - the live remote is asked | unchanged |
| unreachable remote | raises `ProbeError` | unchanged |
| D6's worked example - killed between push and PR | met, only the PR re-runs | unchanged: the tips are equal |
| a completed run re-run | no-op | unchanged while the tips stay equal |

## The test that should have caught this restates the defect

`tests/test_kill_resume.py::test_killed_between_push_and_pr_the_resume_creates_only_the_pr`:

```python
assert probes.branch_on_remote(repo, "feature") is True      # push landed
```

The comment says *push landed*. The predicate says *a branch of that name exists upstream*. The
assertion re-states the thing under test instead of reading it, so it agreed with the probe no
matter what the probe meant. It also never dirties the tree after the push, so `commit` never
becomes unmet and a second local commit is never created.

## Where the two engines differed

They agreed on the verdict, the fix and the refusals. Two details came from one seat only, and both
are in the change:

- **`codex`**: address the remote ref as `refs/heads/<branch>` rather than the short name, and raise
  on output that does not parse as exactly one record.
- **`fable`**: the `postcondition` string and the docstring's *"Does the remote have this branch?"*
  are part of the defect, not decoration, and must move with it.

`codex` could not run commands in this environment - a managed policy rejected every one, even under
a writable sandbox - and said so rather than adopting the measurement it was given. Its review is a
reading of the source; `fable`'s is a run. Recorded because it bears on how much each verdict
carries.

## What both refused

- **Weakening the commit probe** by dropping `working_tree_clean`. It hides the uncommitted work
  rather than pushing it, reverts `CHG-20260830-03`, and is pinned as a mutation.
- **Re-running every effect past the frontier.** Reverts the recorded "nothing already true is
  re-applied" decision and can open a duplicate PR.
- **Reading `refs/remotes/origin/*`.** A stale-ref test forbids it explicitly.
- **Force-pushing on a mismatch.** Turns evidence that needs reconciling into destroyed remote work.
- **Treating remote-ahead as complete.** Another false green, from a SHA that cannot prove ancestry.

## Two consequences of the fixes themselves, both measured rather than predicted

**Three registered mutations went stale.** Rewriting `branch_on_remote` broke the anchors of two
existing entries, and the `commit_exists_for` rewrite broke a third. The harness reported
`ANCHOR GONE` and said in its own words that this *"is not the same as caught"*. All three are
re-anchored onto the lines that carry the same properties now, rather than deleted.

**One existing test stopped discriminating what its docstring says it tests.**
`test_a_chg_id_is_matched_literally_and_not_as_a_pattern` pins `--fixed-strings` with the pair
`axb`/`a.b`. Once a literal Python `in` follows the grep, that pair passes with the flag deleted -
the prefilter finds the commit either way and the literal check rejects it either way. The `fable`
seat measured a needle that still discriminates, because the two disagree on the **prefilter**:
`^x` against a subject containing `^x` is found with the flag and not without it. That assertion is
added; the `a.b` pair stays as the literal-property check.

**And the first ordering of the new probe broke a test's subject.** Reading the local tip before
asking the remote made `test_an_unreachable_remote_is_not_reported_as_not_pushed` fail on the
*local* refusal rather than its own - the test never creates the branch locally. The remote is asked
first now, which is also the better shape: if the remote does not have the branch the answer is
`False` whatever the local tree holds.
