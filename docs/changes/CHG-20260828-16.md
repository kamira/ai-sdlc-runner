# CHG-20260828-16 — a git command whose output held an em dash came back empty, and reported success

- Project: ai-sdlc-runner
- Branch: claude/chg-20260828-16-name-the-codec
- Date: 2026-08-29 (UTC+0)
- Type: a guard that answered safe about something it never read
- Proposed by: two tests failing on `main`, on a machine whose locale is not UTF-8
- Risk: **medium** — it touches every subprocess this project runs, including the agent dispatch
- Autonomy: high
- Related: CHG-20260823-47 (which set the environment variable that hid this from the mutation
  harness), CHG-20260828-06 (whose id-collision guard was one of the two silenced)

## The gap

`subprocess.run(..., text=True)` decodes the child's output with **the caller's locale codec**, not
UTF-8. On this machine that is `cp950`. Given the UTF-8 bytes for an em dash it raises — inside the
reader thread, which is not the calling thread:

```
Exception in thread Thread-3 (_readerthread):
UnicodeDecodeError: 'cp950' codec can't decode byte 0xe2 in position 6
```

`subprocess.run` does not fail. It returns:

```
stdout : None    returncode 0
```

**A successful call with no output.** Every caller checks the return code and sees `0`.

## What it silenced

`ledger_check._at()` — *"a file's content at a git ref, or `None` if the ref or the file is not
there"*:

```python
return done.stdout if done.returncode == 0 else None
```

`None` means *no baseline to compare against*, and `check_ids_are_not_claimed_twice` treats no
baseline as nothing to report. So the id-collision guard **passed without checking** — and it did so
precisely when the change titles contain an em dash, which every title in this repository does.

The same shape is in `cli.py`, where the runner reads an agent's reply: a reply the locale cannot
decode arrives as `None` with `returncode 0`. Not a crash, not a refusal — an answer that isn't
there.

`worktree.py` shows the other half of the story. It reads `(done.stdout or "")` in four places,
defending against a `None` somebody clearly met, at the reading end rather than at the cause.

## It is not hypothetical

`main` is red on this machine. Two tests, and the second one is the test for the fix in
`session_record.py`:

```
FAILED tests/test_ledger_check.py::test_a_second_change_taking_a_taken_id_is_refused
FAILED tests/test_recording.py::test_a_multibyte_character_split_across_two_reads_survives
2 failed, 1599 passed, 4 skipped
```

Both pass with `PYTHONUTF8=1` and fail without it. **Whether this suite passes depends on an
environment variable nobody in this project sets.**

## The lesson was already here, in one file

`tools/session_record.py` decodes by hand and says why:

> `errors="replace"` and an explicit codec, because `text=True` alone decodes with the caller's
> locale and this repository's own messages are full of em-dashes.

Fixed there, in none of the other eleven call sites, and not completely even there — see below.

## The change

**Eleven call sites** in `src/` and `tools/` now name their codec:

```python
text=True, encoding="utf-8", errors="replace"
```

`encoding` is the correctness half — git and the agents emit UTF-8. `errors="replace"` is the
robustness half: a stray byte must not be able to kill a reader thread and turn a failed read into a
silent success. `tools/frozen_tree.py` already had both and was left alone.

**`session_record.py` asks the child to write what it reads.** It decoded UTF-8 while doing nothing
to make the child produce UTF-8 — a Python child on Windows writes its stdout in the machine's ANSI
codepage, so every non-ASCII character arrived as `�`: decoded without error, wrong in every glyph,
and indistinguishable from the chunk-boundary corruption that file's own test exists to catch. It
now sets `PYTHONIOENCODING=utf-8` alongside the `PYTHONUNBUFFERED` it already set, for the same
stated reason.

**The agent is told which codec the order is written in.** This one the suite found: naming UTF-8 on
the parent's side changed the bytes on the wire, and
`test_the_order_reaches_the_backend_deterministically_serialised` went red — `972 == 969`. The child
was reading its stdin in the locale codec, so the CJK in the order's `role_label` arrived as six
characters where three were sent. No error anywhere; an agent answering a question subtly different
from the one asked. The dispatch now passes `PYTHONIOENCODING=utf-8`, the same fix as the recorder,
in the one place where the child is a real agent rather than a test.

**A test that reads the syntax tree**, because eleven sites fixed by hand is a twelfth waiting to be
written. Anything under `src/` or `tools/` that starts a process in text mode without an `encoding`
fails the suite. Same argument as `graph.module_cycle()`: a hand-maintained list stays
correct-looking while the thing it describes moves.

## The mutation harness ran every mutation in a locale no ordinary run has

`tools/mutation_check.py` passed `PYTHONUTF8=1` to every pytest it started, added by
CHG-20260823-47 to get pytest's own output down the pipe. It worked, and it did more than that:
`PYTHONUTF8=1` also makes `locale.getpreferredencoding()` return UTF-8 **inside the suite**, which
is what `subprocess`'s text mode reads.

So the harness could not pin any guarantee about decoding — reverting the fix left the tests green.
It now sets `PYTHONIOENCODING=utf-8`, which fixes the pipe and leaves the locale alone. Measured,
not assumed:

| switch | `getpreferredencoding()` | `sys.stdout.encoding` |
|---|---|---|
| `PYTHONIOENCODING=utf-8` | `cp950` | `utf-8` |
| `PYTHONUTF8=1` | `utf-8` | `utf-8` |

The recording test clears both variables itself now. A test that inherits them is asserting
something about whoever ran it.

## I wrote the defect this change is about, into the guard against it

The first draft of the source check flagged any call passing `text=`. It reported three sites in
`conversations.py` — `self.turn(INSTRUCTION, nth=nth, text=text)`, a keyword that happens to be
spelled `text` on a method with no child process anywhere near it.

**Matching a name and calling it a constraint** is this repository's most-repeated finding, and I
put it in the file whose subject is a guard that never looked. Keying on the callee does not work
either: `worktree.py` calls `run(...)` where `run` is a parameter defaulting to `subprocess.run`.
The rule now requires a text switch **and** a keyword only a process launcher takes. Both the false
positive and the indirect call are pinned by their own tests.

## Risk & rollback

- It changes how **every** subprocess in the project decodes, including the agent dispatch. The
  decode is strictly wider than before: everything the locale codec could read, UTF-8 with
  `errors="replace"` also reads, and it additionally reads what the locale codec could not.
- Changing the harness's environment variable makes mutations run in the ordinary locale. That is
  the point, and it is also the risk: a mutation that only ever passed because of `PYTHONUTF8=1`
  would now show up. The full group was re-run and all five are caught.
- Rollback: drop the two keyword arguments. The guards go quiet again on non-UTF-8 locales.

## Status

**Accepted** — see [ACC-20260828-16](../acceptance/ACC-20260828-16.md).

### Not claimed

**That this is the only place a locale leaks in.** Only `subprocess` was surveyed, on the syntax
tree. File reads in this repository pass `encoding="utf-8"` explicitly, which is why nothing else
surfaced, but that was checked by reading and not by exercise.

**That CI would ever have caught it.** It would not. GitHub's Windows runners are `cp1252`, which
decodes those bytes without raising — into different characters. The guard fails differently there:
it compares mangled text against text read as UTF-8, rather than skipping. Green on both runners,
and reading the wrong thing on one of them.

**That a non-Python child can be made to emit UTF-8.** `PYTHONIOENCODING` reaches Python children
only. `errors="replace"` keeps a non-Python child's ANSI output from killing the read; it does not
make that output correct.
