## Why there is a console at all

The runner works and cannot be operated. Running it today means writing a JSON plan by hand,
watching stdout, and answering a gate by re-running the whole command with `--confirm`. Three things
the requirement asks for have no surface at all:

| The requirement | Today |
|---|---|
| 使用者輸入指令 | there is no input — you write `plan.json` |
| PM 確認方案 | answered by the dispatched agent, never by a person |
| 在 GUI 上設定 | `runner settings` is a curses menu for two fields |

An end-to-end run was done by hand to establish that the flow itself is sound before designing a
surface for it: 19 nodes, 14 asks, stopped at `merge`, resumed after a killed session re-asking only
the pending question, and refused a `git push origin +main:main` declared `ordinary`. The engine is
not what is missing.

**The mock-up:** https://claude.ai/code/artifact/2e387693-6720-4d06-a803-62cfc8e8d0a7 — interactive,
built on the real 23 nodes, 10 gates and 4 seats.

## The screen

Four things, and deliberately nothing else on the main screen:

1. **An instruction box.** Free text, plus **attachments** — a spec, a flow mock-up, a screenshot.
   Attachments become `input_artifacts` on **every** node's work order, so the reviewer reads the
   same spec the engineer built from.
2. **Where the run is.** Six phases (Plan → Assess → Build → Review → Verify → Ship), the current
   one lit, the exact node id beside it, one word of state: running / waiting / stopped / done.
3. **The whole flow**, every node, each showing its role and which model will answer it.
4. **The agent log** — the main content. Every ask: who, which model, via CLI or API, how long, what
   it was asked, what it answered. **Agents, the sub-agents they dispatch, and every model voice are
   visually distinct**, because "an agent said so" and "the engineer the lead dispatched said so" are
   different claims.

Configuration lives on separate tabs: Project, Models, Node → models, Review panel.

## The four design decisions, and what each was corrected from

### 1 · Multi-model means two different things, and the node decides which

Initially every multi-model node was a panel. The user corrected it: a **coding** node has a
main → sub structure, and several models on the sub are **the pool the main may dispatch to** — one
of them does the work. Calling that a vote would have been wrong.

| Node kind | N models means | At run time |
|---|---|---|
| verdict (`lead_task_review`, `qa_accept`, `pm_confirm`…) | **N voices, adjudicated** | N sessions, blind to each other; veto → majority → tie |
| dispatch (`engineer_build`, sub of `lead`) | **a pool** | the main picks one **at random**; one does the work |
| follows (`engineer_selfverify`) | not selectable | whichever model built it |

**Random dispatch is deliberate.** Any cleverer rule is the runner deciding which model is better at
a task it has not seen, and it would quietly become a ranking nobody wrote down.

### 2 · A tie is not a failure — it is nobody deciding

Currently `policy.adjudicate` treats a tie as fail. The user's decision: a tie is **undecided**, and
undecided is a person's job. The console stops and asks, in short plain sentences:

> 2 said yes, 2 said no. Nobody has the casting vote, so the runner will not pick one. This is
> yours to call.

Both sides are shown with the reason each gave and which model gave it. Whichever the person picks
is recorded as their decision.

### 3 · An undecided panel may be re-run, and the re-run carries both sides

Configurable: on/off, and a limit. Each round is fresh sessions — but from round 2 every voice is
told **what every reviewer said last round, for and against, and which model said it.**

That was corrected twice. First it was a blind re-roll, which is close to useless: nothing new enters
the room. Then it carried only the objections — which the user identified as a thumb on the scale, a
reviewer shown three reasons to fail and none to pass is not being asked to weigh anything.

**The cost is anchoring** and it is accepted knowingly: a voice told codex objected may defer to
codex. The reason to accept it is that a panel which ties twice is short of *information*, not of
independence — the two sides never saw each other's reasoning.

The limit still ends at a person, now for a sharper reason: if they have read each other and still
cannot agree, another round will not help.

### 4 · A send-back leads with a summary and appends the originals

The lead writes it — it is the one dispatching the rework, so it is a real ask on the lead's model,
logged like any other. Three objections become three short items.

**The originals are appended to the same work order, below the brief, marked reference rather than
instruction.** Not behind an API call: an appendix nobody has to fetch is one they will not read at
the moment the summary looks wrong. Summarising is where an objection gets softened, and this
repository's entire recorded history is disagreement being flattened.

## The split

**Front end — any language.** Draws the flow, the position, the log. Collects the instruction, the
configuration and the gate answers. Holds **no** governance: never decides a verdict, never
adjudicates, never skips a gate. Closing the tab does not stop a run.

**Back end — the existing runner.** `policy.py` and `graph.py` unchanged. Owns every decision, halt,
adjudication, retry and record. Bound to **one project**. Holds the API keys — the registry stores an
environment variable *name*, never a secret, so a key cannot reach a screenshot or a bug report.

### The three things the engine must learn

| # | Change | Where | Why it is not cosmetic |
|---|---|---|---|
| 1 | **A gate blocks instead of exiting.** A new `Approver` the engine calls at a stopping verdict; the CLI passes one that refuses, the server one that waits. | `engine.walk` | This is the governance core. It is the one change that could break the halt guarantee, and it is why this record is high risk. |
| 2 | **Retries live in the dispatcher.** An attempt that never answers is a lost session — already handled. Retrying is the backend's job, and it is logged, so a run that took four tries does not read like one that took one. | `cli._Process` / the server's dispatcher | Not the engine's business; putting it there would make "one ask, one session" untrue. |
| 3 | **Any node can be a panel.** `engine._adjudicate` already does veto → majority for the seats. Multi-model on a node is the same call with a different set of voices. | `engine.walk`, `_adjudicate` | A generalisation of code that exists, not new governance — which is the only reason it is acceptable at all. |

Plus one policy change: **`adjudicate` gains an `undecided` outcome** where it currently returns
fail on a tie.

### Endpoints

`GET/PUT /project` · `GET/POST /models` · `DELETE /models/:id` (refused while a node selects it) ·
`POST /models/:id/test` · `GET/PUT /config/nodes` · `GET/PUT /config/panel` · `GET /flow` ·
`POST /attachments` · `POST /run` · `GET /run/events` (SSE) · `POST /run/gate` ·
`POST /run/decide` (break a tie) · `POST /run/resume` · `GET /run/objections/:node`

## Risk & rollback

- **Task 1 is the dangerous one.** Every halt in this system currently works by ending the process,
  which is crude and completely reliable. Making it wait introduces a state where the run is alive
  and stopped — and "alive and stopped" is where a bug can look like "alive and continuing".
- **Task 2 changes an existing rule.** `policy.adjudicate` returns fail on a tie today and there are
  tests asserting it. They are not wrong; the rule is being changed deliberately, and the tests must
  change with a reason written next to them, not because they turned red.
- **Task 4 is where a design error would be quiet.** A verdict node silently asking one model when
  the operator configured three is the exact class of failure this repo has shipped four times.
- Rollback: none of it is written yet.

## Status

**草稿 / draft — DESIGN ONLY. No task started. Nothing in `src/` implements any of this.**

The mock-up is a front end with no back end: it simulates the flow in the browser so the interaction
could be judged before anything was built. It is not connected to the runner and does not pretend to
be.

### What is settled

The four decisions above, each corrected by the user at least once during the session, and each
recorded with what it was corrected *from* — because the earlier version is usually the more
instructive half.

### What is not settled

- **The pool's retry behaviour.** If a dispatched model fails its retries, does the main pick a
  different one from the pool, or does the question stay pending on the same one? Not decided.
- **A work-producing node with several models and no main/sub structure** (`pm_plan`, `qa_verify`,
  `pr`) would mean several candidate outputs and no rule for choosing. The mock-up flags it rather
  than inventing a rule.
- **Whether the console should show a run it did not start.** One project, one runner — but two
  browsers on the same runner is not addressed.

### Not claimed

**Acceptance.** Nothing to accept: no code. When implementation begins it needs its own confirm gate
under the `Autonomy` field above, and the tasks are unticked until each one's done-when is met and
demonstrated — not when it is written.
