## Three findings, and what they actually are

Reported by the **defect seat** (`fable`) in round thirteen as L-3, L-4 and L-5, and by the **risk
seat** separately for the journal half. Both engines then reviewed them independently.

`codex` framed them as *"one change record, three defects in one state machine"*. The second
`fable` seat improved on that and I take its framing:

> Not three defects in one state machine. **Two definitions of one count, plus one journal defect
> that intake merely happens to expose.**

- The server's definition (CHG-20260904-05): a stop is an ask **when the operator did the
  supplying act** — `told > mark`.
- The command line's definition (CHG-20260901-17): a stop is an ask **per stopping invocation**.

Those already disagreed before either was touched. L-3 and L-5 are each one writer failing *its
own* definition. And L-4 is not about the count at all: the same shape was measured **outside
intake** — a `pm_confirm` answer naming no branch is journaled, replayed on `--resume` with nothing
dispatched, and refused again. `read_options` is one instance of a class, and this closes it there
first.

## L-3, measured end to end through the real CLI

```
            before                          after
plain 1..5  stops 1,2,3,4,5                 stops 1,2,3,4,5
--resume    stops 6, 7, 8                   stops 5, 5, 5
```

Each of those three resumed runs printed *"4 ask(s) answered from the journal, not re-asked"* in
the same output that advanced the count. **The run said nobody was asked and counted it as an ask
in the same breath.**

`codex` asked for CHG-20260901-17's table to be explicitly superseded. Measured on the repaired
tree, it does not need to be: those five invocations carry no `--resume`, `already` is populated
only inside `if cfg.resume:`, so the seats were asked each time and each stop was a real one. The
table survives untouched.

The discriminator is `len(report.resumed) < len(report.asks)`. `report.resumed` is appended at the
**reuse decision** rather than on journal membership — CHG-20260901-14 is the record of fixing
exactly that. And at an incomplete intake stop `report.asks` is exactly the survey's asks plus any
option ask, because `intake_review` is the first asking node and nothing routes a rejection back
to it.

`cli.py`'s writer had **no executable pin at all** before this change:
`test_the_command_line_can_reach_the_escalation_it_documents` drives `AskJournal` directly and
never calls `cmd_run`.

## L-5, and why `-1` rather than the alternative

`POST /run/instruct` refuses an empty instruction — *"an empty instruction says nothing"*.
`POST /run` accepts one, builds `instructions=[]`, and then `told > mark` is `0 > 0`. The first
stop went uncounted and every later count was one short for the life of the run.

That made CHG-20260904-05's own **task 3** — *the first stop is always an ask* — false whenever a
run began on nothing, which is what the console's start button sends with an empty box.

Three candidate repairs, and only one survives:

| candidate | verdict |
|---|---|
| `>=` | reverts CHG-20260904-05: every attachment would count |
| `or not self.intake_history` | **identical counts to `-1` over every sequence** — and under it CHG-20260904-09's mutation stays **green**, turning an existing guard into a test that cannot fail |
| `mark = -1` | implements CHG-04-05 task 3 and keeps -09's guard able to fail |

The middle row is the one worth recording. Two repairs can be indistinguishable in behaviour and
still differ in whether the suite can tell they were reverted.

Refusing an empty instruction at `start` was measured and rejected: it changes a documented
contract (`API.md`: `{version, instruction?}`), and it does not fix the attach-first run, where an
operator picks a file before typing anything and the count is still behind.

## L-4, and the half that matters to somebody already stuck

`_ask` wrote `journal.answered(...)` before any caller judged the answer. `read_options` refused
afterwards, so a model offering two options where three are required left a **reusable** record of
the thing that caused the refusal, and `--resume` replayed it — an option order does not carry the
brief, so it compares equal — and refused it again.

Measured on a server wired like `cmd_serve`: after one refused option answer, every later
`instruct` re-dispatched the seats and stopped, and **a brand-new run on the same process hit the
same file**, because the journal has no run id. It poisoned the process, not the run.

The repair validates at the **reuse decision**, not only before writing:

```
1. two options offered, three required   -> journaled `refused`, not `answered`
2. --resume, model now offers three      -> re-asked once, suspends with three options
3. a journal poisoned BEFORE this change -> re-asked once, suspends with three options
```

Row 3 is the point. Validating only before writing would fix new runs and leave every existing
journal a trap.

## One of mine, which only the mutation found

`refused-answer`'s first mutation came back **NOT CAUGHT** with 53 tests green. The reason:
`AskJournal.refuse` read the file `record` had written — status `pending`, no `result` — and its
own docstring said *"the result is kept rather than dropped"*. It was not. `answers()` requires a
`result`, so the poisoned-journal test wrote a payload nothing would ever reuse, and the test
meant to prove the reuse check was hollow.

A method whose comment claimed a behaviour it did not have, written **in the same round whose whole
subject is that defect**, and pinned by a test that could not fail. Two engines reviewed the plan
and neither saw it; the suite was green; only the mutation reported it.
