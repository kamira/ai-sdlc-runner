## What changed, precisely

Two readings were checked with the user rather than guessed, because each was worth over a thousand
files:

1. **"不留存任何 skill"** — the repo keeps no skill. Confirmed: delete `skills/` and `elements/`.
2. **Then where does the policy come from?** My first answer was "read the installed skill next
   door", and it was **wrong**. The user corrected it: *不是讀 skill,而是…建置自己的治理版本* —
   the skill's flowchart is a **design input**, not a runtime dependency. The runner **owns** its
   governance.

That second correction is the whole change. Until now this project's founding constraint was
"**read, don't re-implement**" (§8) and its FR-8 was "call the skill's `halt_gate.py`". Both are now
obsolete: there is no skill to read or call. The runner is not a driver for somebody else's
governance — **it is a governed agent in its own right, designed from the flowchart the skill
publishes.**

This is not a defect in the earlier work. CHG-20260617-05 and CHG-20260822-04 were right under the
old positioning; the positioning is what changed, and the code that served it goes with it.

## What the runner must now own

Everything the store used to supply, re-expressed as the runner's own — and shaped by the user's own
role model rather than the skill's thirteen roles, which was the source of the "9 of 13 cannot be
dispatched" gap that no longer needs solving:

| Owned | Was | Now |
|---|---|---|
| the flow | `references/autopilot-loop.md#state-machine`, pinned | `graph.py` — our definition, designed from that flow |
| roles | `agent-hierarchy.md`'s four-row table + `role_refs.json`'s thirteen | the five the requirement names: user, PM, lead, engineer, QA — plus review seats |
| capabilities | three booleans parsed out of a shipped table | our own, per role, and complete by construction |
| halt / risk policy | `halt_policy.json` + `autopilot_policy.json` + `halt_gate.py` | our own policy, with the same shape: risk × gate → auto / confirm / halt |
| review seats | `review_seats.json` | our own seats, count set by the user, floor enforced |

## Modification Guide

### Goal

`runner` drives the development flow the requirement describes, from its own governance definitions,
with no skill present anywhere — one independent session per ask, seats configurable above a floor
the user may lower only through an explicit high-risk mode.

### Global constraints (all tasks)

- **No skill content in this repo, and no skill read at runtime.** Not vendored, not referenced, not
  installed-and-read. The flowchart is a design input; the code is ours.
- **Every asking node is its own session**, opened per ask and closed after. Its tests stay green
  through the rewiring — it is the property most easily lost in a change this size.
- **One node, one kind of work.** The graph keeps that shape.
- No silent fallback anywhere: missing configuration is a hard error naming what is missing.
- Delete what loses its reason to exist. Nothing is kept "just in case"; history holds it.
- Verification bar: suite green; doc-integrity exit 0; the flow still runs end to end.

### Tasks

| # | Task | Interface / output | Done-when | State |
|---|------|--------------------|-----------|-------|
| 1 | Our own governance data | `policy.py`: roles, capabilities, risk × gate matrix, seats | every value the store used to supply has an owned definition, and a test proves none is missing | [ ] |
| 2 | Resolve verdicts from it | `gates`/`engine` read `policy.py`, no subprocess to any skill script | no code path shells out to a skill; the gate still halts where the policy says | [ ] |
| 3 | Roles from the requirement | five roles + seats, each with capabilities | every node in the graph dispatches a role that exists and can be rendered — no undispatchable node | [ ] |
| 4 | Work orders without elements | order carries objective, scope, done-criteria, verdict, capabilities; no skill text | a work order renders with no store and no element tree | [ ] |
| 5 | Delete the skill dependency | `skills/`, `elements/`, `skillstore`, `contract`, `decompose`, `dispatch`, the elements CI job | repo holds no skill content and no module that exists to read one | [ ] |
| 6 | Guideline, structure docs, knowledge | §1/§2/§5/§6/§8, FR-6/7/8/13, `directory.md`, `logical.md`, `design.md`, KN-1/2/5 | no document describes a dependency that is gone | [ ] |

### Risk & rollback

- Risk: **high**. It removes the project's founding constraint and roughly half its modules.
- Named failure mode: quietly keeping a skill-shaped dependency — a default path, a "if the store is
  there use it" branch. A test asserts no source file references a skill path.
- Second: losing session independence or the one-node-one-job shape while rewiring. Both keep their
  tests.
- Third: **re-implementing the skill's logic badly.** The mitigation is that we are no longer bound to
  match it — this is our governance, designed from the same flow, and its correctness is judged
  against the requirement rather than against a file we no longer have.
- Rollback: `git revert`. Everything deleted is in history.
