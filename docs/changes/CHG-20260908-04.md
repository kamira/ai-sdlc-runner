# CHG-20260908-04 — the directories pytest's own cleanup cannot remove

- Project: ai-sdlc-runner
- Branch: claude/chg-20260908-04
- Date: 2026-09-08 (UTC+0)
- **Measured against `origin/main` at `77b5c14`**, pinned by sha
- Type: defect fix in the suite's housekeeping. One fixture in `tests/conftest.py`, one `pytestmark`
  line in each of two modules. No source file and no assertion changed.
- Risk: **low** — a teardown that removes a per-test `tmp_path` and warns when what survives is past
  `MAX_PATH`.
- Autonomy: high
- Status: Done — see ACC-20260908-04

## What pytest cannot do

Two test modules build directory chains past `MAX_PATH` on purpose:

```
tests/test_paths.py                     4 chains, through `_deep` at 34, 47, 59, 226
tests/test_conversations_sqlite.py:483  1 chain, in
                                        test_a_store_past_max_path_still_reports_what_it_could_not_read
```

pytest keeps the last three basetemps and removes the older ones with `shutil.rmtree` on a **plain**
path. Measured, on a basetemp produced by running those two modules with this change's marks
removed:

```
                        top-level dirs   entries   deepest
the run leaves                      45       351   402 chars
plain shutil.rmtree     FileNotFoundError; 30 top-level directories survive
paths.real + rmtree     removed
cmd /c rmdir /s /q      exit 0, removed
```

So the claim is narrower than *"nothing can delete them"*, which the first build of this record
asserted in its title and a seat refuted in one command: `rmdir /s /q` removes them. **pytest's own
cleanup** is what fails, and it is the only thing that was ever going to try.

## What ships

`remove_deep_chains` in `tests/conftest.py` removes `tmp_path` through `paths.real` at teardown, and
**warns when what survives reaches past 259 characters**. Both modules opt in by name.

Named rather than autouse, because the second module was found by a sweep the first round of this
record had listed as *still open* — a fixture that quietly covered every module would have hidden
that a second one existed, and a third will now have to say so.

### The warning, and why it is not `ignore_errors` alone

The first build was `shutil.rmtree(..., ignore_errors=True)` and **both seats refused it**: a
removal that silently does nothing keeps every test green while the directories accumulate, which is
a guard that cannot fail — written into the repair for another defect, in a ledger whose last record
spent twenty-two rounds on that class. The running seat then measured the case: with
`test_sqlite_opens_at_that_depth` **failing** before `db.close()`, the open handle keeps the chain
alive and the removal leaves it.

A raise would be wrong — it replaces the real failure with a teardown error. The warning names the
path and its depth, survives a red test, and cannot be read as success. Measured in both directions:
with a handle held open under a 372-character chain it fires; with the handle closed the chain is
removed and it is silent.

**The warning's condition is narrower than "the removal failed", and the first draft of it got that
wrong.** Firing on any survivor produced 41 warnings on 48 tests of
`test_conversations_sqlite` — ordinary shallow directories held by open sqlite handles, which pytest
removes without trouble and which are not this fixture's business. It fires only when a survivor
still holds a path past `MAX_PATH`, because that is the one pytest will also fail on.

## What the shipped tree actually leaves

```
                        top-level dirs   entries   deepest
with the marks                      41        82   120 chars
```

Not zero, and the first build of this record said zero. Shallow directories still survive when a
handle is open, and that is correct: pytest removes those. What is gone is everything past
`MAX_PATH`, which is the whole claim.

## Sentences the first build made that measurement refuted

Kept here rather than deleted, per this ledger's convention:

- ~~*"nobody — not pytest, not Explorer, not `rmdir /s` — could delete"*~~. `rmdir /s /q` returns
  exit 0 and the directory is gone. Explorer was never measured by anyone and the claim is
  withdrawn rather than tested.
- ~~*"`os.walk` stops at 227 characters"*~~. Measured: plain `os.listdir` succeeds at 250 and first
  fails at 256.
- ~~*"the first attempt to count reported zero, and the reason is the defect"*~~. Plain `os.walk`
  returns 74–75 of 79–83 entries on such a tree; it does not report zero. Both zeros in that
  paragraph came from the same duller cause — a path written in the shell's `/c/…` form, which
  Python on Windows does not resolve — and the account that made them two different mistakes was
  tidier than what happened.
- ~~*"320-character chains"*~~. `_deep` stops at the first component boundary **at or past** 320, so
  the depth depends on the basetemp: 345, 359, 365 and 402 were all measured.
- ~~*"11.7s against 1.1s"*~~. Does not reproduce: 0.87–1.38s with the fixture against 0.66–0.82s
  without, and `--durations` shows no teardown above 0.01s.
- ~~*"each holding four of these chains"*~~. The stranded basetemps hold three from `test_paths` and
  one from `test_conversations_sqlite`; `test_the_plain_api_is_what_could_not_do_that` never gets a
  chain, because the plain `os.makedirs` it exists to fail at is what fails.

## What this does not do

- **It does not touch `src/`.** `git diff --stat 77b5c14 -- src` is empty.
- **It does not remove the directories already on the machine.** Removing them is an operator
  action; `rmdir /s /q` does it.
- **It does not stop a shallow directory surviving a test that leaves a handle open.** Those are
  pytest's to clean and it can.
