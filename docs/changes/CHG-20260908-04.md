## What was left behind, and why nobody could clear it

`tests/test_paths.py` exists to prove that this repository can write past `MAX_PATH`. Four of its
tests do that by building a **320-character directory chain** under `tmp_path`:

```
tests/test_paths.py:34   test_a_file_deeper_than_max_path_writes_and_reads_back
tests/test_paths.py:47   test_the_plain_api_is_what_could_not_do_that
tests/test_paths.py:59   test_sqlite_opens_at_that_depth
tests/test_paths.py:226  test_unlink_removes_a_deep_file
```

pytest keeps the last three basetemps and removes the older ones with `shutil.rmtree` on a **plain**
path — the exact call `paths.py` exists because of. Measured on this machine, on the tree before
this change, running that one file into a fresh basetemp:

```
                       top-level dirs   entries   deepest path
after the run                      39        44     351 chars
plain shutil.rmtree      WinError 3 — "the system cannot find the path specified"; the directory
                         is still there afterwards
paths.real + rmtree      removed
```

So every run of this file left a `pytest-N` directory that nothing on the machine could delete —
not pytest, not Explorer, not `rmdir /s`. Two were found outside pytest's retention, one per
full-suite run, each holding four of these chains.

**The count of four is measured, not read.** The item this record came from said three tests;
`test_unlink_removes_a_deep_file` also builds the chain and unlinks only the file inside it.

## The repair

An autouse fixture in that module removes `tmp_path` at teardown through `paths.real`, which is the
prefix that makes the removal possible and is what the module under test ships. Teardown rather
than a `finally` in each of the four, for the reason the file's own tests argue: a test that has
already failed should still clean up, and a fifth test that builds a chain tomorrow should not have
to remember.

`ignore_errors=True` because a test that never built a chain leaves an ordinary directory pytest
handles itself, and a teardown that raised would turn a green test red for a reason unrelated to it.

## A measurement that was wrong twice before it was right

The first attempt to count what the run left behind reported **zero**, and the reason is the defect:
`os.walk` cannot descend past 227 characters, so a script that walks the basetemp cannot see what is
in it. The second attempt reported zero as well, for a duller reason — the path was written in the
shell's `/c/...` form, which Python on Windows does not resolve, so it was counting a directory that
did not exist. The numbers above come from the third, which walks `paths.real(...)` of a real
Windows path. Written down because both wrong answers were the *same* answer, and a defect that
hides itself from the measurement is worth more than the fix.

## What this does not do

- **It does not change `_deep` or any assertion.** The four tests prove what they proved.
- **It does not touch `src/`.** `git diff --stat 77b5c14 -- src` is empty.
- **It does not clean up the directories already on the machine.** Two are named above; removing
  them is an operator action, not a change to the repository.
