## L-30 — one file, two adjudicators, and only one of them refuses

`_adjudicate` reads a seat's verdict as `str(answer.get("verdict") or answer.get("outcome") or "")`
(`engine.py:1689`). A backend that returns prose rather than JSON gives `{"exit_code": 0, "stdout":
…}` — neither key — so the seat's entry is set to `""`. Measured:

```
adjudicate({conformance:'',      defect:'',      risk:''     })  -> fail · vetoed=['conformance']
adjudicate({conformance:'PASS',  defect:'PASS',  risk:'PASS' })  -> fail · vetoed=['conformance']
adjudicate({conformance:'pass ', defect:'pass ', risk:'pass '})  -> fail · vetoed=['conformance']
adjudicate({conformance:'pass',  defect:'pass',  risk:'pass' })  -> pass · vetoed=[]
```

**Its sibling in the same file refuses all three:**

```
adjudicate_grade('medium')   -> medium
adjudicate_grade('MEDIUM')   -> PolicyError
adjudicate_grade('medium ')  -> PolicyError
adjudicate_grade('')         -> PolicyError
```

And `adjudicate` is not lax by design — it **refuses an unknown speaker and accepts an unknown word
from a known one**:

```
adjudicate({'a': 'pass'})                    -> PolicyError: unknown seat(s): ['a']
adjudicate({'conformance': 'yes', …})        -> fail · vetoed=['conformance']
```

The same asymmetry sits in `engine.py`, sixty lines apart:

| line | what it does with an answer it cannot read |
|---|---|
| `1626` `_answered_branch` | **raises**, naming the branches it would have accepted |
| `1689` `_adjudicate` | writes `""` and **votes with it** |

`_adjudicate`'s own guard cannot see it: `if len(verdicts) != seats` (`engine.py:1690`) counts
**keys**, and line 1689 has already set the key. A panel short a voice in the guard's own words
passes the guard.

`adjudicate`'s CHG-20260831-01 comment was written about exactly this outcome — *"a record stating
something its own author denied."*

## L-29 — three of five agree with the adjudicator by naming coincidence

Five nodes are `answer_decides=True` **and** `mode=MODEL_PANEL`:

```
lead_task_review   branches = fail / pass    <- same words the adjudicator counts
re_review          branches = fail / pass    <- same
qa_accept          branches = fail / pass    <- same
pm_confirm         branches = no   / yes     <- different, and nothing says so
pm_signoff         branches = no   / yes     <- different, and nothing says so
```

`_answered_branch` requires one of the node's branches; `policy.adjudicate` counts only the literal
`"pass"`. **The work order carries neither `branches` nor `answer_decides`** — measured, zero
occurrences of either in `workorder.py`. The voice is never told which vocabulary to speak, and for
three of the five nodes it does not matter because the two vocabularies happen to share their words.

```
node_models={}                      answered 'yes'   -> finished
node_models={}                      answered 'pass'  -> EngineError: not one of ['no','yes']
3 models on pm_confirm/pm_signoff   answered 'yes'   -> walk exceeded 200 steps (pm_confirm x66)
3 models on pm_confirm/pm_signoff   answered 'pass'  -> finished
```

The single path refuses an unknown answer with a clear message. The panel path counts it as a no
vote and re-enters through `rejects_to` until the step ceiling — **267 model sessions**.

CHG-20260901-11 made these nodes routable and left them unanswerable, which is its own guard's
sentence one layer in: *"it takes the whole run with it, and it does so at whichever node the
operator happened to configure."* `tests/test_panel_and_pool.py:357` states the asymmetry **in a
comment** and hard-codes around it; `test_nothing_is_unwired.py` checks symbol reachability, not
semantic reach, so it cannot see this.

## L-31 — a citation that ends in a comment about itself

```
engine.py:21     "Anything that is not `auto` stops the run, so no ordering between `confirm`,
                  `halt` and `halt_independent` is needed anywhere."       <- true of `verdict`
policy.py:979    cites that, and separately grounds `confirm < halt` on
                 "`confirm` can be pre-authorised with `--confirm` and a halt cannot"
_gate            has no rung check at all — all three rungs are treated identically
ARCHITECTURE:71  "A halt is a pause with a way back — `--confirm <gate>` continues past one"
README:689       discloses that `halt_independent` is treated identically to `halt`
```

Measured at `risk=high`: `--confirm plan_confirmed` opens the `halt`, and `--confirm acceptance`
opens the one `halt_independent` cell, both recorded as *"confirmed by the operator"*.

`halt_independent` occurs **once** across `engine.py`, `cli.py` and `server.py` — and that once is
`engine.py:21`, the comment `policy.py` cites as its authority. Nothing in the run distinguishes
the rung from `halt`.

**`README.md:689` is the only one of the four that is honest**, and it is a Known-gaps entry:
*"`halt_independent` does not check independence… The name is an intent."* `ARCHITECTURE.md:64`
states the enforcement unqualified, in the vocabulary table a reader consults first.

**The ruling this record takes, and it is narrower than the one it started with.**

The first version refused *every* approval at the independent rung, and an end-to-end server test
went red saying `the run never reached merge`: at `risk=high` the run stopped at `qa_accept` and a
person driving the server had no way past it. That is not a stricter rule, it is a broken one — the
rung would be unreachable through the only interface a person has.

`policy.py`'s sentence is about **pre-authorisation** — *"`confirm` can be pre-authorised with
`--confirm`"* — and `_gate` already tells the two acts apart. Measured, each path has exactly one
source in `src/` and they do not overlap:

```
the counter path    cfg.confirmed counts   only `--confirm <gate>` — given before the run, naming
                                           no node, for a stop nobody has seen yet
the targeted path   Approval objects       only server.Runner.approve (server.py:323, the sole
                                           site in src/ that mints one) — given after the
                                           suspension was returned and read, naming the node
```

So: **a blanket `--confirm` cannot open `halt_independent`; a person answering the stop they were
shown can.** A person at the stop is what *"stops for a person"* means, and pre-authorising a rung
whose whole content is *"a person is here"* is the thing that was wrong.

> **CORRECTED BY CHG-20260903-34 — the ruling was right and it was implemented on one of the
> two ledgers.**
>
> The guard went on the **counter** path only, reasoning that an `Approval` object *is* the
> person-at-the-stop path. It is not: `node_id` is optional, `server.approve` passes whatever
> the client sent, and `Approval(gate="acceptance")` naming no node is exactly what the
> paragraph above calls blanket — *"naming no node, for a stop nobody has seen yet."* Measured,
> it opened the rung, and the report then contradicted itself two adjacent lines apart, with
> the reassuring line being the false one.
>
> Reachable through the shipped HTTP surface: `_require_suspension` checks *that* the run is
> waiting, never *which* gate it waits at, so a client could approve `acceptance` while
> suspended at `plan_confirmed`, and the pre-authorisation waited for a rung the person would
> never be shown.
>
> The test is now what the answer **names**, not which ledger holds it — and the door refuses
> an approval naming a stop the run is not at. Found by the risk seat reviewing the second
> drafts (L-47).

`policy.py:979`'s comment is amended to say the second clause was false when written and is true
now; `ARCHITECTURE.md`'s vocabulary line stops claiming an independence check it has never made and
says what it does enforce; and its halt sentence names the one exception. `README.md:689`'s Known
gaps entry was the only honest one of the four and is unchanged.

The alternative a seat may still prefer: admit the rungs are one rung and delete `HALT_INDEPENDENT`.
This record does not take it, because 「merge 永遠留一個人」 is written against exactly this rung.

CHG-20260903-25 named this defect, scoped it out, and said it *"is carried out separately"*. Nothing
carried it. This record is that separately.

## Risk & rollback

- **Task 7 is a tightening that can strand a run.** An operator who today passes `--confirm
  acceptance` at `risk=high` gets through; afterwards they do not, and must answer at the stop
  instead. That is the intent — it is the only `halt_independent` cell in `GATES` — but it is a live
  behaviour change and belongs first. Task 7b is what keeps it from being a wall: the server path
  still opens it, which an end-to-end test proved was necessary rather than assumed.
- **Six existing tests had seats that said nothing**, and so were running against a review panel
  that failed for a reason nobody wrote down. Two needed the fixture to say `pass` outright; the
  rest never reach `lead_review`. **Thirty-three fixtures share that idiom** and are untouched here —
  named rather than blanket-edited, because a run that stops earlier is unaffected and a
  thirty-three-file edit inside a defect fix is a worse trade than a recorded follow-up.
- **Task 1 turns a silent miscount into a stop.** An install whose backend returns prose has been
  producing false vetoes; afterwards it produces refusals. Correct, and it will surface as new
  failures on installs that were quietly wrong.
- **Tasks 5 and 6 touch the dispatch loop**, which is where L-29's 267 sessions come from. The cost
  of getting this wrong is measured in model calls.
- **Task 9 edits a doc rather than code**, and a seat may rule the other way — that the rungs are
  one rung and `HALT_INDEPENDENT` should go. This record takes the narrow reading and says so.
- Rollback: revert. The veto is forged again and the run dies at the ceiling again.
