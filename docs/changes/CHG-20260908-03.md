## The defect item 3 was standing next to

`graph.validate`'s panel-routability rule — the one CHG-20260901-11 added, after `pm_confirm` and
`pm_signoff` offered `yes`/`no` while the only thing routing them said `pass`/`fail` — is guarded on
one mode:

```python
if node.mode == MODEL_PANEL and node.branches:
```

A `SEAT_PANEL` node is asked nothing. Measured, by renaming the one seat-panel node's branches and
running `validate` on the result:

```
lead_review with branches approve/reject   validate PASSES
```

It would then have died at `engine.py`'s branch lookup — `node {id} has no branch {choice}` — which
is the same death, at the same line, that CHG-20260901-11 exists to prevent.

**And `panel_branches` cannot save it.** The two modes take their branch by different paths:

```
MODEL_PANEL   choice = node.panel_branches.get(panel_outcome, panel_outcome)
SEAT_PANEL    choice, rework = _adjudicate(node, report, seats)   → returns the outcome itself
```

`_adjudicate` returns `pass` / `fail` / `undecided` as the branch name and does not consult
`panel_branches`. So the escape the model-panel rule's message offers — *"Declare `panel_branches`
on it"* — is not an escape here, and the seat rule must not offer it.

**The mapping is still *read* on that path**, which a seat had to point out and which makes the
refusal sharper than the first draft of this record claimed. After the branch is taken, `engine`
reads `node.panel_branches.get(policy.PASS, policy.PASS)` to name the word that means ratified —
for every branching node, whatever its mode. That second read is what makes the declaration
**load-bearing** for a node whose branches are its own words: `pm_signoff` offers `yes`/`no` and
settles because it declares `{pass: "yes"}`. So the refusal stops at `SEAT_PANEL`, where rule 1 has
already put `pass` among the branches and no declaration can improve on that. A `runner` node
declaring the mapping and passing `validate` is correct, not a gap — an earlier draft of this
record read it as one and widened the rule, and a seat measured that backwards.

That is also why *"`lead_review` qualifies identically"* is wrong. It names its branches `pass` and
`fail`, so it is one of the four — but it is not in the population the two sentences are about,
because those sentences are about a mapping the seat path does not route through. They are right
about `panel_branches` and silent about which nodes they are counting, which is what item 3 reported.

## What ships

- `graph.validate` refuses a `SEAT_PANEL` node whose branches do not include the panel's own words,
  with a message that does **not** offer the `panel_branches` escape.
- `graph.validate` refuses a `SEAT_PANEL` node that declares `panel_branches` — there, and
  nowhere else. `engine` reads the table a second time, after the branch is taken, to name the
  word meaning *ratified*; the rule above forces a seat panel's branches to contain `pass`, so
  that read already lands on a branch it offers and **no declaration can improve it**. Two shapes
  are harmless (`{pass: pass}`, `{fail: fail}`) and one breaks the settling (`{pass: fail}` puts
  `ratified` at a word `_adjudicate` never returns). A seat refused an earlier claim that they all
  misname; what is true of all of them is that none helps.

  **This rule was widened to every mode but `MODEL_PANEL` for one revision, on a reason that
  measures false.** That draft said a declared-but-unrouted mapping gives a `ratified` the node's
  own answer can never equal. Measured, on the node the mechanism was built for: `pm_signoff`
  offers `yes`/`no`, and with its declaration `ratified` is `yes` — a branch it offers, so it
  settles — while without one it is `pass`, which it does not offer. The declaration is what makes
  settling work. Elsewhere it is the only way to name the ratified word, and `engine` says the
  settling is "keyed on the answer, never on the mode", so the widening re-keyed a deliberately
  mode-independent mechanism on the mode. A seat measured it and the rule went back.
- Both sentences in `graph.py` and `engine.py` say which population they count.
- `tests/test_graph_validation.py` gains the reverse test **CHG-20260901-11's own rule never had**.
  This file's docstring lists that rule among nineteen with no reverse test, and names the pattern:
  *the guard a repair installs is itself a place the next defect can hide.* It was.
- `_graph_swap.py` gains `mutated` — the `_mutate` two modules carried — and `swapped_graph`, a
  context manager for the two tests that need the hypothetical graph held **open** while they look
  at it. `validate_with` cannot serve those: it restores before returning, which is its point.

## What this does not do

- It does not change how any node routes. The shipped graph passes both new rules unchanged.
- `validate_with` **is** folded into `swapped_graph`. An earlier draft kept them separate and gave
  the closed-before-return property as the reason; a seat measured the fold, which preserves that
  property exactly — a `with` exits before its function returns. The three modules that call
  `validate_with` are `test_graph_validation`, `test_execution_mode` and `test_risk_adjudicated`:
  **82 collected tests, of whose 76 test functions 44 call it**; all pass folded. (81 and 75 at
  the revision before this one — the commit that corrected this sentence added the test function
  that moved it, which is the defect this record is named for, one round down.) An earlier figure here said 68,
  which counted `test_module_built` in place of `test_risk_adjudicated` — the caller the fold
  actually changed. The reason was not one, so the fold was done rather than re-argued.
- It does not fold in `test_graph_validation`'s deliberate half-swap, for the reason its own
  docstring gives: it exists to be wrong, so the two-view rule has something to refuse.
- It does not touch the redundant function-local `import dataclasses` in two tests. Pre-existing,
  unrelated, and a record that tidies whatever it passes is a record nobody can review.
