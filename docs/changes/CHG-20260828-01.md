# CHG-20260828-01 — a mutation with an ambiguous anchor reports coverage it did not earn

- Project: ai-sdlc-runner
- Branch: claude/chg-20260828-01-mutation-anchor
- Date: 2026-08-28 (UTC+0)
- Type: the missing half of a guard that already exists
- Proposed by: hitting it twice in one day while building CHG-20260827-22 and CHG-20260827-20
- Risk: **medium** — it does not change the runner. It changes what the runner's own evidence means,
  and three shipped mutations turn out to have been reporting about the wrong lines.
- Autonomy: high
- Related: CHG-20260823-51 (added the `NO BASELINE` gate for the same reason, one layer up),
  CHG-20260827-22 and CHG-20260827-20 (where this was found)

## The gap

`tools/mutation_check.py:run` refuses a mutation whose anchor is **gone**, and says so in exactly
the right words:

> `ANCHOR GONE` — *the mutation is stale, which is not the same as caught.*

The symmetric case is missing. The write is:

```python
original.replace(mutation.before, mutation.after, 1)
```

so an anchor appearing **twice** reverts whichever comes first — which need not be the guarantee
`says` names. The run then reports about a different line. `NOT CAUGHT` would at least be
investigated; **`CAUGHT` is the dangerous reading, because it is indistinguishable from coverage.**

This is the same shape as the `NO BASELINE` gate CHG-20260823-51 added: a red that proves nothing,
printed as a red that proves something.

## It is not hypothetical, and one case is worse than the others

Adding the check found **three** ambiguous anchors already in the list:

| mutation | why it was ambiguous |
|---|---|
| `provenance/the plan a run walked…` | `cmd_run` and `cmd_serve` open the same conversation |
| `risk/the plan's workstreams stop reaching the run` | both build the same `RunConfig` — **mutating the console path leaves the tested path working, and the run prints CAUGHT** |
| `risk/a node may point at a workstream nobody declared` | see below |

The third is the one that argues for the check rather than for more care. That anchor was
**unique when it was written**. CHG-20260827-22 added a second `if name not in workstreams:` — the
interfaces guard — and made it ambiguous *as a side effect*. Nothing reported it. The `risk` group
went on printing `13 caught`, and one of those thirteen had quietly started reverting a different
guarantee.

So the failure mode is not "somebody wrote a sloppy anchor". It is **"somebody else's later change
moved the ground under an anchor that was fine"**, which no amount of care at writing time prevents.

## Why it goes in the tool and not in a habit

Both of the cases found during CHG-20260827-22 and -20 were caught by a uniqueness check in a
throwaway generator script — written because the first mis-anchored mutation was noticed by luck.

A guard that lives only in the thing that produces the input is a guard the next author does not
have. This repository has the same finding recorded about `WRITE_SCOPES` (defined, used only by a
test) and about `MAX_DISPATCH_DEPTH` (stated, computed by nothing).

## Risk & rollback

- Nothing in `src/` changes. The runner behaves identically.
- The blast radius is the evidence: three mutations now revert what their labels claim, and any
  future ambiguous anchor is refused rather than silently applied to the first match.
- Rollback: revert. The narrowed anchors are strictly more specific, so they keep working either
  way; only the refusal goes.

## Status

**Accepted** — see [ACC-20260828-01](../acceptance/ACC-20260828-01.md).

### Not claimed

**That the mutations now prove more than they did.** They prove the same thing about the right
lines. The module docstring's larger caveat is untouched and still governs: this answers *"can the
tests I wrote fail?"*, never *"did I write the test for the case that matters?"*

**That uniqueness makes an anchor correct.** A unique anchor can still revert something other than
the guarantee its label names. Nothing here checks that the `says` line describes the edit.
