## The requirement, as stated

Recorded close to the user's own words, because several of these constraints only make sense
together and a paraphrase would lose the reasons:

1. The runner conforms to the autopilot flow, and **splits every node into a separate template used
   as an information request**.
2. **Without modifying the skill.**
3. The runner's goal becomes **splitting into nodes, rather than one skill handling everything**.
4. The runner **makes the whole node set loop**; the user only injects a requirement from outside.
5. **Do not send all the content, do not keep a session**; every node must be **retryable and
   directly runnable** without one; keep requests short.
6. Reasons, given explicitly: ① token cost ② a dropped session must not corrupt the flow
   ③ **flexibility to run different nodes on different models**.
7. The project **uses the original skill's logic** by **decomposing the skill it already points at**;
   every step and flow becomes an independently handled element, and the project consumes the
   decomposed form.
8. **No cap** on how many elements it decomposes into, so long as flow and logic are preserved.

Reason ③ is the sharpest constraint and the easiest to under-serve: a work order that is portable
across models cannot assume a tool set, a skill-loading mechanism, an agent harness, or anything
left in a prior turn.

## Settled design

### D1 — Decomposition unit: two layers

- **Content elements**: each shipped reference deterministically split at its stable `##`/`###`
  headings, anchors preserved. Sub-reference granularity is required, not optional — sending an
  18,703-byte `modification-guide.md` to a node that needs one of its sections still violates
  constraint 5.
- **Dispatch elements**: derived from the shipped policy — `role_refs.json` × `halt_policy.json`'s
  5 gates × `autopilot_policy.json`'s 6 per-risk decision points. Each names only the section
  anchors it needs.
- **The 99 flowchart nodes are not shipped and must not be reconstructed by hand.** `design.md`
  lives in the skill repo's `docs/`, which is absent from both the vendored store and the plugin
  distribution. The node axis therefore comes from the policy JSONs, which *are* shipped.
- Element count is unbounded (constraint 8). The unit is justified by **dispatchability**, never by
  a comfortable file count.

### D2 — When decomposition runs: fused into vendoring

Vendoring a store version and emitting its decomposition are **one governed change**. There is no
state in which a store version exists without its derived elements. CI regenerates independently and
rejects any byte difference.

`skills/v1.64.0/` already landed bare (CHG-20260822-03), so its decomposition is a **one-time
migration** performed by this CHG — a named migration, not a retroactive exception.

### D3 — §7: a narrow, named override extension

`ai-guideline` §7/§8 forbid copying skill markdown into the runner. Committed *extracted* text is the
**same category** as committed *vendored* text — both are skill content living in this repo.
Determinism changes the **drift risk**, not the category. Vendoring required the named
CHG-20260617-05 override; this extends it **narrowly**, to deterministically derived artifacts only.

Recorded rather than argued away. The residual that the override does *not* cover, and that stays
runner-authored interpretation: the **segmentation heuristics** (which headings are stable anchors)
and **manifest composition**. Each heuristic is a fork point and is documented as such.

### D4 — Staleness: provenance + regeneration gate

Every element records **generator version · source path · source SHA-256 · emitted SHA-256**. CI and
the entry handshake re-derive from `skills/<locked>/` and three-state the result:

| | |
|---|---|
| match | pass |
| regenerable drift | **hard fail** |
| source missing | **hard fail** |

This guarantees *elements ≡ the store they came from*. It does **not** guarantee the store matches
upstream — the store was 48 minors behind until hours ago. That remains `runner check`'s job, and
conflating the two would be exactly the false-green this repo keeps catching.

### D5 — The work order: what makes it model-portable

**portable-required**: element id · store version · source paths + anchors (**bodies never inlined**)
· role + scope · objective · done-criteria · input artifact paths · expected output paths ·
acceptance predicate · this node's **resolved** policy verdict (risk × gate → auto/confirm/halt —
small enough to inline) · abstract capability flags (`can_spawn` / `writable` / `can_execute`) ·
idempotence probes · workdir path.

**harness-specific → excluded**: concrete tool names and allowlists (each harness maps capability
flags to its own tools) · the "load the ai-sdlc skill" bootstrap line · session or prior-turn context
· model and dispatch settings.

The exclusions are the part that delivers reason ③. A work order carrying `Read`/`Bash`/`Edit` tool
names is bound to one harness no matter how short it is.

### D6 — Idempotence: the ledger is the authority

1. **The ledger is the single authority for intent.** A node writes its CHG entry — with `Branch:`
   and the task table — **before** taking any effect.
2. **Effect admissibility rule**: an operation may be an effect **only if it leaves a probeable
   postcondition** in the ledger, git, or the forge. Anything that cannot is **not permitted as an
   effect** and must be restructured until it can.
3. Effects are **ordered**, each with its own probe. Resume = find the first unmet probe in order and
   run from there. A partial state is therefore never readable as "never started".
4. Receipts, if ever added, are **optional and non-authoritative** — never consulted for anything the
   ledger can answer; a missing or stale receipt is rebuilt, never an error.
5. **Ship without receipts.** Add them only if probe latency is *measured* to be a real cost.

Worked example, the case that decides the design — a node killed between `git push` and
`gh pr create`: `git ls-remote origin <branch>` reads met; `gh pr list --head <branch>` reads empty;
the frontier is exactly "PR not created"; the engine re-runs only `gh pr create`.

Existing probes this rests on, already true today: commits carry CHG ids; CHG task tables use `[x]`;
ACC files exist per CHG. `state.json` degrades to a cache.

### D7 — Rollout

Engine first, elements in batches (user-set). The engine ships **behind an opt-in flag**; the
four-stage path stays default until the element set is complete, then the default flips and the flag
is removed. **Inside the engine, a node with no element is a hard error naming the node id** — never
a silent fall-back to the generic prompt, which would be the KN-4 anti-pattern: coverage quietly
reverting to old behaviour while looking upgraded.

Old `state.json` checkpoints may simply become invalid (user-approved). No migration.

## Modification Guide

### Goal

`runner run <project> --requirement <text>` walks the node graph to completion, dispatching one
self-contained, model-portable work order per node, halting only where the shipped policy says halt,
and resuming correctly from a cold start after any interruption.

### Global constraints (all tasks)

- **Do not modify the skill**, in this repo or upstream. `skills/<version>/` stays a verbatim archive.
- **Never inline reference bodies into a work order.** Paths and anchors only.
- **No harness-specific field may appear in a work order** (D5 exclusion list).
- **No effect without a probeable postcondition** (D6.2). If an operation cannot be probed, it does
  not ship as an effect.
- **No silent fallback** for an untemplated node.
- The decomposer must be **deterministic**: same store in → byte-identical elements out.
- Verification bar: suite green; regeneration byte-identical in CI; a **kill-and-resume test** that
  interrupts between two ordered effects and proves the engine resumes at the right frontier.

### Risk & rollback

- Risk: **high**. It replaces how the runner executes anything. Mitigated by the opt-in flag: until
  the flag flips, the existing path is untouched.
- Named failure mode: an element set that silently diverges from the store. Task 4 is the mechanical
  answer; Reservation #1 is the part it does not cover.
- Second: a work order that only runs on the harness that produced it — defeating reason ③ while
  looking finished. Task 5's done-when is written as an absence check for exactly that.
- Rollback: the flag never flips; `git revert` removes the decomposer and elements. The four-stage
  path is not modified until task 6's default flip, which is a separate, later decision.

## Structure change summary

Adds a decomposer, a derived element tree per store version, a work-order schema and renderer, and a
node-loop engine behind an opt-in flag. Extends the §7 override. No skill change. No change to the
four-stage path until the flag flips.

### The two segmentation heuristics, named as D3 requires

D3 says the segmentation heuristics are **not** covered by the §7 override and stay runner-authored
interpretation. Both are recorded here as fork points, with the measurement that decided each:

1. **A heading inside a fenced code block is not an anchor.** Of the 257 lines matching `^##?#`
   across the 23 English references, **56 sit inside ``` fences** — document skeletons being *shown*
   (`structure-design.md` alone accounts for 17, `modification-guide.md` 14, `requirement-analysis.md`
   10), leaving **201** real anchors. Splitting on them would invent 56 elements and shred the prose
   around them. The fence tracker follows the CommonMark rule — a fence closes only on the same
   character at least as long — so a fence displayed inside a longer fence terminates nothing.
   Fork point: a different reader could treat every `^##` as an anchor and filter later.
2. **The hash basis is LF-normalised content, not raw working-tree bytes.** `.gitattributes` is
   `* text=auto`, so all 46 references check out **CRLF on Windows and LF on Linux** while the git
   blob stays LF. Hashing raw bytes would make `source_sha256` OS-dependent, and CI runs
   `{ubuntu, windows}` — task 4's gate would hard-fail on one leg of the matrix for a store nobody
   touched. This is the same shape as the five Windows-only failures CHG-20260817-09 had to fix.
   Emission uses `write_bytes`, never `open(..., "w")`, so the normalisation is not undone at the
   last step. Fork point: hashing raw bytes plus a normalisation step in the gate instead.

### Two scope decisions taken while building

- **Both languages are decomposed.** `assets/role_refs.json` maps a role to
  `references/<name>.md (+ .zh-tw.md)`, so the Chinese variants are part of the shipped load set.
  Excluding them would be a hand-made cap on the element set (constraint 8 rules that out) and would
  leave any loadout naming a `.zh-tw` reference with no element — which task 6 turns into a hard
  error. This doubles the element count, which is the intended direction.
- **Task 1 commits no extracted skill text.** The decomposer and its tests land; the element tree
  does not. Emission is to a caller-supplied directory and the tests use `tmp_path`. The committed
  element tree is task 3's "fuse into vendoring", and the §7 override extension is task 8 — so this
  task does not yet engage the §7 tension D3 describes.

### The measurement that decided Q2

Across all **402** real headings in the 46 shipped references, the 11 policy key names score
**0 true positives and 21 false positives** — `pr` matches "Org **pr**inciples" and
"**pr**otecting"; `merge` matches "E**merge**ncy override". The semantically correct anchors are
shipped and exist (`autonomy.md` has "Halt gates", "Decision: risk × gate", "Always-halt actions
(regardless of risk)") but they do not carry the policy keys' names. A key-name matcher is therefore
not "lossy" — it selects nothing while appearing to select, which is the KN-4 shape exactly.

The same substring trap then bit the guard test written for this task: `test_no_node_id_is_written_in_the_source`
failed on first run reporting `merge` and `pr`, both inside ordinary words in our own source. The
test now matches the **quoted string literal**, which is the thing actually forbidden.

### A store defect found while resolving Q3, and not worked around

`assets/autopilot_policy.json`'s axis is four-valued (`auto` / `confirm` / `halt` /
`halt_independent`), and its `_doc` says only "只准加嚴" without ordering `halt` against
`halt_independent`. Looking for the shipped resolver turned up a real gap:

- `scripts/halt_gate.py` ships complete and self-contained → the `halt:*` axis delegates to it
  (FR-8, guideline §8 "calls, not re-implementations"), which `gates.check_halt` already does.
- `scripts/autopilot_runner.py` is present but **cannot be imported from the vendored store**: it
  does `from lib import roles` and `scripts/lib/` was not included in the CHG-20260822-03 archive.
  Verified by running it — `ModuleNotFoundError: No module named 'lib'`.

So there is **no usable resolver for the autopilot axis in the store**. Rather than inventing an
ordering, each `autopilot:*` element carries the risk table verbatim and states
`"shipped_resolver": null` with the reason. The ordering is deferred to task 6, where it can be
tested. Re-vendoring the store's missing `scripts/lib/` is a separate change against
CHG-20260822-03's archive step.

   forbids. The overlap is instead resolved at decision time by the shipped tighten-only rule
   (`autopilot-loop.md` "Halt decision order (strict, tighten-only)", `halt_policy._doc` "只准加嚴").
2. **The anchor set is the role's whole shipped file set**, justified by the measurement above.
   If the skill ever ships a section→checkpoint map, this narrows without changing element shape.
3. **The tighten-only total order on the four-valued autopilot axis** is left undecided here, for
   the reason given above.

### The organising principle, stated once

**Generation is complete and unevaluated; selection happens at dispatch.** Risk, situational flags
and language are all left in the element as complete verbatim data, and the engine picks. This is
what makes the elements a pure function of the store — no CHG, no repo state and no runtime flag can
change what is emitted — which is precisely what task 4's byte-comparison gate needs. It is also why
`role × checkpoint` is not materialised: no shipped file asserts that a given role stands at a given
checkpoint, and 130 such pairs inside an artifact whose provenance claims a shipped source would
have the artifact misrepresenting where it came from.

## Task 4 record — the regeneration gate

Landed on `claude/chg-20260822-04-task4`. `dispatch.verify_elements()` + a `runner elements`
subcommand + its own CI job. No panel round: D4 already fixed the three states and the
"both hard, distinguishably" requirement, and what remained were conventions this repo has
precedent for (exit-code branching, one job per gate).

### The three states, and why they are separate

| state | exit | means | what it asks you to do |
|---|---|---|---|
| `match` | 0 | committed bytes are what the generators produce right now | nothing |
| `drift` | 10 | regeneration succeeds and disagrees | regenerate — or stop hand-editing elements, which guideline §2/§8 forbid |
| `source_missing` | 11 | something the committed elements name as their source is gone | recover the store; regeneration cannot fix this |

Distinct exit codes rather than one red, because the two failures call for **different actions**:
telling an operator "regenerate" when the store version was deleted sends them down a path that
cannot work. The codes follow the shipped `halt_gate.py` convention the runner already branches on
(0 continues, anything else stops, the code says which stop).

`source_missing` outranks `drift` when several versions fail at once — otherwise a run reports
"regenerate" as its headline for something regeneration cannot fix.

### How source-missing is detected — from provenance, not from a rule about what should exist

Each committed manifest records every element's `source_path`. The gate reads those back and checks
the paths still exist in the store. That makes "the source of this element is gone" a mechanical
finding rather than a judgement about which files a version ought to have had — the same principle
that kept a hand-written per-version table out of task 3, and the form fable's binding reservation
required.

It also gives the (iv) rule its teeth in the direction that is otherwise hard to see: a family
committed in the tree whose policy asset has vanished from the archive is a **missing source**, not
a family that was never supposed to exist.

Versions are enumerated from **both** `skills/` and `elements/`. Enumerating only the store would
skip an orphaned element tree entirely, and a deleted store version would read as "nothing to
check" — a silent pass at the exact moment the gate is most needed.

### Verification

13 tests in `tests/test_elements_gate.py`. **Every failure state is produced by actually breaking a
repo** — hand-editing an element, moving the store without regenerating, deleting a reference,
deleting a policy asset, deleting the whole store version — never by stubbing the detector. A gate
exercised only on the happy path is how this repo's false-greens have historically survived; this
one is exercised on all three of its outcomes and on the ranking between two failing versions.

CI gains a dedicated `elements` job rather than a step inside an existing one, so a red there always
means "the derived tree and the store disagree" and never "some other lint failed".

Full suite: **251 passed, 2 skipped**. `doc_integrity_check.py` exit 0. `runner elements --repo .`
reports `match` for all five versions (227 / 256 / 347 / 355 / 479 files byte-identical).

## Task 5 record — the work-order format

Landed on `claude/chg-20260822-04-task5`. `src/ai_sdlc_runner/workorder.py` + 34 tests. Panel: one
round, **both seats agreed on all three questions** (a / b / a) with no divergence.

### The two done-when clauses, each made mechanical

**"No harness-specific field"** is checked by **enumerating what the order contains** against the
closed D5 whitelist, never by searching for banned words — task 2 measured that a substring search
scores 21 false positives on this corpus, and it failed that task's own guard test on first run.
Two layers, both from the panel:

1. `WORK_ORDER_FIELDS` is the complete D5 set and rendering asserts the produced key set is exactly
   it. The node spec the caller passes is closed the same way, so a harness field cannot ride in
   through the back door either (`test_a_field_outside_the_contract_cannot_ride_in_through_the_caller`
   feeds it `model` and `tools`).
2. **A sentinel.** `agents.RoleSpec` carries a `tools` list this runner *synthesises* — `Read`,
   `Bash`, `Edit`, `Write`, `Agent` are Claude Code names hard-coded in `agents.py`, not shipped
   data. The test injects a unique string into it and asserts the string appears nowhere in the
   serialised order, with a guard assertion so the test cannot pass vacuously. Exact-value
   comparison, zero false positives.

`RoleSpec.writes_docs` is excluded on the same grounds — fable caught that it is a **fourth** flag,
guessed from prose in the Notes column, while D5 lists three. The renderer reads only
`can_spawn` / `writable` / `can_execute`, and never derives them back from tool names.

**"Renders without any sibling element"** binds the **artifact**, not the renderer — the same
boundary the panel settled when loadouts became ids-only, and both seats confirmed it here without
needing to reopen A2. The renderer holds the tree and dereferences ids; the node needs only the order
plus the store. Operational form, from fable: *a content element id must never appear in a work order
without the path and anchor it resolves to.* Pinned by three tests, including one asserting the order
contains no path into `elements/` at all.

### Nine of thirteen roles cannot be rendered — deliberately, and recorded rather than defaulted

`agent-hierarchy.md`'s "Role startup spec" table ships **four** rows (A1 / I1 / I1.x / V1). Via
`aliases` that covers analyst, lead-implementer, sub-implementer and verifier. **No shipped data
gives capability flags for `orchestrator`, `integrator`, `reviewer` or the six `seat-*` roles** —
`review_seats.json` names entirely different seats (`conformance`…), and the one sentence in
`role_refs.json`'s `_doc` about seats being read-only is prose, not data.

Rendering an uncovered role is a **hard error naming the role**, listing the covered ones so the
caller sees the shape of the gap. Both seats reached this independently and gave the same reason:
defaulting the flags to `false` is not a neutral safe default but **the runner authoring an
authorization policy**. `orchestrator` plainly must be able to spawn, so an all-false order would
look governed while being wrong; and a silently over-tightened node fails work it was supposed to do.
Both directions of the guess are harmful, which is precisely when guessing is unavailable. Same shape
as D7's "untemplated node = hard error naming the node id".

**Known consequence, recorded now** (fable's binding reservation, and the same handling as the
missing `scripts/lib/`): until the skill ships machine-readable capability data for those nine roles,
the engine cannot dispatch them — **including the review-panel seats**. Task 6 must **not** paper
this over with defaults at dispatch time; that would smuggle the rejected option back in through the
door the panel closed. `test_the_covered_and_uncovered_sets_are_the_whole_role_table` pins 4 + 9 = 13,
so if the skill ever ships more rows this fails and the gap record gets revisited instead of going
stale.

### Boundary: what task 5 does not do

Half of D5's portable-required set cannot be derived from a store — `objective`, `done_criteria`,
artifact paths, `acceptance_predicate`, `idempotence_probes`, `workdir`. It is per-CHG-task data, and
the elements exist before any CHG does; this is the same reasoning that put risk on the runtime side
in task 2. So the renderer takes a closed `node_spec` and an **already-resolved** `policy_verdict`
from the caller, validates both strictly, and refuses to render a partial order. Supplying them is
task 6's job. Both seats chose this boundary, codex noting that pulling CHG parsing in here would mix
the format contract with engine responsibility.

Language and situational flags are selected at dispatch, exactly as risk is: the elements hold every
language complete and unevaluated, and the caller picks. Measured — a verifier order is 14,143 bytes
for one language against 25,375 for both.
