# CHG-20260823-50 — the frontier cannot hear "there is nothing left to build"

- Project: ai-sdlc-runner
- Branch: claude/chg-20260823-50-rerun-idempotence
- Date: 2026-08-27 (UTC+0)
- Type: one correctness fix in the module loop, plus a diagnosable cycle message
- Proposed by: the user — *「把 weather-spa 重跑不冪等那個開成 CHG-50」*, which is reservation 3 of
  ACC-20260823-48
- Risk: **medium** — it changes when the module loop terminates. A wrong `none` ends a run with work
  undone; the current behaviour burns 200 asks and halts.
- Autonomy: high
- Related: CHG-20260823-48 (found while verifying it), CHG-20260823-49 (the same reservation list)

## Reproduced

`examples/weather-spa`, twice, from the same directory, second run with a **fresh journal** and the
first run's `site/` still on disk:

```
=== first  ===  visited: 35 node(s)   asks: 26   state: finished
=== second ===  halted: walk exceeded 200 steps — the flow is cycling without progress
```

Twenty-six asks the first time, **two hundred** the second, and nothing built.

## The mechanism

`engine.py:735`, in `_frontier`:

```python
built = {str((ask.result or {}).get("module")) for ask in report.asks
         if ask.node_id == "engineer_build" and isinstance(ask.result, Mapping)
         and (ask.result or {}).get("module")}
remaining = [m for m in planned if m not in built]
...
return "module" if remaining else "none"
```

The trailing `and (ask.result or {}).get("module")` **discards** an answer whose module is empty.

The example's agent compares content rather than counting files — deliberately, its own comment at
`agent.py:244` explains that counting was the first version's bug — so with `site/` already correct
it answers:

```json
{"module": "", "wrote": "", "note": "every module already matches the brief"}
```

That is a well-formed answer. The engineer is the only party that knows what is left — the work
order does not name a module, so the runner never tells it which one to build — and it has said
there is nothing. The frontier drops the sentence on the floor, `remaining` stays non-empty,
`next_module` says `module`, `engineer_build` is asked again, and the answer is the same forever.

So the loop is not cycling because of a bad plan or a confused agent. **It is cycling because the
runner cannot represent the answer its own protocol allows the agent to give.**

## Why this is the log's most-recorded shape, again

`_frontier`'s docstring argues, correctly and at length, that a fixed sequence is a prediction and
the run's own record is the truth:

> the frontier is the first module with no record … this reads two recorded facts instead of a
> prediction

It then filters one of those recorded facts out. "Read the run, do not read a list" was the right
doctrine and the implementation stops reading at the sentence it finds inconvenient. A name standing
in for a constraint.

## The second failure: the message names the symptom

```
walk exceeded 200 steps — the flow is cycling without progress
```

True and useless. It does not say which node repeated, how many times, or what it kept answering —
all of which the report already holds. An operator who hits this learns only that something looped.

## It is two of the shipped examples, not one

Running the new test against `origin/main`: **`tide-spa` fails too.** Both SPA examples' agents
compare content — `weather-spa/agent.py:244` says counting files was the first version's bug and
`tide-spa` does the same — so both answer `{"module": ""}` on a rerun and both loop.

`minimal` passes on `origin/main`, and for a reason worth naming: its agent returns
`{"module": MODULES[0]}` unconditionally, so it never says "nothing left" and never trips this. The
example that could not exhibit the defect is the one the docs use.

## Proposed fix

1. **The frontier hears the answer.** An `engineer_build` result carrying a `module` **key** whose
   value is empty means the engineer found nothing left to build. The frontier returns `none`.
   Distinguishing *"the key is present and empty"* from *"there is no key"* matters: the first is an
   answer, the second is an agent that did not answer the question, and those must not collapse.
2. **The cycle message says what cycled.** When the step limit trips, name the most-repeated node,
   its visit count, and its last result. The information is in `report.asks` already.
3. **A test that reruns a shipped example** — build once, then run again against the built output —
   which is the check no test performs today.

### What this does not do

It does not make the runner decide that a module is done. Only the engineer's own report can do
that, and this change is about the runner *listening* to it rather than about the runner concluding
anything.

## Risk & rollback

- A run that would have burned 200 asks now ends the loop. No run that finished before finishes
  differently: with `remaining` non-empty *and* the engineer reporting modules, nothing changes.
- The danger is an engineer that returns `{"module": ""}` because it **failed** rather than because
  it was finished. That ends the loop quietly, and `lead_review` / `qa_verify` are what stand between
  that and a merge. Named in *Not claimed*.
- Rollback: revert.

## The fix for the uninformative message was uninformative

The first draft counted visits from `taken`, and I wrote a comment asserting it "has been counting
all along". It has not. `_choose` returns before touching `taken` for a `frontier` decision and for
a plain-string one, and is not called at all for a panel node — so `taken` counts one narrow case
and was empty here. The message came out as:

```
Most-visited: nothing recorded.
```

A fix for a message that says nothing, which said nothing. Caught by the test written for it, on the
first run. Now counted from `report.visited`, which the walk appends to on **every** step.

### Not claimed

**That an empty module is unambiguously "finished".** It is what this example's agent means by it,
and after this change it is what the contract says it means. An agent that returns it on failure
ends the module loop and walks into review with nothing built. Review is the thing that catches that,
not the loop.

**That the 200-step guard is the right limit.** Untouched. This change makes the message
diagnosable; it does not ask whether 200 is a good number, and 200 asks against a paid backend is
already an expensive way to discover a loop.

**That reruns are idempotent in general.** This fixes the module loop's termination. `site/` still
gets rewritten, the journal is still per-run, and nothing here surveys what else a second run
touches.
