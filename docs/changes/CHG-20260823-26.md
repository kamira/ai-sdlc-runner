## The worst thing: the store governed nothing

```python
node_models=plan.get("node_models", {}),
```

`make_config` read the **plan**, not the resolved assignment. So an operator assigns a model,
`GET /config/nodes` answers `{"pm_plan": ["opus"]}` with `source: "store"` — and the next run
dispatches as if nothing had been configured.

Worse than a stale cache, three ways:

- **a node assignment took effect never** — not in that process, not after restart;
- **a seat assignment took effect only after a restart**, because the factory was captured once;
- **`cmd_run` never opened the store at all.**

`_reassign`'s own comment claimed the opposite in as many words: *"a console showing a stale merge
would be reporting an assignment that is not the one the next run will use."* fable-seat put it
precisely — the table was *"read only to be shown back to the person who wrote it."*

**Fixed:** both `run` and `serve` resolve **per walk**, and a test refuses either command reading
`plan.get("node_models")` again. `run` gained `--assignment-store`, so the two commands read the
same file by default.

## The second critical: adding a model broke once anything was assigned

`save_registry` opened with `DELETE FROM models`, which the foreign key correctly refuses:

```
adding a model AFTER an assignment -> IntegrityError: FOREIGN KEY constraint failed
   registry still  : ['a']
```

And the ordering made it worse. `POST /models` had already updated memory and written `models.json`
before reaching the failing line, so the request 500'd with **three copies disagreeing** — console
and file had the model, the store did not — and on the next start the store won and the model
**silently vanished**.

That is exactly the "visible but unassignable" split the code comments twice claimed to prevent,
produced by the code written to prevent it.

**Fixed:** upsert what is present, remove only what is gone, and **refuse by name** when something
still points at it — `"model 'opus' is still assigned to node 'pm_plan'"`. The store is written
**first**, because it is the one that can refuse.

## What the last change record claimed and could not support

Both seats went through it line by line. Four claims were false:

- *"Both take the run `version` like every other POST"* — presence only
- the whole premise, that the store was *"the project's standing assignment"* — it stood in the
  database and governed no run
- *"Every page updated"* — `DATABASE.md` §0.1 still headlined *"only one is persisted here"* and
  called the `models` table *"proposed"*, contradicting its own status line three paragraphs up
- the foreign key described as if refusing an unknown model were its whole role — the same key also
  broke `POST /models`, and it had been tested in one direction only

## The two tests whose absence let it through

fable-seat named both, and they exist now:

1. **add a second model after an assignment exists** — would have caught the registry defect on its
   first run;
2. **any test that a stored assignment reaches a dispatch** — *"its absence is why this could ship
   with every test green."*

## What this round says about the method

Both seats found the critical defects **by driving the real server one step further than I had**.
Every unit test passed on both. The drive script I used to find the threading bug stopped one call
short of the one that mattered — and, when the version check landed, that same script started
failing because it hardcoded `version: 0`, which is the mechanism working on the tool that found it.

### Not claimed

**That two processes on one store are safe.** Both seats said the harness does not exist. The lock
covers threads in one process; `busy_timeout` is all there is between two, and each process still
holds its own `held` cache that the other cannot refresh.

**That disk-full or a read-only file behave well.** Neither was driven. WAL plus transactions make
atomicity likely, and likely is not evidence.

**That the plan file validates anything.** It still bypasses all four refusals — a plan may name a
ghost model on a mode-ignoring node and nothing says so until dispatch.
