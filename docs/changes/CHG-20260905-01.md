# CHG-20260905-01 - the module that survives a crash loses the report of what it survived

- Project: ai-sdlc-runner
- Branch: claude/chg-20260905-01
- Date: 2026-09-05 (UTC+0)
- **Measured against `origin/main` at `6a96e62`**, pinned by sha
- Type: defect fix - behaviour, in `effects.py` and its two callers, plus the first mutation group
  the module has ever carried
- Proposed by: all four seats of the **eleventh review round**, whose subject was
  `src/ai_sdlc_runner/effects.py`. Every finding below was re-measured here before this record was
  written; one was re-measured and **reversed**, and is recorded as reversed rather than fixed.
- Risk: medium - `effects.py` is the crash-safety spine, and three of these changes alter what the

  why the change is worth making and also why it is graded medium rather than low.
- Autonomy: high
- Target ACC: ACC-20260905-01

## Read this first

`effects.py` exists so that a killed run resumes in the right place. Its docstring is about what
happens **after a crash**. The eleventh round found that on exactly that path - the one the module
is for - the module reports nothing, and one class of failure walks out of the process entirely.

The file has never been modified since it was written. It has two commits in its whole history
(`564d041`, `14e3878`), both `CHG-20260822-04`. It carries **0 of the 238 registered mutations**,
while `engine.py` carries 35. Its 12 tests are green and cannot see either headline finding.

## The findings, and who found each

Four seats reviewed independently and never saw each other's answers. The right-hand column is what
I measured myself at `6a96e62` before writing this.

### 1. A probe that cannot answer walks out of the process (conformance, defect L-67, idiom P4, risk §1)

`probes.py` raises `ProbeError` **by design** when a probe is unanswerable - D6 says an unanswerable
probe raises rather than returning `False`, because returning `False` would silently re-apply a step
that may already be done. That design is correct. What is wrong is that nothing between the raise and
the top of the process is prepared for it:

- `effects.run` calls `effect.probe()` in three places and translates nothing.
- `engine._run_effects` catches `effects_mod.EffectError` only (`engine.py:1439`).
- `cli.cmd_run`'s handler tuple is `(EngineError, PolicyError, CliError, IntakeError, SandboxError,
  WorktreeError)` (`cli.py:1087`) - neither `ProbeError` nor `ShipError` is in it.

Measured:

```
=== a probe that cannot answer, which probes.py raises by design ===
   ProbeError escapes `effects.run` uncaught: could not reach origin
   the world by then: ['first']
```

So the run dies with a traceback, there is no report, and - the part that makes this a live
production defect rather than an ugly message - the halt path that keeps a `--worktree` run's trees
is never reached. `cli.py:1085` carries a comment recording that this exact damage was found and
fixed once already, for `IntakeError`:

> *"`--worktree` run leaked its trees on the one path whose comment says the tree is where the
> evidence is. `serve` catches `Exception` broadly and rendered it; `run` did not."*

The same shape, one exception class over, in a module whose entire purpose is surviving failure.

### 2. A failed re-probe destroys the record of what landed (conformance Finding B, defect L-68, risk §1)

`outcome` is a local in `run`. When `run` raises, it is discarded. Measured with a four-effect
sequence whose third effect runs without establishing its postcondition:

```
world after the raise: {'chg': True, 'branch': True}   <- two effects really landed
exception args: (str,)                                  <- carries no EffectOutcome
```

`engine._run_effects` then sets `halted_at`/`halt_reason` and **returns before**
`report.effects[node.id] = outcome.as_dict()`. So on the one path where knowing which effects
already landed matters most, the run report has no effects entry for that node at all.

`docs/ai-guideline.md` (Auditability) says *"Every verdict, confirmation, relaxation, panel decision
and effect outcome is in the run report"*. It is false on the failure path. Measured against a real
halt: `report.effects` was `{}` while `relaxations` (8) and `on_trust` (1) came through the same
halt intact.

### 3. `frontier` and `out_of_order` reach no human (idiom P1, defect L-71, risk §3)

```
  EffectOutcome carries : ['frontier', 'already_met', 'applied', 'out_of_order']
  the terminal prints   : ['applied', 'already_met']
  reaching no terminal  : ['frontier', 'out_of_order']
  the console renders   : nothing (0 hits for "effects" in console/index.html)
```

`out_of_order` is the field whose own docstring says the state it names is *"worth a human's
attention rather than a silent redo or a silent pass"*. It is serialised into `--json` and reaches
no other surface.

The sharp part is where it sits. `cli.py:1155-1157` prints `risk_settled`, and that line **is** the
fix from `CHG-20260903-48` - a field that reached `--json` and the console but not the terminal. The
loop three lines below it repeats the same defect for two more fields.

### 4. `dry_run=True` silently drops the out-of-order guarantee (conformance Finding A, idiom P2, defect L-70)

Same world, two calls:

```
wet:  {'frontier':'branch','already_met':['chg','push'],'applied':['branch','pr'],'out_of_order':['push']}
dry:  {'frontier':'branch','already_met':['chg'],       'applied':[],            'out_of_order':[]}
```

`run` returns at `if dry_run: return outcome` (`effects.py:131-132`) before probing past the
frontier. The shortfall is reported as an **empty list**, which is indistinguishable from "the world
is in causal order" - the exact conflation the docstring exists to prevent. Probe calls measured:
dry `['chg','branch']` vs wet `['chg','branch','branch','branch','push','pr','pr']`.

`FR-15` is a **P0** guideline row - *"anything found true out of causal order is surfaced rather than
redone or waved through"* - and it names `effects.run` with no dry-run caveat.

`dry_run=True` has zero production callers today, so this is latent rather than live. It is fixed
here anyway, because the shape of the defect is that the mode meant for *looking before acting* is
the mode that cannot see the thing most worth looking at, and a first production caller would
inherit that unexamined. Recorded in the same breath: `test_nothing_is_unwired.py` structurally
cannot see this, because its unit is the symbol name, not the branch.

### 5. The construction guard tests the value, not the property (conformance §1, defect L-72, idiom P3)

D6.2 is semantic: an effect is admissible only if it leaves a **probeable postcondition**.
`__post_init__` enforces `callable(self.probe)`. Measured admissions, all accepted silently:

| construction | result |
|---|---|
| `Effect(probe=lambda: True)` - reads nothing at all | admitted |
| `Effect(probe=len)` - wrong arity | admitted; blows up later, inside `find_frontier`, at run time |
| `Effect(probe=<object with __call__>)` | admitted |
| `Effect(probe=True)` / `probe=None` | refused |

The `probe=len` row is the one fixable at construction: a probe that cannot be called with no
arguments is not a probe, and finding that out at run time means finding it out **after some effects
have already been applied**. The `lambda: True` row is not fixable by inspection and is not claimed
to be - see the docstring change in §8.

Mutations `M-A`/`M-B` (`callable(...)` -> `is None`) survive all 245 tests in the module's own
neighbourhood.

### 6. The frontier effect is probed three times in one pass (idiom P5, defect L-69)

`find_frontier` probes it (unmet, returns its index); the loop's `if effect.probe()` probes it again
though we just learned it is unmet; then the post-apply re-probe probes it a third time. The third
is required - it is the false-green check. The second is redundant.

Probes shell out. `probes.DEFAULT_TIMEOUT` is 60s and the module's comment says results are
deliberately not cached, so this is a real round trip to git or to the forge, not a cheap call.

### 7. `continue` versus `break` is invisible to all 12 tests

`run`'s loop correctly `continue`s past an out-of-order effect. Replacing it with `break` would
silently skip every later effect - `pr` would never be created - and no existing test notices.
Measured on `chg,branch,push,pr` with `world={"push": True}`:

```
   frontier: 0
   outcome : {'frontier':'chg','already_met':['push'],'applied':['chg','branch','pr'],'out_of_order':['push']}
```

The dry-run test that exists (`test_dry_run_reports_the_frontier_without_applying_anything`) has a
world of `{"chg": True}` - nothing out of order - so it would also pass against a `run` that never
populated `out_of_order` at all.

## Re-measured and reversed: the `ship` commit probe (risk §2)

The risk seat measured that one untracked file flips `ship`'s composed `commit` probe:

```
clean tree                     commit_exists_for True · working_tree_clean True  -> effect done
one untracked file (?? tmp)    commit_exists_for True · working_tree_clean False -> reads NOT done
--untracked-files=no           ''  -> clean
```

and proposed adding `--untracked-files=no`, or narrowing the probe to this effect's own
postcondition. **Re-measuring moved the scope and reversed the fix.**

`tests/test_ship_refuses.py::test_a_commit_over_a_dirty_tree_is_not_finished` pins both halves of
that probe deliberately, and the dirty file it uses - `two.txt`, written but never added - **is an
untracked file**. Its docstring records that dropping `working_tree_clean` from the probe left every
test green, which is why the assertion exists. `--untracked-files=no` would make that test's own
scenario read clean, reverting a decision `CHG-20260830-03` made on evidence. `tools/mutation_check.py:800`
pins the composed line verbatim as well.

So the seat's *observation* is right and its *fix* is wrong: the probe reading `False` over
uncommitted work is the intended reading. What the observation actually points at is one step later
- whether re-applying `commit` over a dirty tree produces a second commit carrying the same CHG id,
and whether anything refuses that. **I could not measure it here.** Creating a fresh git repository
under the temp directory hung past a 60s timeout twice in this environment, in a probe that ran
correctly earlier in the same session; raw `git init`/`git commit` hung the same way, so it is not
the runner. Nothing about the residual question is settled by this record, and no change is made to
`ship.py` or `probes.py` here. It is carried forward as an open item rather than closed on a
measurement I did not get.

## What changes

In `src/ai_sdlc_runner/effects.py`:

1. Every probe call goes through one helper that translates a raise from the probe into
   `EffectError`, preserving the original as `__cause__`. The raise stays a raise - D6's rule is
   untouched - but it now has the type the module's two callers already handle. The helper is used
   by `find_frontier` and by both probe sites in `run`.
2. `EffectError` gains an `outcome` attribute, and `run` attaches the partially-built
   `EffectOutcome` to every `EffectError` it raises.
3. `dry_run` no longer returns at the frontier. It probes the rest of the sequence - probing is
   read-only - and populates `out_of_order` exactly as the wet path does. `applied` stays empty,
   which is true: nothing was applied.
4. The frontier effect is not re-probed at the top of the loop. `find_frontier` already established
   it is unmet.
5. `__post_init__` additionally refuses a probe or apply that cannot be called with zero arguments,
   read via `inspect.signature`. A callable whose signature cannot be read is admitted - the check
   refuses what it can prove wrong, not what it cannot read.

In `src/ai_sdlc_runner/engine.py`: `_run_effects` records `exc.outcome` into
`report.effects[node.id]` before returning, so a halted node's partial outcome is in the report.

In `src/ai_sdlc_runner/cli.py`: the effects print loop names `frontier` and `out_of_order` when they
are set.
