## The hole, located precisely

CHG-42 said `_advance()` runs outside `_lock` and that `attach()` and `instruct()` could therefore
start a second concurrent walk. **Half of that was wrong**, and the tests found it: `instruct()`
already refuses while a run is `running` —

```
this run is running. An instruction can be added when it is waiting or finished — changing the
brief under a walk in flight would have two nodes answering different questions with nothing
saying which was which.
```

So does `start()` (idle/finished/stopped only), and so do `approve`, `reject` and `rule`
(`_require_suspension`).

**`attach()` is the one that gates only on version** — which is exactly what fable-seat wrote and
what I generalised past when I repeated it. The first version of these tests drove the race through
`instruct` and could not reproduce it, which is how the imprecision surfaced.

## Why not a lock

`_advance` deliberately does not hold `self._lock`. A walk dispatches models and can take minutes;
holding the lock across it makes the whole HTTP surface unresponsive. That is task 1's guarantee and
it is right.

Three ways to close the hole, and the two rejected ones are on the record:

| | | |
|---|---|---|
| **Hold a lock across the walk** | correct | reintroduces exactly the unresponsiveness `_advance` exists to avoid |
| **Refuse the second caller** (`409`) | honest, non-blocking | **silently discards the effect of what the operator did** — the walk in flight built its config before that attachment existed, so the action is recorded and never acted on |
| **Coalesce** | ✔ | one walk at a time, and nothing dropped |

An attachment reaches **every** work order, so "recorded but never walked" would be the project's own
worst failure shape wearing a 409.

## What it does

A caller arriving during a walk sets `_walk_again` and returns the current snapshot — which says
`running`, and is true. The walk in flight, on finishing, sees the flag and goes round again with
the state as it now is. Several arrivals coalesce into **one** further walk, not one each.

Both flags are read and written only under `_lock`; the walk still runs outside it.

## Tests

Four behavioural, one structural:

- an attachment mid-walk starts no second walk, and **is** walked afterwards
- four attachments coalesce into one further walk, not four
- a walk that raises reopens the gate rather than wedging the runner shut
- **which entry points reach `_advance` without a state gate** is asserted to be exactly
  `["attach"]`, so a future caller added without one says so rather than waiting to be rediscovered

Verified by removing the gate: two tests fail, and the suite takes a minute longer because the
ungated walks pile up.

## Risk & rollback

- A caller that arrives mid-walk now returns `running` immediately rather than blocking or
  duplicating. No single-caller behaviour changes.
- The coalescing loop terminates when requests stop arriving; nothing re-arms it internally.
- Rollback: revert.

## Status


Accepted (see docs/acceptance/ACC-20260823-43.md) -- Pass. Cutting the gate fails exactly two behavioural tests, matching the change's own claim.

### Not claimed

**That this makes the run multi-writer.** One project, one runner, one run is still the design. This
stops one operator's second action from racing their first — it does not make the walk re-entrant.

**That coalescing is free.** An attachment posted during a long walk waits for that walk to finish
before it is acted on. The alternative was acting on it in parallel, which is the thing being fixed.

**That CHG-42's description of this was accurate.** It named `instruct()` alongside `attach()` and
`instruct()` was already gated. Corrected here rather than quietly.
