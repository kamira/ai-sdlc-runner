## The item, re-measured — and the first measurement was wrong

Item 11 of the handed-off queue: *"~34 wall-clock or tight-timeout assertions"* in the `wire`
cluster. Its line numbers are against `77b5c14` and no longer resolve, and the figure had not been
re-taken since. `ACC-20260908-05` re-scoped it once, on that same old tree, into 62 timing lines of
which four or five were actually tight — and closed nothing, correctly: it was measuring the
*ceilings*, and found the tightest at a 3× margin.

Counted again on `31535de`, by AST, and partitioned by **what a timeout costs** rather than by how
tight the constant is:

| | on `31535de` |
|---|---|
| wall-clock inside an assertion | **2** |
| `Thread.join(timeout=…)` with no `is_alive()` afterwards | **5** |
| `Thread.join(timeout=…)` with one | 1 |
| `Event.wait(timeout=…)` whose answer is discarded | **2** |
| `Event.wait(timeout=…)` whose answer is read | 1 |

**That first row read `0` for two revisions of this record, and it was a search artifact.** The

shape, in the class this record had declared empty.

The item's "~34" still does not reproduce as one class. But the sentence *"nothing asserts on
wall-clock anywhere"* was a claim about a search, not about the tree.

## The defect, constructed rather than argued

Shorten one join so it cannot complete, leave everything else alone, and read what the suite says.
Against `31535de`, in `test_an_attachment_during_a_walk_does_not_start_a_second_walk`:

```
E   AssertionError: the attachment was never walked
E   assert 1 == 2
```

The attachment **was** walked. What did not happen is the join. A reader is sent after a dropped
file that is sitting in the store. The same construction against the tree that ships here:

```
E   AssertionError: the walk did not finish inside the join's timeout, so what follows would
    blame the attachment for something the wait did not do
E   assert not True
```

The fifth join is worse than misleading: it is in `_config_nodes_keys`'s `finally`, with nothing
after it at all. Forced — join shortened to zero, guard deleted, whole file run — **no test fails**.
Not the one this record originally named as the victim, and not any other: that test takes its own
`threading.active_count()` baseline *after* this helper has already run, so a leaked thread is
inside the baseline, and its closing assertion is `<=`. The leak makes it pass more easily. Which
makes the guard added here the only thing in the file that would report the leak at all — a
stronger reason than the one first written, and the opposite of it.

## The two shapes, and why the repairs differ

`Thread.join` returns nothing whether it completed or not, so the function has to ask `is_alive()`
separately. `Event.wait` — and `Condition.wait_for`, and `Lock.acquire` — **return the answer**, so
discarding it is the same silence with a shorter repair: read it.

Both discarded `wait`s run **inside the walk**, on the background thread, and a walk cannot assert:
`Runner` catches what a walk raises and reports a stopped run — the behaviour
`test_a_failing_walk_reports_stopped_rather_than_looking_idle` exists to pin — so an assertion
there would be swallowed and the test would blame the runner for stopping. They record the timeout
where the test thread can read it instead.

The `finally` is the third case. Raising there would replace whatever the body was already failing
with, so it asks whether **this** `try` is failing — a flag set by the body's own `except`, not
`sys.exc_info()`, which reports whatever exception the *thread* is handling and would have made
this helper silent on the return path whenever a caller ran it inside an `except` block. When the
body is already failing it writes to `stderr` instead — not `warnings.warn`, which `-W error` turns
into the raise this branch exists to avoid — and that write is itself wrapped, because a closed
stream raises too. So the leak is reported unless the stream is gone, and never in place of the
diagnosis already in flight.

## The test that was not silent but wrong

`test_an_action_arriving_as_the_walk_decides_to_stop_is_not_stranded` passed on `31535de` and took
**10.21s** doing it. Its docstring says the third attachment is posted *"from inside the gap, by a
walk that blocks on its second call while another thread attaches"*, and forced
*"deterministically"*. Instrumented on the shipped tree, the order is:

```
walk #1 enters   0.01      the thread it was started on
walk #2 enters   0.02      the main thread, inside runner.attach("one.md")
wait returns False 10.03   released by its own timeout, not by the test
walk #3 enters   10.04
release_second.set()       10.04 — after the walk it was meant to release had ended
```

`attach()` ends in `return self._advance()`, and `_advance` walks **on the calling thread** when
nothing is in flight. The first walk did not block, so it had already returned by the time the test
attached `one.md` — and that `attach` therefore ran the second walk itself, on the main thread,
where it sat until the timeout let it go. The walk the third attachment was supposed to interrupt
had ended before the attachment was posted, and the thread named `first` had been finished since
the second millisecond. The test passed on the count alone, and cost ten seconds of every run.

The repair holds the **first** walk too, so the gate loop — and not the attaching thread — is what
runs the second. Same test, same assertions about coalescing, **0.04s**.

This does not change what the test is worth as a guard on the lost wakeup: its own docstring
already says it does not catch that window, and that
`test_the_release_and_the_decision_are_one_critical_section` is the load-bearing one. That sentence
was true before and is true now. What changed is that the coalescing it *does* cover is now covered
under the arrangement it describes.

## What ships

- Five joins say when they did not complete; the one in a `finally` says it without displacing an
  in-flight failure, and writes to `stderr` rather than falling silent when it cannot raise.
  `warnings.warn` was there for a revision — a warning is configurable into exactly that raise —
  and the write that replaced it is wrapped, because a closed stream raises as well.
- Two discarded `Event.wait` answers are read, by the only thread that can act on them.
- `assert took < 6.0` says what reaching that ceiling means.
- `test_every_bounded_wait_says_when_it_did_not_complete` — the rule, over `tests/*.py` by AST. It
  refuses a bounded `join` with no `is_alive()` **called on the same expression** in the same
  function, a `join` inside a `for`, `while` or comprehension answered for once outside it, and an
  answer from `wait`, `wait_for` or `acquire` that is dropped or kept in a name nothing reads. A
  ceiling counts when it is `timeout=`, or positional on `join`/`wait` and a numeric literal —
  `acquire`'s first positional is `blocking`. A lambda's expressions belong to the function that
  writes it, because a lambda has no statements and so can never hold the guard. It reports 0 on
  this tree and all seven of the repaired sites on `31535de`.
- `test_an_action_arriving_as_the_walk_decides_to_stop_is_not_stranded` runs its walks where it
  says it does, and asserts it.
- `BOUNDED_WAIT_CASES` and `test_the_rule_over_bounded_waits_refuses_what_it_says_it_refuses` —
  the rule's boundary run rather than described, including the false positive it costs.
- Eleven mutations under `--only bounded-wait`, all caught. Three pin the arrangement of the
  repaired test from three sides, and the third is what puts `ran_on` on the stand; one mutates the
  rule and expects the case table to refuse.

## What this does not do

- **It does not touch the timeout constants.** `ACC-20260908-05` measured the tightest of them at a
  3× margin and refused to write a defect sentence for the rest; nothing here disagrees. This
  record is about the branch where a ceiling *is* reached, which that measurement did not cover.
- It does not hold waits with no argument at all. A wait that cannot return early cannot
  misreport — it hangs, which CI reports as itself.
- It does not remove the polling loops. By AST there are, on `31535de`, **two** `sleep` calls
  inside a loop and three one-shot, all in `tests/test_server.py`; one of the two went with the
  test that was rearranged. A first version of this paragraph said *"12 `time.sleep` polling loops
  in five test modules"*, which counted text — including `time.sleep` inside subprocess source
  strings and inside a docstring — and called all of it polling. The survivor polls with a deadline
  and says what the deadline means; the three one-shot sleeps are fixed waits and were never polls.
- It does not hold the arrangement defect in general — that a walk started by `attach` may run on
  the attaching thread. The rule is static and cannot see it. `ran_on` names it in the one test
  where it was found. Two drafts of this record said **nothing could pin that line** — that every
  arrangement mutation is caught first by `gave_up`, because a walk on the attaching thread waits
  there for a release only that thread can send. A seat built the counterexample both times, and
  the second one holds: `walk` blocks only for walks 1 and 2, so a defect landing on the **third**
  leaves `gave_up` empty and `ran_on` alone to refuse. It is registered, and runs in 1.02s. The
  general defect is still unheld; that line is not.
