# CHG-20260828-18 — a mutation run that was killed left the source file mutated, and the next commit would have shipped it

- Project: ai-sdlc-runner
- Branch: claude/chg-20260828-18-a-killed-run-puts-it-back
- Date: 2026-08-29 (UTC+0)
- Type: a guarantee that held for exceptions and not for the case it was written about
- Proposed by: it happened — `git status` after a timed-out run
- Risk: **medium** — the harness writes to source files, and this changes when and how it puts them back
- Autonomy: high
- Related: CHG-20260828-01 (whose uniqueness guard is why the recovery lives in its own file),
  CHG-20260823-51 (which established green-before-red in this harness)

## What happened

`mutation_check.run()` restores in a `finally`, and says why:

> The restore is in a `finally` because leaving a mutated tree behind is a worse outcome than any
> result this function can report.

That is right, and **`finally` does not run when the process is killed** — which is the one case
where nobody is reading the output. A run stopped at a ten-minute timeout left:

```diff
-            if source.is_dir():
+            if False:
```

in `src/ai_sdlc_runner/worktree.py`. It was caught by a glance at `git status` before the next
commit, and only because the next thing done in that tree happened to be `git status`.

**That was the loud version.** The quiet one is a mutation *no test catches*: it leaves a tree whose
suite is still green, so nothing goes red, and a one-line `if False:` in a file the change did not
otherwise touch is exactly the kind of thing a diff review skims past.

## The change

The record of what is in flight lives **on disk**, written before the file is touched and removed
after it is put back. Nothing a signal can do to the process can reach it.

It holds the original **and** the mutated text, so recovery can tell three states apart:

| the file now matches | what happens |
|---|---|
| the mutated text | put the original back |
| the original | nothing to do; clear the record |
| neither | **refuse**, keep the record, and say to reconcile by hand |

The third is the one worth having. Somebody may have fixed the file, or moved on to real work in it,
after the run died — and writing a recorded original over that would destroy work this tool cannot
account for.

`recover()` runs at startup, before the baselines, because a tree left mutated makes every baseline
a measurement of the wrong code.

## The signal handler is not the guarantee, and the kill test is why

A SIGTERM handler was the obvious fix and it was written first. Then a real run was killed with it
installed, and it **did not fire**: on Windows `kill -TERM` becomes `TerminateProcess`, which no
handler can catch, the same as SIGKILL anywhere. `worktree.py` came back mutated.

Running the tool again printed:

```
  restored worktree.py, which a killed run left mutated
```

So the handler is kept for POSIX, where it makes cleanup immediate — and it is documented as the
part that is *allowed* to fail. The on-disk record is what holds.

The same test turned up a second thing: `kill -TERM <pid>` in that shell had stopped a wrapper and
not the Python child, so the first attempt looked clean while the run carried on mutating in the
background. Both survivors had to be killed by real pid, and both trees were recovered by the same
mechanism.

## And a test in the place a person looks

`test_this_repository_has_no_mutation_in_flight` fails the suite while a record exists. For the
quiet case — a mutation nothing catches — that is the only thing that would say so.

## A file cannot pin guarantees about itself

The recovery is in `tools/mutation_recovery.py`, and that is not tidiness.

`mutation_check.py` mutates by exact text, and a mutation's `before` string sits **in that same
file**. So every anchor into `mutation_check.py` appears twice — once in the code, once in the
definition naming it — and CHG-20260828-01's uniqueness guard correctly refuses all four. Moving the
recovery next door is what makes the harness's own safety net something the harness can break on
purpose and watch a test notice.

## The first four mutations were caught for the wrong reason

With the tests in `test_mutation_check.py`, all four came back `CAUGHT` — and every one of them
reported `1 failed, 7 passed`, stopping at test eight. Test eight is
`test_no_shipped_mutation_has_a_stale_anchor`, which walks every shipped mutation: breaking
`mutation_recovery.py` on purpose made the *other* stranded mutations' anchors stale, and the
meta-test went red **before any recovery test ran**.

This harness's own docstring warns about exactly this — *"a red is only meaningful against a green"*
and *"can the tests I wrote fail?" is not "did I write the test for the case that matters?"* The
tests moved to `tests/test_mutation_recovery.py`, and the four mutations now break tests at four
different positions, each one named for the guarantee it broke.

## Risk & rollback

- The harness now writes one extra file per mutation. It is gitignored and removed on the normal
  path; a leftover one is a signal, not litter.
- Recovery writes to a source file at startup. It only ever writes text it recorded itself, only
  when the file still matches the mutation byte for byte, and refuses otherwise.
- Rollback: delete `tools/mutation_recovery.py` and restore the inline `finally`. A killed run
  strands the tree again.

## Status

**Accepted** — see [ACC-20260828-18](../acceptance/ACC-20260828-18.md).

### Not claimed

**That the signal handler works.** It is measured *not* to, on this platform. It is kept for POSIX
and documented as the part allowed to fail.

**That a mutation cannot still be committed.** If somebody runs `git add -A && git commit` in the
window between a kill and the next `mutation_check` or suite run, this changes nothing — the guard
is a later reader, not a lock. Making it a pre-commit hook is a different change with a different
argument.

**That the other tools are safe.** `mutation_check` is the only thing here that deliberately writes
to source files, so it is the only one surveyed. `frozen_tree.py` and `session_record.py` were not
examined for the same shape.
