# CHG-20260907-09 - a node's kind, and what it promises about its edges

- Project: ai-sdlc-runner
- Branch: claude/chg-20260907-09
- Date: 2026-09-07 (UTC+0)
- **Measured against `origin/main` at `dccae44`**, pinned by sha; both reviewers were given a
  detached worktree at that commit rather than the tree being edited
- Type: behaviour and coverage. Two new `validate` rules and one pin, over a vocabulary that was
  never closed and two edge shapes that were never made exclusive.
- Risk: low - the shipped graph satisfies both new rules unchanged; measured, no node has both a
  `next` and branches, and every node's kind is one of the four.
- Autonomy: high
- Target ACC: ACC-20260907-09

## The finding (defect seat, L-3)

`MODES` has been a closed tuple since it was written, and `validate` has
`if node.mode not in MODES: raise`. `kind` has the same shape — four module constants, a field on
every node — and no such rule. Replacing one node's `kind` with the nonsense string `"stpe"` and
changing nothing else is **accepted on 23 of the 31 shipped nodes**:

```
step      ███████████████ 15/15 accepted
decision  █████░░░░░       5/10 accepted
loop      ██               2/2  accepted
terminal  █░░░             1/4  accepted
```

The eight refusals are not a kind rule. Five are the model-panel rule and three are
`permanent and kind != TERMINAL` — both firing on the node's *mode* and *flags*, not on its kind.

## A measurement of mine that a review seat refuted

I first measured whether each kind's own rule, violated *and* with the kind misspelled, is still
refused. It was, every time — by a different rule, naming a different node. I wrote that down as
"bad, but bounded": the reader is sent to the wrong node, which is exactly the mechanism that made
five reverse tests hollow in CHG-20260907-07.

The seat re-ran it per node and refuted it: **I had measured the four nodes that happen to have a
neighbour to trip over.** For all four kinds there is a shipped node where the kind's own rule is
violated, the kind is misspelled, and `validate` accepts it outright:

| node | its kind's rule, broken | before this change |
|---|---|---|
| `record_module` | a step with no successor | **accepted** |
| `done` | a terminal with an outgoing edge | **accepted** |
| `plan_scope` | a loop with one branch | **accepted** |
| `module_built` | a decision with one branch | **accepted** |

Both halves are true and neither is a defence: where a neighbouring rule fires it names the wrong
node, and on these four nothing fires at all. `test_a_kinds_own_rule_does_not_cover_that_kind_misspelled`
is parametrised over exactly these four, so a repair covering three of them cannot pass.

## What it costs at run time

`kind` is read at run time in one place, `engine.py:2856` (`if node.kind == graph.TERMINAL`).
`done` is the only node where nonsense both survives `validate` and reaches that line — the other
three terminals are `permanent`. With every gate confirmed and a real `engine.walk`:

```
kind='terminal'   state='finished'   halted_at='done'
kind='termnial'   state='finished'   halted_at=None
```

The run still finishes. It stops recording *where*. And `finished` there is not a computed answer:
the loop breaks on `node.next` being `None` and `_finish` returns a report whose `state` is still
the dataclass default at `engine.py:392` — the same shape as CHG-20260907-06, where a run that had
stopped reported that it had finished because nothing had overwritten that default.

The loss is not only in the returned report. `engine.py:2077` closes the **durable conversation
record** with `at_node=report.halted_at, why=report.halt_reason`, so the record of the run keeps
`None` and `""` for where it ended.

## A second rule, raised independently by both reviewers

`validate`'s reachability walk takes the **union** of `branches` and `next`. `engine.walk` takes
one **or** the other — `branches` if there are any, `next` otherwise. Nothing required them to be
exclusive, so a node could carry both and the guard and the run would then disagree about what the
graph is. Measured on the shipped flow, moving `reconcile`'s `unresolved` branch onto its `next`:

```
validate calls reachable : 31 nodes
a run can actually reach : 30 nodes
counted but unreachable  : halt_unreconciled
```

A halt becomes unreachable and the only guard over the flow says the graph is fine. This is
CHG-20260907-07's finding again in a different field: *the rule that guards the flow was measuring
a graph that does not run.*

`cli.cmd_flow` prints the dead edge too — `cli.py:480` prints `then → {node.next}` whenever a
`next` exists, in the command whose own comment (CHG-20260903-31) calls it the fastest way to see
what the runner will actually do.

### Where the two reviewers disagreed, and who was right

`codex` reported the other direction of this as *"the engine silently prioritizes `branches` over
`next`"*, so a `STEP` given branches would have a dead `next`. Measured, it is not silent — the run
dies partway through with

```
EngineError: node 'record_module' branches on ['again', 'stop'] but the run supplied
no choice for it — the engine does not guess a branch
```

which is a build-time-checkable declaration failing at run time, a different fault from a dead
edge. `fable` located the silence correctly: it is a `next` on a node that *does* branch, because
`next` is read only in the `else`. Both directions are refused by one rule; the record keeps the
distinction because the harms are not the same one.

## What does not ship, and why

**A rule separating `LOOP` from `DECISION`.** A closed set refuses nonsense; it does not refuse the
wrong member, and one member of this set means nothing. `LOOP` appears in exactly one condition in
`graph.py`, shared with `DECISION`, and nothing else in `src/` or `tools/` reads it. Measured:

| relabelling | accepted |
|---|---|
| both `LOOP` nodes as `DECISION` | **yes** |
| `DECISION` nodes as `LOOP` | **5 of 10** — the other 5 are caught by the model-panel rule, which is not about loops |

No structural rule can separate them either. Both candidates — *is on a cycle*, *has a back-edge* —
hold for 25 of the 31 nodes, because the flow is one cycle. That is the same fact that defeated two
of CHG-20260907-08's four candidate rules a change earlier. **Which kind a node is, is a
declaration**, so it is pinned rather than derived: `test_which_nodes_are_loops_is_pinned` names
the two loops, the four terminals, and the membership of `KINDS` itself.

**`Node.__post_init__` instead of `validate`.** Both reviewers, independently, said `validate`.
`Node` is a frozen dataclass, so construction is the only way a bad kind exists — but
`test_graph_validation.py` and sixteen pinned mutations are built on *construct a broken node with
`dataclasses.replace`, then watch `validate` refuse it*. A construction-time rule would make the
broken node unbuildable and take the reverse tests with it. There is also no constructor of `Node`
anywhere in `src/` outside `NODES`.
