## The gap, which happened rather than being imagined

A change number is claimed by writing `docs/changes/CHG-….md`. **Nothing reserves one**, and the
free list is worked out by looking at what is already there — on `main`.

| | change | claimed |
|---|---|---|
| PR #99, unmerged | *the two sandbox mechanisms are asserted separately* | **12:23** |
| PR #100, merged | *worktree isolation broke an agent that reads the filesystem* | ~**13:00** |

Both are `CHG-20260828-04`. The second is mine, and I picked it by reading `docs/changes/` on
<!-- kept at -04 deliberately: this section describes the number that was contested. The
     second claim was renumbered to CHG-20260828-14 on 2026-08-29. -->
`main` without looking at open branches.

**No check could see it.** Two files with one name cannot coexist in a tree, so `ledger_check`
compares nothing — each branch holds exactly one CHG-20260828-04 and passes. The collision surfaces
only as a merge conflict, after both branches have gone green separately, each looking correct.

That is the shape this repository keeps naming: a check that answers *safe* about something it never
examined.

## The check

For every change on this branch, if `main` has a file with that id and a **different title**, two
changes are wearing one number.

**The title, not the content.** Editing a record is not claiming one, and this repository edits
records constantly — CHG-20260827-21 gained two whole sections after it was accepted. An edit keeps
the headline; a collision has a different one, because two people writing two different changes do
not write the same sentence.

**When there is nothing to compare against, it says so.** On a shallow checkout `main` may not be
present. The run prints that the check did not happen and how to get it back, rather than passing
quietly — `--sandbox`'s rule, applied to a lint.

## What it does not do

It catches the collision at the **second** merge, not at the second claim. Whoever merges first
keeps the number; the other branch is told, by name, on its next CI run. Reserving numbers properly
would need somewhere to reserve them, and this repository's ledger is files in git.

That is a real limit and it is the honest one: this turns a silent conflict into a named refusal, and
it does not make the numbering safe.

## Risk & rollback

- Nothing in `src/` changes; the runner behaves identically.
- The blast radius is CI refusing a PR that takes a taken number, which is the point. A false
  positive would be a record whose title changed deliberately — that is a rename, and renaming a
  change is worth a conversation.
- Rollback: revert. The collision returns to being invisible.

## Status

**Accepted** — see [ACC-20260828-06](../acceptance/ACC-20260828-06.md).

### Not claimed

**That the numbering is now safe.** It is checked, not reserved. Two sessions can still pick the
same number; what changed is that the second one to merge is told, by name, instead of meeting a
conflict.

**That titles are stable.** A record whose headline is rewritten will read as a collision against
itself. That is a rename and it should be noticed, but it is a false positive if somebody expects to
retitle freely.
