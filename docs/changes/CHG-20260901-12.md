# CHG-20260901-12 — a person's "no" never reached the node it sent the run back to

- Project: ai-sdlc-runner
- Branch: claude/chg-20260901-07-10-v2
- Date: 2026-09-01 (UTC+0)
- Type: a second live defect on `main`, found by the same design panel
- Proposed by: the operator — 「mockup 如果遇到需要修正則需重新mockup交給用戶確認」, which is the
  loop this defect makes impossible
- Risk: **medium** — what every node reached by a rejection is asked
- Autonomy: high
- Related: CHG-20260901-11 (the first live defect from the same panel), CHG-20260901-07..10

## What happened

The operator asked for a mockup that is redrawn and re-confirmed when it needs correcting. The
design panel's defect seat had already measured why that loop cannot work — and it is not a
property of the proposed node. It is true of **eight shipped nodes** today:

```
pm_confirm      rejects_to=pm_plan            lead_task_review  rejects_to=fix_pass
lead_assess     rejects_to=pm_plan            lead_review       rejects_to=review_failed
pm_signoff      rejects_to=pm_plan            qa_verify         rejects_to=next_module
engineer_selfverify rejects_to=engineer_build qa_accept         rejects_to=acceptance_failed
```

A person refuses a gate with a reason. The reason goes into `report.rejections` as a prose line and
into the conversation, and **nowhere else**. `_order_for` — which builds the work order for the node
the run is sent to — never sees it.

Measured, refusing `plan_confirmed` at `pm_confirm` with a reason and reading both of `pm_plan`'s
work orders:

```
pm_plan order 1 mentions the reason: False
pm_plan order 2 mentions the reason: False
order 1 == order 2 byte-for-byte: True
```

**The same question, asked twice.** So the second lap produces the same plan, `pm_confirm` refuses
it again, and the loop turns until `max_steps` — where the operator is told `walk exceeded 200
steps`, which this repository's own note calls out as telling somebody the runner gave up rather
than what happened.

That is not "unbounded". It is **non-convergent**: no path through the loop can change its own
input.

## Why the fix is small

The channel already exists and is already used — for the *other* re-ask. When a model panel is
split, `carried` puts both sides' reasons into the next round's order, with a comment giving the
reason: *"'Somebody objected' is not something a reviewer can weigh."*

That is the same sentence about a person's rejection, and it was never wired.

## The fix

1. A `sent_back` ledger on the walk, keyed by the node `rejects_to` names, written where the
   redirect is taken. It carries the refusing node, the gate, and the reason.
2. `_order_for` takes it and folds it into `instructions`, beside `carried`.
3. **Spent, not read.** `sent_back.pop(node.id, None)` — a node reached again for an ordinary
   reason must not be told about a refusal it has already answered. That is what makes this a
   message rather than a standing property of the node.
4. A refusal with **no** reason says so: *"They gave no reason. Do not guess at one — say what you
   would need."* A model told only that it was refused will invent what to change, which is worse
   than being told nobody said.

## What this does not do

- It does not **bound** any loop. A person who refuses forever still refuses forever; what changes
  is that each lap is answering a different question. Bounding is a separate decision and every
  existing bound in this flow (`re_review`, `reconcile`, `change_retry`) is a graph edge, not an
  engine rule.
- It does not reach the **seats**. `intake_review` is a `SURVEY` and is not a `rejects_to` target,
  so the intake loop the design panel measured is untouched by this. That belongs with
  CHG-20260901-10's rewrite.
- It does not survive as history. The reason is spent on the next visit; `report.rejections` remains
  the record, as it was.

## Risk & rollback

- **Every node reached by a rejection is asked something different.** That is the change. A model
  that was producing the same output on a second lap will now produce a different one, which is the
  point and is also a behaviour change to every rejection path in the flow.
- **The order grows two lines** when and only when the run arrived by rejection.
- **Nothing is bounded that was not bounded before**, and nothing that was bounded is loosened.
- Rollback: revert. A person's reason goes back to being recorded and not delivered.
