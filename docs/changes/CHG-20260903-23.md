## ① L-26 — a red line the **plan** wrote stopped the run; the same sentence **typed by a person** did not

**FR-19 is P0:**

> A node's own brief — **every field of it** — is read against the red lines before anything else.

And `_spoken_halt`'s own docstring:

> **Every** field of the spec is read, not a chosen few. Choosing was the mistake, and it was the
> same mistake twice.

`_order_for` merged the operator's instructions and attachments into a **local copy** of the spec.
`_spoken_halt` read `cfg.node_specs` — the un-merged original. Measured by the seat:

```
A. red prose in the PLAN's node spec `instructions`  -> stopped at engineer_build
B. the SAME prose typed by the OPERATOR              -> ran to merge

what engineer_build was told in B:
  order['instructions'] = 'do the work\ninstruction 1 of 1: drop table users from the production database'
what _spoken_halt read for that same node:
  'do the work'   ->  None
```

Identical text, identical field of the identical work order. **The console's instruction box and its
attachments are the most likely runtime source of a red line, and they were the one path the scan
could not see.**

This is that docstring's mistake a **third** time, one layer out: not which **fields** are read, but
which **copy** of them. So the merge is now one function, `_brief`, and both readers go through it —
with a test that fails if a third reader ever merges its own copy.

After: an operator typing `drop table users from the production database`, or attaching
`deploy/production/config.yaml`, stops the run at `intake`, and the reason names the field.

## ② L-25 — approving an incomplete requirement bricked the run permanently

`server._require_suspension`'s comment is the rule: *"A gate asks whether the run may proceed; a tie
asks which way. Accepting one for the other would record an answer to a question nobody was asked."*

The engine emits **three** shapes and the check read `undecided` alone:

```
shape       incomplete  undecided   approve?   rule?
gate        False       False       accepted   refused
incomplete  True        False       ACCEPTED   refused     <- wrong
tie         False       True        refused    accepted
```

`intake_review` has no gate, so `approve()` stored `Approval(gate=None, …)` — and `walk`'s up-front
check then refuses it on **every** subsequent walk. `RunState.approvals` is only ever appended to and
read; there is no removal route, so the run was **unrecoverable short of `POST /run`**.

The refusal text was wrong too: at an incomplete stop it said *"waiting for a gate to approve"*. It
is waiting for a requirement somebody has to finish, and it now says so and names the route that
answers it.

## ③ L-24 — one of four operator-decision ledgers said when it went unused

`_finish`'s docstring is the rule:

> A confirmation the run never spent is **not** an error … But dropping it silently leaves the
> operator believing an approval was used, and it matters most for the gate they thought hardest
> about.

It was applied to the blanket `confirmations` count and to nothing else. `walk` holds three more —
targeted approvals, rulings, refusals — as locals it never handed over. Measured, a `low`-risk run
where everything aimed at `plan_confirmed` is unspendable by construction:

```
blanket  --confirm plan_confirmed  -> "plan_confirmed was confirmed 1 more time(s)…"
targeted Approval                  -> (silent)
Ruling                             -> (silent)
Rejection                          -> (silent)
```

`walk` states the rule twenty lines above the ledger it describes — *"an answer that cannot be
applied anywhere must say so now, **not be held and silently never spent**"* — and its **"One
ledger."** comment is about `confirmed` and `targeted` being one thing. `_finish` read half of it.
All four say so now.

## ④ L-28 — `sandbox.py` says three times that an unsandboxed run is recorded. Nothing recorded it.

> a run this machine cannot bound returns `enforced: False`, and **the caller records an unsandboxed
> run in the report and the export.**

Said in `sandbox.py`'s module text, again at `wrap`, and again in the `--sandbox` help an operator
reads. Measured: `cli._Process.sandbox` is touched on exactly two lines in the whole file — its
declaration and its assignment — and there is **no `sandbox` field on `RunReport`**. The only
surface was `print(f"sandbox: {describe()}")`, which reports what the **machine** can do rather than
what the **run** was granted, and vanishes with the terminal.

Counted on the factory, the way `isolated` already is, because only the factory sees more than one
ask — and appended to `report.relaxations` **before** the conversation closes, because *"this run was
not bounded"* is a statement about what the run was permitted to do, the same kind of fact as
`undeclared="allow"`.

## Risk & rollback

- **① stops runs that used to proceed.** Any project whose operator types something the red lines
  name now halts where it did not. That is the P0 requirement finally being kept, and it will read
  as a new refusal to whoever hits it first.
- **① widens what `_spoken_halt` reads on every node**, because the operator's instructions are
  appended to every ask. A run with a red word anywhere in a typed instruction stops at the first
  node that does work, which is `intake`.
- **② refuses an API call that used to be accepted.** A console that was approving intake stops was
  bricking its own run; it now gets a refusal naming `/run/instruct`.
- **③ adds lines to `report.confirmations`** on any run that supplied a targeted decision it did not
  reach. Nothing parses that list — it is prose in a report — but it is longer now.
- **④ adds a relaxation line to nearly every run on this platform**, because Windows has no sandbox
  mechanism. That is the honest reading of what has been happening and it will look like a
  regression.
- Rollback: revert. Each of the four is independent.
