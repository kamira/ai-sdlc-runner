## What is already there

`intake.ASPECTS` requires six things of a requirement and a run halts without them. Two are this
territory:

    ("flow", "the flow — what happens, in what order, and where it can go wrong")
    ("ui",   "the screen — what a person sees and what they can do to it")

And more than the first draft admitted: `intake.option_request` already asks a **model** for at
least three concrete options for any aspect asked three times and not supplied, `read_options`
refuses fewer than three, and they reach `report.options` and the console. For `flow` and `ui` that
is model-authored candidate mechanisms, put to a person to choose between.

**It is not this.** That path is a fallback for a conversation that has failed three times, on an
aspect the person did not supply. This is the ordinary path: a *complete* requirement, drawn so the
person can agree to the mechanism before anything is planned against it. But the first draft's audit
did not mention `option_request` at all, and the two must not grow into two ways of doing one thing.

`grep -rin "mockup\|wireframe" src/` finds **one** incidental mention, in the console's attachment
comment. Not two, as the first draft said.

## The design

```
intake_review → [CHG-10's acknowledgement] → mechanism_drawn? → pm_draw → pm_mechanism_confirm → pm_plan
                                                  │  supplied         ↑           │
                                                  └───────────────────┘           └─ no ─→ pm_draw
```

| | `mechanism_drawn` | `pm_draw` | `pm_mechanism_confirm` |
|---|---|---|---|
| kind | `LOOP` | `STEP` | `DECISION` |
| role | — (runner) | `pm` | `pm` |
| mode | `RUNNER` | `SINGLE` | `MODEL_PANEL` |
| gate | — | — | `mechanism_confirmed`, `after` |
| `panel_branches` | — | — | `{"pass": "yes", "fail": "no"}` |
| `rejects_to` | — | — | `pm_draw` |
| branches | `{"supplied": "pm_mechanism_confirm", "absent": "pm_draw"}` | — | `{"yes": "pm_plan", "no": "pm_draw"}` |

**Three nodes, not two.** The first draft claimed a supplied mockup would simply not be drawn, "the
same shape as `next_module`". That mechanism does not exist: `next_module` is a `LOOP` with
`mode=RUNNER` computing its branch from the report, and a `STEP` with a role always asks. This
repository has the exact counter-example — `module_built` is a guard `DECISION` added by
CHG-20260828-15 because a `STEP` walked onto an empty lap and `record_module` wrote a worklog entry
for a module nobody built. A guard node is how this flow says "not this time".

**`pm_draw`, not `mechanism`.** Every role-owned `STEP` here is a verb with its owner:
`pm_plan`, `sub_plan`, `lead_assess`, `engineer_build`, `fix_pass`, `qa_verify`. `mechanism` named
the artefact and said neither who nor what.

**`panel_branches` is declared**, which CHG-20260901-11 made possible. Without it this node would
have been the third unroutable one in the flow.

### The gate

    "mechanism_confirmed": {"low": CONFIRM, "medium": CONFIRM, "high": HALT}

**Not `{low: AUTO, ...}` mirroring `plan_confirmed`, and this is the correction that matters most.**
The first draft argued the gate would halt because `RunConfig.risk` defaults to `"high"`. It does —
and `cli.py` reads `risk=args.risk or plan.get("risk", "high")`, so the default applies only when a
plan omits the key. **All three shipped example plans declare `risk: low`**, and every documented
invocation passes `--risk low` on top. At `low → AUTO` this gate would never have fired on any run
this repository ships. The first draft proposed a stop that the repo's own examples turn off, in a
record whose sibling argues that a gate which cannot fire is decoration.

`merge` is the precedent for the shape that works: `{low: CONFIRM, medium: HALT, high: HALT}`, with
the reason *"it stops earliest of anything here — including at low risk, where it asks rather than
halts. 'Low risk' grades the change, not the door."* Building against an unconfirmed mechanism is
not a one-way door, but everything downstream rests on it, so it asks even at `low`.

### The redraw loop the operator asked for

`no` and a rejection both route to `pm_draw`, and CHG-20260901-12 is what makes that mean something:
the person's reason now reaches the node it sends the run back to. Before it, `pm_draw` would have
been handed a byte-identical work order and drawn the same picture — measured on `pm_plan`, where
two orders across a rejection compared equal.

**It is still not bounded.** `re_review`, `reconcile` and `change_retry` each have a terminal; this
does not, and neither does CHG-10's. That is open question 3.

## The cost, stated

Three new asking nodes with `role="pm"`, on the path every run walks. Two consequences the first
draft's Risk section did not mention, both measured by the panel:

```
$ runner run --plan examples/minimal/plan.json --risk low --confirm merge
stopped at: intake_confirm — does work that could change the world and declares no operations
--undeclared allow  →  node 'intake_confirm' has no work order: no node spec was supplied for it
```

`stopped`, not `suspended` — unresumable, three nodes in, before the PM is asked anything. Every
plan in existence needs a `node_specs` entry **and** an `operations` declaration for each new asking
node. The prototype's full suite was `316 failed, 1586 passed`.

`pm_draw` and `pm_mechanism_confirm` are asking nodes and carry this cost. `mechanism_drawn` is
`RUNNER` and does not.

## Open questions for the panel

1. **What the artefact is.** This runner writes files; it does not render images. Mermaid plus a
   described screen is the honest form, and the probe is that both parse. Prose that merely *claims*
   to be a flowchart makes `pm_mechanism_confirm` a stop in front of nothing.
2. **How `mechanism_drawn` knows.** It is a `RUNNER` node deciding from the run's own state, like
   `plan_scope` reading the plan's `workstreams`. What does it read — an artifact on the plan, a
   file on disk, an aspect answer? Nothing in the report holds a mockup today.
3. **Neither loop is bounded.** A person can refuse a mechanism forever. Every other loop in this
   flow ends at a terminal; a bound here means a fourth `halt_*` node, and the alternative is
   `max_steps`, which tells an operator only that the runner gave up.
4. **Does this subsume `option_request` for `flow` and `ui`?** Two mechanisms that both put
   candidate mechanisms in front of a person will drift. Either this replaces that path for those
   two aspects, or the record must say why both exist.
5. **Is the migration acceptable at all?** Four new asking nodes across this and CHG-10 would have
   been worse; this has two. Every plan still needs editing. The alternative — making the mockup an
   *aspect* and reusing CHG-10's acknowledgement — adds no node and no migration, and is not what
   was asked for.

## Risk & rollback

- **Every existing plan file stops working** until it declares specs and operations for two new
  asking nodes. Unresumable, three nodes in. This is the largest migration this flow has imposed.
- **Every run gains a stop before planning**, at every grade, including `low` — deliberately, or the
  gate fires on nothing this repository ships.
- **Together with CHG-20260901-10 there are two stops before `pm_plan`**, and nothing that early can
  tell a new project from a one-line fix: the grade that would is settled at `pm_signoff`, six nodes
  later.
- Rollback: revert. The flow returns to `intake_review → pm_plan`.
