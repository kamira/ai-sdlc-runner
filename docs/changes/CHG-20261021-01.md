# CHG-20261021-01 — the runner writes a run report from its own record

- Project: ai-sdlc-runner
- Branch: local/chg-run-report (from main after CHG-20261019-01's PR merges)
- Date: 2026-10-21 (UTC+0)
- Type: feature (runner): a report of each run, built from the run's conversation record. It
  adds a file and a read route, and changes no existing behaviour.
- Proposed by: the user, 2026-10-21 (「如果在runner測試驗證時也要提供報告的可行性?」, then
  「起草這個 CHG 給我看」)
- Risk: **low**. It only reads what the run has already recorded, and writes one new file per run.
  It sends nothing to any model. No existing output, route or schema changes. It is rolled back by
  reverting it. Reports already written stay on disk as plain files that nothing reads.
- Autonomy: high
- Related: CHG-20261019-01 (its `measure.py` and report are the prototype this moves into the
  runner); CHG-20260827-21 Task 6; the follow-up CHGs named below.

## Why

CHG-20261019-01's report was written by the orchestrating session, not by the runner. Its numbers
were computed by `measure.py` from the runner's own record. Its prose was written by a model, and
the DIR-3 panel caught that prose disagreeing with the record four times:
- the run 1 account, twice;
- an ask count;
- a coverage claim.

The user asked whether the runner itself can give a report when it runs and verifies a change. It
can. The material is already in the record:
- every `ASK` and `ANSWER` turn with its time;
- the instructions and the gate decisions;
- the person stops and their answers;
- the `relaxation` turns, such as unsandboxed asks;
- the usage the backend reported;
- `RunReport`: the visited nodes, the asks, the verdicts, the adjudications and the seat models.

What is missing is the step that puts these together. That step should be the runner's own, so
that every fact in the report comes from the record and none passes through a model.

## What changes

1. **A run report, written by the runner when a run reaches a terminal or resting state**
   (`finished`, `stopped`, or `suspended` at a stop that needs a person), and rewritten when the
   run resumes and rests again.
   - **Where.** Beside the conversation store: `<store-root>/reports/<run-id>.md` and `.json`. With
     `drive.py`'s state directory (CHG-20261019-01), that is outside the build model's workdir.
   - **What is in it.** Every item comes from the record, with the turn or field it came from:
     - **The run.** The brief as typed, the plan, the backends with their model, effort and reach,
       and whether each ask ran sandboxed.
     - **Time.** The time from the brief to the last turn, the time inside asks, the module loop's
       share, any time waiting for a person, the runner's overhead, and each node's asks with
       their total and mean seconds. This is `measure.py`'s computation, moved in with its tests.
     - **Spend.** Each ask's tokens and cost where the backend reported them. Where it did not,
       the report says "not reported" by name and does not show 0.
     - **Writes.** Every file under the run's outputs, with the ask whose interval contains its
       last write. A write by a node that is not a build node is flagged.
     - **Review and verification.** The seats' verdicts per dimension, the adjudications, and what
       `lead_review`, `qa_verify` and `qa_accept` answered, quoted from their answers and labelled
       as the model's words.
     - **Stops.** Each stop, what kind it was, what the person was shown, and the answer and its
       time.
     - **Limits.** Relaxations, an unsandboxed run, and seats that sat in for others. The report
       shows each one here and does not leave it out.
2. **`runner report <run>`** prints or rewrites the report for a past run from its record, so a
   report can be made again after the runner changes.
3. **`GET /run/report`** returns the latest report as JSON, and the console links to it from the
   run's panel. The JSON is the source and the markdown is rendered from it, so the two cannot
   disagree.
4. **No model writes any part of it.** A later change may add a prose summary written by a model,
   but only as a separate, labelled section whose every claim cites a field of the report. That is
   not in this change.

## Interpreted, and what it was chosen over

- **"報告" means a record-derived report, not a narrative.** The narrative parts of
  CHG-20261019-01's report are where the errors were, such as what went wrong and what to improve.
  The record can say what happened. It cannot say why something matters, and this change does not
  pretend it can.
- **Written at rest, not streamed.** A report per rest point is simple and complete. Streaming
  progress belongs to the console's per-node display (CHG-20261019-01 report §4 item 9), which is
  a separate change.
- **Kept beside the store, not in the workdir.** A build model with Write must not be able to edit
  the report of its own run (CHG-20261019-01 DIR-3 round 3).
- **`measure.py` moves into `src/`, and the measurement copy stays where it is.** The copy under
  `docs/measurements/CHG-20261019-01/` is evidence of how those numbers were taken, so it is not
  edited.

## Not in this change, proposed separately

These are needed for the report's "verification" part to show what actually ran, as opposed to
what a model said it checked:
- **QA that can execute** (CHG-20261019-01 report §4 item 8). A `qa_verify` that may run the
  built output in a confined environment and record the result and a capture.
- **The sandbox before write grants** (item 14). Without it, "the model could not have edited X"
  rests on behaviour nobody tested.
- **The console's per-node progress** (item 9). Captures during a run need it before they say
  anything.
- **A `follows` node's own grant** (item 2). This is the gap the user accepted on 2026-10-21 for
  `engineer_selfverify`.
