## The gap

Every session opened with the same line:

> 未收尾 CHG:CHG-20260823-51, CHG-20260827-17, CHG-20260827-18, CHG-20260827-19,
> CHG-20260827-23——先收尾再開新需求。

And every session ran `ledger_check`, which said:

```
ledger check passed (108 changes)
```

**Two readers, the same two files, opposite answers** — and the one wired into CI was the one saying
fine. The five changes each have an acceptance concluding **Pass**, while their own `## Status`
still reads `Under review` or `Proposed`.

## Why the lint could not see it

`check()` walks changes and asks *does a status that says finished have an ACC?* CHG-20260828-02
added the other direction: *does an ACC name a change that exists, and is it filed against the one
it claims?*

Both check that a record **exists**. Neither reads what either record **says**. So an acceptance
concluding `Pass` sitting behind a change marked `Proposed` is invisible to both, and the ledger
reports passed while an accepted change looks, to anyone reading it, like work still awaiting a
decision.

## The check

An acceptance **is** the decision. A change cannot still be waiting for one that has already been
recorded against it.

The verdict is read from the `Conclusion` field with the same discipline `_status_word` uses on
`## Status` — the head of the field decides, and the sentence explaining it does not. `Pass, on a
reduced scope that the operator approved` is a pass. The vocabulary is closed for the same reason
the two status vocabularies are: a word nobody wrote down is a question, not a pass. Checked against
all 107 acceptances in this repository — **0 unrecognised, 0 ambiguous**.

**Not every unfinished status contradicts a pass, and that distinction is the whole check.** A
change can be accepted and *later* superseded, halted, paused or withdrawn; an acceptance sitting
behind one of those is history. Only the statuses that say the decision **has not been made yet**
can contradict a record of it having been made. Applied to this repository, seven changes have an
unfinished status alongside an ACC, and exactly five of them are contradictions:

| change | status | its acceptance |
|---|---|---|
| CHG-20260823-48 | `superseded in part by CHG-20260823-51` | Pass — accepted, then superseded. Not a contradiction. |
| CHG-20260823-50 | `superseded in part by CHG-20260823-51` | **Withdrawn** — both seats returned `not sound`. Consistent. |
| CHG-20260823-51 | `under review` | Pass |
| CHG-20260827-17 | `under review` | Pass |
| CHG-20260827-18 | `under review` | Pass |
| CHG-20260827-19 | `proposed` | Pass |
| CHG-20260827-23 | `under review` | Pass, on a reduced scope |

The five it names are **exactly** the five the handshake gate has been naming. The two readers agree
now.

## Absence is not a problem

An acceptance with no `Conclusion` field is skipped, not flagged. The first draft made it a problem
and broke four existing tests — rightly, because that is a new *formatting* requirement, and
`_target_chg` already argues the case against one:

> Absence is not a problem here: older records predate the field, and inventing a requirement for
> them would turn a traceability check into a formatting one. What is checked is **disagreement**.

All 107 acceptances here happen to carry the field. Requiring it would still have been a second
feature wearing this one's number.

## The five are closed in this commit

Not left for later. A lint that ships red is a lint people learn to skip, and
`test_this_repos_own_ledger_passes` would have gone red the moment the check landed. Each one gets
`**Accepted** — see [ACC-…](…)`; CHG-20260827-23 says on the reduced scope, because that is what its
acceptance concluded.

## Risk & rollback

- The check can only add problems, never remove one. A ledger that passed before and has no
  contradiction still passes.
- Closing the five changes their `## Status` line and nothing else. No code, no tasks, no claims.
- Rollback: delete the check. The two readers disagree again, and the handshake gate goes on naming
  changes CI calls fine.

### Not claimed

**That the five were right to be accepted.** This reads what their acceptances concluded and makes
their changes agree. Whether each acceptance was sound is the question those records answer, and
re-opening it is not what a lint does.

**That every stale status is now visible.** The mirror — a change marked `Accepted` whose acceptance
did *not* pass — is deliberately **not** checked, and the reason is measured rather than assumed.
Two pairs here match that shape:

| change | status | its acceptance |
|---|---|---|
| CHG-20260823-17 | `accepted` | `superseded in its headline` |
| CHG-20260823-24 | `accepted` | `superseded` |

Neither is a defect. The **acceptance** was superseded by a later record while the change stayed
accepted, which is a different sentence from the one this check makes. Symmetry would have added
two false positives, and a lint that cries twice is a lint people stop reading.
