## ① `--worktree` says "require" and required nothing for a configured model

The flag's own help:

> **require each module to build in its own git worktree.** Without it a run isolates where it can
> and RECORDS where it could not; with it, **a machine that cannot make a tree refuses to run
> instead.**

`Trees.path_for` keeps the second half — it raises when the machine cannot make one. **`_cwd_for`
returned before reaching it** whenever the argv came from the model registry rather than
`agent_command`. So on a machine that *can* make trees, a module node run by a configured model was
quietly counted into the shared tree and the run continued.

That population is exactly `node_models` — what a project configures, and the entire subject of the
design review that found this. Measured, real git repo, `--worktree` on:

```
                    agent_command node    registry-model node
--worktree off      ISOLATED              shared / shell dir      <- recorded, as documented
--worktree on       ISOLATED              **not refused**         <- before
--worktree on       ISOLATED              REFUSED                 <- after
```

### A refusal, not a relocation

`_cwd_for`'s docstring is right and stands:

> A seat command or a registry command was named in the operator's shell and keeps the shell's
> directory; isolating it would change how its own relative path resolves, which is a different
> change from the one this record proposes.

This change does not move it. It **stops**, which is what the flag says it does — the posture
`--sandbox` already takes with its own require flag, and the seat's comparison: *two flags making
the same promise, one refuses and one counts.*

Without the flag, the existing behaviour is untouched and is pinned by its own test, so the refusal
cannot grow into the default.

## ② `plan.FIELDS`' drift guard looked one way

`FIELDS`' own comment claims both directions:

> each of these appears as a `plan.get(...)` in `cli.py`, and a test walks the source to prove the
> two lists **have not drifted apart**.

The test asserted `read <= set(plan.FIELDS)` and nothing else. The unchecked half is the one
`plan.check`'s refusal is about — *"Ignoring them would let a setting look configured and do
nothing"* — because a name in `FIELDS` that `cli.py` never reads is a key a plan may set, the door
accepts, and nobody acts on.

**Latent, not live**: both directions are clean today, measured. It is fixed because it is the
identical shape to CHG-20260901-17 M-3 — *a guard reporting "no drift" for the half it never looked
at* — in a different file, two changes later. `SHIP_FIELDS` had the same one-way guard and now has
the same two-way one.

## ③ Three sentences that were false

Found by the conformance seat's sweep for texts the design under review would falsify. These three
were already false, and are not that design's business.

**`engine.py` — and this one caused a real error.** A comment beside the panel-branch lookup read:

> `validate` is called by `cli.cmd_flow` and by the tests, and by **nothing on a `run`**

`graph.validate()` runs at the top of `walk`, before the loop, on every run. The comment was false
when it was written, and it was *believed*: the second draft of CHG-20260901-15 cited it and built a
task on the claim, and the conformance seat found the error one `grep` away. **A comment that is
wrong about where a check runs is worse than none, because it is the thing a reader consults instead
of looking**, and this one has the receipt.

**`docs/structure/logical.md`** said the lead's gate *"is consulted **before** the work"*.
CHG-20260901-14 moved it to `after` — and moved the resolution with it — for the reason the node's
own note gives: *"the thing a person is being asked to confirm IS the lead's assessment, and stopping
in front of it hands them an empty page."* `docs/structure/design.md` has said the corrected version
all along, so the doc set disagreed with itself.

**`docs/structure/data.md`** said settings has *"Two fields, both about the seat floor"*, over a
table of two. `settings.FIELDS` has three, and the third — `ordinary_commands` — is not about the
seat floor: it is about what a permanent-halt check reads. Both the count and the claim are fixed,
and the missing row is added.

## Risk & rollback

- **① turns a passing run into a refusal**, for anyone using `--worktree` together with
  `node_models` on a module node. That is the flag's stated meaning and it has never been enforced,
  so every such run has been reporting isolation it did not have. The refusal says which node and
  what to do about it.
- **① does not fix the isolation.** A configured model still runs in the operator's shell directory
  without the flag, exactly as `_cwd_for` documents. Whether that *should* change is a different
  change, and this one deliberately is not it.
- **② is latent.** Nothing fails today; the guard can now fail tomorrow. Adding a `FIELDS` entry
  without a `plan.get` in `cli.py` will turn it red, which is the intent and will read as a
  surprise to whoever adds one first.
- **③ changes no behaviour at all** — three sentences and one table row. Recorded as a change rather
  than folded into another because one of them was believed by a design record, and a false comment
  that produced a real error is worth its own entry.
- Rollback: revert. ① is the only behaviour change.
