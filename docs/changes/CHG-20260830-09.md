## Veto 1: the test destroyed the thing it was written to guard

`_guard_says` — added in CHG-20260830-08 to drive the in-flight guard — wrote and then unlinked the
repository's **real** `IN_FLIGHT`. It is the only helper that writes to it: the `sentinel` fixture,
whose docstring reads *"Point the harness's in-flight record at a temporary file, **never** the
repository's own"*, is what every other record-touching test uses. (~~"the only test in a 22-test
file that does not take the `sentinel` fixture"~~ — measured at the reviewed parent, the file held
**21** tests and **six** took no `sentinel`; 22 was the post-fix count. Corrected in
CHG-20260831-01, conformance seat.)

All twelve `stranded` mutations run that file. So on every mutation, this helper deleted the
harness's own record — the way back **and** the lock — while a source file sat mutated. Three seats
measured it independently:

```
apply() + _pytest(), exactly as run() does it:   20 passed, 1 skipped
afterwards:  record gone, subject still MUTATED, recover() -> None
             --recover prints "nothing in flight; the tree is as it should be"
a second run of the same suite:                  21 passed, over the mutated tree
```

A kill in that window leaves a mutated file with no record, no `--recover` path, and a guard that
cannot fire. That is the CHG-20260828-18 incident, reopened by the change whose entire subject is
that detector — and `restore_on_signal`'s own docstring says the handler does not fire on Windows
and *"`recover()` is therefore the guarantee"*, which is exactly what this removed.

The fix is the risk seat's own sentence: *the environment argument justifies the real env, not the
real record path.* `IN_FLIGHT` now honours `MUTATION_IN_FLIGHT`, the test points at its own file,
and the real record is never touched.

## The guard now checks an identity, not a variable

Skipping on `MUTATION_RUN` alone meant one stray `export MUTATION_RUN=1`, or the name appearing in
any CI environment, disarmed the detector everywhere and silently. `_pytest` sets it to
`os.getpid()` and `begin` writes that same pid as the record's `owner`, so the guard now requires
them to match — an identity between two things the harness wrote, not an inference about a process.

The **writer** half is pinned too. Deleting `MUTATION_RUN` from `_pytest`'s environment left 30
tests green, and then put every `stranded` mutation back to being credited to the guard.

## Two rulings, both taken

**`policy.adjudicate`.** The seat ruled the veto *rule* correct and must not change: a seat able to
decline its own veto makes the veto advisory, and counting votes on a matter of fact is what it
exists to prevent. What is wrong is the `reason` **string** — it reports a speech act (*this seat
vetoed*) where the code knows only a rule (*this seat holds a veto and did not pass*). Only the
string changed; `outcome` and `vetoed` are byte-identical, so no gate, class or graph edge moves.

**A void acceptance closing a change.** Ruled an error, and scoped: `superseded` means a change was
replaced, which is history; `void` means the verdict never held. `ledger_check._never_held` refuses
a DONE change whose acceptance is void. ~~It fires on exactly one pair — CHG/ACC-20260828-24~~ —
**it fires on none**: this same change set that record's status to `superseded`, which is not a
DONE status, so the branch never runs. Corrected in CHG-20260831-01, which is where the claim
should have been re-taken. The rule is prospective and needs no grandfathering date, unlike
`BRANCH_REQUIRED_FROM` and `TESTS_MUST_EXIST_FROM`. That
change's status now says it was superseded rather than closed.

## Risk & rollback

- `src/ai_sdlc_runner/policy.py` — **one string**. First `src/` change in three rounds, and it moves
  no outcome. §7 red lines (`GATES`, `PERMANENT_HALT_KINDS`, `CLASSES`, the graph) untouched.
- `tools/ledger_check.py` gains a rule that **fails** a state the ledger is currently in, which is
  why CHG-20260828-24's status changed in the same commit. Anyone reverting this must revert both.
- `MUTATION_IN_FLIGHT` is a second environment knob on the harness. It only moves where the record
  lives; a leaked value points the harness at a file it will not find, which fails loudly.
- Rollback: revert. The guard's test starts deleting the live record again.
