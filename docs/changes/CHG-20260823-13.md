# CHG-20260823-13 — The seats read the requirement before anybody builds against it

- Risk: **medium** — it adds a node to the flow and a mode to the graph, and every run now begins by

- Autonomy: high
- Related: CHG-20260823-11 (the console, attachments, the progressive brief), -12 (the flowchart)

## What was missing

A requirement went straight to `pm_plan`. Whatever the operator typed became a plan, and the first
time anybody asked whether the requirement was *answerable* was at `pm_confirm` — after a plan had
been written against it.

Now `intake → intake_review → pm_plan`, and the middle one is the seats reading what was asked for.

## A survey, not a vote — and this is the interesting part

Everywhere else in this runner, several voices are **adjudicated**: veto, then majority, and a tie
decides nothing. Here they are **collected**, and a problem one seat raised is kept whether or not
the other three agree.

That is the opposite rule, so it needs its reason:

> Adjudication answers **"may this proceed?"** — a question with one answer, where counting is how
> you get it. Intake answers **"what is wrong with this?"** — a question with as many answers as
> there are things wrong, where counting **destroys** the information. A problem three seats missed
> and one saw is still a problem, and outvoting it would be the panel agreeing not to know
> something.

So `graph.SURVEY` is the one mode that reaches no verdict. No veto, no tie, and `policy.adjudicate`
is never called. The user asked for exactly this — *「這次不達成共識而是統整出所有問題」* — and it is
worth recording that it is a deliberate exception rather than an oversight, because every other
multi-voice node in this system works the other way.

Each seat also keeps its **own** findings rather than being flattened into one list: *who saw this*
is most of what makes a problem actionable.

## The six aspects, and being asked three times

A requirement is expected to say six things: **flow, architecture, requirements, inputs, outputs,
UI**. The list is closed, because an open list is one nobody can be incomplete against — and
"incomplete" is the whole point.

Missing any of them is not "bad", it is **incomplete**, which gets a different response: the run
stops before anything is planned and says exactly what it does not have.

Asking again is the right first move. Asking forever is not. After the third unanswered ask for one
aspect, the runner **stops asking and puts at least three options on the table**:

- **Three**, because two is a false choice and one is a decision wearing a question mark.
- **It does not pick one.** The options widen the decision; they do not make it.
- **A model authors them**, recorded as an ask like any other. A runner that quietly writes
  requirements has stopped being a runner.
- A model that returns fewer than three is **refused**, since the point of reaching this stage was
  to stop narrowing somebody else's decision.

`>=` and not `>`: the third unanswered ask is the one that has failed, not the fourth.

## No gate

`intake_review` has none. What stops a run here is the requirement being incomplete — not a risk
grade. A gate firing on a *complete* requirement would be asking a person to approve the absence of
a problem, and one that never fires is decoration, which `policy.py` says in as many words. The first
version of this change added a `requirement_read` gate that halted at every grade; it stopped 212
tests and it was wrong for this reason.

## Driven live, four instructions

```
1st: "Make it better."                              missing: flow, architecture, requirements, outputs, ui
2nd: + "must accept a date … return a label"        missing: flow, architecture, ui
3rd: + "the flow is: parse, classify, render"       missing: architecture, ui
4th: + "still not sure about the rest"              missing: architecture, ui  → OPTIONS, three each
```

Five seats' worth of findings unioned at the first stop; each later instruction narrows it; the
fourth triggers the escalation. **Nothing was planned or built at any point** — the run never got
past `intake_review`.

## The defect this found

**`/run/instruct` did not re-walk.** The instruction landed, the version moved, the snapshot came
back — and **nobody was re-asked**. So the seats went on reporting what the *first* instruction had
not said, however much was added afterwards. "Add to the brief" looked like it worked and changed
nothing anybody could see.

Found by driving it: `intake asks so far: 1` after three instructions, with identical findings each
time. `instruct` and `attach` now walk again, which is safe for the reason CHG-20260823-11 already
established — the journal reuses every answer whose question is unchanged, and a changed brief
changes every question, which is precisely when re-asking is correct.

## Risk & rollback

- **Every run now begins by stopping** if the requirement is thin. That is the intent, and it is the
  one behavioural change existing users would notice.
- 24 tests updated where the flow genuinely moved — the first asking node is no longer `pm_plan`.
  Two of those updates were fixtures using a **proxy** for the thing they meant (`Recorder` treated
  "the first panel" as "the review panel"), which is the same lesson this repository keeps learning
  and is now written next to both.
- Rollback: the node and the mode; nothing persists.

### Not claimed

**That the seats are good at this.** The demo's seats look for *words*. A real model reading a real
requirement is the point, and how well that works is not something this change can assert.

**That six aspects are the right six.** They are the ones the user named. The list being closed is
defensible; its contents are a first answer.

**That the escalation is the right shape.** Three asks then three options is a rule with a reason,
not a measured one.
