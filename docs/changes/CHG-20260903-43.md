## Read this first

```
policy.GATES["merge"]     low: CONFIRM     medium: HALT     high: HALT
policy.py:291             "a halt is not a question"
policy.py:53              STOPPING = (CONFIRM, HALT, HALT_INDEPENDENT)
                          "Anything that is not `auto` stops the run"
```

Measured:

```
merge at risk low      -> confirm     asks
merge at risk medium   -> halt        stops
merge at risk high     -> halt        stops
```

And what the documents say:

```
docs/structure/logical.md:59   "a one-way door has to be stopped in front of, not behind,
                                so it asks at every risk grade"
docs/ARCHITECTURE.md:62        "merging is a one-way door, so it asks at every grade."
docs/ARCHITECTURE.md:64        "auto proceeds · confirm asks · halt stops for a person"
```

**`ARCHITECTURE.md` defines the word two lines below the sentence that misuses it.** Its legend
separates *asks* (`confirm`) from *stops for a person* (`halt`), and merge is `halt` at two of the
three grades.

## The right sentence already exists in the code

`STOPPING`'s own comment is the accurate claim: *"Anything that is not `auto` stops the run."* Merge
**stops** at every grade — which is the property the surrounding argument actually needs, since the
point is that a one-way door is not passed silently. It *asks* at exactly one grade.

So this is not a case of the documents being roughly right. The sentence they use is the weaker
claim **and** the wrong word, in a file that had already written the correct vocabulary down.

## Why a documentation fix gets a rule

Editing two sentences fixes today. A third document, or a re-worded fourth, brings it back — and
`docs/` has already had a round of this (CHG-20260903-37, six documents describing a different
program). The guard derives from `policy.GATES`: **a document may say a gate "asks at every grade"
only if every grade of that gate is `CONFIRM`.**

That is a rule over instances rather than a pin on two lines: it holds for gates nobody has written
about yet, and it goes red if `GATES` changes under a sentence that was true when written.

## The second finding shrank when it was measured, and that is the result

`tools/session_record.py` says it records *"what the command **emitted**, plus the command line
itself as the first event."* Measured:

```
docstring     "plus the command line itself as the first event"
first event   [0.1106, "o", "hello from the child"]      <- the child's output
the command   header["command"] only, never an event
```

`events = []` and the first `append` is the first chunk the child wrote. The command is **not** an
event and never was.

**But the effect the sentence promises is delivered**, by a different mechanism:
`tools/render_cast.py:107` reads `header["command"]` and renders it. A person reading a cast does
see what was run.

So the fix is the sentence, **not the recorder**. Emitting the command as event 0 — the change the
docstring's wording invites — would print it **twice** on every rendered page, once from the header
and once from the stream. Writing that down because taking the sentence at face value and "fixing
the code to match" was the obvious move, and it was the wrong one.

## The rule passed twice by examining nothing, for two different reasons

Both were found by mutating the sentence and watching the rule **not** go red — not by reading it.

**First: markdown emphasis inside the phrase.** `ARCHITECTURE.md` writes `**stops** at every grade`
and the rule searched for the literal `stops at every`. It matched **nothing at all** in that file,
before or after the mutation. It appeared to work only because `logical.md` happens to be written
plainly. The rule now strips emphasis and flattens each paragraph — it reads prose the way a person
does.

**Second, and this one was my own reasoning, not the code**: I wrote the rule on the assumption that
a document naming the act would name the gate, because *merging* contains *merge*.

```
"merge" in "merging"   ->   False
```

It does not. The fifth letter is an `i`. I asserted it twice while reasoning about why the mutation
survived, and both times the measurement is what settled it. Gate ids and prose are two vocabularies,
and a rule that polices claims about gates has to know both: `_forms` accepts the id plus the
ordinary words built from its stem.

```
ARCHITECTURE.md says asks, plainly     ██████████  red
ARCHITECTURE.md says asks, in bold     ██████████  red
logical.md says asks again             ██████████  red
the rule forgets prose word forms      ██████████  red   <- the floor
the floor stops checking the policy    ██████████  red
```

## And my first edit made the document worse

The first version of the `ARCHITECTURE.md` fix narrated its own history — *"It said asks at every
grade, two lines above the legend…"* — inside the section that should simply say what the gates do.
That belongs in this record, and it put the wrong phrase back into the very file the rule polices.
Rewritten as a statement.

## Risk & rollback

- **A reader planning around the old sentence expected a prompt at high risk** and would have got a
  permanent halt that routes to a named function. That is the actual behaviour and it is stricter,
  not looser, so nothing unsafe was authorised by the wrong word — but a person building an
  expectation of "I will be asked" was building it on a sentence the code contradicts.
- **No behaviour changes.** `policy.GATES` is untouched; whether merge *should* halt at medium is a
  separate question this does not open.
- Rollback: revert. The one-way door is described with a word the same file defines as something
  else.
