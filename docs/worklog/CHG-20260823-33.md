# Worklog — CHG-20260823-33, the recording machinery

Written while the work happened. What the cast and the replay cannot show: what was decided, on what
evidence, and what was abandoned.

## The ask

> 之後錄影整個過程我要review

Four readings were possible and they lead to materially different work, so I asked rather than
guessed. The answer was three of the four: a **runner execution playback**, a **development process
log**, and a **terminal session capture** — not a screen-recorded GIF.

That answer decided the shape: build the recording machinery first, then do the two pending changes
under it. A camera built after the filming records nothing.

## What was built, and one thing that was not

- `tools/session_record.py` — wraps a command, tees its output, writes a cast.
- `tools/render_cast.py` — a directory of casts to one self-contained page.
- `--format playback` — the fifth export format.
- `docs/RECORDING.md` — what each recording answers, and what it is silent about.
- This file, as the convention for the third.

**Not built: a GIF recorder.** It was offered and not chosen. It would also have been the weakest of
the four — it can only capture what a browser shows, and the terminal is where this work happens.

## Decisions, with what settled them

**The cast format is asciinema v2, the player is ours.** The data shape is one that already exists
and can be read by tools that know nothing about this repository; a private format would have made
every recording depend on this repo staying alive. But an external *player* is a network fetch, and
a recording that needs the network to replay is not a recording you can keep. So: standard data,
local player.

**One cast per command, not one per session.** A single growing file needs a lock the moment
anything runs concurrently, and a half-written trailing event from a killed process corrupts the
whole session rather than one command. A directory of small files has neither problem.

**The recorder forces the child unbuffered.** This one is a real trade and it is worth naming. It
*changes the child's behaviour*. The alternative is worse: Python line-buffers to a terminal and
block-buffers to a pipe, and a recorder is always a pipe, so a script printing steadily for two
minutes records as **one event at the end** — every timing gone. Forcing unbuffered brings the
recording closer to what a person at the terminal would have seen. Measured before and after: the
same driver recorded **2 events** buffered and **10** unbuffered.

**`playback` and `html` share `_stops()`.** They were separate for about ten minutes. Two renderings
of one run that disagree about where a stop begins make both untrustworthy, and there is no way to
notice the drift from either page alone. One function, and a test that asserts the rail length, the
stop count and the waterfall's markup all agree.

## What was got wrong, and how it was found

**The first replay was three seconds long.** 55 turns, no gaps over the cap, total playback 3.0s —
strictly accurate and completely unwatchable, because the stand-in agent answers in milliseconds.
Found by opening it, not by reading it.

The fix is `MIN_BEAT`: a turn plays for at least 0.35s however fast it was. That is a *legible*
rendering of real time rather than a literal one, so the page says so in its own header. It
compresses the ratio instead of erasing it — a 40s seat still lands six times longer than its
neighbour, which a test now pins.

**An injection vector in the replay, found by a test.** The playback embeds turn bodies as JSON
inside a `<script>` block. The waterfall escapes model text for *markup*, and I reused that mental
model without checking where this text actually lands. It lands in script context, where the rules
are different: a literal `</script>` inside an answer ends the block early and everything after it
parses as page content.

The test that caught it used `<img src=x onerror=…>`, which is inert inside a JS string — so the
first version of the test was arguably testing the wrong thing while pointing at the right bug. I
then wrote the test for the vector that actually matters: an answer containing `</script><script>`
and `<!--`. A model writes that sequence the moment it is asked about HTML, which this repository's
own tide example does.

Fixed at the JSON level (`<`, `>`, `U+2028`, `U+2029`) rather than by matching sequences, because a
fix that depends on enumerating dangerous strings is a fix that depends on my enumeration being
complete.

**Heredoc backslash mangling, twice more.** `\\u2028` in a test assertion collapsed to a literal
`U+2028`, producing a test that contradicted itself one line later — and the function under test was
correct the whole time. This is a documented rule of my own, broken again. Both files were fixed
with the editor rather than the shell.

**A test that read a comment.** `test_the_driver_does_not_depend_on_the_callers_locale` grepped
`scenarios.py` for `text=True` and failed on the comment explaining why it is *not* used. Rewritten
to read the `subprocess.run` keywords out of the syntax tree. Third instance of this class this
session.

## Not claimed

**That these recordings prove the work is correct.** They show what ran and what came back. A green
suite recorded is still a green suite — the recording adds reviewability, not correctness.

**That the terminal capture is complete.** It records what commands emitted. It does not record
input (no pty), and it only holds the steps I chose to wrap. A step run outside the recorder is
absent from it without leaving a hole, which is the honest limit of this design and the reason the
worklog exists alongside it.

**That the playback timings are literal.** They are compressed at both ends and the page says which.
