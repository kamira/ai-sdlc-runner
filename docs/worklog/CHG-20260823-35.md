# Worklog — CHG-20260823-35, removing the Mongo and TinyDB backends

Recording at `docs/recordings/chg-35.html`. This is the part it cannot show.

## Why this was still open

The ruling — *「只留 sqlite + file，移除 mongo 和 tinydb」* — was given, reviewed by both seats, and
**merged as design** in CHG-20260823-19. The code never caught up: `--store {file,tinydb,mongo}` was
still in the CLI three changes later. I found it while reading `export --help` for something else.

That gap is worth naming, because it is the shape of a defect this repository refuses everywhere
else: a decision that looks made and does nothing. Merging the design closed the argument, not the
surface.

## The scope decision, and why it is not the whole ruling

The ruling has three clauses. Only the first is a self-contained unit:

1. *「只留 sqlite + file，移除 mongo 和 tinydb」* — **this change.** Unambiguous, reduces surface,
   nothing depends on the removed code.
2. *「file 只作為 server 的 config 才處理」* — file for server config only, which means conversations
   move **into** SQLite. Not done here.
3. *「sqlite 內容不僅限於紀錄，也包含 model 模型配置」* — already done: `store.py` holds `models`,
   `node_assignments`, `seat_assignments`.

Doing (1) alone leaves `file` as the *only* conversation backend, which is momentarily at odds with
(2). I judged that acceptable and it is worth defending rather than glossing: three backends where
the ruling wants one is further from (2) than one backend is, so this is a step toward the ruling
rather than away from it. (2) is a data migration with an importer, and `docs/design/sqlite-only.md`
says in its own words that the proposition is *"corrected but still unreviewed in its corrected
form"* and that *"implementation should not start on the assumption"* a fourth review round finds
nothing. That is a change that needs a review round, not a rider on a deletion.

## What came out

About 250 lines. Most of it was not backend code — it was **Mongo URI hardening**:
`local_mongo_uri`, `_unix_socket`, `_hardened`, `MONGO_OPTIONS`, `LOOPBACK_HOSTS`, and eleven tests.

That code was some of the most carefully reasoned in the repository. `MongoClient` performs topology
discovery, so a loopback *host* was never the check: a loopback seed that turns out to be a
replica-set member is read from the server and every member it names gets connected to. The check
needed a single-host `mongodb://` URI, a host that round-trips to loopback, an option **allowlist**,
and `directConnection=true` forced on the client — and an earlier denylist version was got past
twice by a seat (`?proxyHost=…`, and `?replicaset=` walking past a check spelled `replicaSet`).

Deleting it is the right call and it is still a loss of reasoning. The README now carries the
summary of *why* it was that shape, because someone will eventually propose a remote store again and
the argument should not have to be rediscovered.

## The one guarantee this genuinely weakened

A duplicate `seq` used to be **refused at write time** by Mongo's unique index and TinyDB's check.
Neither exists now. `file` cannot refuse one without a read per append, so a duplicate is now
**detected at read time and prevented nowhere.**

I found this by reading a comment that had become false, not by any test failing — the comment said
"refused by the two backends that can", and there are no longer two backends that can. That sentence
would have quietly survived the removal and gone on claiming a guarantee nothing kept, which is the
exact defect (a name standing in for a constraint) this project's log is full of.

It is written down in three places now: the module comment, the README, and a test that appends a
duplicate `seq` directly to the file and asserts the reader *reports* it. Acceptable because the
design declares one writer per conversation — and it is the first line that has to change if that
ever stops being true.

## Two tests of mine that read vocabulary instead of behaviour

Both written today, in this change:

- `test_the_locality_flags_went_with_the_backend_that_needed_them` grepped `cli.py` for
  `--store-remote` and failed on **the comment explaining why the flag is gone**. Rewritten to build
  the argparse parser and inspect its `dest` set. Third instance this session.
- Then the README gate caught *me*: my new prose said "`--store-uri` and `--store-remote` went too",
  and `test_every_cli_flag_the_readme_names_actually_exists` refused it, correctly. I reworded
  rather than loosening the gate — a check that learns an exception for prose stops being a check.
  My first rewording added a parenthetical containing the literal `--flag`, which tripped the same
  gate again.

That last one is a small comedy but the principle held: the gate was not weakened, twice.

## Not claimed

**That the ruling is now implemented.** One clause of three. Conversations are still in the file
store, which clause 2 says they should not be.

**That nothing used these backends.** Nothing in this repository did, and no test exercised them
against a real server — the eleven Mongo tests all tested the URI *string* rules. An operator with a
local mongod and a `--store mongo` config now gets a refusal that names the change.

**That the removed reasoning is preserved.** A README paragraph is a summary. The full argument is
in the git history and in `docs/design/reviews/conversation-store-*`.
