# Worklog — CHG-20260823-38

The first review round in this project where I sent work out and got `not sound` back from both
seats on things I had shipped and believed.

## The gap that caused it

Fourteen change records marked **Under review**; no seat had read a single implementation; the last
acceptance record was four days old. I had been shipping on green CI and my own tests. Green CI
proves the tests pass. It says nothing about whether the tests test the claim — which is this
project's documented failure mode, and which is exactly what both seats found.

## Where they agreed

Both, independently, named the `paths.py` coverage overclaim as the worst thing in the batch. Both
found the `render_cast.py` injection. Both verified the `instructions` asymmetry against
`engine.py:515` and both said it stands. That much agreement on a first read is itself information:
the batch was not uniformly bad, and the two defects were both **claims** rather than code.

## Where they split, and how it was settled

The `NAME_MAX` unit.

- **fable-seat**: "the `NAME_MAX` per-component refusal is genuinely cross-platform." Sound.
- **codex-seat**: "Windows filesystem component limits are not measured in UTF-8 bytes… rejects 100
  CJK characters… not the Windows rule." A defect.

A split does not pass, and averaging is forbidden. So I ran it:

```
chars: 100 | utf-8 bytes: 300 | utf-16 units: 100
the filesystem ACCEPTED it -> True
paths.check REFUSED it
```

codex-seat was right; fable-seat had reasoned about the module rather than testing that case. Settled
by the filesystem, not by preferring a seat.

Worth noting what fable-seat got that codex-seat did not: the specific observation that
`attachments.py` **still carries the 32-character band-aid** while bypassing the fix written to
replace it, and that `attachments.py:139` has a comment *describing* the failure mode it is still
exposed to. That is the detail that makes the overclaim sting.

## The one that should worry me most

Not the injection — that was a missed sibling, and the fix is mechanical.

It is `test_the_limit_is_counted_in_bytes_not_characters`. I wrote a test that asserted the limit was
counted in bytes, which is what my code did, and it passed while the code was wrong. I have now
caught this class three times in one session by *failing* on correct code, and this is the first one
that shipped — because it passed on incorrect code and nothing distinguishes those two from inside.

The replacement asks the filesystem. That is the only form of this test that could have failed.

And the defect fell only on non-Latin names. A Latin name hits 255 bytes and 255 characters at the
same moment, so the entire original test set was structurally incapable of noticing. This repository
is operated in Chinese by someone whose project names are Chinese. The test set reflected the code's
author, not its user.

## A confound in my own new test

The first version of the filesystem-truth test failed four of nine cases against **correct** code. I
was probing with the plain API, so `tmp_path`'s own depth pushed the total path over MAX_PATH — a
different limit, and the one the prefix already lifts. Probing through `paths.real()` isolates the
component question, which is what `check` is actually about.

Small, but the same shape as everything else here: a check that fails for a reason other than the one
it names is as useless as one that passes for a reason other than the one it names.
