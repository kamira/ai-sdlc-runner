## What the seats called unsafe

### seat: defect

- The CWA key is a secret the user types into the page. The spec puts it in the URL query string ([redacted:Authorization] and that is how CWA works. It will therefore appear in the browser history of fetch requests (not the address bar), in devtools, and in any proxy or server log. This is inherent to CWA. A builder must not log the URL (console.log, error text, a 'source URL' line), must not persist it in any way beyond localStorage, and must not put it in a page hash or search. The stored key stays readable by any script on the same origin, and file:// shares an origin in some browsers. State this risk to the person who uses the page, and keep the password field with autocomplete=off.

## Problems the seats raised

- conformance: With the CWA source, the spec does not say where today's hourly temperature curve comes from. F-D0047-063 is a weekly forecast with 12-hour (and some 3-hour) steps, and O-A0003-001 is a single observation. A true hourly curve is therefore not available from CWA. Without a stated rule, the builder might invent interpolated points, which the no-made-up-numbers rule forbids. The spec should say whether the chart shows only the real CWA points or shows an error or empty state.
- conformance: The spec does not say what happens when a key is entered and the CWA request fails. It should state that the page shows an error naming CWA and does not fall back to Open-Meteo, because a silent fallback would mislabel the source.
- conformance: The spec does not say whether opendata.cwa.gov.tw allows cross-origin requests from a page opened from file://. If it does not, the CWA source cannot work in a pure static page. The error state must then name CWA as the failed source.
- conformance: 'Timeout' is listed as a failure condition, but no timeout value is given, so the builder has to choose one.
- conformance: The CWA key has to go in the Authorization query parameter, so it is part of the request URL. This conflicts mildly with 'not shown in URLs'. The spec should say this applies only to the page's displayed URL and address bar, not to the outgoing request.
- conformance: The expected_outputs and acceptance_predicate say 'all ten files exist and parse', but this seat has can_write false and the order says not to create or change files. This seat can only judge conformance, not build.
- conformance: The order also says to build one module at a time, but the schema asks for a single review answer. Nothing blocks the review.
- defect: Weather-code display is unspecified: the Open-Meteo query requests weather_code (current and daily), but no module or UI element shows it, and no WMO-code-to-label mapping is defined. It will go unused, or each implementer will invent a different mapping. The same applies to wind_speed_10m, which is fetched but never shown. Decide whether to display both or drop them from the query.
- defect: CWA field mapping is not given. F-D0047-063 and O-A0003-001 return deeply nested, element-based JSON: ElementName values for temperature, humidity, PoP12h and so on. The brief names no locationName or element names. It does not say which Taipei district to use, since F-D0047-063 holds all 12 districts of Taipei City. It does not say which station fields to read from 466920, or that the 'Taipei' station is not at 25.0330N 121.5654E. Example: the first location in the response is taken, so the page shows a different district's forecast under a heading that says Taipei. Pick one district and state it.
- defect: CWA reports rain chance in 12-hour slots (PoP12h) and temperature in 3-hour or 12-hour slots. Open-Meteo gives a daily max, a daily min and an hourly series. normalize.js cannot get a per-day max and min or an hourly curve from CWA without aggregation rules. The brief gives none. With CWA, 'today's hourly curve' is only 3-hourly points, or has none. The page would then either show an empty chart or interpolate, which is made-up numbers and is forbidden. The spec needs a defined behaviour for the CWA chart (3-hourly points, labelled as such).
- defect: CWA data is missing in normal operation: O-A0003-001 returns -99 as a sentinel for missing values, and humidity can be '-99' or null. If this is shown, the page prints -99°C. The brief says 'wrong format shows an error' but does not say a sentinel counts as one. Spell out that sentinel and null values become 'no data' for that field, not a number and not the whole source failing. The same applies to precipitation_probability_max, which Open-Meteo can return as null for some days.
- defect: The key-bearing URL contradicts 'not shown in the URL display'. CWA takes Authorization as a query parameter, so the key sits in the request URL. The spec forbids it in the page and in the address bar display. But error messages that echo the failed URL or err.message, a source-URL line on the page, and the console would all leak it. The error state must be built from the source name and status only, and never from the request URL. Add this to the rules for cwa.js and app.js, and name it in the acceptance check.
- defect: The CORS assumption is unverified. opendata.cwa.gov.tw may not send Access-Control-Allow-Origin for browser calls, and from file:// the origin is null. If it blocks, every CWA attempt fails. The spec says the key is only used when typed, so there is no way back to Open-Meteo without clearing the key. Behaviour after a CWA failure is undefined: show the error only, or offer to retry or clear the key? Falling back silently to Open-Meteo would label data wrongly. It would also break the spec's 'no backup numbers' rule if the source label did not change. Specify an error with a visible 'clear key / use Open-Meteo' control.
- defect: There is no key-entry UI or storage spec: where the password field is, a save and clear button, the localStorage key name, and what happens on an invalid key (CWA returns 401 or a 200 with success:false). A 200 with success:'false' passes the 'non-2xx' check but is invalid. The spec lists 'format wrong', yet nothing says to check the success flag. Also, localStorage can throw (private mode, blocked storage under file://), which crashes the load unless it is caught.
- defect: Timeout is named but has no value, and no module owns it. fetch has no built-in timeout, so without AbortController the loading state can hang forever. Repeated clicks or refreshes can also let a slow earlier response overwrite a newer one (race), so the 'source' label and the data can disagree. Specify a timeout value and a request token or abort of the previous call.
- defect: Time zone and 'today' are ambiguous. The query uses timezone=Asia/Taipei, but the browser can sit in another zone. 'Today's curve' and weekday names must be taken from the API's own date strings (hourly.time 'YYYY-MM-DDTHH:mm' is local Taipei, with no offset). Parsing them with new Date() and displaying in the viewer's zone shifts the curve and the weekday labels. Example: a viewer in UTC-5 sees hour labels shifted by 13 hours and today's slice gets the wrong 24 points. 'Fetched time' also needs a zone stated. Use slicing by date string, not by Date objects. Likewise the 'today' slice should come from current.time's date or daily.time[0], not from the browser clock.
- defect: The acceptance predicate 'page requests nothing but the two named API hosts' is unclear on what is checked. Do fonts, favicon (browsers auto-request /favicon.ico, and that is a request to the page's own origin) and CDN assets count? The check needs a definition, for example that it covers the code's fetch targets and any src or href in index.html. And 'ten files exist and parse' has no parse check for HTML. And the spec says 'no key in any file', but nothing says how to test it (grep for what pattern, given that a CWA key looks like CWA-XXXXXXXX-...).
- defect: The role constraint conflicts with the task. This seat's capabilities say can_write false and 'Do not create or change any file', yet the brief says to build ten files. So this node is only a review. The requirement does not say who builds, and the 'one module at a time' build order is not tied to any node. This is a flow gap, not a defect in the content.
- defect: The module dependency order is not fixed. Plain script tags share one global scope. Nothing defines the global names (namespace object versus loose globals), so two modules can collide: a 'normalize' function, 'render', 'state', or 'API_URL' redeclared with const in two files throws SyntaxError and the later script fails to load. Require one namespace object per module, such as window.Weather.openmeteo. Also fix the script order in index.html: sources, openmeteo, cwa, normalize, now, week, chart, app. A script that runs before a dependency throws at load.
- defect: Chart details are open: scale, 24 points vs the 25 that Open-Meteo returns for a day boundary, a null in hourly.temperature_2m (breaking the line with NaN in SVG path), a day where min equals max (division by zero in the y-scale, a flat line with NaN), and no canvas vs SVG choice. With no external libraries, canvas needs devicePixelRatio and resize handling. Chosen SVG output would be simpler. Missing values should produce a gap in the line, not zero.
- defect: Open-Meteo returns 200 with {error:true, reason:...} for bad parameters. That passes the non-2xx check. The 'format wrong' check must test the arrays: daily.time length is 7, and hourly, current and daily have the expected keys and equal lengths. Otherwise a missing field renders as 'undefined°' or 'NaN' on screen, which is a made-up value in effect.
- defect: Display precision is unspecified: Open-Meteo gives decimals like 27.3 and CWA gives strings ('27.3'). Whether to round, how to show the unit (°C, %), and what to show for null all have to be set in normalize.js. And the seven-day list needs a rule for what the first row is called ('today') and whether the middle block shows 'now' only from current, not from daily.
- defect: UI language and accessibility are not stated. The brief is in Chinese, so labels should presumably be in Traditional Chinese, but this is unspecified, as are the weekday format and the chart's text alternative. The error state needs role=alert, and the loading state needs aria-busy. 'Middle of the screen' is also ambiguous on mobile: centred horizontally, or a block in the vertical middle between header and week list?
- risk: Reversibility is good: ten new static files, no build, no deploy, no data. Everything can be deleted or rewritten, so the main risk is correctness in use, not undoing the work.
- risk: Secret leak risk: the CWA key is typed by the user and sent as the `Authorization` query parameter, so it lands in the request URL. That URL can show up in browser history, devtools, proxy logs and Referer headers. The spec bans the key in files and on screen, but not in logs or error text. Error messages must not echo the request URL, and the `Authorization` parameter should be built in `cwa.js` only. Add `<meta name="referrer" content="no-referrer">`. Storing the key in localStorage leaves it readable by any script on the same origin. That is acceptable here because the page loads no external scripts, but the page should offer a way to clear the key.
- risk: The "no made-up numbers" rule is a production hazard in the other direction too. If `normalize.js` coerces missing, null or non-numeric fields to 0 (for example a null `precipitation_probability_max` becoming 0%, or a CWA value of -99 meaning missing), it will show invented numbers. Normalization must treat null, NaN and CWA sentinels (-99, -990) as missing, show "—", and treat a wholly invalid shape as a source failure. Show no stale cached data under a fresh timestamp.
- risk: Fallback ambiguity: the spec says no key means Open-Meteo, but not what happens when a key is set and CWA fails. A silent switch to Open-Meteo would mislabel the data source. It would also conflict with "no backup numbers". The safe reading is to show an error naming CWA and not switch automatically. A bad key should be reported as a CWA failure and not misread as success.
- risk: CWA's response differs from the 7-day, 3 metric shape Open-Meteo gives. F-D0047-063 gives 12-hour periods and has no hourly temperature curve. O-A0003-001 returns current observations only (and the station data can have missing fields). The spec does not say how to produce today's hourly curve, daily high/low or rain chance from CWA. Nor does it say whether a missing curve is an error or an empty state. That must not be filled by interpolation. Without a decision, the builder may invent data. The spec also uses the query `locationName` and the element names without stating them. The builder cannot check these without a real key, so the CWA path is untestable here and likely to break in production.
- risk: Browser-side CWA requests may be blocked by CORS. If the CWA API does not send CORS headers for browser origins, the optional source will always fail, and the failure will look like a network error. If the page is opened from `file://`, the origin is `null`, which makes CORS worse. The error state must say which source failed and should hint at the cause without exposing the URL.
- risk: Time handling: Open-Meteo is called with `timezone=Asia/Taipei`, so its times are local Taipei strings with no offset. Parsing them with `new Date()` in a browser in another timezone shifts the hours, which would make "today" and "now" wrong. The "fetched at" time and the "today" filter must be handled explicitly in Asia/Taipei, and the 24 hourly points must be picked by the date string and not by the browser clock.
- risk: Failure modes to build in: a request timeout (fetch has none, so use AbortController), non-2xx, non-JSON, a wrong shape and partial data (for example `current` present but `daily` missing). Each should produce a visible error naming the source. Check array lengths match (7 days). Concurrent refreshes and a slow response arriving late must not overwrite a newer result.
- risk: The "only two hosts" acceptance check is easy to break by accident: no web fonts, no CDN, no favicon request to another host, no inline `<img>` from outside. A favicon request goes to the page's own origin, which is fine for the check as written, but it is worth stating.
- risk: Verification gap: `can_write` is false for this seat, and the acceptance predicate calls for parsing all ten files and scanning for keys. The scan should look for a literal key and not just the word `Authorization`, which is legitimately present in `cwa.js`. The live API cannot be called in a sandbox, so the failure-path rendering must be checked with a forced bad URL, not only the happy path.
