1.
做一個台北的一週氣象單頁網站，座標 25.0330°N 121.5654°E。畫面中間顯示現在的氣溫和濕度；七天預報要有每天的最高溫、最低溫和降雨機率；另外把今天每小時的氣溫畫成一條曲線。 ## 資料：頁面在瀏覽器裡、執行時向外取得真實資料 - 預設來源是 Open-Meteo，不需要金鑰： `https://api.open-meteo.com/v1/forecast`，查詢參數為 `latitude=25.0330`、`longitude=121.5654`、 `current=temperature_2m,relative_humidity_2m,weather_code,wind_speed_10m`、 `hourly=temperature_2m`、 `daily=weather_code,temperature_2m_max,temperature_2m_min,precipitation_probability_max`、 `timezone=Asia/Taipei`、`forecast_days=7`。 - 選用來源是中央氣象署（CWA）開放資料 API，只用 API，不爬網頁、不下載檔案： `https://opendata.cwa.gov.tw/api/v1/rest/datastore/F-D0047-063`（臺北市未來一週預報）和 `https://opendata.cwa.gov.tw/api/v1/rest/datastore/O-A0003-001`（現在觀測，測站 `466920`）， 金鑰放在 `Authorization` 查詢參數。只有在使用者於頁面的密碼欄位輸入金鑰時才使用； 金鑰只存在這個瀏覽器的 localStorage。沒有金鑰就用 Open-Meteo。 - **任何檔案裡都不可以出現金鑰**：不寫進程式、設定、範例或說明，也不印在畫面或網址顯示上。 - 頁面要標明「資料來源」是哪一個，以及「取得時間」。 - 請求失敗（網路、逾時、非 2xx、格式不對）時，畫面要有看得見的錯誤狀態，並指出是哪個來源失敗； **絕對不可以顯示編造的數字或備用數字**。 ## 模組：十個檔案，各自獨立，一次建一個，都放在 `site/` 底下 1. `index.html` — 頁面骨架：版面區塊、載入各模組的 script，以及標明來源與取得時間的位置 2. `styles.css` — 版面與樣式，包含載入中與錯誤狀態的樣子 3. `sources.js` — 來源設定：兩個來源的名稱、網址與查詢參數，以及依有無金鑰選用哪一個 4. `openmeteo.js` — Open-Meteo 的請求，回傳它原本的回應 5. `cwa.js` — CWA 的請求（金鑰從 localStorage 讀），回傳它原本的回應 6. `normalize.js` — 把兩個來源的回應整理成同一種格式，並負責數字與時間的顯示格式 7. `now.js` — 中間的「現在」區塊：氣溫與濕度 8. `week.js` — 七天清單：每天的最高溫、最低溫和降雨機率 9. `chart.js` — 今天每小時氣溫的曲線 10. `app.js` — 進入點：串起以上模組，處理載入中與錯誤狀態 ## 限制 - 沒有建置步驟，不用任何外部函式庫，全部是瀏覽器直接打開的純檔案（用 `<script src>` 依序載入， 不要用需要伺服器的 ES module）。 - 一次只做一個模組，每個模組自己能被讀懂；後面的模組可以呼叫前面模組已經有的東西。 - 除了上面兩個 API 之外，頁面不得向任何其他網址發出請求。

problems: defect: CWA has no hourly data. F-D0047-063 is a one-week forecast in 12-hour steps. With a key, the 'today's hourly temperature curve' has no real source. Interpolating hourly points would be made-up numbers. The brief must say what the chart shows under CWA: either 12-hour points only, or an error or 'not available from this source' state for the chart.
problems: defect: CWA daily values do not map straight onto Open-Meteo's. CWA gives MaxT, MinT and PoP12h per 12-hour period, not a daily max, min or precipitation_probability_max. normalize.js needs a stated rule for combining the periods into a day. For example, a 12-hour period that is missing or has a blank PoP ('' or ' ') must not count as 0%.
problems: defect: The CWA dataset F-D0047-063 returns all 12 Taipei districts, and the brief names none. The coordinates 25.0330, 121.5654 are in Xinyi District (信義區), but the brief does not say to use it. Station 466920 (臺北) is not at those coordinates either. Without a stated district, an implementer could silently show another district's numbers. The page should show which district and station were used.
problems: defect: CWA marks missing observations with -99 (and sometimes -99.0 or a string). The current-conditions block would show '-99°C' or '-99%' unless normalize.js treats those as missing. Open-Meteo can also return null, for example precipitation_probability_max. null or missing must render as '—', never as 0 or as a number coerced from null.
problems: defect: 'Today' must come from the API's Asia/Taipei time strings (current.time or the daily date), not the browser clock. Open-Meteo returns 168 hourly points with offset-less strings like '2026-10-19T00:00'. If chart.js parses them with new Date() or filters by the viewer's local date, a viewer in UTC or the US gets a different 24 points. Taipei's evening can then show tomorrow's hours. The fetch time should also be shown in an explicit Asia/Taipei zone, or labelled with its zone.
problems: defect: The brief does not say what happens when a key is present and CWA fails. Falling back to Open-Meteo would show numbers from a source the person did not select. The brief does say source and failure must be named, but not whether silent fallback is allowed. It should say the error state shows 'CWA failed' with no automatic switch.
problems: defect: The CWA flow makes two requests (forecast and observation), and cwa.js returns 'the original response' for both. The brief does not say what to show if one succeeds and the other fails: a half-filled page, or a single error naming the failed dataset. Mixing a live observation with an old or absent forecast must not look complete.
problems: defect: No module owns the key input. The brief mentions a password field, but index.html is skeleton only and app.js is the entry point. Nothing says who reads, saves or clears the key in localStorage, what the localStorage key name is, or how a person removes a stored key. Without a way to clear it, the page uses CWA forever on that browser. This is also not in the ten-module job split.
problems: defect: CORS from opendata.cwa.gov.tw for a page opened from file:// (origin 'null') is not guaranteed. The brief demands a visible CWA error in that case, with no fallback numbers. The plan should state that a CORS block is a normal 'network' failure, not something to work around with a proxy or a third host.
problems: defect: 'Timeout' is a failure condition, but no limit is given and no mechanism is named (AbortController plus a number of seconds). Without one, a hung request leaves the page on 'loading' forever, which is neither data nor an error state.
problems: defect: The Open-Meteo query asks for weather_code and wind_speed_10m, but nothing on the page displays them (no icon, text or wind). Either they are unused request weight, or the implementer adds a weather-code table and a wind display the brief did not ask for. The plan should drop them or say where they show.
problems: defect: With no ES modules, ten plain scripts share one global scope. The brief does not set a namespace convention, so two modules can silently overwrite each other's names (for example a 'fetch' or 'format' helper). Also, index.html is built first and loads files that do not yet exist, so the page throws script-load 404s until module 10 exists. Both are acceptable, but the plan should say so.
problems: risk: Risk: the CWA key is typed into a password field and kept in localStorage. Any script on the page origin can read it. The 'no external libraries' rule and the two-host limit both reduce that exposure, so the plan must keep them. It must also offer a way to clear the key. The brief does not say how a person removes it. A clear button is a small addition that the key rule requires, so it should be treated as part of the key rule and not as extra scope.
problems: risk: Risk: the CWA key goes in the Authorization query parameter. That means the full URL contains the key. The page must never print, log, or show that URL, and the error state must name only the source, not the request URL. A failure message built from the URL or from a caught error's text could leak the key. The plan should say that error text is written from fixed wording plus the source name.
problems: risk: Risk: the brief says 'no made-up numbers', but it does not say what happens when only part of the response is bad. For example, the current block may be fine while the hourly array is missing, or a day has a null precipitation_probability_max. The plan should show an empty or error state for just the missing part, never a zero or an average. normalize.js should return null for missing values, and the display should show a dash or an error and never 0.
problems: risk: Risk: if the person has a key and the CWA request fails, the plan must not silently fall back to Open-Meteo. The data would then come from a source the page does not label correctly, or the label would hide the fallback. The brief says to name the failing source. The safest reading is to show the error for CWA and let the person remove the key to go back to Open-Meteo. The plan should state this choice.
problems: risk: Risk: CWA's response shape is the least certain part of the plan. F-D0047-063 gives elements in time slices, not a clean daily array, and O-A0003-001 returns all stations, so station 466920 has to be picked out of the list. Mapping this into the same format as Open-Meteo is where wrong numbers could slip in, for example a mismatched day, unit, or time zone. normalize.js should check the shape and treat any mismatch as 'format wrong' and show the error state, not guess. Also, the CWA datastore may not be reachable from a browser because of CORS. If so, CWA will always fail visibly. That is acceptable, but the plan should not add a proxy, since the two-host rule forbids it.
problems: risk: Risk: the brief says to open files directly, as plain files with <script src> loaded in order. Opened from file://, the page has a null origin. Open-Meteo allows CORS, so it should work. A CWA failure from CORS would look the same as any other failure, and the error should still name CWA. Script order is a fragile point: the ten modules share globals, so the load order in index.html must match the dependency order, and a missing earlier file breaks everything after it. The plan should fix that order in index.html and have app.js check that the earlier modules exist.
problems: risk: Risk: reversibility is good overall. Nothing is deployed, nothing is migrated, and there is no data to delete. All ten files are new and can be deleted easily. The only state that persists is the localStorage key in the person's own browser. The permanent halts are not touched, because the plan changes no secrets or permissions and does not publish anything. The risk that remains is after-the-fact: if the finished site is later put on a public host, the key stays safe only because it is never in a file, so any later move to a hosted version should be rechecked for that.
