      Which model answers which node

      Pick one model and the node is asked once. Pick several and it becomes a panel: each model is asked separately, in its own session, blind to the others, and their answers are adjudicated — veto first, then majority, and a tie does not pass. The same rule the review seats already use, applied wherever you want it.

      What this configuration means

      Seats

      How many seats
      Named reviewers with a question each. The floor is 3.
      High-risk mode
      The only way below the floor. Every run records it.
      Re-run when undecided
      A tie is put to the panel again — fresh sessions, but each voice is told what every reviewer said, for and against, and which model said it.
      How many times
      After this many, it goes to you regardless.
      2
      Seats differ from a multi-model node in one way: each seat has its own question. Two models on the same question is a second opinion; four seats is four different questions. Both are adjudicated the same way.

      Where the line falls

      Front end — any language

      • Draws the flow, the position, the log
      • Collects the instruction, the configuration and the gate answers
      • Holds no governance: never decides a verdict, never adjudicates
      • Can be closed and reopened mid-run
      ── HTTP + SSE ──▶

      Back end — the existing runner

      • policy.py, graph.py unchanged
      • Owns every decision, halt, adjudication, retry and record
      • Bound to one project; writes its ask journal there
      • Holds the API keys — the browser never sees one

      Change 1 — the gate blocks. Today a gate halts and the process exits. A console needs it to wait: a new Approver the engine calls at a stopping verdict.

      Change 2 — retries in the dispatcher. An attempt that never answers is a lost session, already handled. Retrying is the backend's job, and it is logged.

      Change 3 — any node can be a panel. engine._adjudicate already does veto → majority → tie-fails for the review seats. Multi-model on a node is the same call with a different set of voices, so this is a generalisation of code that exists rather than new governance.

      MethodPathDoes
      GET/PUT/projectThe one bound project. PUT refused mid-run.
      GET/POST/modelsThe registry. POST adds one: vendor, id, access, command or endpoint, key env var.
      DELETE/models/:idRefused while a node still selects it.

      GET/run/eventsSSE: position, asks, retries, voices, adjudications.
      POST/run/gateAnswer the gate it is waiting on.
      POST/run/decideBreak a tie the panel could not resolve. Recorded with who decided.
      GET/run/objections/:nodeThe reviewers' original wording. Also appended to the work order under the brief, so it rarely needs fetching.

      What each side may not do

      RuleWhy
      The front end never adjudicates. It shows the voices; the server decides the outcome. Anything a browser can decide, a browser can be made to decide wrongly.
      API keys never reach the browser. The registry stores an env var name, not a secret. A key in a page is a key in a screenshot, a bug report and a cache.
      Closing the tab does not stop a run.A gate waits on a person, not a socket.
      Model choice cannot relax a gate.Who answers is configuration. Whether the answer passes is not.
      The six red lines are not reachable from the API.A UI that could would be a UI worth attacking.
