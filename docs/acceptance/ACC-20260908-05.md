## The half a mutation cannot stage

The accounting is deliberately unregistered. A mutation removing it runs against a tree where the
race is already fixed, so no worker dies, `failures` is empty either way, and the test passes —
`NOT CAUGHT`, correctly. **The accounting only bites when something else is broken**, which is what
it is for and what a mutation of a green tree cannot arrange. Registering it would mean a second
test that deliberately kills a worker, whose only subject would be this test's own bookkeeping.

What replaces it is the injection measurement in the table above, and the reason sits at the group
in `tools/mutation_check.py` rather than only here, so a reader meeting `NOT CAUGHT` finds it where
they are standing.

## Three hollow tests, written by the operator, on the way to the one that works

Recorded because each was green:

1. A patch anchored on a remembered test name that does not exist. Caught by the script's own
   assertion, at no cost.
2. A fixture hooked on `Store.all`, which `start`, `instruct` and `attach` also call — under the
   lock. It parked on `instruct`'s read, and the test failed on a stale version: red, for the wrong
   reason. The hook is `order_paths`, which only the walk calls.
3. **A barrier that held nothing open.** It parked *after* the read completed, so no handle spanned
   it, and the test **passed with the lock reverted**. A guard that could not fail, inside the
   change that exists because of one. Found by reverting the fix and expecting red — which is why
   that step is not optional.

## Two things this review nearly recorded and did not

**A four-fold slowdown that was the reviewer's own load.** One run of `tests/test_server.py` on this
branch took 202s with one failure, against 55s and green on `9bcffb5`. The obvious reading is that
the lock is expensive. It is not: a clean re-run is **153 passed in 57.52s**, and `--durations`
shows the new test at 5.09s and nothing else moved. The 202s run overlapped mutation runs and a
`git archive` in the same session. The seat's independent measurement agrees — the walk's read is
~2% of what `attach` already holds the lock for.

**An intermittent test read as a regression.** `test_a_connection_that_says_nothing_does_not_hold_a_thread_forever`
was the failure in that run. It passes 5 of 5 alone here, the file is green on a clean run, and it is
already recorded in this queue's hand-off as intermittent under load. What settled it was running
the same file on `9bcffb5` twice — 152 passed both times — rather than assuming either way.

## What is still open, and belongs elsewhere

- **`tests/test_server.py:2659`** — a `join(timeout=10)` in a helper's `finally` whose expiry would
  silently reintroduce a flake in `test_a_connection_that_says_nothing_does_not_hold_a_thread_forever`'s
  `active_count()`. Same class — a bounded wait whose completion the verdict depends on and whose
  result is unasserted — but not a false green.
- **The class itself**, as the reading seat framed it: *a bounded wait whose completion is required
  for the test's verdict, but whose completion result is neither asserted nor otherwise acted upon*,
  plus *worker failures must reach the parent test*. Worth a suite rule; not written here, because
  a rule over every ignored wait would ban waits that use a timeout only as pacing.
- **Whether the race reaches Linux.** The mechanism is Windows file-sharing semantics. Not measured
  on Linux, and the fix is platform-independent either way.
- **The collision rate through the real HTTP route**, which is what would settle priority rather
  than existence. Not measured: the route-level deterministic collision the reading seat described —
  status and body, both manifests' hashes, the state snapshot before and after, then after retry and
  restart — is a larger measurement than this change needed.
