## Reservations, all six of them

Recorded in full because the specification is where this change's risk lives.

1. **The six-phase strip does not exist.** The record's "The screen" section describes *Plan → Assess
   → Build → Review → Verify → Ship, the current one lit*. It is in no file — not the console, not
   the server, not the graph. Task 11's done-when does not mention it, so the State column is not
   false; a reader of the design section is nonetheless told about a thing that was never built.
2. **Six endpoints in the design section have no route**: GET/PUT `/project`, POST `/models/:id/test`,
   DELETE `/models/:id`, GET/PUT `/config/panel`, POST `/run/resume`, GET `/run/objections/:node`.
   None appears in any task's done-when. Same shape as (1): spec-versus-build divergence, not a false
   task claim.
3. **`GET /run/events` has no test consuming it.** "The stream sends the snapshot first" is
   implemented (`server.py:867-870`) and the console depends on it, but cutting that line fails
   nothing. The one place in this change where a mechanism has no biting test.
4. **The three live-drive narratives** (slugify, tip-splitter, notes — "verified live") rest on the
   author's word, corroborated only by one committed recording
   (`test_demo_pages.py::test_the_recording_replays_a_real_console_driven_run`). The record flags the
   hand-run but not these.
5. **Stated counts have drifted** with later changes: 23 nodes to 24, six modes to seven with
   `SURVEY`, 45 registry tests to 48. Drift, not false when written.
6. **The design verdict is still "does not pass."** Three review rounds, all split or fail, and the
   record itself says a fourth round against the built code was never run. This acceptance does not
   substitute for it: it confirms the build claim and nothing more.
