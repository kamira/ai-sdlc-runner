## The reservation conflated two things, and that is why it stayed open

It said normalising *"would mean parsing a type language this runner does not have"*. True of
**semantic** normalising — `List[int]` against `list[int]` needs the language. Not true of
**whitespace**.

Run together, the sentence reads as *"normalising is impossible"*, and the cheap half went undone
for that reason. Separating them was the whole work; the regex is four characters of thought.

## The first rule was wrong, and it is pinned as wrong

*Strip all whitespace* is the obvious move and it merges `int x` with `intx` — two different
declarations in every notation this could plausibly hold. It was tried, rejected against a table of
five pairs, and now has its own mutation:

```
"all whitespace is stripped, so two different declarations read as one"  ->  CAUGHT
```

A mutation for a rule that was never shipped is unusual. It is here because the wrong rule is the
one a reader reaches for, and the test that refuses it is the only thing that says why.

## Reservations (disclosed, not waived)

1. **Semantic differences are still conflicts.** `List[int]` against `list[int]`, and
   `(id) -> User` against `(uid) -> User` — the second looks like a typo and is treated as a
   disagreement, correctly, because this runner cannot tell a typo from a decision.

2. **The false stop is still not measured.** The reservation said so and it remains true: nothing
   counts how often two planners would space a signature differently. The case is reasoned from what
   two people writing the same interface do, not observed.

3. **The rule is a judgement about notations.** *Whitespace touching punctuation is formatting* holds
   for every language likely to appear in a signature, and "likely" is doing work. A notation where
   `( id )` and `(id)` differ would be silently mis-compared.

4. **Verified by the implementer**, from a reservation the implementer wrote. Fourth time this week
   — an argument for writing them honestly, not for the reviewer.
