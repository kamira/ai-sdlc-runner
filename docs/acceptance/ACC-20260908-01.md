## The claim this record made twice, and a seat broke twice

`ran_on` is the assertion that says the walks ran on the thread the test started. Two mutations
were registered as pinning it, and neither does:

```
mutation                                        first line to refuse             time
if held in entered:  ->  if held == 2:          "the first walk never started"   12.64s
... wait(...)  ->  held != 1 and ... wait(...)  "walk(s) [2] were released ..."   12.34s
```

From that the record concluded *nothing pins it, and no small mutation can*, and gave a structural
reason: a walk that runs on the attaching thread waits there for a release only that thread can
send, so its timeout is always seen first by `gave_up`. A seat refused the universal and built the
case. **The reason is true of walks 1 and 2 only** — `walk` blocks when `held in entered`, and
`entered` is `{1, 2}`. Move the last attachment to after the join, and `_advance` runs walk **3** on
the main thread, where it neither signals nor waits:

In the order the test evaluates them:

```
first.is_alive()   False                  the guard passes
gave_up            []                     passes
set(ran_on)        {first, MainThread}    the only line that refuses — 1 failed in 1.02s
len(walks)         3                      would have passed
```

Deterministic, because the join orders it. It was the tenth entry added to the group, and sits
ninth in it — a seat read the two as the same thing, which they are not.

The lesson is the one this record states in its own criteria and then broke twice: a universal is a
claim about the search that produced it until somebody tries to break it. Two searches here, two
counterexamples, both from a seat rather than from the author.

## The sweep behind criterion 8

The cases live in `BOUNDED_WAIT_CASES` in `tests/test_server.py`, and
`test_the_rule_over_bounded_waits_refuses_what_it_says_it_refuses` runs each through
`_silent_waits` — the same function the rule itself calls — and refuses if the verdict is not the
one recorded beside it. A mutation keeps the table honest: take `While` out of `_under_a_loop` and
the cases refuse.

Their labels are not copied here. Two revisions of this section carried the table itself — the
first hand-counted, with a duplicated row and a tally wrong in both columns; the second a script's
stdout that nobody but its author could run, indexed by a sentence that went stale while the block
under it was being rewritten. A list whose only job is to be re-typed correctly is the defect this
record is about.

One case is not a defect the rule catches. It is the **false positive** the docstring names: a join
guarded by a helper the function defines and calls. It is in the table so that the boundary is run
rather than only described.

## The finding this record is really about

`test_an_action_arriving_as_the_walk_decides_to_stop_is_not_stranded` was green on `31535de` and
took **10.21s** being green. Instrumented on that tree:

```
walk #1 enters      0.01     on the thread the test started
walk #2 enters      0.02     on the MAIN thread, inside runner.attach("one.md")
wait returns False 10.03     released by its own timeout
walk #3 enters     10.04
release_second.set() 10.04   after the walk it was meant to release had ended
```

`attach()` ends in `return self._advance()`, and `_advance` walks **on the calling thread** when
nothing is in flight. With the first walk returning at once, the test's own `attach` ran the second
walk, on the main thread, and stayed inside it until the timeout. So the third attachment was never
posted from inside a walk; the thread named `first` had been finished since 0.02; the count came out
at 3 anyway, and the test passed on it.

This is what a bounded wait costs when nothing asks whether it completed: not a flake, a **test that
has never run the scenario in its own docstring** while saying *"forced deterministically"*.

## What is still open, and belongs elsewhere

- Waits with no argument at all — a `join()` and several `wait()`s in other modules. They hang
  rather than misreport. Different failure, different remedy.
- The general arrangement defect: any test that starts a walk on a thread and then calls a mutating
  route from the main thread may have the route walk it synchronously instead. This record pins the
  one place it was found. The three `_gated_runner` tests were checked and do not have it — their
  walk blocks from the first call, so the attaching thread always finds one in flight.
- The escapes from the rule, and its two false positives. They are listed in its docstring and are
  not re-typed here: the last time this section carried its own copy of that list, the copy was
  four entries against a docstring list longer than four, in the same document whose table records
  fixing exactly that truncation two sections above.
- The two wall-clock assertions themselves. One now says what its ceiling means; neither was moved,
  because `ACC-20260908-05` measured the margins and found no defect in them.
