## The finding this record is really about

`test_an_action_arriving_as_the_walk_decides_to_stop_is_not_stranded` was green on `31535de` and
took **10.21s** being green. Instrumented on that tree:

```
walk #1 enters      0.01     on the thread the test started
walk #2 enters      0.02     on the MAIN thread, inside runner.attach("one.md")
wait returns False 10.03     released by its own timeout
walk #3 enters     10.04
release_second.set() 10.04   after the walk it was meant to release had ended
```

`attach()` ends in `return self._advance()`, and `_advance` walks **on the calling thread** when
nothing is in flight. With the first walk returning at once, the test's own `attach` ran the second
walk, on the main thread, and stayed inside it until the timeout. So:

- the third attachment was never posted from inside a walk;
- the thread named `first`, which the test joins and reasons about, had been finished since 0.02;
- the count came out at 3 anyway, and the test passed on it.

This is what a bounded wait costs when nothing asks whether it completed: not a flake, a **test
that has never run the scenario in its own docstring** and says *"forced deterministically"* while
saying it. The repair holds the first walk so the gate loop runs the second, and `ran_on` asserts
that every walk ran on `first` — the property the test's name asserts and never checked.

What it does not change: this test is still not the guard on the lost wakeup. Its docstring already
said so, and `test_the_release_and_the_decision_are_one_critical_section` is still the load-bearing
one. That sentence was true before this record and is true after it.

## What a mutation cannot stage here

The four `is_alive()` guards. Deleting an assertion makes no test fail — the run reaches the same
next line and fails there, with the same wrong sentence it had before. That is not a hole in the
registry; it is the reason the repair could not stop at four assertions. The rule is what makes the
class refusable, and the mutations move the things the rule reads.

The fifth mutation is a different kind: it puts back the *arrangement*, not a guard. The rule is
static and cannot see which thread a walk runs on, so `ran_on` is pinned by reverting the hold on
the first walk and watching the test refuse.

## What is still open, and belongs elsewhere

- Waits with no `timeout=` — a `join()` and several `wait()`s in other modules. They cannot return
  early, so they cannot misreport; they hang, which CI reports as itself. A different failure with
  a different remedy, and not held by this rule.
- The general arrangement defect: any test that starts a walk on a thread and then calls a mutating
  route from the main thread may have the route walk it synchronously instead. This record pins the
  one place it was found. The three `_gated_runner` tests were checked and do not have it — their
  walk blocks from the first call, so the attaching thread always finds one in flight.
- The 12 `time.sleep` polls across five modules. Each has a deadline and an assertion afterwards
  that says what the deadline means, which is the property this record asks for.
