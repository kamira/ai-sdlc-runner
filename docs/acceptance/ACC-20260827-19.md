## Two design errors, both caught by this repository's own guards

**I put the five functions in `ROLES`.** `test_policy.py:41` asserts
`set(graph.roles_used()) == set(policy.BY_ROLE)` — every role must be one some node names. These are
never dispatched a work order, and `Role`'s three capability flags describe what a **work order** may
do. Answering `can_spawn`/`can_write`/`can_execute` `False` five times is not a description; it is a
shrug in the shape of one. They have their own roster now: **a recipient is told, a role is
dispatched.** The guard refused a conflation, not a bookkeeping slip.

**The operator landed in the middle of the list.** Appending `policy.recipients(kind)` per crossed
kind gave `['release', 'operator', 'security']` for a target that is both a credentials file and a
production path. The list is documented first-named-first, so an operator sitting in the middle
misreports who is told first. Owners now go in the order their kinds were crossed, then the operator,
once, at the end. Found by check 6 on its first run.

## A false negative in `test_nothing_is_unwired`, reported not fixed

`store.halt_routing` was **not** wired at the point the guard passed it. The guard matches bare
names, and `halt_routing` appears in `engine.py:400` as a `RunConfig` field and inside two SQL
strings — so the reader looked reachable while nothing called it.

That is a name standing in for a constraint, inside the test written to catch names standing in for
constraints. It belongs to another session's change (`test_nothing_is_unwired.py`, CHG-20260827-01..15)
and is left for its author rather than edited from under them; the function is genuinely wired now,
so this repository is not currently relying on the false negative. **Recorded here because the next
person it lets through will not be so lucky.**

## Reservations (disclosed, not waived)

1. **Naming a recipient does not make them reachable.** This runner records who should be told. It
   has no notification channel and this change does not add one — the record is a record, and
   somebody still has to look at it. Stated in the CHG's *Not claimed* and repeated here because it
   is the gap most likely to be misread as closed.

2. **The five shipped recipients are drawn from the six halts, not from any real organisation.** A
   roster is a fact about a company. That is why the store accepts any name and why nothing
   validates one.

3. **`serve` reads the routing; the console has no page for it.** `POST /config/halts` exists and is
   exercised, but an operator configures routing with an HTTP request rather than a control.

4. ~~**Task 6 says "appears in the export".** It appears in `report.halts` and in the `run`
   output. The conversation export was not extended, so a halt's recipient is in the run report and
   not in `--format markdown`.~~

   **Closed by [CHG-20260828-09](../changes/CHG-20260828-09.md).** Checking it found more than this
   said: the closing turn recorded the word `stopped` and nothing else, so a **permanent halt** was
   absent from the durable record entirely. It now carries the node, the rule and the recipient.

5. ~~No end-to-end run drives a routed halt through the real CLI.~~ **Closed rather than
   disclosed.** `test_a_routed_halt_reaches_the_projects_own_function_through_the_cli` configures
   `deploy -> sre-oncall` in a real store, gives a node a real `deploy` operation, and runs the CLI.
   It covers the one seam nothing else did: `store.halt_routing(db)` reaching `cfg.halt_routing`.
   Every other end-to-end check builds a `RunConfig` by hand, so an edit dropping the store read
   would have left all of them green.

   Its first draft asserted `"release" not in out` and failed on a correct run:
   `PERMANENT_HALT_KINDS["deploy"]` reads *"production deploy or release"*, so the word sits in the
   **kind's description** and says nothing about who was told. A substring check against a word that
   means two things — this log's most-named defect class, in a test written for this change. It now
   reads the `for:` line.

6. **`test_nothing_is_unwired` has a false negative** — see the section above. Reported, not fixed,
   because it belongs to another session's change.
