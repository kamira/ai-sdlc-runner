## A side effect worth naming

(CHG-20260822-01 upstream). So vendoring v1.64.0 also pulls the pyproject-reading
`toolchain_probe.sh` into this repo's store.

as an outstanding reservation, on the grounds that a fix landed upstream "would not reach this repo
until a fixed skill version is installed or vendored". It has now been vendored. The reservation is
discharged **transitively**, not by this CHG's intent — worth writing down so nobody later reads it
as a coincidence.

## Reservations (disclosed, not waived)

1. **A 48-minor jump was vendored in one step, and nothing here verifies the skill's *own* behaviour
   changed safely between 1.16 and 1.64.** The runner reads that skill; 44 new scripts and 14 new
   references came with it. What is verified is that *this repo* still passes its suite and the new
   lint — not that every intermediate skill change is compatible with how the runner uses it. The
   honest scope of check 9/10 is "no regression detected here", not "the upgrade is proven safe".
2. **`contract_version` now points at a version no existing project uses.** By design (first-run
   default only), but the first project created after this lands is also the first real exercise of
   v1.64.0 through the runner.
3. **The store is much larger.** 51 scripts vs 7. Unavoidable — it is a verbatim archive of a skill
   that grew — but the repo now carries five full skill copies.
4. **CI is still advisory.** `main` has no branch protection; unchanged from prior rounds.

session's entry handshake. It stopped being cosmetic when the runner was scoped to become
