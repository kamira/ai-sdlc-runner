## The mutation that would have passed for the wrong reason

The chase is one line at the end of `cmd_run`. The first version of its test called
`_chase_emergencies` directly — which asserts the helper works and says **nothing about whether
anything calls it**. Removing the call from `cmd_run` would have left that test green.

That is the defect a mutation found in this repository once already, on the dispatch-depth bound:
*"the test called the function directly."* Caught here before shipping because the mutation was
written first and had to be pointed at a test that could fail. It now drives the real `cmd_run` with
a stub agent, a plan file and a pre-seeded emergency in the store.

## Two more defects, both found by the paperwork rather than the tests

**A person's review was filed under the runner.** `_VOICES` had no entry for `REVIEW`, so
`_voice_of` fell through to its `("runner", …)` default and an export would have attributed
somebody's sign-off to the machine — in a document whose whole purpose is keeping the model's side
and the person's side apart. This is precisely the defect CHG-20260828-03 fixed for `RELAXATION`,
one kind over, and it was found by writing the line in `docs/SCHEMAS.md` that says which voice a
review is and then checking whether that was true.

**A guard of mine fired on a change it does not describe.**
`test_no_path_open_has_appeared_since`, shipped this morning in CHG-20260828-19, pinned `file:line`
pairs. Inserting a hundred lines into `conversations.py` moved them, so a change that added no
`.open(` at all failed a test about which `.open(` calls exist. It pins receivers now, not lines: a
guard that fires on an edit it does not describe is one people learn to re-baseline without reading,
which is worse than not having it.

## The turn-kind table caught the new kind three times

`test_every_turn_kind_the_module_declares_can_actually_be_written`, `docs/SCHEMAS.md` and
`docs/schema-atlas.html` each went red on `REVIEW` — a declared kind that nothing wrote, a table
missing a row, and a count that said nine. The first is the interesting one: its docstring says *"a
kind nothing writes is a name with no constraint behind it"*, and `REVIEW` is written by
`record_review` rather than by a `Conversation` method, deliberately — putting it on the
conversation object would put it where a walk could reach it. The test drives `record_review` now
rather than exempting the kind.

## Why the queue is derived

An emergency run is already recorded — its `CLOSED` turn carries the class in force. A second list
of outstanding reviews would be a second source of truth about one fact, and CHG-20260828-17 is a
whole change about what happens then: two readers of the same files, opposite answers, and CI
trusting the one that said fine. A view cannot drift from the thing it is a view of.

## A shape that was wrong on the first attempt

`record_review` passed `document.get("header")` to `Backend.append`, which is `None`: `_assemble`
returns the header **flattened** with `turns` added, so there is no `header` key. It failed loudly
on `KeyError: 'conversation_id'` rather than writing a headerless turn, which is the store's guard
doing its job. The header is now rebuilt from the document minus its reading-time keys.

## Reservations (disclosed, not waived)

1. **A turn saying somebody reviewed it is not a review.** This records a claim with a name against
   it and makes the *absence* of one visible. It cannot tell a real review from a rubber stamp —
   the limit `class_in_force` already states about renewal, one obligation over.

2. **Nothing expires an unreviewed emergency.** A class expires back to `normal` when its review
   date passes; an outstanding *run* review does not age. It is listed forever and never escalates,
   so a queue nobody clears is a longer and longer list rather than a louder one.

3. **The chase is on `run` only.** `serve` finishes walks too, and says nothing. That is a gap, not
   a decision — `serve`'s output is a stream to a console rather than a terminal report, and where
   the line belongs there was not worked out.

4. **The queue is per-store, not per-project, when it chases.** `_chase_emergencies` reports every
   outstanding run in the store the finishing run used, including other projects'. That is arguably
   right — an unreviewed emergency elsewhere is still unreviewed — but it was not the considered
   choice; it was the simpler one.

5. **Verified by the implementer.** The design question this rested on — where the queue lives —
   was decided by an argument the repository had already had, which is the nearest thing to an
   independent seat available here.
