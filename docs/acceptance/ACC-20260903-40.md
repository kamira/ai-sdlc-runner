## The reproduction

```
store said nothing at all
  cmd_serve printed   3 assignment(s) from the plan override it
  actually overrode   0
```

`resolve` returns ``key -> plan|store``, and its docstring says it answers **which source put an
assignment there**. For that question `FROM_PLAN` is correct on both of these:

```
plan says X, store says X    FROM_PLAN    the plan overrode the store
plan says X, store silent    FROM_PLAN    the plan overrode NOTHING
```

## What was not changed, and why

`resolve` is untouched, no third constant was added, and no existing test moved. `cmd_run`'s footer
counts `FROM_STORE` and says *"the plan did not name"* — which is exactly what `FROM_STORE` means,
so one of the two footers was already right. **One reader took a “who put it there” map for a “what
did it displace” map**, and `cmd_serve` holds both inputs, so it can answer the second itself.

`store.overrides` returns ``key -> what the store had``, not a count, so the person reading the
footer can be told what was displaced rather than only how many.

## Criterion 3 — why no test contradicted it

Both existing tests of `FROM_PLAN` use a key **the store also named**:

```
test_the_plan_wins_and_the_store_fills_and_both_are_named   lead_review: plan AND store
test_an_override_is_never_silent                            defect:      plan AND store
(no test)                                                   plan names it, store never did
```

Every exercise of the value was the override case, so the misreading was never put in front of a
case that refutes it. The row is now covered — not because `resolve` is wrong on it, but because a
value whose only tested shape is the one it is later misread as is a value nothing is holding.

## Criterion 5 — the mutations

```
the footer counts FROM_PLAN again              ██████████  caught (1)
overrides answers the naming question instead  ██████████  caught (3, incl. the invariant)
```

The invariant test caught the second, which is what it is for: it does not name the defect, it holds
`set(displaced) <= {k: FROM_PLAN}` across five arrangements and refuses to pass if the two never
differ on any of them.

## The structural guard is read as structure

`test_the_serve_footer_counts_displacement_not_naming` reads `cmd_serve`'s AST and asserts no
`FROM_PLAN` tally survives in it. A guard pinning the wording would go red on a rename and green on
the defect — the trap CHG-20260903-39 had to undo **twice in one change**, in `models.save`'s guard
and in the provenance hand-over's.

## Reservations

1. **A printed count changes.** An operator who read “3 override it” against an empty store was
   reading a defect, but the number drops for anyone whose plan names more than it displaces.
2. **`resolve`'s vocabulary still cannot express the distinction**, and `GET /config/nodes` answers
   that vocabulary — a surface CHG-20260903-39 had just finished making honest. A console rendering
   `plan` beside an assignment the store never named is telling a true thing about origin that can
   be read as a false thing about override. Nothing renders it yet, which is why this is a
   reservation and not a task: the console draws no assignments at all.
