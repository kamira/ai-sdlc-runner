## The first implementation counted the wrong thing

`_change_retry` began by counting `lead_review` asks whose verdict was `fail`. `lead_review` is a
**seat panel**: three seats, three asks, **one** rejection. It counted a single panel failure as
three, so `rejections > 1` was true on the *first* rejection — a bound of one wearing the label of
two.

It passed every unit test, because those built a report by hand with one entry per rejection. The
end-to-end walk found it: `test_one_panel_rejection_goes_back_into_the_module_loop` halted when it
should have gone round.

The count is now of the two nodes a rejected change routes **through** — `review_failed` and
`acceptance_failed`, reached only from a `fail` branch, once per rejection whatever the panel's
shape. That is the thing itself rather than a signal that accompanies it, and
`test_one_panel_rejection_counts_once_however_many_seats_voted` holds it there with three seat asks
in the report.

## The README named one loop and there were two

The gap says `lead_review` → `review_failed` → `next_module` → `lead_review`. Reading the graph to
fix it found `qa_accept` → `acceptance_failed` → `next_module` → `lead_review` → `qa_verify` →
`qa_accept`, unnamed and identical in kind. Bounding only the one the document mentions would have
been fixing the example rather than the class.

## The test fixture already contained a workaround for this defect

`test_flow`'s `Recorder` fails `lead_review` on the **first** panel only, and says why:

> A panel that fails every time loops forever — `lead_review` routes to `review_failed`, which
> returns to the module loop, which comes straight back — and a test that hits `max_steps` proves
> nothing about the branch it was written for.

That is this defect, written into a fixture as an accommodation. With the bound in place a panel
that fails every time *halts*, so rejecting every time is now something a test can do — and this
change needed a dispatcher that does exactly that.

`Recorder` was **left alone**. Other tests depend on its one-failure behaviour, and rewriting a
shared fixture to suit one new file is how a fixture stops meaning what its users think it means.

## Reservations (disclosed, not waived)

1. **Two is the module loop's number, borrowed.** The argument is `halt_second_fail`'s and it
   transfers, but nothing here measures whether a third lap would have passed. That needs a corpus
   of real runs this repository does not have.

2. **A gate rejection at `qa_verify` is still unbounded**, and deliberately: `rejects_to` is a
   person declining and sending it back, not the flow cycling on its own. A bound there would cap
   how many times an operator may say no. It is a different question and this does not answer it.

3. **The count is per run, not per change.** A resumed run rebuilds `visited` from the walk it is
   doing, so two rejections spread across a stop and a resume may not meet. The module loop has the
   same property and neither was designed for it; it is stated here because a bound that resets is
   a bound with a hole.

4. **`halt_change_rejected` says what happened, not what to do about it.** The terminal's label
   reaches the operator; the panel's reasons are in the record but nothing gathers them into the
   halt. `halt_second_fail` has the same shape and this change did not improve on it.

5. **Verified by the implementer.** The correction that matters came from a test rather than from
   review, which is the part worth keeping: the wrong count survived every unit test written for it.
