## The reproduction, and the probe that missed it

```
walk  missing        the <p> said     the counter said
  1   flow           asked once       1
  2   architecture   asked once       2      <- disagree
  3   architecture   asked twice      3      <- disagree
  4   architecture   asked twice      3      <- disagree
```

**My first probe built the history by hand and showed the two agreeing.** Three stops, one aspect
repeated: `stop_reason` said *"asked 3 times"* and `len(history)` was 3. It was measuring one
aspect, where the total and the per-aspect count are equal by construction — and it was computing
both at the same moment, where they are equal again.

The divergence needs two things the hand-built version had neither of: **more than one aspect**,
and **the two moments** — the engine reads before the stop is recorded, the snapshot after. Driving
the real `Runner` supplied both. A "does not reproduce" from that first probe would have been the
third false negative of this session, and the memory it would have violated is its own: *use the
repo's own harness.*

## The count here is deliberately **not** the shared name

```
the engine checks BEFORE the stop is written   ->  asks_including_this_one   (tally + 1)
the snapshot is read AFTER it is appended      ->  times_asked               (the tally)
```

`CHG-20260903-42` created the shared name because two readers disagreed; routing this third reader
through it would count the ask in flight twice. **The same question has two correct answers at two
moments**, which is the sharper form of that record's lesson: one name is right when the readers
ask at the same instant, and a comment plus a test are what carry the case where they do not.

## Reservations

1. **A snapshot key is renamed and changes type** — `intake_asks` (int) → `intake_asks_by_aspect`
   (map). Both consumers are in this repository and both are updated; an external client reading
   the old key finds it absent, which is louder than finding it wrong, and that is the intended
   direction.
2. **The map is keyed by every aspect that has ever been missing**, not only the ones missing now.
   The console reads it per rendered aspect so the extra entries are invisible there, but the API
   carries them, and a client listing the map's keys sees the run's history rather than its current
   stop. Named rather than trimmed: dropping them would make the field's meaning depend on which
   stop the run is at.
