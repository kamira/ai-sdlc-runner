## Why it survived CHG-20260903-34

That change fixed `approve` and wrote the reasoning into `approve`'s body. `reject` is three methods
below in the same class and `rule` five; neither got it. **CHG-20260903-36 was *"two fixes shipped
into one module and never swept into their siblings"* — this is that, inside the module that record
was about.**

The fix is `_answering`, one place where *"is this decision about the stop the run is at?"* is
asked. A fourth decision method cannot be written without it, and criterion 5's rule asks the
question of every method that appends an operator decision rather than of three names.

The second and third are caught **only** by the rule: a missing `run_id` changes no behaviour until
a stale decision arrives, so no behavioural test can see it today. That is what a rule is for.

The fourth is worth noting the other way round: mutating the shared helper turns CHG-20260903-34's
original guard red, which is the evidence that the extraction did not weaken what that change built.

## Reservations

1. **Two live HTTP routes begin refusing requests they accepted.** A client sending a refusal that
   names a gate the run is not at was exercising this defect, but it is a behaviour change on a
   running interface.
2. **`run_id` starts being set**, which makes the engine's staleness guards live for console
   traffic. A decision typed into a stale tab for a different run was previously spent and will now
   be refused — the guard working, and a change in what a person sees.
3. **Four more live defects from the same seat, in the same round, are not fixed here** and are
   named in the change record rather than left implied: the post-work class relaxation that reaches
   no durable surface (CHG-20260903-41's sibling site, missed this morning), `review_by` never
   validated as a date, `settings.py`'s scoping sentence being false in two ways with a vacuous test
   under it, and a grading panel's grade reaching no terminal surface. Each needs its own record.
