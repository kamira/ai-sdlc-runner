## Eight nodes, not one

`rejects_to` is set on `pm_confirm`, `lead_assess`, `pm_signoff`, `engineer_selfverify`,
`lead_task_review`, `lead_review`, `qa_verify` and `qa_accept`. Every one of them routes a person's
refusal to a node that was not told why. The design that surfaced this proposed a ninth; the eight
were already there.

## Why the fix is four lines of mechanism and not a new one

`carried` already carries a split panel's reasons into the next round, under a comment that is the
same sentence about a different speaker: *"'Somebody objected' is not something a reviewer can
weigh, and naming only the objectors would be sending half the room's reasoning."*

A person's refusal is exactly that, from one voice instead of several. Building a second channel
for it would have been two mechanisms that must agree about how a re-ask is told what changed —
the shape this ledger has watched drift more than once.

## Reservations (disclosed, not waived)

1. **Written by the implementer**, on a defect somebody else measured. The design panel's prototype
   is what found it; nothing in this repository's suite would have.

2. **Nothing is bounded.** A person who refuses forever still refuses forever — what changed is that
   each lap answers a different question. Every existing bound in this flow is a graph edge
   (`re_review → halt_second_fail`, `reconcile → halt_unreconciled`,
   `change_retry → halt_change_rejected`), and the three loops without one — including both loops
   the front-phase designs propose — remain without one. Bounding them is a decision about the flow,
   not about the engine.

3. **The seats are not reached.** `intake_review` is a `SURVEY` and no node's `rejects_to`, so the
   intake loop CHG-20260901-10 proposes is untouched here. Its convergence is that record's problem
   and one of the reasons it is being rewritten.

4. **The reason is spent on the next visit.** A node sent back to twice for two different reasons is
   told each in turn, which is right; a node that then loops for an unrelated reason is told
   nothing, which is also right. What is *not* available is the history — that stays in
   `report.rejections`, where it already was.

5. **A model may ignore it.** This puts the reason in the instructions; nothing checks that the
   next answer responds to it. Checking would mean judging content, which is a model's job wearing
   a lint's clothes — the same line this ledger drew about a mutation's `says` field.
