## The survey script was the defect it was looking for

The first version passed `--plan` as an **absolute** path, then asserted the recorded value was
absolute. It printed `OK` beside a description reading *"stored as typed, not resolved"* — the
description was correct and the assertion could not fail. A coarse check answering safe about the
single field it existed to examine.

Caught by reading its own output, not by anything structural. That is the fourth instance today of
this class and the third inside something written to catch the class:

1. CHG-47's `assert imported or refused` — passed on the abort it forbade
2. CHG-48 draft one — `minimal` passed by resolving to the original example still in the repo
3. CHG-48's `.gitignore` guard — `"/greet.py" not in text`, satisfied by `examples/*/greet.py`
4. this survey — an absolute input to a check for absoluteness

The pattern is stable enough to name: **when I write a check, my default input is the one that makes
it pass.** `mutation_check.py` exists for exactly this and did not help here, because the flaw was in
a throwaway script rather than in a shipped test.

## CI caught what four of its five jobs could not

The first version of `_where` used `Path(...).resolve()` alone. It passed here, and passed on
ubuntu py3.9, ubuntu py3.13 and windows py3.13. **windows py3.9 failed**, and was right to:

```
assert Path(cli._where("plan.json")).is_absolute()
E   AssertionError: assert False
E    +  where WindowsPath('plan.json') = Path('plan.json')
```

Before Python 3.10, `Path.resolve()` on Windows returned a **non-existent** relative path unchanged
(bpo-38671). `requires-python` here is `>=3.9`. So on a supported platform the function written to
stop a path being recorded as typed **recorded it as typed** — which is the defect it exists to
prevent, shipped inside its own fix, for the second time in three changes.

Two things are worth separating here.

**The matrix earned its keep.** One job of five, and the combination that failed is the oldest
Python on the platform this project is developed on. Four green jobs would have merged it.

**The two integration tests could not have caught it, by construction.** They walk a real run, so
their plan file *exists*, and an existing path resolves correctly on every version. Only an input
naming a file that is not there separates the two implementations. The unit test that did catch it
was the smallest and least interesting-looking of the three, and I nearly wrote it as an assertion
about `None` alone.

Fixed with `os.path.abspath` — absolute by string arithmetic against the working directory, no
filesystem access, no version to depend on — with `resolve()` still run afterwards on the
already-absolute path, because following symlinks is the part worth having. The missing-path case is
now its own named test over three shapes.

### And I wrote a number into this document without running it

The row above first said *"3 of 4 fail against the previous commit"*. I did not check it; I reasoned
it. Both halves were wrong, and running it took one command:

| against | result here |
|---|---|
| `origin/main`, no `_where` at all | **4 of 4 fail** |
| the `resolve()`-only version CI rejected | **0 of 4 fail** |

The second row is the one that matters. **This machine cannot tell the two implementations apart**,
because local Python is 3.11 and `resolve()` returns an absolute path there. So
`test_a_plan_that_does_not_exist_is_still_recorded_as_a_place` — the test written *because* CI caught
something — is a test whose teeth do not exist on the machine it was written on. Its only proving
ground is one CI job of five.

That has a consequence worth stating plainly for whoever reads `_where` later and thinks the
`abspath` line is redundant: **simplifying it back to `resolve()` alone leaves every local run
green.** Only windows-py3.9 objects. The comment in the function says so; this is the second place
it is written down.

It also bounds `mutation_check.py`. Its `provenance` entry mutates the *call site*
(`_where(args.plan)` → `str(args.plan)`), which the integration tests catch on any platform — that
one is real. A mutation of `_where`'s *body* back to `resolve()`-only would report "NOT CAUGHT" here
and "caught" on one CI job, so it is deliberately **not** added: a mutation table that reports a
false negative on the developer's machine is worse than one that admits a gap in prose.

## Reservations (disclosed, not waived)

1. **The recorded plan is a path, not the plan.** If the file changes after the run, the record still
   points at it and says nothing about what it contained. A content hash would be the honest version;
   this is not that.

2. **Relative defaults are unchanged.** `--settings` defaults to `config/settings.json`,
   `--assignment-store` to `.runner/config.sqlite`, `--token-dir` to `.runner`. So `runner settings`
   typed in one directory and `runner serve` in another read different files — and `--settings`
   holds the review seat count and the high-risk bypass. Ordinary CLI behaviour, now written down in
   the CHG rather than left to be discovered.

3. **The survey covered CLI flags and config keys, not every path in the system.** Paths inside a
   plan file's `targets`, and anything an agent is handed on stdin, were not examined.

4. **Nothing reads `run.plan`.** The fix improves a field with no programmatic consumer. That is
   argued in the CHG as the reason to fix it; it is also the reason the fix cannot be shown to change
   any outcome, and the tests assert the record rather than any behaviour depending on it.
