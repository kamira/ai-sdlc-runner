## The rule that shipped is not the rule proposed, and the operator chose it

CHG-20260827-23 task 6: *no mechanism ⇒ refuse to dispatch.*

`sandbox.available()` returns `None` on every Windows machine. An unconditional refusal therefore
raises on **every** dispatch — fourteen test files and the runner itself, on the platform this
project is developed on. That is `policy.py`'s own named failure about the red lines: *a check that
gets switched off.*

I put the three options to the operator rather than deciding it, because the readings lead to
materially different software. They chose: **enforce where the machine can, record where it cannot,
refuse only when `--sandbox` was passed and cannot be honoured.**

The safety property survives in the form that survives contact with the platform: *nothing is
silent*. What changed is which case stops a run — "somebody asked and it cannot be done", not
"nobody asked".

## Two things the guards caught

**The refusal was a raw traceback.** Every other refusal in this runner prints a named message and
exits with a code; `SandboxError` was not in `run`'s handler, so `--sandbox` on Windows dumped a
stack. Task 6 asks for "non-zero exit, platform and flag in the message" — a traceback has the
message and none of the manners. Now exit 10, like the rest.

**`WRITE_SCOPES` was decoration.** `test_nothing_is_unwired` refused it: defined, and used only by a
test. Its honest job is guarding the table — `_bwrap` reads anything that is not `"workspace"` as no
write, so a typo like `"workspaces"` would bound the process *more tightly than the table claims and
say nothing*. `sandbox_for` refuses it now. A mechanism nothing calls is not built, and the guard was
right to say so.

## §7 prohibition re-check

- No skill logic re-implemented; nothing under `skills/` exists here.
- No red-line action. This change **narrows** what a dispatched process may do and can never widen
  it; `PERMANENT_HALT_KINDS`, `GATES` and `--undeclared refuse` are untouched.
- The bypass is the *absence* of a flag, and it is recorded on every run rather than assumed.

## Reservations (disclosed, not waived)

1. **The denial itself is unexercised here.** Stated in the table above, in the module docstring, and
   in the skip reason. The next person to run this on Linux with `bwrap` installed will be the first
   to know whether it works.

2. **The grade→policy table is a claim.** It applies "expensive to undo" to a second axis, and the
   first axis took several rounds to grade well. Written as data so a seat can argue with the table
   rather than the code.

3. **`can_spawn` is not enforced.** Writes and network are. Stopping a process from starting another
   is a further restriction and is not here — the CHG says so and it remains true.

4. **A sandbox says nothing about correctness.** It bounds a blast radius. It does not say the module
   is right, and it says nothing about what the process does *inside* the workspace — which contains
   this repository, `docs/changes/`, and the conversation store.

5. ~~`_may_write` is conservative and coarse.~~ **Fixed, and it was the headline claim.**

   Writing this reservation is how the defect was found: the factory saw only a seat name, so a
   `qa` node got `can_write=True`. The policy layer refused the pen correctly and **nothing ever
   asked it about qa** — the table was right, the promise was not kept, and the acceptance's check 4
   passed at the policy layer while the wiring did not deliver it.

   The role now reaches the factory (`engine._open` passes it the same way it passes seat and
   model, only if the factory asks), and `can_write` comes from `policy.BY_ROLE`. Verified per
   role: `qa` and `seat` `False`, `engineer`/`lead`/`pm` `True`, an unknown role left at the
   grade's default rather than guessed at. Pinned by a test and a mutation.

   That this was found by prose rather than by a test is the reservation that remains.
