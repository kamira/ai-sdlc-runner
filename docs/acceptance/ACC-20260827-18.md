## What made this change necessary, in one line

The two failures point in **opposite directions**: with one scalar, either the copy tweak drags the
whole run to `high` or the schema change rides along at `low`. No single value fixes both. That is
the argument that the scalar is the wrong *shape*, and it is the one thing this acceptance is really
checking.

Check 12 deserves its reason written down: a node in an undeclared workstream falls back to the
**strictest** grade, which is *safe* and silently not what the plan meant. Refusing it at the door is
the difference between a plan that is wrong and a plan that is wrong and running. The fallback is
still there — and tested — for a `RunConfig` built directly rather than through `plan.check`.

## `risk` and `risk_override` are two fields because they are two different things

Before this change they were the same string and nothing could tell them apart.

A plan grading itself `low` must not lower a workstream that says `high` — the plan is a proposal.
An operator passing `--risk low` may, because that is a person deciding. Expressing both through one
field is letting a proposal impersonate a decision, which is the same shape as the circularity
CHG-20260827-17 removed one layer up.

## Reservations (disclosed, not waived)

1. **Nothing assigns nodes to workstreams yet.** `node_workstream` is a plan field a human writes.
   The CHG's related record CHG-20260827-22 (sub-plans) is where a workstream would come from a
   plan the runner produced, and that is not this change.

2. **A workstream is a grade and nothing else.** It has no name policy, no owner, no relation to the
   halt recipients CHG-20260827-19 added. Two changes now describe "who and what a part of the work
   is" and they do not know about each other.

3. ~~No end-to-end run drives a workstreamed plan through the real CLI.~~ **Closed rather than
   disclosed** — and the closing took three attempts, each caught by the mutation table rather than
   by me:

   * Draft one asserted the run "did not finish". It did not pass `--confirm merge`, so the run
     stopped at the merge gate **whether or not workstreams reached it**. Deleting the CLI wiring
     outright left the test green.
   * Draft two confirmed the merge and added a control run with no workstreams, which is what makes
     the comparison mean anything — but asserted the stop happened at `pm_signoff`. The run
     correctly halted **earlier**, at `pm_confirm`, because `plan_confirmed` is also `halt` at
     `high`.
   * It now asserts a gate resolved *at* `high`. Which gate notices the grade first is not the
     claim.

   `tools/mutation_check.py --only risk` includes the wiring itself, so this cannot rot back.

4. ~~**`risk_override` is `args.risk or None`**, so an operator who passes `--risk` matching the
   plan's grade is indistinguishable from one who passed nothing.~~

   **Not true, and checked rather than argued (2026-08-28, CHG-20260828-12).** `--risk` is declared
   with `default=None`, so an absent flag gives `None` and `--risk low` gives `"low"` — the two are
   distinguishable, and were when this was written:

   ```
   nothing passed              args.risk=None    risk_override=None
   --risk low, plan also low   args.risk='low'   risk_override='low'
   ```

   The `or None` is a no-op on a value that is already `None` or a non-empty grade. The concern the
   reservation raises — *"it stops being harmless if anything later reports why a grade was
   chosen"* — is sound, and the mechanism it feared is already absent.
