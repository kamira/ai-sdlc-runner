## The finding that justifies the second round

The first panel's headline was a `src/` fix that did not work, shipped with a test that could not
tell. **The two tests written to close it were themselves vacuous for it.** Measured by reverting
`plain_in` to the body the change exists to replace:

```
tests/test_paths.py::test_plain_in_strips_the_prefix_from_a_real_os_error  PASSED
tests/test_store.py::test_the_refusal_shows_the_path_a_person_would_type   PASSED
```

Both assert the prefix is absent — true of the broken output, which ate the `?` and left `'\\\C:\…'`.
Both assert `"C:"` survives — true of that stump too. The one sequence that separates fixed from
broken was asserted by nothing.

So the defect class this session has been chasing — *a test that cannot fail for the reason it
names* — reproduced inside the change written to correct it, in the two tests most specifically
aimed at it. That is the strongest evidence so far that self-verification does not reach this class.

## What three seats found independently

The seats did not see each other's answers, and two findings came back from three of them:

- **the lock did not lock.** `main()` recovers before it applies, so a second run cleared the first's
  record on the way in. Conformance vetoed it; defect and risk reached it separately.
- **the AST rule saw one site of three**, because it matched the substring `exc`.

A finding that three independent readers reach is a different kind of evidence from one that one
reader reaches. Neither was visible to the suite: every test passed while both were live.

## A defect I introduced and my own probe caught

Adding the owner check to `end()` made `recover()` unable to clear the dead run's record it had just
restored — `end()` correctly refuses to drop a record it does not own, and the record it was cleaning
up was, by construction, somebody else's. The probe that was verifying the fix printed
`record cleared: False`, which is the only reason it was noticed. Recovery now unlinks directly,
with a comment saying why it does not go through `end()`.

## Reservations (disclosed, not waived)

1. **This acceptance is written by the implementer, again.** The panel judged CHG-20260830-05.
   Nothing independent has read *these* corrections. Round 1 found 35; round 2 found 36 **in round
   1's corrections**, including that four of that record's eleven verification rows were wrong.
   The rate did not fall between rounds, so there is no basis in this history for expecting round
   3 to be empty.

2. **The rule's boundary is drawn, and 35 sites are outside it.** A handler is in scope when it
   catches something that can carry a filename, or records onto an operator-facing list. A bare
   `except Exception` that does neither is not covered, and 35 such sites exist — measured, most in
   `cli.py`. Routing all 44 was attempted first; the mechanical pass produced a `server.py` that did
   not parse, because `ast` reports column offsets in UTF-8 **bytes** and these files are full of
   em-dashes. Every narrower boundary tried excluded a site the seats had named, which is why the
   rule is stated in two clauses rather than one.

3. **A reused pid reads as alive.** `_alive` has no start-time to disambiguate. The failure that
   remains is a *refusal* to recover a file a killed run left mutated — the tree stays wrong and
   says so loudly. The failure removed was recovering over a live run, silently.

4. **`plain_in` remains approximate.** It rewrites driver text rather than rebuilding the message
   from `exc.filename`. Unchanged from CHG-20260830-05, and now applied in eight more places, so the
   surface of that approximation is larger.

5. **The mutation restore writes LF, and it degrades the guard this module depends on.** The defect
   seat reported it; verifying this change reproduced it, which is better evidence than either of us
   had. A group run here was killed by a timeout mid-mutation. `--recover` did its job —
   *restored worktree.py, which a killed run left mutated* — and afterwards `git status` reported
   `cli.py` and `server.py` modified. Both are **byte-identical to HEAD** once line endings are
   normalised: `mutation_recovery.write` forces `newline="\n"`, so on this `core.autocrlf=true`
   checkout every file the harness touches comes back LF.

   No content is at risk. What is at risk is the check: `test_this_repository_has_no_mutation_in_flight`
   tells the operator to read `git status`, and `git status` now names files nothing happened to.
   A guard whose advice produces false positives stops being read.

   Not fixed here, deliberately. `run()` reads with universal newlines and matches anchors against
   `\n`-spelled text, so the fix is to carry each file's original newline in the record rather than
   to stop normalising — a change to the read path, the record schema and the restore, in the middle
   of a round that already expanded once and produced a file that did not parse. It is the next
   change, with the reproduction above as its evidence.

6. **Risk's five observations from round 1 are still untouched.** `reach_of` grading every
   single-label host `internal`; the secret scan reading only the query string; two markdown formats
   pinned by test; the constant-time test foreclosing hashed tokens. Each deserves its own change,
   and none of them is this one.
