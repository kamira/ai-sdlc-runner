## The measurement that decided the harness fix

The obvious repair was to delete `PYTHONUTF8=1` from `tools/mutation_check.py`. That would have
broken what CHG-20260823-47 added it for — pytest's own output going down a pipe. Both switches were
measured rather than reasoned about:

| switch | `locale.getpreferredencoding(False)` | `sys.stdout.encoding` |
|---|---|---|
| `PYTHONIOENCODING=utf-8` | `cp950` | `utf-8` |
| `PYTHONUTF8=1` | `utf-8` | `utf-8` |

`subprocess`'s text mode reads the first column. `PYTHONIOENCODING` fixes the pipe and leaves the
locale real, which is the only part that had to stay.

## Three things went wrong on the way, and each is pinned

**1. A grep where a parse was needed.** The first applier keyed on `text=True` and counted
occurrences per file. `tools/frozen_tree.py` already had `encoding=` on the *continuation line*, so
the rewrite produced `encoding="utf-8"` twice and the file stopped parsing. The check became an AST
walk, and `test_a_call_split_across_lines_is_read_as_one_call` holds it there.

**2. A name standing in for a constraint — in the guard against exactly that.** Flagging any call
with a `text=` keyword reported `self.turn(INSTRUCTION, nth=nth, text=text)`. Pinned by
`test_a_keyword_merely_spelled_text_is_not_a_subprocess`.

**3. A guarantee that could not be pinned because the harness set the environment.** The recorder
mutation came back `NOT CAUGHT` twice — first because the harness set `PYTHONUTF8`, then because
`PYTHONIOENCODING` leaks from the harness into the grandchild the recorder starts. Fixed where it
belongs: the test clears both variables itself.

The `AMBIGUOUS` outcome added in CHG-20260828-01 also earned its place here — the first
`ledger_check` mutation matched two identical lines and said so, instead of reverting whichever came
first and reporting a result about the wrong one.

## The suite found the half I had not looked at

Naming UTF-8 on the parent's side changed what the child receives, and
`test_the_order_reaches_the_backend_deterministically_serialised` failed on `972 == 969` — three
characters, the three CJK glyphs in the order's `role_label`, each arriving as two.

The change had been about **reading**. The dispatch also **writes**, and a child left to itself
decodes stdin with its own locale. That is live: `cli.py` is where a real agent is asked a real
question. It now sets `PYTHONIOENCODING=utf-8` for the child, and a new test asserts the non-ASCII
round-trips with both switches cleared from the environment first.

The first version of that test counted em dashes and asserted `0 == 0` — the order has none. Its own
guard line caught it, which is the only reason it is not in the suite proving nothing.

## Reservations (disclosed, not waived)

1. **Only `subprocess` was surveyed, and by reading.** File I/O in this repository passes
   `encoding="utf-8"` explicitly, which is why nothing else surfaced. Nothing exercises that claim.

2. **CI cannot fail on this.** GitHub's Windows runners are `cp1252` and decode those bytes into
   different characters without raising, so the id-collision guard there compares mangled text
   rather than skipping. The change is right on both, but the green that protects it is not evidence
   about either.

3. **A non-Python child on Windows still writes ANSI.** `errors="replace"` keeps that from killing
   the read. It does not make the text correct, and nothing in the project currently starts one.

4. **The eleven sites were fixed mechanically and reviewed as a set, not one by one.** The AST check
   proves each now names a codec; it does not prove UTF-8 is the right codec for each child. It is
   right for git and for the agents, which is all of them today.

5. **Verified by the implementer.** The defect was found by a test failing rather than by review,
   which is the part of this that went right — and the three mistakes above were found the same way.
