## The fix for the uninformative message was uninformative

The cycle message's first draft counted visits from `taken`, and I wrote a comment asserting it "has
been counting all along". It has not: `_choose` returns before touching `taken` for a `frontier`
decision and for a plain-string one, and is not called at all for a panel node. The message came out
as:

```
walk exceeded 200 steps without reaching an end. Most-visited: nothing recorded.
```

A fix for a message that says nothing, which said nothing.

What is worth recording is *how* it was caught: the test written for that message failed on its first
run, immediately, before the change went anywhere near review. That is the first time today one of my
own errors was caught by the thing I had just written rather than by re-reading it afterwards or by
CI. The difference was writing an assertion about the **content** of the message (`"Most-visited"`,
the node name, `"last answered"`) instead of about the fact that a message appeared.

Counted from `report.visited` now, which the walk appends to on every step.

## Two existing tests pinned the old sentence, and both were asserting a phrase

The full suite failed on:

```
tests/test_example_weather_spa.py::test_an_agent_that_cycles_is_stopped_by_the_step_cap
tests/test_flow.py::test_a_cycling_flow_is_stopped_rather_than_spun_forever
```

Both asserted `"cycling without progress" in ...` — the exact wording, which this change removes.
The temptation is to swap the string and move on. What they were *for* is that a cycle stops and
says something useful, and a fixed phrase tests neither. Both now assert the content: the limit, the
node that spun, and what it kept answering. `test_flow`'s single case became two, so "it stopped" and
"it said what stopped" fail separately.

### Then the scenario suite caught the message's shape

With the assertions strengthened, `weather-spa` scenario C still failed:

```
the refusal does not say what the repeating node kept answering:
walk exceeded 200 steps without reaching an end. Most-visited: engineer_build ×39,
engineer_selfverify ×39, lead_task_review ×39. enginee
```

The message was correct. `examples/weather-spa/scenarios.py:233` truncates a reported error at **150
characters**, and the first draft spent them on a three-node summary and a sentence of advice — so
the one fact an operator needs fell off the end.

Reordered: node, count, and its last answer first; the other nodes and the explanation after. The
information was always there; where it sat in the sentence decided whether anyone would see it. Not
a cosmetic point, and now written in the code beside the reorder.

## Reservations (disclosed, not waived)

1. ~~**`lead_review` and `qa_verify` are what stand between a silently empty build and a merge.**~~
   **False, and written without being checked** — the same act that caused the defect it was
   excusing. One seat drove the run to `merge` and `finished`; the other confirmed node by node that
   nothing compares `pm_plan.modules`, `expected_outputs`, or the filesystem. Worse, the quiet
   ending was not confined to the failing run: it latched, foreclosing every later plan in the same
   walk. CHG-20260823-51 refuses the contradiction and records the ending.

2. **The 200-step guard is untouched.** This makes its message diagnosable. It does not ask whether
   200 is the right number, and against a paid backend 200 asks is an expensive way to find out a
   loop exists.

3. **"Idempotent" is doing narrow work here.** The module loop terminates correctly on a rerun. The
   run still rewrites `site/`, still mints a new conversation, still writes a fresh journal. Nothing
   here surveys what else a second run touches.

4. **The two SPA agents were not changed.** They answer `{"module": ""}`, which is now the documented
   contract, so they are correct — but they arrived at it independently and nothing tested that
   agreement before today.
