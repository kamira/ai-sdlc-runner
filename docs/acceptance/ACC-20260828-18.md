## The kill test changed the design, which is why it was worth running

The SIGTERM handler was written first and looked sufficient. Killing a real run with it installed
left `worktree.py` mutated: on Windows `kill -TERM` becomes `TerminateProcess`, uncatchable. The
on-disk record is what put the file back on the next invocation —

```
  restored worktree.py, which a killed run left mutated
```

— so the handler is documented as the part that is *allowed* to fail, and the record is the
guarantee. Had this shipped on the handler alone it would have been a fix that does not fix, on the
platform it was written on.

The same test showed `kill -TERM <pid>` in that shell stopping a wrapper rather than the Python
child. **Two mutation runs went on executing in the background while the tree was believed clean**,
and the first one's apparent innocence was only the interval between two mutations. Both were killed
by real pid; both trees were recovered by the same mechanism, which is a second unplanned exercise
of it.

## Four mutations that were caught for the wrong reason

With the tests in `test_mutation_check.py`, all four reported `CAUGHT` — and all four reported `1
failed, 7 passed`, stopping at the same test. That uniformity was the tell. Test eight is
`test_no_shipped_mutation_has_a_stale_anchor`; breaking `mutation_recovery.py` made the *other*
stranded mutations' anchors stale, and it went red before any recovery test ran.

Verified directly before changing anything, by mutating by hand and reading the failure names.
After the split into `tests/test_mutation_recovery.py`, each mutation breaks the tests that name its
guarantee:

| mutation | tests that go red |
|---|---|
| recovery ignores the record | all five recovery cases |
| recovery overwrites an edited file | `…refused_not_overwritten`, `…rather_than_recreated` |

## The structural finding

`mutation_check.py` cannot be mutated by exact-text anchors, because a mutation's `before` string
lives in that same file — every anchor into it matches twice and CHG-20260828-01's uniqueness guard
refuses it. That is not a bug in the guard; it is a limit of exact-text mutation, and it is the
reason the recovery is a separate module rather than a section.

## Reservations (disclosed, not waived)

1. **The signal handler is unverified where it might work.** It is measured not to fire on Windows.
   Whether it fires on Linux was not tested — CI never kills a mutation run, so there is no natural
   exercise of it, and it is marked `pragma: no cover`.

2. **The window is narrowed, not closed.** Between a kill and the next `mutation_check` or suite
   run, a `git add -A && git commit` still commits the mutation. The guard is a later reader, not a
   lock. A pre-commit hook is a different change.

3. **Only `mutation_check` was surveyed.** It is the only tool here that deliberately writes to
   source files, but `frozen_tree.py` and `session_record.py` were not examined for the same shape.

4. **Recovery trusts its own record.** If the record is corrupted in a way that still parses as JSON
   with the right keys, recovery will write whatever it says over a matching file. The three-state
   comparison bounds the damage to files that byte-match the recorded mutation.

5. **Verified by the implementer**, though not by argument: the defect was an incident, the design
   was changed by an experiment that contradicted it, and the mutations were wrong once before they
   were right.
