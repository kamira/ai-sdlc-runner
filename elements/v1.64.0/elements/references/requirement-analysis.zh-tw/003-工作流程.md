## 工作流程

1. **讀既有脈絡**:若專案已有 `docs/ai-guideline.md`,先讀,避免重複或衝突。
2. **釐清,不臆測**:對關鍵未知處主動提問——目標、使用者、規模、限制、期限、技術偏好、驗收標準。一次問重點,不要一次丟一堆問題淹沒使用者。
3. **歸納需求**:把對話拆成功能需求與非功能需求,標出假設與待確認項。
4. **產出 Guideline**:用下方模板寫出 `docs/ai-guideline.md`。
5. **交回確認**:請使用者確認 Guideline,再進入結構設計。

**代問模式(能分配 subagent 時)**:**主決策 agent 不參與使用者問答**。引導者(A1)擁有整段對話——發問、往復到需求**完全了解**(待確認項全數解決或明確擱置)——然後上交一份**企劃**:Guideline 草稿+已釐清事項+影響概描。主決策 agent 讀的是**企劃、不是逐字稿**(逐字稿會複製錨定——和「不給驗收者實作者自述」同一個理由),並把企劃交審議會共同審議(決策席次 ≥5,見 review-panel)。這把「資訊蒐集」與「裁決」分離;**確認閘仍直達使用者**——核准權永不轉包。無法 spawn → 同一個 agent 自問自裁,並在記錄中註明此限制。

**知識庫先建(開工前奠基,不是懶惰式)**:建立 `docs/` 的同時就建 `docs/knowledge/`——空的 INDEX(+ vocabulary 骨架)就是合法的知識庫。不要等第一次糾正:互動風格的觀察從第一句對話就算數——連「使用者指示下達方式需要調整」都是一條知識(tag `interaction`;見 knowledge)。
