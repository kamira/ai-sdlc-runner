## 工作流程

1. **讀基準**:讀 `docs/ai-guideline.md` 與 `docs/structure/*.md`,掌握現況。沒有這些文件時,先補建(回到對應 skill)或在記錄中註明缺漏。**若本次是因驗收未通過而進入,先讀對應的 `docs/acceptance/ACC-*.md`,把未達標項當作這次要修正的目標清單。**
2. **影響分析**:判斷這次變更會動到哪些模組、元件、資料、介面,以及連帶影響(相依方向、相容性、資料遷移)。**同時查假設**:掃過受影響範圍內先前 CHG 的決策表——若本次變更推翻了某條記錄在案的前提假設,該決策必須重新評估(併入本 CHG 或另開一筆),不可默默放著。
3. **產出修改指引**:用下方模板寫出具體、可執行的修改步驟,讓實作者(人或 AI)照做即可。實作過程中,**每完成一步立刻打勾**——萬一 session 中途掛掉,下一棒用未勾步驟對帳 working tree(見 handshake),不必用猜的。
4. **調整結構文件 + 修正 Guideline**:若變更改動了結構,**同步更新** `docs/structure/` 對應檔案——結構文件必須永遠反映最新真實。若變更也動到需求/範圍/驗收條件,**一併修正 `docs/ai-guideline.md` 並升版**(過時的 Guideline 會誤導後續)。
5. **留下變更記錄**:在 `docs/changes/` 新增一份記錄(見模板),寫清楚動機與取捨。因驗收未通過而修正者,在記錄的「關聯」欄連回該 ACC 報告。
6. **確認閘(動碼之前)**:把摘要給使用者確認才實作——動機、影響範圍、**代決事項**(凡從 Guideline/文件/使用者指示推導不出的決策)、風險分級,以及**中/高風險時的設計圖**。設計圖是這一步的必備材料而不是裝飾:前四樣全是散文與表格,而使用者真正要攔截的「模組接錯邊了」「資料流向不對」恰好是散文最不擅長表達、也最容易讓人看過就點頭的——**一份看不懂的確認材料,拿到的不是確認,是默許**。畫兩張(受影響範圍的架構圖 + 本次變更的流程圖,Mermaid 為主、ASCII 亦可),**呈給使用者檢視、依指正改到他確認為止,才往下做**。使用者可以決定不看:在表頭寫 `Diagrams: skipped — <理由>`;**理由空白視同沒宣告**(空白簽名不算簽名),而**沒宣告時的預設是畫**。低風險/CHG-lite 免圖——記帳成本必須隨風險縮放。這**不新增停點**:停不停仍由風險×閘矩陣決定(低 auto、中 confirm、高 halt),本步只規定「停下來時要給使用者看什麼」。使用者在此**覆核風險欄**(見分級:高風險清單命中不接受自評降級)。**預授權**:使用者可對某類變更豁免逐次確認(「這類直接做」)——記為 knowledge directive,且必須寫**窄**(情境+邊界;邊界模糊時回退為問)。使用次數計入治理健康度;闖禍的類別**自動失效**(見 CHG-lite)。單人 session 中,AI 發現同一類變更被重複確認時,應**主動建議**預授權。自主連跑走 halt 契約(autonomy)而非本互動閘——同一意圖、兩個通道。
7. **當場驗收(不可交棒)**:實作完成後,**在同一輪內**立刻依 `acceptance-verification` 產出對應的 `docs/acceptance/ACC-*.md`,並把本 CHG 狀態更新為「已驗收」並連結該 ACC。**不可只標「待驗收」就結束**——跨 session 開發下,下一個 session 來的是新需求、不會有人回頭補驗收,驗收一旦交棒就會永遠懸著。**若仍有未通過項,回到第 1 步,形成「修正 → 重新實作 → 重新驗收」的迴圈,直到全數通過或使用者明確接受。** 收尾時另比對:本次變更的**動機/目的是否重複了先前某筆 CHG**——第二次出現即自主建立 **shallow knowledge record**(證據與計數落在條目;見 knowledge「自主觸發」)。**比對結果不論有無重複,都要寫進 CHG 標頭的「重複性檢查」欄**——「無重複」也是答案,空欄=沒做檢查。這個欄位就是讓這一步真的發生的機制:純散文提醒已被實測次次略過,故 lint 對 v1.17+ 寫成的記錄強制此欄(前瞻適用,同所有新規則)。
