# onboarding — 接進治理

> 語言 / Language: **繁體中文** · [English](onboarding.md)

## 用途

`init` 與 `adopt` 是同一個問題的兩半:**這個 repo 沒有治理,該走哪扇門、而什麼不准被破壞**。
兩支共用本檔,因為路由判斷**只能有一處**——分成兩份,兩支就會各猜一次,而它們會猜出不同答案。

握手(見 handshake)處理的是「已經有帳本」之後的事。本檔處理它之前的那一步。

## 判準:找帳本,不是找 `docs/`

**`docs/` 不是身分證。** 它是這套流程*提議*的位置,不是保證會有、也不是保證是它的。
skill 自己就寫了「若目標專案已有文件慣例,依其慣例」。而 `docs/` 是軟體專案最常見的目錄名之一:

| 別人的用途 | 把帳本寫進去的後果 |
|---|---|
| 發佈根目錄(MkDocs / Docusaurus / Jekyll / Pages source) | CHG/ACC 被建進網站導覽,變成使用者看到的產品文件頁;front-matter 不合的產生器會**建置失敗** |
| 生成產物(Sphinx build、自動產生的 API 文件) | 下一次重新生成**把帳本刪掉**,而且無聲 |
| 另一個 agent 慣例的地盤 | 兩套東西互相覆寫 |

第二列是**資料遺失**,不是揭露——治理帳本本來就該公開,問題從來不是機密。

**`AGENTS.md` 同樣不是身分證**:它現在是跨廠商慣例,別的工具也會寫它。

唯一不含糊的標記是**帳本本身**——一個裝著 `CHG-YYYYMMDD-NN.md` 的目錄,不管它在哪。
機器輔助:`doc_integrity_check.ledger_roots(repo)`,候選根由 `DOC_ROOT_NAMES` 決定(資料,不是寫死)。
**找不到就回空清單,不回傳假設**——「找不到就當作在 `docs/`」會讓呼叫端掃出零筆、
然後回報沒問題,而沒有人會去追查一個綠燈(KN-001 的鏡像)。

## 四態路由

```
找帳本(不假設 docs/)
├─ 找到 ──────────────────► 已治理:走 handshake
└─ 找不到
   ├─ 無既有程式 ─────────► init
   ├─ 有既有程式 ─────────► adopt
   └─ docs/ 存在但是別人的 ► 先決定落點(見下),再依上面兩條走
```

「有既有程式」的判準:除了文件與設定以外,存在任何原始碼、測試或建置設定。
**判不出來時倒向 `adopt`**——把空 repo 當存量處理,代價是多問幾句;
把存量當空 repo 處理,代價是覆寫別人的東西(KN-004:看失敗代價往哪邊倒)。

## 落點:`docs/` 是預設,被佔用才換

| 情況 | 落點 |
|---|---|
| `docs/` 不存在,或存在而空著 | **`docs/`**(預設不變) |
| `docs/` 已被佔用 | **`sdlc_docs/`** |

**佔用判準**(任一成立):

- 有 site generator 設定:`mkdocs.yml`、`docusaurus.config.*`、`_config.yml`、
  `conf.py`(Sphinx)、`book.toml`(mdBook),或 repo 設定把 `docs/` 當作 Pages source。
- 有生成產物標記:`docs/_build/`、`docs/.doctrees/`、`docs/site/`,或 `.gitignore` 忽略 `docs/` 的一部分。
- `docs/` 底下已有非我方內容,而其中沒有任何帳本。

**落點一律寫進 Guideline 表頭——宣告,不推論。** 下一棒不該再判一次;
判斷會隨環境變化,而宣告不會。

## 進行中標記:「導入到一半」不得看起來像「導入完成」

路由判準是「找得到帳本」,而**帳本在 onboarding 途中就會變成找得到**——
`init` / `adopt` 只要建出第一個 `CHG-*.md`(或第一個 `changes/` 目錄)就中斷,
下一次進場會掃到帳本、判為「已治理」,然後**跳過剩下沒做完的步驟**。
半套的骨架就這樣直接進了變更流程,而且沒有任何東西抗議。

所以 onboarding **第一個動作**是寫標記,**最後一個動作**才是移除它:

```
<root>/.onboarding        # 內容:INIT|ADOPT + 進行到哪一步 + 時間(UTC+0)
```

- **進場時標記還在** → 上一次的 onboarding 沒做完。**不得往下走變更流程**,
  先從標記記的步驟續作(見上方「不覆寫、可續跑」),完成後才移除標記。
- 標記與 handshake 的關係:handshake 第 5 步對帳讀到它,視同「未收尾階段」處理。
- 這是「最後一次行為紀律」在 onboarding 上的實例:動手前意圖先落盤,
  做完立刻記結果。守住它,中斷與正常結束留下的狀態是可分辨的——
  而**可分辨**正是這裡唯一要的東西(KN-003:「做到一半」與「做完了」必須分得開)。

## 不覆寫、可續跑

`init` 與 `adopt` 都是多步驟且會寫檔的流程,而 session 可能在任何一步結束(見 handshake
「最後一次行為紀律」)。所以兩者都必須:

- **既有檔一律不覆寫**。已存在就跳過並具名列出,由人決定要不要合併。
  「重跑一次比較快」不是覆寫別人修正的理由。
- **可續跑**:重跑只補缺的部分,不重建已有的部分;中斷不留半套。
- **先印計畫,再動手**:寫檔前列出「會建立哪些檔」,已存在的標為跳過。

## init —— 從零起手

1. 決定落點(見上),寫進 Guideline 表頭。
2. requirement-analysis → `<root>/ai-guideline.md`。
3. structure-design → `<root>/structure/{directory,logical,design,data}.md`。
4. 建立 `<root>/changes/`、`<root>/acceptance/`、`<root>/knowledge/`
   (零條目 INDEX + 種子 `vocabulary.json`——見 knowledge「先建」)。
5. 建立 root `AGENTS.md`;既有的工具專屬慣例檔(`CLAUDE.md`、`GEMINI.md`、
   `.cursorrules`、`.github/copilot-instructions.md`…)各留**兩行 stub** 指向它,
   stub 不承載自己的內容(複本必然分岔)。

## adopt —— 存量專案導入

程式已經在跑、從未治理。與 init 的差別不在步驟多寡,在**兩件事的方向相反**:
結構文件是**反推**出來的,而歷史**不能假裝有治理過**。

### 反推結構文件時要標明來源等級

從既有程式反推的內容,必須逐項標明是哪一種:

| 標記 | 意思 |
|---|---|
| **觀察事實** | 從程式碼直接讀得到(這個模組 import 那個模組) |
| **推論** | 從證據推出來的意圖(看起來是為了支援多租戶) |
| **未知** | 看不出來,需要人回答 |

不標等級的代價很具體:**偶然的實作、歷史缺陷、甚至死碼,會因為被寫進結構文件而取得規範地位**。
「未知」不是失敗,是待辦;把「未知」寫成「推論」才是。

### 治理基準點:六條最低限度

宣告一個 commit 當基準點,不足以防止偽裝。以下六條是最低限度:

1. **基準只能是導入當下所見的完整 SHA**——不是日期、不是 tag(可移動)、不是簡寫。
2. **另建一個導入 commit**,並記下它的 **parent SHA**。基準代表導入前的狀態,
   導入 commit 代表導入這件事本身;混成一筆就分不出「原本就有的」與「導入時修的」。
   **這一條已有機器強制**(CHG-20260811-02)。宣告寫在 Guideline 表頭:

   ```markdown
   - Governance-baseline: <40 位十六進位的完整 SHA>   # 導入前的狀態
   - Adopt-commit: <40 位十六進位的完整 SHA>          # 導入這件事本身
   ```

   `doc_integrity_check` 會逐項對 git 求證:commit 存在、**parent 剛好一個**
   (merge 會讓邊界糊掉、root commit 沒有導入前的狀態)、**parent 等於宣告的基準**、
   導入 commit **只動治理檔**。兩個欄位**要一起**——只有基準等於沒有錨,
   只有導入 commit 等於沒有起點。**而宣告一旦在歷史裡出現過就不准消失**:
   刪掉之後這道閘會回報「不適用」,而不適用看起來跟通過一樣。
   沒宣告的專案(絕大多數,它們不是導入來的)回報**不適用**,不是通過。
3. **記錄工作樹狀態**:未提交的變更、未追蹤檔、submodule、LFS 指標。
   宣告的 commit 不等於真正被盤點的狀態。
4. **禁止替基準點以前補造 CHG**。此前沒有治理,而那件事本身就是記錄。
   把它補寫成好像有治理過,是把「沒有記錄」換成「錯誤的記錄」——後者更難發現。
5. **第一個受治理的變更從導入 commit 之後開始**,不早於它。
6. **「已盤點」不等於「已驗收」**。既有缺陷、測試空洞、安全債不因導入而被追認;
   要驗收就走 acceptance-verification,不能靠導入這個動作順帶生效。

第 6 條是最容易失守的一條:導入之後 repo 看起來很整齊,而整齊會被讀成健康。

### 既有缺陷的處置

反推過程中發現的缺陷,登記為**待補項**(具名、可查),不是靜靜修掉、也不是靜靜留著。
靜靜修掉會讓導入 commit 混進實質變更(違反第 2 條);靜靜留著會讓它隨導入一起被追認。

## 舊路徑遷移

帳本已經在某處、但要換落點時(例如 `docs/` 後來被 site generator 佔用):

- **只搬我方檔案**:`CHG-*.md`、`ACC-*.md`、`structure/`、`knowledge/`、`ai-guideline.md`。
  認的是「這是什麼」,**不是「在哪個目錄底下」**——別人的檔一個都不動。
- **`git mv`**,讓歷史跟著走。非 git 專案降級為複製 + 刪除,並在 ack 中聲明。
- **預設 dry-run**:先印完整搬移清單,確認後才動。在別人的 repo 裡搬檔是不可逆方向。
- **可續跑**:中斷後重跑只搬剩下的,不留半套。
- 遷移本身開一筆 CHG,並在 Guideline 表頭更新落點。

機器輔助:`scripts/ledger_migrate.py`(預設 dry-run)。

## 與既有流程的關係

- 本檔在 handshake **之前**:握手假設帳本找得到,本檔負責讓它找得到。
- `init` 的第 2、3 步分別走 requirement-analysis 與 structure-design,本檔不重述那兩份的內容。
- `adopt` 的驗收走 acceptance-verification;導入**不是**驗收。
- 落點決定會影響所有機器輔助的搜尋範圍——`doc_integrity_check` 與 `governance_health`
  都走 `ledger_roots()`,不寫死目錄名。
